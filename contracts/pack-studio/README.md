# Контракт Студии шаблонов

API `/api/v1/pack-studio/*` и `/api/admin/pack-studio*` (`docs/design/template-studio.md`, разделы 3, 4, 5.5-5.8, 6 и 12; срезы T5, T6, T7, T9 и T13). Расхождение сторон ловит `services/api/tests/unit/contract/test_pack_studio_contract.py`: эталоны проверяются строгими моделями `api/schemas/pack_studio.py`, коды ошибок сверяются с `PackStudioErrorCode`. Клиент (срез T8) разбирает те же эталоны схемами zod.

Состав:

- `error_codes.json` закрытый список кодов ошибок Студии шаблонов. Тело ответа `{detail, code, ...}`: `detail` на языке интерфейса, остальные поля по коду (`etag` и `content` у `stale_file`, `path` у `version_released` и `releases_read_only`, `op` и `reason` у `yaml_patch_conflict`, `limit` у `file_too_large`, `workspace_limit` и `preview_quota`, `field`, `value` и `reason` у `preview_invalid`, `reason` у `version_unreadable`, `place_invalid`, `model_invalid` и `submission_invalid`). Сбои git рабочего пространства (клон, выборка, доступ) идут кодами `contracts/git-sync/error_codes.json`, в том числе в поле `error.code` карточки пространства. Сбой локального git над хранилищем пространства (команда без сети) идёт кодом `workspace_git_failed` (409) с полем `hint`: подкоманда git и первые строки ошибки без адресов, токенов и путей сервера (например `git status: fatal: could not fetch <oid> from promisor remote`), чтобы человек мог прислать её без доступа к журналу; полный очищенный вывод git остаётся в журнале сервера. Блоб частичного клона, которого не хватило локальной команде, сервер сначала сам догружает с доступом пространства и повторяет команду, поэтому этот код означает сбой, который догрузка не лечит. Коды T6: `fork_required` (поле `can_create`: форк можно создать токеном, только GitHub), `push_denied`, `lint_failed` (`errors`, `warnings`, `findings` с ошибками проверки пака), `merge_conflict` (`files` от папки паков), `workspace_dirty`, `nothing_to_propose`, `branch_name_invalid`, `service_access_*`; `pr_permission_missing` приходит полем `pr_error` ответа «Предложить», а `ci_status_unavailable` полем `reason` статуса проверок, не ошибкой. Коды T15: `id_invalid` (`field`: `pack` или `template`, `value`), `name_required` (`field`), `pack_id_taken` (`id`, `where`: `workspace` или `studio`), `template_id_taken` (`id`), `pack_not_found` (`pack`). Коды T10: `version_not_found`, `version_taken` (`version`, `suggested`, у выпуска `released_in_base`), `version_number_invalid` (`reason`), `version_not_modified`, `class_softer_than_changes` (`minimum`, `chosen`), `lint_failed` у выпуска (находки линтера версии). Коды вычислителя результата (`docs/design/template-studio-outcome.md`, 4.6): `inputs_invalid` (`field`, `value`, `reason`), `scenario_invalid` (`reason`), `scenario_not_found`, `scenario_taken`, `atlas_too_large` (`limit`, `rows`), `diff_base_unavailable` (`reason`: `no_git`, `no_base`, `new_version`), `outcome_busy` (`reason`, `retry_after_s`), `outcome_element_not_found` (`section`, `id`), `outcome_too_large` (413, `limit` и `size` в байтах: ответ «до и после» или матрицы больше предела). Коды следующих срезов заняты заранее;
- `fixtures/<Схема>/<вариант>.json` эталонные тела запросов и ответов, по каталогу на схему. Эталон содержит все поля явно, в том числе `null`.

## Предпросмотр

`{pack}`, `{template}`, `{version}` это имена папок, как в дереве (`hse-cs-sse/coursework/2026.1.7`). Комбинация это словарь `{переключатель: значение}`, все значения строки: `lang`, `kind`, `staffing` (`solo`, `team2`, `team3`), `supervisor` (`university`, `company`, `none`), `co_supervisor` и `academic_supervisor` (`yes`, `no`), `nda` (если у версии есть NDA) и `meta.<поле>` для первых пяти полей select и bool. Недостающие значения берутся из набора данных (`lang`, `kind`, `staffing` в файле примера), затем по умолчанию; ответ всегда несёт полную комбинацию.

Наборы данных: файлы `<пак>/templates/<шаблон>/examples/<id>.yaml` (правятся обычными `PUT .../files/...`, вне каталога версии: выпуска не требуют) и автонаборы `auto:normal`, `auto:long` (строки втрое длиннее), `auto:empty` (только обязательные при создании поля). Файл, который не разобран, приходит с `error`, собрать по нему нельзя.

Сборка: `status` `queued` (рендер синтетического проекта и очередь), `running` (раннер взял задачу), затем `succeeded`, `failed` или `cancelled`. `key` это ключ кэша: тот же ключ значит тот же PDF, `cached: true` значит, что задачи не было. Коды `error.code`: `render_failed` (шаблон пака упал или превысил предел), `interrupted` (процесс перезапустился посреди сборки), `pdf_missing` и коды сборки проекта (`build_failed`, `font_missing`, `image_missing`, `docker_unavailable`, `no_runners`, `quota_exceeded` и другие). Новая сборка того же документа в том же наборе и комбинации отменяет прежнюю; идущих сборок у человека не больше `HSE_STUDIO__PACK_STUDIO__PREVIEW_MAX_CONCURRENT` (429 `preview_quota`).

Предпросмотр с вариантом и сценарием (срез O9). Все поля добавлены без поломки: запрос без `variant` и `scenario` ведёт себя как раньше, а у клиента, которому не нужны новые поля ответа, они не мешают (в схемах они необязательные).

- **Опции.** У документа в `PackPreviewOptions.documents[]` есть `langs` (языки редакций: `supported_langs` документа, иначе все языки версии, те же, что `languages` документа результата), `variants[]` (`id`, `label`, `langs`, `pdf`) и `default_variant` (первый вариант, `null` без вариантов). `variants[].langs` пусто, если вариант доступен при любом языке; редакции ISO и IEEE доступны только при `en`, поэтому клиент показывает варианты по `lang` комбинации (`variants[].langs` пусто или содержит `lang`). `pdf: false` у варианта, из которого PDF не получить: у него нет движка и исходник не офисный и не PDF (RevealJS); такая сборка кончается `pdf_missing`. У PowerPoint движка нет, но PDF выходит конвертацией LibreOffice (как у сборки проекта, если конвертер доступен), поэтому `pdf: true`. Варианты не входят в `switches`: комбинация осталась прежней, а форма точек сдачи (`submission/routes`) её видит как раньше.
- **`variant` запроса** выбирает вариант документа и допустим только у запроса ровно с одним документом (`preview_invalid`, `field: variant`, `reason: needs exactly one document`). Вариант, которого у документа нет: `reason: unknown variant`; у документа нет вариантов: `the document has no variants`; вариант доступен не при языке комбинации: `not available for this language`. Без `variant` берётся вводная `variant.<документ>` сценария, иначе первый вариант (как при создании проекта). Вариант определяет исходник, движок и итоговое имя файла (`output_name` варианта).
- **`scenario` запроса** (id сценария пака, `scenarios/<id>.yaml` рабочего дерева) берёт вводные и набор данных из сценария: набор запроса главнее, затем набор сценария, без него автонабор `auto:normal` (как у `outcome`); `combination` ложится поверх вводных сценария. Вводные считает ядро результата (`inputs` по всем вводным версии, а не только пять полей анкеты предпросмотра): `variant.<документ>` становится вариантом документа, ответы анкет `answer.*` на сборку не влияют, остальное это комбинация проекта, и она в ответе целиком. Нет файла: `scenario_not_found` (404), файл не по формату: `scenario_invalid` (400); вводная сценария, которой нет в версии или со значением вне списка: `preview_invalid`, `field: scenario`, `value` это id сценария, `reason` называет вводную; вводная из `combination`: `preview_invalid`, `field: combination.<вводная>`.
- **Какие документы собираются.** Документ есть в комбинации, если движок создал его экземпляр (`create_project._build_documents` на синтетическом проекте, тот же проект, что у результата и у сборки); `preview_invalid`, `field: document`, `reason: not in this combination` иначе. Итоговое имя файла считает та же функция, что для `documents[].instances[].file_name` результата (`document_file_name`), поэтому у сценария, который и результат, и сборка читают одинаково, имена совпадают; тест паритета держит это на всех комбинациях реальных паков.
- **Ответ сборки** сообщает `variant` (выбранный вариант, `null` у документа без вариантов), `file_name` (имя файла в пакете), `scenario` (id или `null`) и `scenario_inputs` (вводные сценария как в файле, до наложения `combination`; пусто без сценария).
- **Ключ кэша** PDF учитывает выбранный вариант (исходник другой, PDF другой). Сценарий входит в ключ через то, что из него вышло, то есть через синтетический проект и вариант: правка вводных сценария меняет ключ, два сценария с одинаковым итогом делят один PDF. Слот отмены (новая сборка отменяет прежнюю) различает вариант и сценарий.
- **MCP.** У `pack_preview_build` те же аргументы `variant` и `scenario`; в ответе сборки есть `variant`, `file_name` и `scenario`.

## Места подписей

`PackSignatures` это каталог `signatures.slots` версии: у слота `default_place` (общее место, как его читает лоадер; `default_set` ложно, если ключа нет), `places` (записи `placements` по документам), `dates` (метки `default_dates` с индексом в списке YAML: битая метка пропущена, индексы остальных не сдвигаются). Записи в мм (`source: mm`) или на якоре шаблона (`source: anchor`), та же форма, что у мест пака в состоянии подписей проекта. С `build_id` у слота, применимого к документу сборки, есть `document`: чья запись (`place` своя, `default` общая), рамка `box` по якорям сборки (null: места в этой сборке нет) и состояние якоря, метки даты с рамками; `build` перечисляет якоря подписи и даты сборки.

Правки (`ops`, до 50): `set_place` (рамка `box`; без `doc` это общее место), `remove_place`, `make_default`, `bind_anchor` и `unbind_anchor` (без `doc` общее место), `add_date` (`mark` в мм или `anchor` строки даты сборки), `set_date` и `remove_date` по `index`. Место на якоре двигается относительно своей линии, новое место документа встаёт на строку шаблона с id слота, если она есть в сборке на той же странице; координаты округляются до 1 мм. Ответ это `PackSignatures` по новому тексту с новым ETag.

## Формы версии

`PackVersionModel` это манифест версии (`manifest.data` как его читает `yaml.safe_load`, даты строкой ISO) и документы ростера: у документа папки (`files/<id>/doc.yaml`) свой `manifest` с ETag, у записи v1 прямо в ростере `manifest: null` и данные в `data`. `files` это файлы папки документа от `files/` версии: `bare` путь без языкового кода, `lang` код (пусто у файла для всех языков), по грамматике суффиксов загрузчика. `usage` говорит, где печатается поле: документ, макросы `\hse...` подключённых инклудов, `direct` (исходник ссылается сам), `whole` (строка инклуда на весь документ, например шрифт). `checks` это файлы проверок версии без `.yaml` (для `gost_ref`). `references` документа это места манифеста, где он назван (слоты, места, метки даты, профили сдачи). `problems` это находки лоадера и схемы по манифестам сейчас.

Правка (`PackModelPatchRequest`): `file` от каталога версии (`version.yaml` или `files/<id>/doc.yaml`), `ops` те же, что у `PATCH .../files/...` (до 50). Правка не пишется, если после неё у файла есть находка лоадера или схемы, которой не было раньше (`model_invalid`, причина в `reason`): старые находки не мешают править дальше. Операции (`PackModelActionRequest`): `rename_field` (`field`, `to`: ключ в `meta_fields` и ссылки `project.meta.<ключ>`, `author.meta.<ключ>` во всех текстовых файлах `files/` версии), `add_document` (`document`, `name`; `source` это папка документа-заготовки, без неё пустой документ: `doc.yaml` и главный `.tex` для всех языков), `remove_document` (запись ростера и папка документа), `add_translation` (`document`, `lang`; `files` это пути без кода: без них переводятся все файлы с редакцией языка по умолчанию копией в `<stem>.<код>.<ext>`, файл для всех языков переводится только по явной просьбе и становится редакцией языка по умолчанию). Ответ это модель после правки, `changed` перечисляет записанные и удалённые пути.

## Точки сдачи

`PackSubmission` это `pack_submission.profiles` версии так, как их читает лоадер, но с индексами в списках YAML: профиль адресуется индексом `index`, записи `items`, `extra_items` и `signing_slots` своим `index`; запись, которую лоадер не читает, приходит с `entry: null` и причиной `error`, у профиля `error` это первая проблема строгого разбора. `supported_kinds` записи пусто: запись в обоих видах; `methods` без слота: любой способ. `slots` каталог слотов (для подписей пункта и `signing_slots`), `forms` анкеты версии (для `extra_items`: `source` это файл ответов анкеты в проекте), `route` порядок версии (`null`: ключа нет, действует `builtin_route`).

Правки (`ops`, до 50): `add_profile` (`head`: id, name, description; пунктов пока нет), `set_profile` (`head`, `deadline_hint: null` убирает подсказку), `remove_profile`, `move_profile` (`to`), `set_profile_route` (`steps`, `null` убирает ключ), `add_entry`, `set_entry`, `remove_entry`, `move_entry` у списка `entries` (запись полем по виду: `item`, `extra` или `slot`), `set_route` (порядок версии, `null` убирает ключ). Поля со значением лоадера по умолчанию не пишутся, незнакомые форме ключи записи остаются как были. После правки у профилей и порядка не должно появиться новых проблем строгого разбора лоадера и схемы `contracts/pack/version.schema.json`, иначе `submission_invalid` с причиной; связи (документ в ростере, слот в каталоге) проверяет линтер после записи.

`PackSubmissionRoutes` маршрут каждого профиля на синтетическом проекте комбинации тем же кодом, что маршрут проекта: `steps` людьми (персона, роль, имя из набора; пусто: подписи точке не нужны), `pairs` подписи маршрута (`point` требует пункт, `preset` добавил `signing_slots` по условию), `skipped` слоты сверх точки, которые условие не пропустило, `may_add` подписи, которые автор проекта включит сам, `items_off` документы пунктов, которые в этой комбинации не сдаются, `order_source` откуда порядок (`profile`, `version`, `builtin`). Профиль, который лоадер не читает, в ответе отсутствует.

## Вычислитель результата

Контракт «результат в центре» (`docs/design/template-studio-outcome.md`, раздел 4, модели `api/schemas/pack_studio_outcome.py`, схемы zod `entities/pack-studio/api/outcome.ts`). По версии шаблона и вводным сервер считает результат (документы, поля, анкеты, участники, точки сдачи, маршрут, проверки) и объясняет каждое решение цепочкой правил. Эндпоинты `outcome/inputs`, `outcome` (срез O2 плана), `outcome/atlas` (O4), `outcome/explain` (O5), сценарии (список, запись, удаление, прогон; O6) и сравнения `compare`, `impact`, `matrix` (O7) работают, остальные (`lint`) приходят со своими срезами; ядро расчёта (срез O1) реализовано в `core/pack_studio/outcome` и `use_cases/pack_studio/outcome` и воспроизводит эти эталоны; эталоны собраны существующим кодом расчёта на реальных паках `hse-cs-se` (ВКР 2026.1.2) и `hse-cs-sse` (курсовой проект 2026.1.6) и закрепляют форму. Эталоны с реальными правками (`PackOutcomeImpact`, `PackScenarioRun`) получены на копии версии с изменённым условием слота `academic_supervisor`.

Отпечатки (`fingerprint` результата, у раздела в `digest.sections`) считает ядро (`core/pack_studio/outcome/summary.py`): хэш структуры результата без косметики (имена файлов, языковая редакция, доступность и выбор варианта, имена и организации людей, значения примера) и без раздела `checks` (проверки приходят по `include`, отпечаток от него не зависит). Значения хэшей в эталонах от прототипа и поэтому не совпадают с хэшами ядра: тест `test_resolve_real_packs.py` сверяет их форму (12 и 16 знаков), всё остальное целиком. У поля анкеты `required` значит «обязательно в этой комбинации»: скрытое поле и поясняющий текст ответа не требуют. `why` пункта точки, выключенного документом (`absent`, `inactive`), перечисляет решения документа до первого невыполненного включительно.

Маршруты (все под `/pack-studio/workspaces/{id}`, только чтение, кроме записи и удаления файлов сценариев; работают `outcome/inputs`, `outcome`, `outcome/explain`, `outcome/atlas`, `compare`, `impact`, `matrix` и четыре маршрута сценариев, остальные пока будущие):

Эндпоинты `outcome/inputs` и `outcome` (срез O2):

- **Права.** Как у всего раздела: гард `pack_studio_guard` (раздел включён, право «Автор шаблонов», область токена `packs`), пространство берётся у владельца. Эндпоинты только читают и ничего не пишут.
- **Состояние** `state` выбирает источник. `work_tree` читает рабочее дерево (модель версии разбирает отдельный процесс, как у предпросмотра, манифесты читаются с диска). `head` (последний коммит) и `base` (вершина базовой ветки) читаются из git пространства без checkout; недостающие блобы частичного клона догружаются сетью с доступом пространства. У папки на диске, у пространства без базовой ветки и у версии, которой нет в коммите или в базе, ответ `diff_base_unavailable` с `reason`: `no_git`, `no_base`, `new_version`.
- **`revision`** это дайджест текстов `version.yaml`, `files/*/doc.yaml` и файла выбранного набора данных (`examples/<id>.yaml`, у автонабора файла нет).
- **ETag.** Ответ несёт `ETag` по ключу запроса: пространство и версия, состояние и его источник (дайджест каталога у `work_tree`, коммит у `head` и `base`), `revision`, день, набор данных, вводные и `include`. Порядок вводных не важен. По `If-None-Match` (список, `*`, слабая форма) ответ 304 без тела и без расчёта. `Cache-Control: private, no-cache`.
- **Кэш.** LRU результатов на 256 ответов (и не больше 96 МБ), словарей вводных и разобранных версий `head` и `base` по коммиту. Несохранённые правки учитываются сами: ключ несёт дайджест каталога и `revision`.
- **Пределы.** Расчёт в потоке с таймаутом 5 с и не больше 4 одновременных (`HSE_STUDIO__PACK_STUDIO__OUTCOME_*`); сверх них отказ сразу. Таймаут и перегрузка это 503 `outcome_busy` с `reason` (`timeout`, `overloaded`), `retry_after_s` в теле и заголовком `Retry-After`. Частота: правило `pack_outcome`, 20 запросов в секунду на человека на оба эндпоинта (429 `rate_limited`, только на сервере). Вводных до 64, значение до 128 знаков.
- **Ошибки.** `inputs_invalid` (`field`, `value`, `reason`: незнакомая вводная, значение вне списка, неизвестный или битый набор данных у `field: example`), `scenario_not_found` (поле `scenario`: нет файла `scenarios/<id>.yaml` в выбранном состоянии), `scenario_invalid` (`reason`: файл сценария не по формату), `version_not_found`, `version_unreadable` (лоадер или вычислитель не прочитали версию, `reason`), `diff_base_unavailable`, `outcome_busy`, `workspace_not_found`, `workspace_not_ready`.
- Тело ответа это `PackOutcome` (`PackOutcomeInputs`) плюс `workspace_id`, `pack`, `template`, `version`, `state` (имена папок из адреса) и `elapsed_ms` (время запроса целиком в мс, из кэша малое).
- Признак `pack_outcome` в `capabilities` ответа `GET /api/v1/session/bootstrap`: эндпоинты доступны (сейчас вместе с `pack_studio`). Интерфейс открывает пространство на «Результате» только при нём.
- **MCP** (срез O3). Те же вычисления доступны тулам группы `packs`: `pack_outcome_inputs` (то же, что `outcome/inputs`) и `pack_outcome` (то же, что `outcome`, плюс текстовый вид для агента). Права, область токена `packs` и правило частоты `pack_outcome` те же, что у эндпоинтов; состояния `state`, `inputs_invalid`, `diff_base_unavailable` и `outcome_busy` переходят как есть, к отказу добавлено поле `hint`. Подробности: `docs/design/template-studio-outcome.md`, раздел 4.7, и `docs/ru/workbench/mcp.md`.

Эндпоинт `outcome/explain` (срез O5): всё, что у `outcome` (права, `state`, ETag и 304, LRU, пределы, частота `pack_outcome`, только чтение), плюс следующее.

- **Запрос** `PackOutcomeExplainRequest`: вводные, набор данных и `state` как у `outcome`, `element` это `{section, id}` из результата. Идентификаторы: документ `id`, поле проекта `id`, анкета `id` и поле анкеты `<анкета>/<поле>`, участник `persona`, точка `id`, пункт `<точка>/<документ>` (дополнительный файл точки `<точка>/<источник>`), маршрут точки целиком `route` и `id` точки, шаг `<точка>/step/<номер>`, пара `<точка>/<документ>/<слот>` (у автора команды в конце персона), слот, которого в маршруте нет, под тем же id (`state: absent`), правило проверки `id`.
- **Ответ** `PackOutcomeExplain`: `state` (у документа `active`, `inactive`, `absent`; у остальных `present` или `absent`) и `chain`, решения элемента из его `why` в том же порядке, строками `trace` результата (`rule.file` и `rule.pointer` ведут к правилу в манифесте, `terms` это предикат, `actual` фактические вводные, `status` `held`, `not_held` или `skipped`). Цепочка документа равна его `why` в `outcome`. У шага маршрута своего `why` нет: цепочка шага это порядок маршрута и решения пар, в которых участвуют его люди. Пункт, выключенный документом, объясняют решения документа до первого невыполненного включительно (как его `why`); у включённого пункта и у участника цепочка бывает пустой.
- **`readers`**: другие элементы, о которых говорят решения цепочки (решения склеиваются по содержимому, одно решение бывает у многих элементов, например порядок подписей версии у всех маршрутов), без самого элемента, не больше 64.
- **`counterfactuals`**: минимальные изменения, то есть одна вводная в другое своё значение, при которой состояние элемента меняется, с состоянием после. Считает пересчёт ядром (`resolve` без трассы) для каждого другого значения каждой вводной: у ВКР 14 пересчётов, у курсового проекта 10. Первыми идут вводные невыполненных условий цепочки, затем остальные вводные цепочки, затем прочие; не больше 24 записей. Пересчёт ограничен 96 соседними комбинациями на набор вводных (вводные, которые читает хоть одно решение трассы, считаются первыми). Изменений сразу двух вводных нет: форма ответа их не выражает. Косметика (язык, имена файлов, вариант презентации) состояния элемента не меняет и в список не попадает.
- **Кэш.** Тело ответа лежит в том же LRU, что результаты (ключ несёт и элемент). Результат с трассой и соседние комбинации для набора вводных кэшируются отдельно (по 16): другой элемент тех же вводных не пересчитывает ничего. Проверки (`checks`) всегда в расчёте: у `include` в запросе нет.
- **Ошибки.** Те же, что у `outcome`, плюс `outcome_element_not_found` (404, `section`, `id`): такого элемента нет в результате для этих вводных (другой элемент, чем в версии, или версия сменилась).

Эндпоинты `outcome/compare`, `outcome/impact` и `outcome/matrix` (срез O7; ядро `core/pack_studio/outcome/compare.py` и `matrix.py`, расчёт `use_cases/pack_studio/outcome/compare.py`, служба `use_cases/pack_studio/outcome_compare.py`, MCP `pack_outcome_compare` и `pack_outcome_impact`): права, область токена `packs`, `state`, `diff_base_unavailable` (`reason`: `no_git`, `no_base`, `new_version`), ETag и 304, `outcome_busy`, только чтение, как у `outcome`, плюс следующее.

- **Сравнение** `PackOutcomeCompareRequest`: стороны `left` и `right`, каждая `{state, scenario, example, inputs}` (вводные сценария лежат под `inputs`, как у `outcome`). Ответ `PackOutcomeCompare`: `left` и `right` (`state`, `revision`, `fingerprint`, полные `inputs`), `identical` (изменений нет; равные `fingerprint` значат то же), `summary` (по разделам: добавлено, изменено, убрано; равна счёту `changes`) и `changes`. `fingerprint` здесь отпечаток структуры вместе с применимостью проверок: у результата с `checks` он считается от `fingerprint` результата и отпечатка раздела `checks`, у `PackOutcome` без `checks` совпадает с ним. Стороны на одном состоянии (два набора вводных, два сценария) или на двух (`work_tree` против `head` и `base`). Вводные, не подходящие версии стороны, это `inputs_invalid` с полями `field`, `value`, `reason` и `side` (`left` или `right`).
- **Изменение** `OutcomeChange`: знак (`+` появилось, `-` исчезло, `~` изменилось), раздел, вид (`document`, `meta_field`, `form`, `form_field`, `participant`, `point`, `item`, `extra_item`, `route_step`, `route_pair`, `skipped_pair`, `may_add`, `check_rule`), id по общему правилу (документ `id`, пункт `<точка>/<документ>`, шаг `<точка>/step/<номер>`, пара `<точка>/<документ>/<слот>`), подпись, `before` и `after`. Изменения берутся из структуры элементов результата (та же, что у отпечатков): косметика (имена файлов, язык редакции, доступность и выбор варианта документа, имена людей, значения примера) в них не входит. Знак у «флагов» (документ в состоянии `active`, пункт и поле, пара, шаг, правило проверки включено) по появлению в комплекте и исчезновению из него, у остальных по появлению и исчезновению элемента; `~` значит, что элемент остался, но структура другая (у `~` `before` и `after` строки, у `+` и `-` они `null`, кроме документа, шага и пары, у которых значение показано). Поле `why` (до шести причин `OutcomeChangeReason`) заполняют `compare` и `impact`: `rule` (файл и указатель либо зашитое правило), `kind`, `terms`, исход решения слева и справа (`before`, `after`; `null`: у элемента на этой стороне такого решения нет) и фактические значения вводных (`before_actual`, `after_actual`). Берутся решения элемента (`why` результата) с каждой стороны, у которых отличается исход, значения или условие (правило, которое поправили, одна причина с условием «после»); если таких нет, цепочка стороны, где элемент есть. У расхождения прогона сценария со снимком `why` пусто: снимок трассы не хранит.
- **«До и после»** `PackOutcomeImpactRequest`: `base` (`base`: вершина базовой ветки, `head`: последний коммит; по умолчанию `base`), `scenarios` (id, не больше 200; `null`: все) и `include_atlas` (по умолчанию `true`). Сценарии читаются из рабочего дерева и считаются на версии «до» (`base` или `head`) и «после» (`work_tree`) с проверками; сценарий вне своих `versions` в расчёт не входит. Сценарий со статусом `error` не читается на одной из сторон (`message` называет сторону: `base: ...` или `work_tree: ...`), в том числе вводная, которая появилась только в новой версии, и сломанный файл сценария. `summary.sections` это счёт всех изменений всех сценариев; `summary.atlas` считается по таблицам атласа обеих сторон (ответы `outcome/atlas` для `work_tree` и для базы, из их кэша): `rows_total` строк таблицы «после», `rows_changed` из них с другим результатом на базе (та же комбинация считается прямо на базе; вводная или значение, которых на базе нет, это изменение), `outcomes_before` и `outcomes_after` числа исходов обоих атласов; `null`, если `include_atlas` выключен или таблица шире предела атласа. `new_findings` сегодня пуст: его заполнит линтер результата (срез O8). `base_revision` и `work_tree_revision` это `revision` манифестов сторон.
- **Матрица** `PackOutcomeMatrixRequest`: `state`, `scenarios` (не больше 200; `null`: все) и `against: base`. Сценарии читаются из того же состояния, что версия. Строка `MatrixRow`: сценарий, полные вводные (у ошибки пусто), `status` как у прогона (`passed`, `failed`, `error`, `unchecked`) и `message` (причина ошибки). Клетка `MatrixCell`: отпечаток раздела и счётчик (документов в комплекте, видимых полей, применимых анкет, участников, активных пунктов, пар маршрута, включённых правил проверок), `status` (`matched`: ожидание сценария по разделу выполнено; `changed`: не выполнено или, с `against: base`, раздел отличается от базы; `unchecked`: у раздела ожидания нет; `error`: результата нет, отпечаток пуст, счётчик 0) и `changed` (отличие от базы по отпечатку; `null`: с базой не сравнивали или сценарий на базе не считается). Утверждение относится к разделу по виду (`document_*` к документам, `meta_visible` к полям, `participant_present` к участникам, `item_active` к пунктам, `route_*` к маршруту), снимок покрывает все разделы кроме проверок.
- **Проверки** (`checks`) считаются во всех трёх запросах (применимость правил, без `include`): раздел проверок в сравнении, «до и после» и матрице иначе был бы пуст. Отпечаток раздела `checks` в клетке считается по применимости правил, а у `PackOutcome` и снимка сценария этого раздела нет.
- **Пределы.** `compare` считает две стороны в пуле службы результата (5 с, `outcome_busy`) под правилом `pack_outcome` (20 в секунду на человека). `impact` и `matrix` считают каждый сценарий дважды в отдельном потоке: срок 20 с (проверяется между расчётами сценариев), не больше двух одновременных на процесс, полная очередь и истёкший срок это 503 `outcome_busy` с `Retry-After`, частота 6 запросов в минуту на человека (правило `pack_impact`, 429); одинаковые одновременные запросы делят один расчёт. Сценариев не больше 200 (`scenarios` длиннее это 422; без `scenarios` берутся первые 200 по `id`). Ответ больше 8 МиБ это 413 `outcome_too_large` (`limit`, `size` в байтах).
- **Кэш и ETag.** Ключ ответа складывается из ключей служб результата обеих сторон (пространство и версия, состояние и его источник, `revision`, день, набор данных, вводные), дайджестов файлов выбранных сценариев и параметров запроса, поэтому правка манифеста, сценария, база или коммит меняют ETag, а `If-None-Match` отвечает 304 без расчёта. Сравнение кэшируется на 128 ответов, «до и после» и матрица на 32 (и не больше 64 МиБ).
- **MCP.** `pack_outcome_compare` (стороны `left`, `right`, общие `state`, `scenario`, `example`, `inputs`, `sections`, `detail`, `format`) и `pack_outcome_impact` (`base`, `scenarios`, `include_atlas` по умолчанию выключен, `sections`, `detail`, `format`): компактный текст для агента (сводка, изменения со знаками, главная причина) и структура; отказы с полем `hint`. Права, область токена `packs` и частота те же, что у эндпоинтов.

Вводные это словарь `{id: значение}`, все значения строки, как комбинация предпросмотра: `lang`, `kind`, `staffing`, `supervisor`, `co_supervisor`, `academic_supervisor`, `nda` или `meta.<поле>`, `answer.<анкета>.<поле>`, `variant.<документ>`. Состояние версии `state`: `work_tree` (рабочее дерево с несохранёнными правками), `head` (последний коммит ветки), `base` (вершина базовой ветки). Персоны авторов команды в результате `author1`, `author2`, `author3` (в одиночной работе `author`), у руководителей `supervisor`, `co_supervisor`, `academic_supervisor`.

Результат ссылается на трассу: у элемента `why` это id решений `trace`, у решения `subjects` это элементы (`{section, id}`). Решение несёт правило (`rule`: файл и JSON Pointer манифеста либо имя зашитого в движок правила), условия закрытого языка (`terms`: `in`, `equals`, `contains_any`, `present`, `truthy`), фактические значения (`actual`) и исход `held`, `not_held`, `skipped` (условие не проверялось). Идентификаторы элементов: документ `id`, поле `id`, анкета `id`, поле анкеты `<анкета>/<поле>`, участник `persona`, точка `id`, пункт `<точка>/<документ>`, шаг маршрута `<точка>/step/<номер>`, пара `<точка>/<документ>/<слот>`. `out_of_scope` перечисляет то, что в результат не входит: правила проверок на Python, места подписей по якорям PDF, содержимое TeX и Jinja.

Атлас (срез O4, ядро `core/pack_studio/outcome/atlas.py`, перебор `use_cases/pack_studio/outcome/atlas.py` и `impact.py`, служба `use_cases/pack_studio/outcome_atlas.py`, эндпоинт в `api/routers/v1/pack_studio_outcome.py`): `dimensions` это вводные, меняющие хотя бы один раздел результата; `ignored` вводные вне таблицы (`no_effect`, `cosmetic`: только имена файлов, язык редакции, доступность вариантов); `rows` это `{key, outcome}`, где `key` значения измерений по порядку `dimensions` через `|` (в значении `|` пишется `%7C`); `outcomes` это уникальные исходы с `digest`, по которому клиент мгновенно рисует результат.

Как строится атлас. Измерения определяет анализ влияния: вводная меняет раздел, если в какой-то группе комбинаций, где остальные вводные одинаковы, её значения дают разные отпечатки раздела; у измерения `affects` это эти разделы, `rules` правила, которые её читают (до 32). Вводная без влияния на структуру идёт в `ignored`: `cosmetic`, если меняются имена файлов, языковая редакция или варианты документов, иначе `no_effect`. Если комбинаций вводных не больше 2048, анализ перебирает их все и точен (у курсовой `hse-cs-sse` их 576). Выше берутся умолчания и все комбинации, где от них отличаются не больше трёх вводных (у ВКР `hse-cs-se` из 5184 комбинаций это 418 расчётов, около 1,5 с вместе с таблицей); влияние, которое видно только при четырёх отклонениях сразу и больше, такой режим не найдёт. На ВКР он совпадает с полным перебором (проверяет тест). Таблица это произведение значений измерений при остальных вводных на умолчаниях набора данных; `outcomes[].id` это `o1`, `o2` в порядке первого появления, `digest` берётся из первой строки группы (у строк группы он один, косметика в отпечаток не входит). Ключ строки: значения через `|`, внутри значения `|` пишется `%7C` (другие символы не кодируются). `pin=<вводная>:<значение>` (повторяемый, делится по первому `:`) закрепляет вводную: она остаётся измерением с одним значением и своим `default`, ключ не меняет форму, `rows_total` падает; `combinations_total` от закреплений не зависит. Закрепление незнакомой вводной, значения вне списка, повтор вводной, больше 64 закреплений и неизвестный `example` это `inputs_invalid`. Больше 2000 строк это `atlas_too_large` (`limit`, `rows`), без расчёта строк. Ответ несёт `ETag` по ключу запроса (тот же ключ и те же правила, что у `outcome`: пространство и версия, состояние и его источник, `revision` манифестов, день, набор данных; плюс закрепления): `If-None-Match` отвечает 304 без расчёта, правка TeX атлас не сбрасывает. Состояния `work_tree`, `head` и `base` читаются как у `outcome` (`diff_base_unavailable` у папки без git и у версии, которой нет в коммите). Расчёт идёт в потоке под семафором (два на процесс), срок 20 с и полная очередь это 503 `outcome_busy` с `Retry-After`, кэш на 16 атласов и 8 анализов влияния и общий расчёт одинаковых одновременных запросов; частота 6 запросов в минуту на человека (правило `pack_atlas`, 429), ответ сжимает общий gzip.

Сценарий это файл `<пак>/templates/<шаблон>/scenarios/<id>.yaml` рядом с `examples/`, вне каталога версии (дайджест выпущенной версии не меняется). `format: 1`, `inputs` частичные, `versions` шаблоны номеров, ожидание это `snapshot` (`digest` результата) и (или) `assertions` закрытого набора (`document_state`, `document_count`, `meta_visible`, `participant_present`, `item_active`, `route_steps`, `route_pair`). Прогон: `passed`, `failed`, `error` (вводные не подходят), `unchecked` (нет ожидания).

Сценарии (срез O6, `core/pack_studio/outcome/scenarios.py`, `scenario_check.py`, службы `use_cases/pack_studio/scenario_service.py` и `outcome_service.py`):

- **Права и пределы.** Гард раздела (право «Автор шаблонов», область токена `packs`), как у `outcome`. Прогон идёт тем же пулом, с тем же пределом 5 с и ответом 503 `outcome_busy`, под правилом частоты `pack_outcome` (20 в секунду на человека). Сценариев до 200 на шаблон (201-й это `scenario_invalid`), утверждений до 64, вводных до 64.
- **Файл.** `id` это имя файла: строчная латиница, цифры и дефис между ними, до 64 знаков (иначе `scenario_invalid` с `reason: id: ...`). Писать можно в любой шаблон, который есть на диске (нет шаблона: `version_not_found`, папки не создаются); выпущенность версий не мешает, файл лежит вне каталога версии. Запись идёт каноническим YAML (одинаковый сценарий всегда даёт одинаковые байты; круг «разбор, запись» байт в байт) обычным путём записи файлов пространства под замком и теми же проверками путей (`path_not_allowed` у ссылок и выхода из папки паков).
- **Создание и правка.** `PUT` без `If-Match`: файла быть не должно (`scenario_taken` 409, файл не затирается). С `If-Match` ETag файла: нет файла `scenario_not_found`, другая версия `stale_file` (с `etag` и `content`). Ответ несёт `ETag` файла и `PackScenarioEntry`. Формат проверяется на записи (`scenario_invalid`, 400, `reason` с путём: `assertions[2].kind: unknown kind ...`; тело, которое не проходит строгую модель, отвечает 422), допустимость вводных относительно версии при прогоне: сценарий переживает версии.
- **`record_snapshot`** (`work_tree`, `head`, `base`) заменяет `snapshot` результатом сценария на этой версии и состоянии; снимок из тела запроса затирается. Версия: поле `version` запроса (не из `versions` сценария: `scenario_invalid`), без него старшая по номеру версия шаблона на диске, подходящая под `versions`. Вводные, которые не подходят версии, и неизвестный набор данных это `scenario_invalid` с причиной, файл не пишется.
- **Удаление.** `DELETE` удаляет файл (мягко: в git он остаётся в истории, возвращается правкой git; клиентская «Отмена» пишет сценарий заново без `If-Match` и получает те же байты). Нет файла (или это папка): `scenario_not_found`; `If-Match` с чужим ETag: `stale_file`.
- **Список.** `GET .../scenarios?state=` читает рабочее дерево или коммит (`head`, `base`; у папки без git `diff_base_unavailable`). Видны все `*.yaml` папки сценариев по `id`; не читающийся файл несёт `error` (первая причина с путём), `scenario` у него `null`. Прочие файлы папки сценарием не считаются.
- **Подстановка в результат.** `scenario` у `outcome` берёт файл сценария из того же `state`: вводные ложатся между умолчаниями (с набором данных) и `inputs` запроса; набор данных `example` запроса, иначе `example` сценария, иначе автонабор «Обычный». Нет файла `scenario_not_found`, файл не по формату `scenario_invalid`, вводная не подходит версии `inputs_invalid`. `versions` сценария при этом не проверяются. `GET outcome/inputs?scenario=` считает словарь на наборе данных сценария. `outcome/explain` (поле `scenario`) подставляет вводные так же, как `outcome`. `GET outcome/atlas?scenario=` берёт набор данных сценария, а его вводные делает основой таблицы (у измерений `default` и остальные вводные это значения сценария); вводная сценария, не подходящая версии, это `inputs_invalid`. Дайджест файла сценария входит в ключ и ETag у всех трёх. MCP: аргумент `scenario` у `pack_outcome` и `pack_outcome_inputs`. ETag ответа несёт `id` и дайджест файла сценария: правка файла меняет ETag, 304 при той же правке не отдаётся.
- **Прогон.** Версия: поле `version` запроса, иначе старшая по номеру версия шаблона на диске (в `head` и `base` она читается из коммита: версии там может не быть, `diff_base_unavailable` с `reason: new_version`). Сценарии читаются из того же `state`, что версия. Результаты по порядку `id`. Нет версии: `version_not_found`. Сценарий, которого нет в `scenarios`: `scenario_not_found`. Сценарий вне своих `versions` на этой версии: `unchecked` с `message` («version 2026.1.9 is outside versions: ...»). Набор данных сценария: `example`, иначе автонабор «Обычный». ETag по состоянию версии, дайджестам выбранных файлов сценариев и набору наборов данных, 304 по `If-None-Match`.
- **`failures`.** У утверждения `index` в списке, `kind`, `expected` и `actual` строками (`true`, `false`, состояние, число, JSON шагов), `why` это решения трассы по затронутому элементу. У снимка `index` `null`, `kind: snapshot`, `expected` это отпечаток снимка (по отпечаткам его разделов), `actual` отпечаток результата, а подробности в `changes`: документы (`+` вошёл в комплект, `-` вышел, `~` другое состояние), участники, видимые поля, пункты точек, шаги маршрута (`<точка>/step/<номер>`), число пар (`<точка>/pairs`); изменение отпечатка раздела, которое `digest` не объясняет, это одна строка раздела с отпечатками в `before` и `after`. Неизвестная точка или документ в утверждении это расхождение (`missing`, `missing point`), а не ошибка прогона.
- **Покрытие.** Набор правил (`rules_total`) считается по трассам умолчаний и каждой вводной, переключённой по одной, и по результатам самих сценариев. Это приближение атласа (срез O4): правило, которое видно только при сочетании двух вводных, попадёт в набор, когда его увидит сценарий. Правило, которое во всех результатах только пропущено (`skipped`), считается непокрытым.

Покрытие: правило (файл и указатель либо зашитое) покрыто полностью, если сценарии видели оба исхода (`held` и `not_held`), наполовину, если один; в ответе только правила, покрытые не полностью.

Пути файлов идут от папки паков пространства (`hse-cs-sse/templates/coursework/versions/2026.1.5/version.yaml`): без `..`, абсолютных путей, обратных слешей, `.git` и символьных ссылок.

Операции git идут под замком пространства: вторая одновременная отвечает `workspace_busy`. Пространство со служебным доступом (`service_access: true` при создании, только сервер) отправляет ветку токеном установки, а коммит подписан человеком; форк ему недоступен (`push_denied`).

Официальные паки (срез T22, `docs/design/template-studio.md`, 4.7): вклад только своим аккаунтом GitHub (личный доступ git, форк человека, поток T6); бота установки нет. У пространства `official` (адрес совпадает с официальным репозиторием установки) и `license_accepted_at`; первое «Предложить» из официального пространства без `accept_license: true` отвечает `license_consent_required` (`license`, `license_url`, `contributing_url`). Ветка официального пространства и любого служебного доступа не трогает ничего вне папки паков, иначе `paths_outside_packs` (`files`). Статус проверок: `awaiting_approval` (запуск ждёт одобрения сопровождающего) и `pr_state` (`open`, `merged`, `closed`).

Форму меняют так: сначала эталоны, затем модели и клиент, тесты в том же коммите.

## MCP: паритет с интерфейсом

Каждое действие раздела `/pack-studio` имеет инструмент `pack_*` (`use_cases/mcp/tools/`: `packs.py`, `pack_git.py`, `pack_workspaces.py`, `pack_scenarios.py`, `pack_edit.py`, `pack_help.py`, `pack_outcome*.py`). Общее для всех:

- Права и область токена те же, что у маршрутов: раздел включён, право «Автор шаблонов», область `packs` у PAT (`PackStudioAccess.require`); без них тулы скрыты из `tools/list`.
- Отказ сценария это ответ с ошибкой `{code, detail, ...поля кода, hint}`: код из `error_codes.json`, `hint` подсказывает следующий шаг (`version_released` -> `pack_new_version`, `stale_file` -> перечитать, `workspace_dirty` -> `pack_git_commit`).
- Выпущенные версии и реестры выпусков неизменяемы (`version_released`, `releases_read_only`); деструктивные действия (`pack_workspace_delete`, `pack_git_start_over`, `pack_delete_file`, `remove_document`, `apply` и `disconnect` каталога) выполняются только с `confirm: true`, без него описывают последствия. `pack_propose` опасный и выключен по умолчанию.
- Токены и пароли в аргументах не принимаются и в ответах не возвращаются: пространство ссылается на сохранённый доступ по `credential_id` (`pack_list_credentials`).
- Ответ: компактный текст по умолчанию, `format: json` структура, `both` оба вида.
- Частота: те же правила, что у эндпоинтов (`pack_outcome`, `pack_atlas`, `pack_impact`, `git_sync`, `upload`).
