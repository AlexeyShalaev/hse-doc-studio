# Контракт Студии шаблонов

API `/api/v1/pack-studio/*` и `/api/admin/pack-studio*` (`docs/design/template-studio.md`, разделы 3, 4, 5.5-5.8, 6 и 12; срезы T5, T6, T7, T9 и T13). Расхождение сторон ловит `services/api/tests/unit/contract/test_pack_studio_contract.py`: эталоны проверяются строгими моделями `api/schemas/pack_studio.py`, коды ошибок сверяются с `PackStudioErrorCode`. Клиент (срез T8) разбирает те же эталоны схемами zod.

Состав:

- `error_codes.json` закрытый список кодов ошибок Студии шаблонов. Тело ответа `{detail, code, ...}`: `detail` на языке интерфейса, остальные поля по коду (`etag` и `content` у `stale_file`, `path` у `version_released` и `releases_read_only`, `op` и `reason` у `yaml_patch_conflict`, `limit` у `file_too_large`, `workspace_limit` и `preview_quota`, `field`, `value` и `reason` у `preview_invalid`, `reason` у `version_unreadable`, `place_invalid`, `model_invalid` и `submission_invalid`). Сбои git рабочего пространства (клон, выборка, доступ) идут кодами `contracts/git-sync/error_codes.json`, в том числе в поле `error.code` карточки пространства. Сбой локального git над хранилищем пространства (команда без сети) идёт кодом `workspace_git_failed` (409) с полем `hint`: подкоманда git и первые строки ошибки без адресов, токенов и путей сервера (например `git status: fatal: could not fetch <oid> from promisor remote`), чтобы человек мог прислать её без доступа к журналу; полный очищенный вывод git остаётся в журнале сервера. Блоб частичного клона, которого не хватило локальной команде, сервер сначала сам догружает с доступом пространства и повторяет команду, поэтому этот код означает сбой, который догрузка не лечит. Коды T6: `fork_required` (поле `can_create`: форк можно создать токеном, только GitHub), `push_denied`, `lint_failed` (`errors`, `warnings`, `findings` с ошибками проверки пака), `merge_conflict` (`files` от папки паков), `workspace_dirty`, `nothing_to_propose`, `branch_name_invalid`, `service_access_*`; `pr_permission_missing` приходит полем `pr_error` ответа «Предложить», а `ci_status_unavailable` полем `reason` статуса проверок, не ошибкой. Коды T15: `id_invalid` (`field`: `pack` или `template`, `value`), `name_required` (`field`), `pack_id_taken` (`id`, `where`: `workspace` или `studio`), `template_id_taken` (`id`), `pack_not_found` (`pack`). Коды T10: `version_not_found`, `version_taken` (`version`, `suggested`, у выпуска `released_in_base`), `version_number_invalid` (`reason`), `version_not_modified`, `class_softer_than_changes` (`minimum`, `chosen`), `lint_failed` у выпуска (находки линтера версии). Коды вычислителя результата (`docs/design/template-studio-outcome.md`, 4.6): `inputs_invalid` (`field`, `value`, `reason`), `scenario_invalid` (`reason`), `scenario_not_found`, `scenario_taken`, `atlas_too_large` (`limit`, `rows`), `diff_base_unavailable` (`reason`: `no_git`, `no_base`, `new_version`). Коды следующих срезов заняты заранее;
- `fixtures/<Схема>/<вариант>.json` эталонные тела запросов и ответов, по каталогу на схему. Эталон содержит все поля явно, в том числе `null`.

## Предпросмотр

`{pack}`, `{template}`, `{version}` это имена папок, как в дереве (`hse-cs-sse/coursework/2026.1.7`). Комбинация это словарь `{переключатель: значение}`, все значения строки: `lang`, `kind`, `staffing` (`solo`, `team2`, `team3`), `supervisor` (`university`, `company`, `none`), `co_supervisor` и `academic_supervisor` (`yes`, `no`), `nda` (если у версии есть NDA) и `meta.<поле>` для первых пяти полей select и bool. Недостающие значения берутся из набора данных (`lang`, `kind`, `staffing` в файле примера), затем по умолчанию; ответ всегда несёт полную комбинацию.

Наборы данных: файлы `<пак>/templates/<шаблон>/examples/<id>.yaml` (правятся обычными `PUT .../files/...`, вне каталога версии: выпуска не требуют) и автонаборы `auto:normal`, `auto:long` (строки втрое длиннее), `auto:empty` (только обязательные при создании поля). Файл, который не разобран, приходит с `error`, собрать по нему нельзя.

Сборка: `status` `queued` (рендер синтетического проекта и очередь), `running` (раннер взял задачу), затем `succeeded`, `failed` или `cancelled`. `key` это ключ кэша: тот же ключ значит тот же PDF, `cached: true` значит, что задачи не было. Коды `error.code`: `render_failed` (шаблон пака упал или превысил предел), `interrupted` (процесс перезапустился посреди сборки), `pdf_missing` и коды сборки проекта (`build_failed`, `font_missing`, `image_missing`, `docker_unavailable`, `no_runners`, `quota_exceeded` и другие). Новая сборка того же документа в том же наборе и комбинации отменяет прежнюю; идущих сборок у человека не больше `HSE_STUDIO__PACK_STUDIO__PREVIEW_MAX_CONCURRENT` (429 `preview_quota`).

## Места подписей

`PackSignatures` это каталог `signatures.slots` версии: у слота `default_place` (общее место, как его читает лоадер; `default_set` ложно, если ключа нет), `places` (записи `placements` по документам), `dates` (метки `default_dates` с индексом в списке YAML: битая метка пропущена, индексы остальных не сдвигаются). Записи в мм (`source: mm`) или на якоре шаблона (`source: anchor`), та же форма, что у мест пака в состоянии подписей проекта. С `build_id` у слота, применимого к документу сборки, есть `document`: чья запись (`place` своя, `default` общая), рамка `box` по якорям сборки (null: места в этой сборке нет) и состояние якоря, метки даты с рамками; `build` перечисляет якоря подписи и даты сборки.

Правки (`ops`, до 50): `set_place` (рамка `box`; без `doc` это общее место), `remove_place`, `make_default`, `bind_anchor` и `unbind_anchor` (без `doc` общее место), `add_date` (`mark` в мм или `anchor` строки даты сборки), `set_date` и `remove_date` по `index`. Место на якоре двигается относительно своей линии, новое место документа встаёт на строку шаблона с id слота, если она есть в сборке на той же странице; координаты округляются до 1 мм. Ответ это `PackSignatures` по новому тексту с новым ETag.

## Формы версии

`PackVersionModel` это манифест версии (`manifest.data` как его читает `yaml.safe_load`, даты строкой ISO) и документы ростера: у документа папки (`files/<id>/doc.yaml`) свой `manifest` с ETag, у записи v1 прямо в ростере `manifest: null` и данные в `data`. `files` это файлы папки документа от `files/` версии: `bare` путь без языкового кода, `lang` код (пусто у файла для всех языков), по грамматике суффиксов загрузчика. `usage` говорит, где печатается поле: документ, макросы `\hse...` подключённых инклудов, `direct` (исходник ссылается сам), `whole` (строка инклуда на весь документ, например шрифт). `checks` это файлы проверок версии без `.yaml` (для `gost_ref`). `references` документа это места манифеста, где он назван (слоты, места, метки даты, профили сдачи). `problems` это находки лоадера и схемы по манифестам сейчас.

Правка (`PackModelPatchRequest`): `file` от каталога версии (`version.yaml` или `files/<id>/doc.yaml`), `ops` те же, что у `PATCH .../files/...` (до 50). Правка не пишется, если после неё у файла есть находка лоадера или схемы, которой не было раньше (`model_invalid`, причина в `reason`): старые находки не мешают править дальше. Операции (`PackModelActionRequest`): `rename_field` (`field`, `to`: ключ в `meta_fields` и ссылки `project.meta.<ключ>`, `author.meta.<ключ>` во всех текстовых файлах `files/` версии), `add_document` (`document`, `name`; `source` это папка документа-заготовки, без неё пустой документ: `doc.yaml` и главный `.tex` для всех языков), `remove_document` (запись ростера и папка документа), `add_translation` (`document`, `lang`; `files` это пути без кода: без них переводятся все файлы с редакцией языка по умолчанию копией в `<stem>.<код>.<ext>`, файл для всех языков переводится только по явной просьбе и становится редакцией языка по умолчанию). Ответ это модель после правки, `changed` перечисляет записанные и удалённые пути.

## Точки сдачи

`PackSubmission` это `pack_submission.profiles` версии так, как их читает лоадер, но с индексами в списках YAML: профиль адресуется индексом `index`, записи `items`, `extra_items` и `signing_slots` своим `index`; запись, которую лоадер не читает, приходит с `entry: null` и причиной `error`, у профиля `error` это первая проблема строгого разбора. `supported_kinds` записи пусто: запись в обоих видах; `methods` без слота: любой способ. `slots` каталог слотов (для подписей пункта и `signing_slots`), `forms` анкеты версии (для `extra_items`: `source` это файл ответов анкеты в проекте), `route` порядок версии (`null`: ключа нет, действует `builtin_route`).

Правки (`ops`, до 50): `add_profile` (`head`: id, name, description; пунктов пока нет), `set_profile` (`head`, `deadline_hint: null` убирает подсказку), `remove_profile`, `move_profile` (`to`), `set_profile_route` (`steps`, `null` убирает ключ), `add_entry`, `set_entry`, `remove_entry`, `move_entry` у списка `entries` (запись полем по виду: `item`, `extra` или `slot`), `set_route` (порядок версии, `null` убирает ключ). Поля со значением лоадера по умолчанию не пишутся, незнакомые форме ключи записи остаются как были. После правки у профилей и порядка не должно появиться новых проблем строгого разбора лоадера и схемы `contracts/pack/version.schema.json`, иначе `submission_invalid` с причиной; связи (документ в ростере, слот в каталоге) проверяет линтер после записи.

`PackSubmissionRoutes` маршрут каждого профиля на синтетическом проекте комбинации тем же кодом, что маршрут проекта: `steps` людьми (персона, роль, имя из набора; пусто: подписи точке не нужны), `pairs` подписи маршрута (`point` требует пункт, `preset` добавил `signing_slots` по условию), `skipped` слоты сверх точки, которые условие не пропустило, `may_add` подписи, которые автор проекта включит сам, `items_off` документы пунктов, которые в этой комбинации не сдаются, `order_source` откуда порядок (`profile`, `version`, `builtin`). Профиль, который лоадер не читает, в ответе отсутствует.

## Вычислитель результата

Контракт «результат в центре» (`docs/design/template-studio-outcome.md`, раздел 4, модели `api/schemas/pack_studio_outcome.py`, схемы zod `entities/pack-studio/api/outcome.ts`). По версии шаблона и вводным сервер считает результат (документы, поля, анкеты, участники, точки сдачи, маршрут, проверки) и объясняет каждое решение цепочкой правил. Эндпоинты `outcome/inputs` и `outcome` (срез O2 плана) и сценарии (список, запись, удаление, прогон; срез O6) работают, остальные (`explain`, `atlas`, `compare`, `impact`, `matrix`, `lint`) приходят со своими срезами; ядро расчёта (срез O1) реализовано в `core/pack_studio/outcome` и `use_cases/pack_studio/outcome` и воспроизводит эти эталоны; эталоны собраны существующим кодом расчёта на реальных паках `hse-cs-se` (ВКР 2026.1.2) и `hse-cs-sse` (курсовой проект 2026.1.6) и закрепляют форму. Эталоны с реальными правками (`PackOutcomeImpact`, `PackScenarioRun`) получены на копии версии с изменённым условием слота `academic_supervisor`.

Отпечатки (`fingerprint` результата, у раздела в `digest.sections`) считает ядро (`core/pack_studio/outcome/summary.py`): хэш структуры результата без косметики (имена файлов, языковая редакция, доступность и выбор варианта, имена и организации людей, значения примера) и без раздела `checks` (проверки приходят по `include`, отпечаток от него не зависит). Значения хэшей в эталонах от прототипа и поэтому не совпадают с хэшами ядра: тест `test_resolve_real_packs.py` сверяет их форму (12 и 16 знаков), всё остальное целиком. У поля анкеты `required` значит «обязательно в этой комбинации»: скрытое поле и поясняющий текст ответа не требуют. `why` пункта точки, выключенного документом (`absent`, `inactive`), перечисляет решения документа до первого невыполненного включительно.

Маршруты (все под `/pack-studio/workspaces/{id}`, только чтение, кроме записи и удаления файлов сценариев; работают `outcome/inputs`, `outcome` и четыре маршрута сценариев, остальные пока будущие):

Эндпоинты `outcome/inputs` и `outcome` (срез O2):

- **Права.** Как у всего раздела: гард `pack_studio_guard` (раздел включён, право «Автор шаблонов», область токена `packs`), пространство берётся у владельца. Эндпоинты только читают и ничего не пишут.
- **Состояние** `state` выбирает источник. `work_tree` читает рабочее дерево (модель версии разбирает отдельный процесс, как у предпросмотра, манифесты читаются с диска). `head` (последний коммит) и `base` (вершина базовой ветки) читаются из git пространства без checkout; недостающие блобы частичного клона догружаются сетью с доступом пространства. У папки на диске, у пространства без базовой ветки и у версии, которой нет в коммите или в базе, ответ `diff_base_unavailable` с `reason`: `no_git`, `no_base`, `new_version`.
- **`revision`** это дайджест текстов `version.yaml`, `files/*/doc.yaml` и файла выбранного набора данных (`examples/<id>.yaml`, у автонабора файла нет).
- **ETag.** Ответ несёт `ETag` по ключу запроса: пространство и версия, состояние и его источник (дайджест каталога у `work_tree`, коммит у `head` и `base`), `revision`, день, набор данных, вводные и `include`. Порядок вводных не важен. По `If-None-Match` (список, `*`, слабая форма) ответ 304 без тела и без расчёта. `Cache-Control: private, no-cache`.
- **Кэш.** LRU результатов на 256 ответов (и не больше 96 МБ), словарей вводных и разобранных версий `head` и `base` по коммиту. Несохранённые правки учитываются сами: ключ несёт дайджест каталога и `revision`.
- **Пределы.** Расчёт в потоке с таймаутом 5 с и не больше 4 одновременных (`HSE_STUDIO__PACK_STUDIO__OUTCOME_*`); сверх них отказ сразу. Таймаут и перегрузка это 503 `outcome_busy` с `reason` (`timeout`, `overloaded`), `retry_after_s` в теле и заголовком `Retry-After`. Частота: правило `pack_outcome`, 20 запросов в секунду на человека на оба эндпоинта (429 `rate_limited`, только на сервере). Вводных до 64, значение до 128 знаков.
- **Ошибки.** `inputs_invalid` (`field`, `value`, `reason`: незнакомая вводная, значение вне списка, неизвестный или битый набор данных у `field: example`), `scenario_not_found` (поле `scenario`: нет файла `scenarios/<id>.yaml` в выбранном состоянии), `scenario_invalid` (`reason`: файл сценария не по формату), `version_not_found`, `version_unreadable` (лоадер или вычислитель не прочитали версию, `reason`), `diff_base_unavailable`, `outcome_busy`, `workspace_not_found`, `workspace_not_ready`.
- Тело ответа это `PackOutcome` (`PackOutcomeInputs`) плюс `workspace_id`, `pack`, `template`, `version`, `state` (имена папок из адреса) и `elapsed_ms` (время запроса целиком в мс, из кэша малое).
- Признак `pack_outcome` в `capabilities` ответа `GET /api/v1/session/bootstrap`: эндпоинты доступны (сейчас вместе с `pack_studio`). Интерфейс открывает пространство на «Результате» только при нём.

Вводные это словарь `{id: значение}`, все значения строки, как комбинация предпросмотра: `lang`, `kind`, `staffing`, `supervisor`, `co_supervisor`, `academic_supervisor`, `nda` или `meta.<поле>`, `answer.<анкета>.<поле>`, `variant.<документ>`. Состояние версии `state`: `work_tree` (рабочее дерево с несохранёнными правками), `head` (последний коммит ветки), `base` (вершина базовой ветки). Персоны авторов команды в результате `author1`, `author2`, `author3` (в одиночной работе `author`), у руководителей `supervisor`, `co_supervisor`, `academic_supervisor`.

Результат ссылается на трассу: у элемента `why` это id решений `trace`, у решения `subjects` это элементы (`{section, id}`). Решение несёт правило (`rule`: файл и JSON Pointer манифеста либо имя зашитого в движок правила), условия закрытого языка (`terms`: `in`, `equals`, `contains_any`, `present`, `truthy`), фактические значения (`actual`) и исход `held`, `not_held`, `skipped` (условие не проверялось). Идентификаторы элементов: документ `id`, поле `id`, анкета `id`, поле анкеты `<анкета>/<поле>`, участник `persona`, точка `id`, пункт `<точка>/<документ>`, шаг маршрута `<точка>/step/<номер>`, пара `<точка>/<документ>/<слот>`. `out_of_scope` перечисляет то, что в результат не входит: правила проверок на Python, места подписей по якорям PDF, содержимое TeX и Jinja.

Атлас: `dimensions` это вводные, меняющие хотя бы один раздел результата; `ignored` вводные вне таблицы (`no_effect`, `cosmetic`: только имена файлов, язык редакции, доступность вариантов); `rows` это `{key, outcome}`, где `key` значения измерений по порядку `dimensions` через `|` (в значении `|` пишется `%7C`); `outcomes` это уникальные исходы с `digest`, по которому клиент мгновенно рисует результат.

Сценарий это файл `<пак>/templates/<шаблон>/scenarios/<id>.yaml` рядом с `examples/`, вне каталога версии (дайджест выпущенной версии не меняется). `format: 1`, `inputs` частичные, `versions` шаблоны номеров, ожидание это `snapshot` (`digest` результата) и (или) `assertions` закрытого набора (`document_state`, `document_count`, `meta_visible`, `participant_present`, `item_active`, `route_steps`, `route_pair`). Прогон: `passed`, `failed`, `error` (вводные не подходят), `unchecked` (нет ожидания).

Сценарии (срез O6, `core/pack_studio/outcome/scenarios.py`, `scenario_check.py`, службы `use_cases/pack_studio/scenario_service.py` и `outcome_service.py`):

- **Права и пределы.** Гард раздела (право «Автор шаблонов», область токена `packs`), как у `outcome`. Прогон идёт тем же пулом, с тем же пределом 5 с и ответом 503 `outcome_busy`, под правилом частоты `pack_outcome` (20 в секунду на человека). Сценариев до 200 на шаблон (201-й это `scenario_invalid`), утверждений до 64, вводных до 64.
- **Файл.** `id` это имя файла: строчная латиница, цифры и дефис между ними, до 64 знаков (иначе `scenario_invalid` с `reason: id: ...`). Писать можно в любой шаблон, который есть на диске (нет шаблона: `version_not_found`, папки не создаются); выпущенность версий не мешает, файл лежит вне каталога версии. Запись идёт каноническим YAML (одинаковый сценарий всегда даёт одинаковые байты; круг «разбор, запись» байт в байт) обычным путём записи файлов пространства под замком и теми же проверками путей (`path_not_allowed` у ссылок и выхода из папки паков).
- **Создание и правка.** `PUT` без `If-Match`: файла быть не должно (`scenario_taken` 409, файл не затирается). С `If-Match` ETag файла: нет файла `scenario_not_found`, другая версия `stale_file` (с `etag` и `content`). Ответ несёт `ETag` файла и `PackScenarioEntry`. Формат проверяется на записи (`scenario_invalid`, 400, `reason` с путём: `assertions[2].kind: unknown kind ...`; тело, которое не проходит строгую модель, отвечает 422), допустимость вводных относительно версии при прогоне: сценарий переживает версии.
- **`record_snapshot`** (`work_tree`, `head`, `base`) заменяет `snapshot` результатом сценария на этой версии и состоянии; снимок из тела запроса затирается. Версия: поле `version` запроса (не из `versions` сценария: `scenario_invalid`), без него старшая по номеру версия шаблона на диске, подходящая под `versions`. Вводные, которые не подходят версии, и неизвестный набор данных это `scenario_invalid` с причиной, файл не пишется.
- **Удаление.** `DELETE` удаляет файл (мягко: в git он остаётся в истории, возвращается правкой git; клиентская «Отмена» пишет сценарий заново без `If-Match` и получает те же байты). Нет файла (или это папка): `scenario_not_found`; `If-Match` с чужим ETag: `stale_file`.
- **Список.** `GET .../scenarios?state=` читает рабочее дерево или коммит (`head`, `base`; у папки без git `diff_base_unavailable`). Видны все `*.yaml` папки сценариев по `id`; не читающийся файл несёт `error` (первая причина с путём), `scenario` у него `null`. Прочие файлы папки сценарием не считаются.
- **Подстановка в результат.** `scenario` у `outcome` берёт файл сценария из того же `state`: вводные ложатся между умолчаниями (с набором данных) и `inputs` запроса; набор данных `example` запроса, иначе `example` сценария, иначе автонабор «Обычный». Нет файла `scenario_not_found`, файл не по формату `scenario_invalid`, вводная не подходит версии `inputs_invalid`. `versions` сценария при этом не проверяются. `GET outcome/inputs?scenario=` считает словарь на наборе данных сценария. ETag ответа несёт `id` и дайджест файла сценария: правка файла меняет ETag, 304 при той же правке не отдаётся.
- **Прогон.** Версия: поле `version` запроса, иначе старшая по номеру версия шаблона на диске (в `head` и `base` она читается из коммита: версии там может не быть, `diff_base_unavailable` с `reason: new_version`). Сценарии читаются из того же `state`, что версия. Результаты по порядку `id`. Нет версии: `version_not_found`. Сценарий, которого нет в `scenarios`: `scenario_not_found`. Сценарий вне своих `versions` на этой версии: `unchecked` с `message` («version 2026.1.9 is outside versions: ...»). Набор данных сценария: `example`, иначе автонабор «Обычный». ETag по состоянию версии, дайджестам выбранных файлов сценариев и набору наборов данных, 304 по `If-None-Match`.
- **`failures`.** У утверждения `index` в списке, `kind`, `expected` и `actual` строками (`true`, `false`, состояние, число, JSON шагов), `why` это решения трассы по затронутому элементу. У снимка `index` `null`, `kind: snapshot`, `expected` это отпечаток снимка (по отпечаткам его разделов), `actual` отпечаток результата, а подробности в `changes`: документы (`+` вошёл в комплект, `-` вышел, `~` другое состояние), участники, видимые поля, пункты точек, шаги маршрута (`<точка>/step/<номер>`), число пар (`<точка>/pairs`); изменение отпечатка раздела, которое `digest` не объясняет, это одна строка раздела с отпечатками в `before` и `after`. Неизвестная точка или документ в утверждении это расхождение (`missing`, `missing point`), а не ошибка прогона.
- **Покрытие.** Набор правил (`rules_total`) считается по трассам умолчаний и каждой вводной, переключённой по одной, и по результатам самих сценариев. Это приближение атласа (срез O4): правило, которое видно только при сочетании двух вводных, попадёт в набор, когда его увидит сценарий. Правило, которое во всех результатах только пропущено (`skipped`), считается непокрытым.

Покрытие: правило (файл и указатель либо зашитое) покрыто полностью, если сценарии видели оба исхода (`held` и `not_held`), наполовину, если один; в ответе только правила, покрытые не полностью.

Пути файлов идут от папки паков пространства (`hse-cs-sse/templates/coursework/versions/2026.1.5/version.yaml`): без `..`, абсолютных путей, обратных слешей, `.git` и символьных ссылок.

Операции git идут под замком пространства: вторая одновременная отвечает `workspace_busy`. Пространство со служебным доступом (`service_access: true` при создании, только сервер) отправляет ветку токеном установки, а коммит подписан человеком; форк ему недоступен (`push_denied`).

Официальные паки (срез T22, `docs/design/template-studio.md`, 4.7): вклад только своим аккаунтом GitHub (личный доступ git, форк человека, поток T6); бота установки нет. У пространства `official` (адрес совпадает с официальным репозиторием установки) и `license_accepted_at`; первое «Предложить» из официального пространства без `accept_license: true` отвечает `license_consent_required` (`license`, `license_url`, `contributing_url`). Форму меняют так: сначала эталоны, затем модели и клиент, тесты в том же коммите.
