# Контракт серверного режима

Общие файлы бэкенда и фронтенда для этапа 2. Расхождение сторон ловят два теста, которые читают одни и те же файлы:

- `services/api/tests/unit/contract/test_server_contract.py` проверяет эталоны строгими моделями `api/schemas/session.py` (`extra=forbid`) и сверяет коды ошибок с `errors.json`;
- `services/web-app/src/entities/session/api/contract.test.ts` разбирает те же эталоны схемами zod (`z.strictObject`) и сверяет коды с `errors.json` обоих языков.

Состав:

- `error_codes.json` закрытый список кодов ошибок входа, регистрации и аккаунта (тело ответа `{detail, code}`, модель `AuthErrorBody`). Сообщения лежат в `errors:code.<код>` для ru и en. Код, общий с Git-синхронизацией (`rate_limited`), хранит одно сообщение на оба случая;
- `fixtures/<Схема>/<вариант>.json` эталонные тела запросов и ответов, по каталогу на схему; каталог без схемы в обоих тестах считается ошибкой. Эталон содержит все поля явно, в том числе `null`;
- единственный публичный ответ о состоянии входа: `GET /api/v1/session/bootstrap` (`Bootstrap`: режим, состояние первого запуска, способы входа, пользователь, возможности клиента, CSRF-токен). Возможности клиента определяются `capabilities`, а не проверкой «режим server»;
- мастер первого запуска: шаговые ручки `/api/v1/server-setup/status|admin|environment|settings|complete` (`ServerSetupStatus`, `ServerSetupAdminRequest`, `ServerSetupEnvironment`, `ServerSetupSettingsRequest`; `GET settings` отдаёт `ServerSetupSettings`: действующие значения и `locked_by_env`, ключи, заданные окружением, шаг показывает их только для чтения) и экран `/first-run`; отдельного POST first-run нет. Администратора создаёт `admin` (ответ `LoginResponse`, сессия сразу выдана), остальные шаги идут его сессией. Токен установки печатается в журнале api и нужен, пока админа нет; его не нужно при `SETUP_TOKEN_REQUIRED=false` и при админе из окружения. `environment` пускает по заголовку `X-Setup-Token` или сессией админа. Пока мастер не завершён, прочие маршруты отвечают `503 setup_required` всем, кроме админа;
- ответы регистрации и «забыл пароль» всегда нейтральные (`status: check_email`); `link` непустой только без SMTP, когда ссылку копирует сам человек; у «забыл пароль» и повторной отправки подтверждения `link` всегда пуст (иначе любой, знающий адрес, получил бы чужую ссылку), без SMTP сброс выдаёт администратор;
- `GET|PATCH /api/v1/account` (`AccountProfile`, `UpdateAccountRequest`): имя, язык и подпись коммитов; `null` в запросе значит «не менять», пустая строка в `commit_name` или `commit_email` сбрасывает подпись к умолчанию (имя аккаунта и noreply-адрес `<id>@noreply.<хост public_url>`; настоящий e-mail попадает в коммиты только по `commit_use_account_email` или как собственный адрес);
- токены доступа: `GET|POST /api/v1/account/tokens`, `DELETE .../tokens/{id}` (`ApiToken`, `CreateApiTokenRequest`, `CreateApiTokenResponse`; значение токена приходит один раз в `token`, в списке только `prefix`); способы входа: `GET /api/v1/account/identities` (`AccountIdentity`: пароль или привязка OIDC, `can_unlink` ложно у пароля и у последнего способа), `DELETE .../identities/{id}` (последний способ даёт `409 last_login_method`), `POST .../identities/link/start` (`LinkIdentityRequest` -> `LinkIdentityResponse.redirect_url`, адрес на своём сайте);
- `ProjectSummary` и `CreateServerProjectRequest` форма списка проектов и создания в серверном режиме: владелец (`owner`) и роль текущего человека (`my_role`), без пути папки;
- отказ по роли: `403` с телом `{detail, code: "forbidden_role", required_role}` (`required_role` одна из `reader|reviewer|editor|owner`); фронтенд показывает тост «нужна роль X». Без роли в причине (гость, личные условия) бэкенд отвечает простым `403 forbidden`, тост показывает общий текст;
- настройки установки в админке: `/api/admin/settings/registration|auth|smtp`, `POST /api/admin/settings/smtp/test` и CRUD `/api/admin/oidc-providers`. Каждая группа отдаёт `fields`: по ключу `source` (`env|admin|default`) и `locked` (значение задано окружением и из интерфейса не меняется, ответ `409 setting_locked`). Секреты (пароль SMTP, секрет клиента OIDC) только на запись: в ответах лишь `password_set` и `client_secret_set`. Последний способ входа не выключается (`409 last_login_method`);
- организации участника и доступ к проекту: `GET /api/v1/account/orgs` (`MyOrg`: моя роль и группы), `DELETE /api/v1/account/orgs/{slug}/membership` (выйти; единственный владелец получает `409 last_owner`); панель «Доступ»: `GET /api/v1/projects/{id}/members` (`ProjectAccessEntry`, читать может любой участник проекта), `GET .../members/candidates?q=` (`ProjectAccessCandidate`: люди и группы организации проекта), `PUT .../members` (`SetProjectAccessRequest`, добавление и смена роли одной ручкой), `DELETE .../members/{user|group}/{id}`. Менять доступ может владелец проекта (`403 forbidden_role` с `required_role: owner`); владельца проекта и доступ через организацию-владельца здесь не меняют (`locked`), понизить единственного владельца нельзя (`409 last_owner`), неизвестного человека или группу сервер не находит (`404 member_not_found`);
- состояния сборки: `CompileWait` в поле `wait` деталей сборки (`GET .../compiles/{id}`) и в событии `wait` потока сборки: `reason` одно из `queued|quota_wait|no_runner|runner_lost|superseded`, место в очереди (`queue_position`, с 1), оценка ожидания, попытка из максимума; `superseded` приходит у завершённой (отменённой) сборки. Редактор документов при исчерпанном лимите сессий отвечает `OfficeEditorBusy` (`state: editor_busy`, через сколько секунд повторить, лимит); в локальном режиме поле и состояние не встречаются;
- `Admin*` эталоны черновые: они фиксируют имена полей до экранов админки и дополняются в срезах админки.

Форму меняют так: сначала эталоны, затем обе стороны и оба набора тестов в одном коммите. Таблица владения и единый список URL, scopes и env-имён: `docs/design/stage2-ownership.md`.
