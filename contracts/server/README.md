# Контракт серверного режима

Общие файлы бэкенда и фронтенда для этапа 2. Расхождение сторон ловят два теста, которые читают одни и те же файлы:

- `services/api/tests/unit/contract/test_server_contract.py` проверяет эталоны строгими моделями `api/schemas/session.py` (`extra=forbid`) и сверяет коды ошибок с `errors.json`;
- `services/web-app/src/entities/session/api/contract.test.ts` разбирает те же эталоны схемами zod (`z.strictObject`) и сверяет коды с `errors.json` обоих языков.

Состав:

- `error_codes.json` закрытый список кодов ошибок входа, регистрации и аккаунта (тело ответа `{detail, code}`, модель `AuthErrorBody`). Сообщения лежат в `errors:code.<код>` для ru и en. Код, общий с Git-синхронизацией (`rate_limited`), хранит одно сообщение на оба случая;
- `fixtures/<Схема>/<вариант>.json` эталонные тела запросов и ответов, по каталогу на схему; каталог без схемы в обоих тестах считается ошибкой. Эталон содержит все поля явно, в том числе `null`;
- единственный публичный ответ о состоянии входа: `GET /api/v1/session/bootstrap` (`Bootstrap`: режим, состояние первого запуска, способы входа, пользователь, возможности клиента, CSRF-токен). Возможности клиента определяются `capabilities`, а не проверкой «режим server»;
- мастер первого запуска: шаговые ручки `/api/v1/server-setup/status|admin|environment|settings|complete` (`ServerSetupStatus`, `ServerSetupAdminRequest`, `ServerSetupEnvironment`, `ServerSetupSettingsRequest`; `GET settings` отдаёт `ServerSetupSettings`: действующие значения и `locked_by_env`, ключи, заданные окружением, шаг показывает их только для чтения) и экран `/first-run`; отдельного POST first-run нет. Администратора создаёт `admin` (ответ `LoginResponse`, сессия сразу выдана), остальные шаги идут его сессией. Токен установки печатается в журнале api и нужен, пока админа нет; его не нужно при `SETUP_TOKEN_REQUIRED=false` и при админе из окружения. `environment` пускает по заголовку `X-Setup-Token` или сессией админа. Пока мастер не завершён, прочие маршруты отвечают `503 setup_required` всем, кроме админа;
- ответы регистрации и «забыл пароль» всегда нейтральные (`status: check_email`); `link` непустой только без SMTP, когда ссылку копирует сам человек; у «забыл пароль» и повторной отправки подтверждения `link` всегда пуст (иначе любой, знающий адрес, получил бы чужую ссылку), без SMTP сброс выдаёт администратор;
- `GET|PATCH /api/v1/account` (`AccountProfile`, `UpdateAccountRequest`): имя, язык и подпись коммитов; `null` в запросе значит «не менять», пустая строка в `commit_name` или `commit_email` сбрасывает подпись к умолчанию (имя аккаунта и noreply-адрес `<id>@noreply.<хост public_url>`; настоящий e-mail попадает в коммиты только по `commit_use_account_email` или как собственный адрес);
- токены доступа: `GET|POST /api/v1/account/tokens`, `DELETE .../tokens/{id}` (`ApiToken`, `CreateApiTokenRequest`, `CreateApiTokenResponse`; значение токена приходит один раз в `token`, в списке только `prefix`); способы входа: `GET /api/v1/account/identities` (`AccountIdentity`: пароль или привязка OIDC, `can_unlink` ложно у пароля и у последнего способа), `DELETE .../identities/{id}` (последний способ даёт `409 last_login_method`), `POST .../identities/link/start` (`LinkIdentityRequest` -> `LinkIdentityResponse.redirect_url`, адрес на своём сайте);
- `ProjectSummary` и `CreateServerProjectRequest` форма списка проектов и создания в серверном режиме: владелец (`owner`) и роль текущего человека (`my_role`), без пути папки. В серверном режиме `GET /api/v1/projects` отдаёт страницу `ProjectSummaryPage` из каталога (без чтения project.json): `q` по названию, владельцу и руководителю, фильтры `archived`, `owner=me|org|shared`, `org` (slug), `pinned`, `sort=name|updated_at|created_at` (по умолчанию `-updated_at`); в локальном режиме ответ прежний, массив;
- отказ по роли: `403` с телом `{detail, code: "forbidden_role", required_role}` (`required_role` одна из `reader|reviewer|editor|owner`); фронтенд показывает тост «нужна роль X». Без роли в причине (гость, личные условия) бэкенд отвечает простым `403 forbidden`, тост показывает общий текст;
- настройки установки в админке: `/api/admin/settings/registration|auth|smtp`, `POST /api/admin/settings/smtp/test` и CRUD `/api/admin/oidc-providers`. Каждая группа отдаёт `fields`: по ключу `source` (`env|admin|default`) и `locked` (значение задано окружением и из интерфейса не меняется, ответ `409 setting_locked`). Секреты (пароль SMTP, секрет клиента OIDC) только на запись: в ответах лишь `password_set` и `client_secret_set`. Последний способ входа не выключается (`409 last_login_method`);
- эксплуатация в админке: `GET /api/admin/queue` (`AdminJobPage`: новые первыми, фильтры `state|kind` повтором параметра, `user_id|org_id|project_id|runner_id`, `from|to` по времени постановки; непрозрачный `next_cursor` (base64url от `seq`, старый курсор цифрами принимается), `total_estimate` по статистике только без фильтров; в строке `user_name|user_email|org_name|project_name|runner_name`), `GET /api/admin/queue/summary`, `POST /api/admin/queue/{id}/cancel`; `GET|PUT /api/admin/quotas` (`AdminQuotas`, полная замена, `null` снимает лимит, исчерпание значит ожидание в очереди); `GET /api/admin/services` (недоступный сервис даёт `state: down` и причину, а не 500); `GET /api/admin/storage` (счёт по базе, кэш на минуту, `?refresh=true` пересчитывает); `GET|PUT /api/admin/settings/signing` (`server_keys: allowed|forbidden`, по умолчанию `forbidden`); общие ИИ-провайдеры `/api/admin/ai-providers` (ключ только на запись, в ответах `key_set`). Токен регистрации раннера и готовая команда запуска (`command`) приходят один раз в ответе на создание; `status` раннера считается от `last_seen_at`: `online` до минуты, `stale` до пяти, дальше `offline`, плюс `paused` и `revoked`. Каждая мутация пишет событие аудита;
- списки эксплуатации страницей `Page` (`items|total|limit|offset`; `limit` 1..200, по умолчанию 50, `q` до 200 символов, `sort=field|-field` из разрешённых полей, иначе 422): `GET /api/admin/runners` (`AdminRunnerList`; `status` повтором, `tag`, `resource_class`, `outdated`; порядок по умолчанию `status`), `GET /api/admin/runners/summary` (`AdminRunnerSummary`: счётчики по статусам, `outdated` и `newest_version` среди неотозванных), `GET /api/admin/runner-tokens` (`AdminRunnerTokenList`; `status=active|expired|exhausted|revoked`), `GET /api/admin/storage/owners` (`AdminStorageOwnerList`; `kind=user|org`, порядок `projects|bytes|name`), `GET /api/admin/ai-providers` (`AdminAiProviderList`, только общие провайдеры; `type`); пикеры для фильтров очереди `GET /api/admin/pickers/runners|projects` (`AdminPickerList`: до 20 совпадений и `has_more`, без страниц; `?id=` находит одну запись по id, проект и удалённый, чтобы фильтр из ссылки показал имя);
- жизненный цикл данных: `DELETE /api/admin/users/{id}` (204; только отключённая учётная запись, `409 user_not_disabled`; пока человек единственный владелец проекта или организации, `409 user_has_projects`; последний админ `409 last_admin`), `GET /api/v1/account/export` (JSON-вложение с данными самого человека, только сессией), `GET /api/admin/settings/retention` (`AdminRetentionSettings`, сроки хранения из окружения, только чтение);
- импорт проекта из локальной Студии: `POST /api/v1/projects/import` (multipart-поле `file`, zip с папкой проекта вместе с `.hse-studio`), ответ 201 `ProjectImportResult`: `project_id`, `id_regenerated` (id из архива был занят), число файлов, байт и перенесённых чатов, `warnings` с кодами `remote_needs_access|records_skipped|store_hardened|junk_skipped|chats_unreadable` (`detail` число затронутого или пусто). Архив отвергается целиком до записи на том: путь наружу, симлинк, шифрование, неверный размер, нет `.hse-studio/project.json`. Отказ `{detail, code}`: 422 `import_archive_invalid|import_archive_unsafe|import_no_project|import_project_newer`, 413 `import_too_large`, 503 `import_unavailable`; в локальном режиме маршрута нет (404);
- организации и группы: `/api/v1/orgs*` и `/api/v1/groups*` (`Org`, `OrgMember`, `Group`, `GroupMember` и тела запросов). Организацию видят только её участники (не участнику 404, и админу установки тоже: управление идёт через `/api/admin`), мало роли даёт 403, конфликты 409 с кодами `last_owner`, `slug_taken`, `name_taken`, `already_member`, `org_has_projects`;
- участники проекта: `PUT|DELETE /api/v1/projects/{id}/members/{user|group}:{id}` (`SetProjectMemberRequest`, `ProjectMember`), только владелец проекта, назначаются роли reader, reviewer, editor; роль владельца записью не выдаётся, группа должна быть из организации проекта (или из организации владельца);
- организации человека `GET /api/v1/account/orgs` (`MyOrg`: моя роль и названия моих групп; только свои организации), `DELETE /api/v1/account/orgs/{slug}/membership` (выйти; единственный владелец получает `409 last_owner`); панель «Доступ»: `GET /api/v1/projects/{id}/members` (`ProjectAccessEntry`, читать может любой участник проекта), `GET .../members/candidates?q&limit&kind=user|group` (`ProjectAccessCandidateList`: `{items: ProjectAccessCandidate[], has_more}`, группы и люди общих организаций, у проекта организации только она, плюс те, кому владелец уже открывал свои проекты; `limit` до 20). Список `GET .../members` отдаётся страницей `ProjectAccessList` (`q`, `kind`, `role`, `sort=name|role`; владелец и организация-владелец всегда первыми). `GET .../transfer-candidates?q&limit&kind=user|org` (`ProjectTransferCandidateList`, форма пикера) предлагает организации, где смотрящий владелец или админ (id это slug), и людей общих организаций. Запись доступа идёт существующими `PUT|DELETE .../members/{user|group}:{id}`; менять доступ и искать кандидатов может владелец проекта (`403 forbidden_role` с `required_role: owner`), владельца проекта и доступ через организацию-владельца здесь не меняют (`locked`), понизить единственного владельца нельзя (`409 last_owner`);
- организации в админке: `/api/admin/orgs*` (`AdminOrg`, `AdminOrgMember`, `AdminGroup` и тела запросов) обслуживает админ установки без членства: создатель организации становится её владельцем, последний владелец остаётся (`409 last_owner`), организацию с проектами не удалить (`409 org_has_projects`), группа принимает только участников организации (состав меняют точечно `POST|DELETE .../groups/{id}/members/{user_id}`, полная замена `member_ids` в PATCH оставлена старым клиентам); настройки установки `GET|PUT /api/admin/settings/instance|build` (`AdminInstanceSettings`, `AdminBuildSettings`) помечают значения из окружения как `locked`, запись такого ключа даёт `409 setting_locked`;
- состояния сборки: `CompileWait` в поле `wait` деталей сборки (`GET .../compiles/{id}`) и в событии `wait` потока сборки: `reason` одно из `queued|quota_wait|no_runner|runner_lost|superseded`, место в очереди (`queue_position`, с 1), оценка ожидания, попытка из максимума; `superseded` приходит у завершённой (отменённой) сборки. Редактор документов при исчерпанном лимите сессий отвечает `OfficeEditorBusy` (`state: editor_busy`, `retry_after_s` и `limit`: через сколько секунд повторить и сколько сессий допускает установка; остальные поля ответа редактора при этом пустые); в локальном режиме поле и состояние не встречаются;
- списки админки ищут, фильтруют, сортируют и листают только на сервере: `limit` 1..200 (по умолчанию 50), `offset`, `q` до 200 символов (подстрока без учёта регистра, `%` и `_` обычные символы), `sort` одно поле `field` или `-field` из разрешённых ресурсом (неизвестное даёт 422), к сортировке добавляется вторичный ключ id; ответ `{items, total, limit, offset}` (`AdminUserList`, `AdminUserOrgList`, `AdminInvitationList`, `AdminOrgList`, `AdminOrgMemberList`, `AdminGroupList`, `AdminGroupMemberList`). Перечислимые фильтры повторяются (`status=active&status=disabled`). Счётчики чипов отдают `GET /api/admin/users/facets` с теми же `q`, `status`, `is_admin`, `org`, что у списка, каждый счётчик без своего фильтра (`AdminUserFacets`: `status`, `admins`, `members`) и `GET /api/admin/orgs/{slug}/members/facets?q=` (`AdminOrgMemberFacets`); `AdminOrg.owner_count` заменяет подсчёт «последнего владельца» на клиенте, `AdminGroup` несёт `member_count` и до пяти `preview` вместо состава. Список участников организации принимает `not_in_group=<id>`: пикер «добавить в группу» не предлагает тех, кто в ней уже есть. Пикеры `GET /api/admin/pickers/users|orgs?q&limit` (до 20, `AdminPickerList`: `{items: [{kind, id, name, detail}], has_more}`) не листаются: `has_more` значит «уточните поиск». `AddAdminOrgMemberRequest` принимает `user_id` из пикера или `email` (ровно одно);
- журнал `GET /api/admin/audit` листается непрозрачным курсором `cursor` (base64url ключа; старый курсор из цифр ещё принимается), новые первыми: фильтры `category` (префикс до точки, можно несколько), `action` (точное, можно несколько; значение с точкой в конце читается как префикс), `actor_id`, `target`, `from` и `to` (старые имена `since` и `until`), `q` (подстрока в действии и цели или имя и почта действовавшего). Строка `AdminAuditEvent` несёт `actor` (`{id, name, email}`, у удалённого человека имя это псевдоним) и `target_label`; `AdminAuditPage.total_estimate` есть только без фильтров;
- личные раннеры (`MyRunner*`, `RunnerPairing*`, `ProjectBuildRunners`, `CompilePlacement`): человек подключает свой раннер в `/api/v1/account/runners*` (токен регистрации `hsrt_` и команды запуска приходят один раз в `MyRunnerTokenCreated`, новый токен раннера один раз в `MyRunnerRotated`), подтверждает код устройства в `/api/v1/account/runner-pairings/{user_code}`; чужой раннер или токен даёт 404. Владелец личного проекта выбирает в `/api/v1/projects/{id}/build-runners`, где идут сборки соавторов (`shared` по умолчанию или `owner`); свои сборки владельца предпочитают его раннер всегда, если тот в сети. Соавтор видит у раннера владельца только имя и состояние. Где идёт сборка, показывает `placement` деталей сборки и событие `placement` потока (`CompilePlacement`, пометка `fallback`, когда сборка ушла на общий раннер); `CompileWait.reason` получает `personal_runner`. В админке раннеры получают владельца (`owner_kind`, `owner`), вид хоста, имена ИИ-адресов и состояние `disabled`; задачи очереди получают `route`, `runner_scope`, `route_reason`; настройки сборки получают `personal_runners_enabled`, `personal_runner_wait_s`, `personal_runners_max_per_user` (ключи `runners.*`). `Capabilities.personal_runners` истинно у вошедшего человека на сервере при разрешённых личных раннерах, `remote_runner` только в локальном режиме (`/api/v1/remote-runner*`, `RemoteRunnerStatus`);
- облачные сборки локальной Студии (только локальный режим, на сервере 404): `GET|PUT|DELETE /api/v1/remote-runner`, `POST /api/v1/remote-runner/pair|token`, `DELETE /api/v1/remote-runner/pairing` (`RemoteRunnerStatus`, `UpdateRemoteRunnerRequest` с `null` как «не менять», `RemoteRunnerPairRequest`, `RemoteRunnerTokenRequest`). Токен регистрации есть только в теле запроса, в ответах секретов нет; `ai_endpoints[].url` видит только хозяин машины, на сервер уходят имя и вид. Отказ `{detail, code}`: 422 `remote_runner_url_invalid`, 502 `remote_runner_unreachable`, 409 `remote_runner_disabled`. Возможность клиента `capabilities.remote_runner` истинна только в локальном режиме;
- ссылки доступа (трек links, `ShareLink*`, `OpenShareLink*`, `GuestInfo`, `OrgSharingPolicy`, `AdminSharingSettings`): владелец и редактор с правом делиться управляют ссылками проекта в `/api/v1/projects/{id}/links*` (действие `SHARE`; редактор видит и правит только свои); адрес ссылки `<public_url>/s/hsl_…` есть только у действующей и заблокированной политикой (`state: active|expired|revoked|blocked`, `blocked_reason: links_disabled|org_links_off|org_role_cap|nda`). Страница ссылки зовёт публичные `GET /api/v1/links/{token}` (`ShareLinkPreview`: несуществующая, отозванная и истёкшая одинаково `inactive`; при `password_required` имени проекта и роли нет) и `POST /api/v1/links/{token}/open` (вошедший получает ссылочное право, гость cookie `hse_guest`, `__Host-` по HTTPS; ответ `landing: workspace|view`). Гость читает `Bootstrap.guest` и CSRF-токен своей сессии в `csrf_token`, правит имя `PATCH /api/v1/links/session`, выходит `DELETE /api/v1/links/session`. `ProjectSummary.via_link` и поля проекта `via_link`, `link_label` говорят, что роль держится на ссылке. Политика: `GET|PUT /api/v1/orgs/{slug}/sharing-policy` (правят владелец и админ организации) и `GET|PUT /api/admin/settings/sharing` (окружение блокирует ключи, `409 setting_locked`);
- приглашения в проект, запросы доступа, передача владения и «Входящие» (трек invites): `GET|POST /api/v1/projects/{id}/invitations`, `POST .../invitations/{id}/resend`, `DELETE .../invitations/{id}` (`ProjectInvitation`, `ProjectInvitationPage`, `CreateProjectInvitationRequest`, `ProjectInvitationCreated` с `delivery: email|manual|inbox` и `link` только для пересылки вручную), `GET .../access-requests`, `POST .../access-requests/{id}/approve|deny` (`AccessRequestView`, `ApproveAccessRequest`, `DenyAccessRequest`), `GET|POST|DELETE .../transfer` (`ProjectTransferState`, `StartProjectTransferRequest`; организации нужен `confirm_name`); у адресата `GET /api/v1/account/invitations`, `POST .../invitations/{id}/accept|decline` (`MyInvitation`), `GET /api/v1/project-invitations/{token}` без входа (`ProjectInvitationPreview`, имя проекта только у `ok`, `registration_token` для регистрации в режиме «по приглашению»), `POST .../{token}/accept` (`403 invitation_email_mismatch` с `email_hint`), `POST /api/v1/access-requests` (всегда 202 `AccessRequestAccepted`, только сессией), `GET|DELETE /api/v1/account/access-requests*` (`MyAccessRequest`), `GET /api/v1/account/transfers`, `POST .../transfers/{id}/accept|decline` (`MyTransfer`), `GET /api/v1/account/notifications`, `POST .../notifications/read` (`Notification`, `NotificationPage`, `MarkNotificationsReadRequest`), `GET /api/v1/account/inbox/summary` (`InboxSummary`); `Bootstrap.inbox` (`{unread}`) у вошедшего. `PUT .../members/user:{id}` для нового человека отвечает `409 invitation_required` (S10). Отказ `409 invitation_pending` несёт `invitation_id`;
- PDF локальной сборки на сервере (`ProjectArtifactList`, `PdfUploadResult`, docs/design/local-sync.md): локальная Студия грузит файл `PUT /git/-/projects/{id}/documents/{doc}/pdf` (токен с `git:write`, тело `application/pdf`, в запросе `sha256`, необязательно `name`, `pages`, `commit`, `built_at`; ответ 201 или 200, если тот же файл уже последний). Отказ `{detail, code}`: 413 `artifact_too_large` или `project_quota_exceeded`, 415 `artifact_not_pdf`, 422 `artifact_checksum_mismatch`, 404 `artifact_unknown_document`, 403 `artifact_forbidden` (нужна роль редактора и право на документ) или `git_scope_missing`. Читают `GET /api/v1/projects/{id}/artifacts` и `.../artifacts/{id}/file` те, кто видит результат сборки (`OUTPUT_READ`), удаляет `DELETE .../artifacts/{id}` тот, кто пишет файлы; хранится `keep_per_document` последних версий, размер не больше `max_pdf_bytes`; загрузка и удаление пишут аудит `artifact.pdf_uploaded` и `artifact.deleted`;
- `Admin*` эталоны черновые: они фиксируют имена полей до экранов админки и дополняются в срезах админки.

Форму меняют так: сначала эталоны, затем обе стороны и оба набора тестов в одном коммите. Таблица владения и единый список URL, scopes и env-имён: `docs/design/stage2-ownership.md`.
