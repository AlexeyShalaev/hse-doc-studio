# Контракт раннера

Общие файлы API и раннера: протокол pull поверх HTTPS JSON под `/api/runner/v1`. Расхождение сторон ловит `services/api/tests/unit/contract/test_runner_contract.py`:

- `openapi.yaml` описание вызовов (регистрация, долгий опрос, пульс, лог, блобы, выходы, итог) и схем; схемы совпадают по полям, обязательности и перечислениям с `api/schemas/runner.py` (`extra=forbid`);
- `error_codes.json` закрытый список кодов ошибок (тело `{detail, code}`), совпадает с `RunnerErrorCode` и `x-error-codes`;
- `fixtures/<Схема>/<вариант>.json` эталонные тела; каждое проходит строгую модель и совпадает после круга через проводные датаклассы `core/jobs/wire.py` и `codec`. Конверт покрыт для каждого вида задачи. Вложенные схемы (`ActorWire`, `JobSpecWire`, `JobResultWire`, `BlobLocationBody`) отдельных эталонов не имеют.

Конверт несёт снимок актора и его роль в проекте на момент постановки (`actor_role`): применение результата пересобирает актора по ним, а не берёт системного. Каждый вызов по задаче несёт `attempt`, устаревшая попытка получает 409 `stale_attempt`.

Личные раннеры и ретрансляция ИИ идут той же версией протокола через согласование возможностей:

- `POST /announce` (токен раннера) сообщает имя (`null` не меняет имя, заданное хозяином на сайте), теги, слоты сборок и ИИ (`ai_concurrency`), вид хоста (`cli`, `desktop`), возможности и объявленные ИИ-адреса (только имя и вид, без URL); ответ несёт пересечение возможностей (`announce`, `offline`, `ai_slots`, `ai_relay`), владельца раннера и паузу. Старый сервер отвечает 404, и раннер работает в старом режиме;
- пока возможность не объявлена, сервер ничего нового не шлёт: старый раннер регистрируется и собирает как раньше (в том числе как личный), но задачи `ai.relay` не получает; `free_ai_slots` в опросе есть только у раннера с `ai_slots`;
- `POST /offline` (мягкая остановка) и `POST /deregister` (раннер отзывает себя сам);
- `POST /deployment` (возможность `deployment_info`): как раннер развёрнут, для админки. Исполнитель, namespace, под и ServiceAccount, requests и limits раннера и подов сборки, securityContext; без токенов, окружения и адресов. Раннер шлёт его только после согласования возможности, поэтому старый сервер его не получает, а у старого раннера в админке «нет данных». Сервер хранит отчёт только общих раннеров;
- сопряжение по коду устройства: публичные `POST /pair/start` и `POST /pair/poll`; токен регистрации приходит ровно один раз при `approved`, опрос чаще `interval` даёт 429 `slow_down`;
- ретрансляция ИИ: задача `ai.relay` (тег `ai`, без манифеста, нагрузка без тела запроса), тело забирается `GET /jobs/{id}/relay/request` (заголовок `X-Relay-Sha256`), ответ модели уходит порциями `POST /jobs/{id}/relay/events` (ровно один `head`, затем `data`, в конце `end` или `error`); подтверждение порции и пульс задачи доставляют отмену. Путь и метод только из белого списка (`models`, `chat/completions`, `completions`, `embeddings`), URL знает только раннер.

Конверт задачи для личного раннера не несёт e-mail актора, гостевую ссылку и признак админа.

Форму меняют так: сначала `openapi.yaml` и эталоны, затем `wire.py`, pydantic-схемы и тесты в одном коммите.

## Личные раннеры и согласование возможностей

Путь остаётся `/api/runner/v1`. Новый раннер сразу после регистрации зовёт `POST /announce` и сообщает возможности (`announce`, `offline`, `ai_slots`, `ai_relay`), теги, слоты и объявленные ИИ-адреса (только имя и вид, без URL). Сервер отвечает пересечением и шлёт новое (вид `ai.relay`, поле `free_ai_slots`) только после него. Старый сервер отвечает на `/announce` 404, и раннер работает по-старому; старый раннер без `/announce` собирает как раньше и ретрансляцию не получает. `POST /offline` (мягкая остановка) и `POST /deregister` (раннер отзывает сам себя) без тела. Сопряжение по коду устройства: `POST /pair/start`, затем `POST /pair/poll` не чаще `interval`, токен регистрации выдаётся один раз.

## Якоря сборки

Возможность `build_anchors` (`docs/design/signing-route.md`, 15.17.6). Раннер, согласовавший её, выгружает у compile-задачи файл позиций `<stem>.hsepos` рядом с PDF, под тем же путём, что SyncTeX (`<каталог исходника>/<stem>.hsepos`), и только если его записал последний проход TeX (строка `OUTPUT` в `.fls`). Сервер кладёт файл в `.build/<doc_id>/` и при публикации PDF переводит в `anchors.json` с sha256 этого PDF. Без согласования раннер файл не выгружает: белый список прежнего сервера отверг бы задачу целиком (`output_not_allowed`). Сервер принимает файл только от раннера, объявившего возможность, иначе отбрасывает его при `/complete`, а задача не падает. Сборка раннером прежней версии оставляет якоря неизвестными. Версия протокола не меняется.

## Ретрансляция ИИ

Задача `ai.relay` (тег `ai`) идёт только на выбранный раннер хозяина. Нагрузка несёт имя адреса и путь из белого списка (`GET models`, `POST chat/completions`, `POST completions`, `POST embeddings`), тела запроса в ней нет: раннер забирает его `GET /jobs/{id}/relay/request` и сверяет `X-Relay-Sha256` и размер. Ответ модели идёт порциями `POST /jobs/{id}/relay/events`: ровно один `head` раньше любых `data` (base64, до 64 KiB на событие), затем `end` или `error` с кодом; `seq` растёт с нуля, повтор порции безвреден, пропуск даёт 409 `relay_out_of_order`. `cancel: true` в подтверждении порции или в ответе пульса обрывает запрос к модели; пока порций нет, раннер шлёт пульс каждые `relay_keepalive_s`. Итог задачи `{status_code, bytes_out, upstream_ms}`.

## Канал команд и диск раннера

Возможности `control` и `disk` (`docs/design/storage-cleanup.md`, раздел 6). Команды идут отдельным долгим опросом `POST /control/poll` (`{wait_s}` до 25 с, ответ `{command}` или `null`), открытым и у раннера, занятого сборками. Конверт команды `{id, kind, payload, issued_at}`: `disk.measure` с пустой нагрузкой или `disk.cleanup` с `{targets, include_rollback}`. Сервер передаёт только цели, не ссылки на образы: что удалить, раннер решает по свежему замеру. Ход и итог `POST /control/{command_id}/progress` (`running`, `done`, `cancelled`, `error` и шаги), ответ `{cancel}` доставляет остановку; повтор итога безвреден, ход по закрытой команде получает 409 `command_finished`. Замер `POST /disk` (`RunnerDiskReportBody`, до 64 КБ, иначе 413 `disk_report_too_large`) без путей, имён рабочих папок и чужих образов; у Kubernetes и локальной Студии Docker-части нет (`docker_reason`). Вызов без согласованной возможности получает 409 `feature_not_negotiated`. Модель `core/jobs/disk.py`, сообщения канала в `wire.py`; эталоны покрывают каждый вид команды и каждое состояние Docker-части.

Возможность `disk_auto` (`docs/design/storage-cleanup.md`, раздел 14). Раннер с Docker-частью раз в 5 минут шлёт `POST /control/disk-check` (`{free_bytes, total_bytes}` тома данных). Сервер сверяет место с настройкой автоочистки раннера (включена, порог в процентах, не чаще раза в час, нет идущей очистки) и отвечает `{command}`: команду `disk.cleanup` с `auto: true`, уже доставленную, или `null`. Дальше ход и итог идут как у любой команды. Флаг `auto` в нагрузке едет только когда он `true`, и только раннеру, объявившему возможность. Без согласования адрес отвечает 409 `feature_not_negotiated`.
