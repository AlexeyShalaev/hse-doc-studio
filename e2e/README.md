# Приёмочные e2e на стенде server-lite

Playwright проходит сценарии M1 по настоящему стенду (образ приложения в режиме server и Postgres в compose), а не по демо-миру фронта. Что проверяется, на ru и en:

- аноним попадает на экран входа, неверный пароль отклоняется;
- после входа видны только свои проекты (три демо-пользователя из seed);
- проект создаётся мастером (11 шагов) и остаётся в списке после перезагрузки;
- второй пользователь не видит чужой проект ни в списке, ни по прямой ссылке, ни через API;
- выход закрывает сессию.

Язык интерфейса задаёт локаль браузера, поэтому каждый сценарий идёт дважды. Скриншоты каждого шага лежат в `screenshots/ru` и `screenshots/en`, в CI это артефакт `e2e-screenshots`.

## Запуск

Из корня репозитория:

```bash
make server-lite-up server-lite-seed   # стенд и демо-данные
make e2e-install                       # один раз: зависимости и Chromium
make e2e-m1                            # сценарии
```

Вместо загрузки Chromium можно взять установленный Chrome: `make e2e-m1 E2E_CHANNEL=chrome`.

Против любого другого стенда: `E2E_BASE_URL=http://localhost:8100 E2E_SEED_PASSWORD=... pnpm test` из этого каталога. Пароль это `SERVER_LITE_SEED_PASSWORD` из `scripts/dev/server-lite/.env`.

Сценарии создают проекты `E2E проект ru` и `E2E проект en`: на чистом стенде они единственные новые, при повторном прогоне появляются дубли названий, список от этого не ломается. Чистый стенд: `make server-lite-reset`, затем up и seed.

## Лендинг на том же стенде

`tests/landing.spec.ts` (проект Playwright `landing`) идёт по стенду server-lite. На ru и en:

- гость на корне видит лендинг и форму входа рядом с описанием, входит и попадает в свои проекты; вошедший корень не меняет;
- на телефоне (390 px) форма открывается из кнопки «Войти» в диалоге;
- прямой `/login`, возврат по `?next=`, закрытый адрес гостя и ссылка приглашения работают как раньше;
- корень отдаёт теги Open Graph без выполнения скриптов (curl-подобный запрос), картинка предпросмотра доступна с того же сайта;
- админ выключает лендинг в настройках установки: гость сразу попадает на экран входа, затем лендинг включается обратно.

```bash
make server-lite-up server-lite-seed
make e2e-landing          # пароль админа берётся из server-lite/.env
```

## Узкие панели

`tests/sidebar-overflow.spec.ts` (проект `mobile`) на ru (светлая тема) и en (тёмная): левая панель проекта (документы с плашкой «Получить облачные сборки» и блоком «Сейчас», замечания, сдача, файлы) и строка управления под полем чата агента на ширине панели 280 и 380 px (десктоп) и 320 и 480 px (телефон, панель на весь экран), размер текста 100% и 140%. Ничто не выходит за рамку панели, текст не обрезан без многоточия, органы управления не налезают друг на друга, название модели в чате видно. Облачные сборки, документы с длинными кодами и провайдер подменены заглушками. Скриншоты: `screenshots/<язык>/sidebar-*.png`, `agent-*.png`.

## Телефон на том же стенде

`tests/mobile.spec.ts` (проект Playwright `mobile`, базовое устройство Pixel 7, размеры задаёт сценарий) идёт по стенду server-lite на 360x740 и 390x844, на ru и en, плюс планшет 820x1180:

- гостевые экраны (лендинг, вход, регистрация, сброс пароля) и после входа список проектов, входящие, «Подключить Студию», «Локальная версия» не дают горизонтальной прокрутки: страница приложения не прокручивается сама, поэтому проверяются и `scrollWidth`, и элементы за правым краем окна вне блоков со своей прокруткой;
- вход с экрана `/login`, список проектов, открытие проекта;
- основные кнопки и все поля, кнопки и ссылки первого экрана не меньше 40 px;
- фильтры списка проектов открываются шторкой снизу (`data-form="sheet"`, во всю ширину, прижата к низу), выбор применяется сразу;
- меню аккаунта шторкой, тема и язык переключаются из неё;
- окно («Импорт из zip») шторкой, закрывается крестиком и касанием по фону;
- на планшете список остаётся десктопным, окно остаётся окном.

```bash
make server-lite-up server-lite-seed
cd e2e && E2E_SEED_PASSWORD=... pnpm exec playwright test --project mobile   # скриншоты screenshots/{ru,en}/mobile-*.png
```

## Passkey на том же стенде

`tests/passkeys.spec.ts` (проект Playwright `passkeys`) идёт по стенду server-lite с виртуальным аутентификатором Chrome (CDP `WebAuthn.addVirtualAuthenticator`: платформенный ключ с биометрией, обнаруживаемые ключи, присутствие и проверка пользователя подтверждаются сами). На ru и en:

- человек входит паролем, в «Аккаунте» добавляет passkey без повторного подтверждения (сессия свежая), ключ ложится в аутентификатор с RP ID `localhost`;
- второй раз тот же аутентификатор ключ не создаёт (сервер исключает его в `excludeCredentials`), экран показывает ошибку;
- поле e-mail на экране входа размечено `autocomplete="username webauthn"`, вход кнопкой «Войти с passkey» без пароля;
- ru: админ видит ключ в карточке человека и сбрасывает его, после чего вход тем же ключом отклоняется;
- en: человек удаляет ключ сам.

```bash
make server-lite-up server-lite-seed
make e2e-passkeys          # пароль админа берётся из server-lite/.env
```

Повторный прогон на том же стенде добавляет ключи заново: прежние ключи остаются у людей в списке, тест считает разницу.

## Маршрут подписания на том же стенде

`tests/signing-route.spec.ts` (проект Playwright `signing-route`, срез E1 из `docs/design/signing-route.md`) идёт по стенду server-lite с общим раннером поддельного TeX (`scripts/dev/server-lite/fake_tex_runner.py`, сервис `runner` профиля `runner`). Это настоящий раннер из образа api: протокол, рабочие папки, выгрузка PDF, проверка открепленных подписей gpg. Заменён только исполнитель TeX: он кладёт рядом с исходником одностраничный PDF A4, одинаковый для одинаковых исходников документа (как воспроизводимая сборка), поэтому образ TeX Live стенду не нужен. Пока раннер запущен, сборки всех людей стенда идут на нём, поэтому M1 (стенд без раннеров) идёт раньше. Людей и проекты сценарий заводит сам, с меткой прогона. На ru:

- студент на точке «Заявка на тему КП» открывает «Отправить на подписание», собирает оба документа, видит порядок по умолчанию (автор, научрук), добавляет подпись академрука (встаёт последним шагом), видит помеху «подпись не размещена», размещает подписи, загружает свою картинку и отправляет; «Скопировать ссылку» даёт адрес страницы подписи научрука;
- научрук находит задачу во «Входящих → На подпись» и согласует нарисованной подписью;
- академрук выбирает ЭП, задаёт плашку открытым ключом OpenPGP, согласует (заявление фиксируется) и подписывает итоговый PDF готовой открепленной подписью, сделанной gpg хоста; карточка точки: «Все подписали», в итоговом PDF картинки и плашка, подпись действительна и относится к нему;
- пока маршрут идёт, панель подписей документа закрыта с пояснением «Документ на подписании», правка размещения через API получает 409 `route_locked`; сборка без правок даёт тот же PDF, сборка после правки маршрут тоже не останавливает: подписывают версию, снятую при отправке, на карточке «Есть изменения после отправки на подпись»;
- академрук возвращает на доработку с комментарием, автор видит его на карточке, правит и пересобирает заявление, «Отправить заново»: новый раунд, согласие научрука сброшено, его картинка на месте, повторное согласие одним нажатием.

```bash
make server-lite-up server-lite-seed
make e2e-signing-route     # поднимает раннер, гонит сценарии, гасит раннер; нужен gpg на хосте
```

`tests/signing-snapshot.spec.ts` (тот же проект `signing-route`, срез E2, раздел 12 дизайна: версия на подписи) идёт следом на том же раннере. Маршрут с двумя документами («Описание проекта» и «Заявление»), подписи научрука и академрука картинками:

- автор правит исходник описания в редакторе: «Документ на подписании. Изменения не попадут в подписываемую версию» спрашивает один раз, «Продолжить» пускает правку, дальнейшая правка и «Собрать» не спрашивают; маршрут идёт, на карточке «Есть изменения после отправки на подпись. Подписывают версию от …» и дата версии у документа, на вкладке «Подписи» «Подписывать текущую сборку» выключена;
- научрук на странице подписи видит «Вы подписываете версию от …», PDF страницы это версия на подписи (тот же sha, что при отправке), расхождения не видит, согласует;
- «Отправить новую версию» с «Что изменилось»: в подтверждении изменилось описание, без изменений заявление; согласие научрука сброшено только по описанию, на заявлении его картинка осталась («Без изменений: вы уже подписали»), запрос новой версии с сообщением автора, повторное согласие одним нажатием;
- академрук согласует, маршрут завершён; пакет точки собран из подписанных версий; после ещё одной правки и сборки пакет тот же, с предупреждением «изменён после отправки на подпись: в пакет попала версия на подписи от …» (`changed_after_sent`); «Подписывать текущую сборку» выключена и после завершения, `DELETE .../pinned` получает 409 `route_locked`.

Какая сборка лежит в PDF страницы подписи и пакета, сценарий узнаёт по отпечатку исходников, который поддельный TeX печатает на странице: он переживает картинки, поставленные на PDF. Общие помощники обоих файлов в `tests/signingRouteKit.ts`.

Второй стенд рядом с первым: своё имя проекта compose и порт, например `SERVER_LITE_PROJECT=hds-e1` и `SERVER_LITE_PORT=8197` в `scripts/dev/server-lite/.env`; то же имя проекта передаётся всем целям `make server-lite-*` и `e2e-signing-route`. Отправить маршрут заново можно не раньше чем через минуту после прошлой отправки, поэтому сценарий возврата (E1) и новая версия (E2) ждут остаток этой минуты (прогон около трёх минут на оба файла).

## Полный смоук на стенде deploy/server

`tests/full.spec.ts` (проект Playwright `full`) идёт по полному серверному набору: api, раннер, Postgres и MinIO. Сценарии по порядку на одной базе:

- мастер первого запуска (язык, администратор по токену из журнала api, регистрация, входы, окружение, готово) создаёт администратора и открывает регистрацию, после завершения его ручки закрыты;
- регистрация без SMTP по приглашению админа: ссылка подтверждения в ответ не попадает, почту подтверждает приглашение, вход;
- изоляция: чужой проект не виден в списке, по ссылке и через API, `/api/admin` не-админу отвечает 404;
- сборка через раннер, PDF отдаётся владельцу временной ссылкой на хранилище, чужому 404;
- квота один запуск на пользователя и справедливая очередь: 15 сборок одного пользователя не задерживают сборку другого (раннер на паузе новые сборки не принимает, поэтому очередь копится квотой);
- раннер убит посреди сборки, сборка заканчивается после его возвращения;
- рестарт api посреди сборки: сессия жива, запись доведена до конца;
- админка, раннеры, на ru и en;
- люди в админке: приглашение со ссылкой (её открывает гость без сессии) и журнал аудита, на ru и en.

```bash
make server-stack-build server-stack-up   # образ с extra server и стенд на 127.0.0.1:17251
make e2e-install                          # один раз
make e2e-full                             # сценарии, скриншоты в screenshots/{ru,en}/full-*.png
make server-stack-down                    # стереть стенд
```

Сборка тянет образ TeX Live (несколько гигабайт) при первом прогоне. В CI то же делает джоб `server-stack-smoke` в deploy-smoke. Раннер запускает TeX в соседнем контейнере `texlive/texlive:TL2024-historic`: образ должен быть на docker-хосте заранее, иначе сборка заканчивается `image_missing`. Порт и тег образа задают `STACK_PORT` и `TAG`.

## Личные раннеры на том же стенде

`tests/personal.spec.ts` (проект Playwright `personal`) идёт после полного смоука на том же стенде: к нему добавлен оверлей `deploy/server/compose.personal.yml` с личным раннером Анны (`runner-personal`, профиль `personal`) и поддельной OpenAI-совместимой моделью (`fake-openai`, сеть `personal-net`, api её не видит). Сценарии по порядку:

- Анна создаёт токен в «Мои раннеры», тест поднимает её раннер (`stack.sh personal-up TOKEN`), строка раннера «В сети»;
- сборка Анны идёт на её раннере (`placement.state = personal`, в очереди админа `runner_scope = personal`) и проходит при квоте в одну сборку и общем раннере на паузе;
- сборка соавтора Бориса идёт на общем, пока Анна не выберет «На моих раннерах», затем на раннере владельца; своих раннеров у Бориса нет, раннер Анны по id ему 404;
- мягкая остановка (`stack.sh personal-stop`): сборка сразу на общем с пометкой «не в сети»; убийство без ухода (`stack.sh personal-kill`): окно ожидания, затем общий с пометкой «не взял за 5 с»;
- ИИ через раннер: провайдер «через мой раннер» загружает модели поддельного сервера, Борис его не видит и не может создать такой же; api до модели напрямую не достаёт;
- админ видит личный раннер с владельцем и выключает личные раннеры (раннер «Выключен», сборка на общем с пометкой), затем включает;
- Анна отзывает раннер: процесс раннера завершается, сборки идут на общих.

```bash
make server-stack-build server-stack-up
make e2e-full                                   # сначала полный смоук: он создаёт администратора
cd e2e && pnpm exec playwright test --project personal   # скриншоты screenshots/{ru,en}/full-personal-*.png
```

## Личные раннеры: самостоятельный прогон

`tests/personal-runners.spec.ts` (проект Playwright `personal-runners`) не зависит от полного смоука: на свежем стенде сам создаёт администратора через мастер, людей заводит с меткой прогона, поэтому его можно гонять повторно. Почти всё проходит через интерфейс:

- Анна подключает раннер из «Мои раннеры» (токен в диалоге), тест поднимает его вторым контейнером раннера (`stack.sh personal-reset`, `personal-up TOKEN`), строка «В сети»;
- сборка Анны на её раннере (чип `build-placement` во вкладке сборки), при квоте одна сборка и общем раннере на паузе; две сборки разом: вторая сразу на общем с пометкой «занят» и берётся, пока первая ещё идёт (личная не в счёте квоты);
- Борис (соавтор из общей организации): по умолчанию на общем, после «На моих раннерах» в настройках проекта на раннере Анны, после «На общих» снова на общем; раннер Анны ему 404;
- провайдер «Через мой раннер» создаётся в настройках, модели приходят через раннер, ответ чата идёт потоком событий; Борис провайдера не видит, своего на раннер Анны не заведёт, чужим провайдером в чате не воспользуется, поддельная модель его запроса не получает; api до модели напрямую не достаёт;
- админ выключает личные раннеры в `/admin/instance` (раннер «Выключен», сборка на общем с пометкой, провайдер «выключено админом») и включает обратно;
- мягкая остановка: сборка сразу на общем; убийство без ухода: общий берёт сборку через окно ожидания (5 с) плюс не больше 1,5 с;
- админ видит раннер в `/admin/runners` с владельцем и отзывает его через меню и подтверждение по имени: процесс раннера завершается.

Второй стенд рядом с первым задают `STACK_PROJECT` и `STACK_PORT` (свои `.env`, каталоги раннеров и тома):

```bash
export STACK_PROJECT=hse-doc-studio-pr-e2e STACK_PORT=19805 TAG=pr-personal
scripts/dev/server-stack/stack.sh build && scripts/dev/server-stack/stack.sh up
cd e2e && eval "$(../scripts/dev/server-stack/stack.sh env)" && pnpm exec playwright test --project personal-runners
../scripts/dev/server-stack/stack.sh down
```

Очередь на настоящем Postgres дополнительно проверяет soak `services/api/tests/integration/e2e/test_queue_soak_pg.py`: 200 задач, случайные сбои раннеров, ни дублей закрытия, ни потерянных задач.

## Раннер вне сети сервера: адрес хранилища в ссылках

`tests/outside-runner.spec.ts` (проект Playwright `outside-runner`) идёт на стенде deploy/server с оверлеем `compose.outside.yml`. Личный раннер Анны сидит в сети `outside`, где есть api и шлюз `files` (имя `files.outside.test:9000`, TCP-проброс к MinIO с неизменным `Host`), но нет самого MinIO: так выглядит ноутбук при внутреннем адресе хранилища в ссылках. Режим для внешних раннеров переключает `stack.sh outside-mode none|public|proxy` (пересоздаёт api):

- `none`: публичного адреса нет, сборка на раннере завершается ошибкой `storage_unreachable` (раньше `PUT presigned url: ConnectError`), самодиагностика даёт `warn` с причиной `object_not_public`;
- `proxy`: результат идёт через api (`PUT /api/runner/v1/jobs/{id}/artifacts/{sha256}`): MinIO раннеру не виден, поэтому успешная сборка доказывает путь через api; предупреждения нет;
- `public`: ссылка подписана для `files.outside.test:9000`, результат проходит через шлюз, сборка проходит, предупреждения нет.

```bash
export STACK_PROJECT=hse-doc-studio-outside STACK_PORT=19831 TAG=pr-outside
scripts/dev/server-stack/stack.sh build && scripts/dev/server-stack/stack.sh up
cd e2e && eval "$(../scripts/dev/server-stack/stack.sh env)" && pnpm exec playwright test --project outside-runner
../scripts/dev/server-stack/stack.sh down
```

Образ TeX берётся из `OUTSIDE_TEX_IMAGE` (по умолчанию `texlive/texlive:TL2024-historic`, на хосте он должен быть заранее). Проект в CI не запускается.

## Бэкапы на стенде deploy/server

`tests/backups.spec.ts` (проект Playwright `backups`) идёт после полного смоука на том же стенде и на двух языках интерфейса. Сценарии по порядку:

- локальное назначение создаётся формой (путь наружу корня отвергается), проверка подключения проходит, повтор имени и путь `..` через API дают 409 и 422;
- запуск бэкапа из админки доходит до статуса ok, бэкап виден в назначении;
- verify (предпросмотр восстановления) ничего не пишет и не включает режим обслуживания; неверное подтверждение (422) и перезапись без согласия (409) отклоняются;
- повреждённая часть (правится `dd` внутри контейнера api) даёт ошибку целостности и закрытую кнопку записи;
- восстановление с перезаписью: id бэкапа и переключатель, 503 `maintenance` на обычных ручках, api перезапускается сам, вход работает, назначение на месте.

```bash
make server-stack-build server-stack-up
make e2e-install
eval "$(scripts/dev/server-stack/stack.sh env)" && cd e2e && pnpm exec playwright test --project=backups
```

Сценарий меняет данные стенда (восстановление заменяет базу), поэтому запускайте его на стенде, который не жалко. В CI это шаг `Run backups e2e` джоба `server-stack-smoke`.

## Очистка места на стенде deploy/server

`tests/storage-cleanup.spec.ts` (проект Playwright `storage-cleanup`, срез E1 из `docs/design/storage-cleanup.md`) идёт на стенде deploy/server с оверлеем личного раннера. В CI это последний шаг джоба `server-stack-smoke`, на свежем стенде администратора создаёт сам. Раннеры собраны из текущего кода и согласуют `control` и `disk`. Сценарии по порядку:

- общий раннер: после сборки админ открывает «Диск» из меню строки, «Обновить» даёт новый замер с категориями («Сама программа», кэш файлов и рабочие копии раннера); висячие образы (тест делает один, загружая крошечный образ `docker import` дважды под одним тегом) и кэш раннера чистятся с подтверждением, итог «Освобождено», висячий образ пропал с хоста, раннер сам присылает новый замер, в журнале аудита `runner.disk_cleanup` и `runner.disk_cleaned` с id команды;
- «Хранилище», «Освободить место»: задача сборки состарена на 60 дней (`applied_at`), предпросмотр её считает, прогон удаляет, итог «Готово: удалена …», аудит `lifecycle.sweep` и `lifecycle.swept`;
- личный раннер Анны: две «старые версии» Студии (`hse-doc-studio:0.0.1-e2e` и `0.0.2-e2e`, крошечные образы) дают список и откат; владелец в «Мои раннеры» видит флажок отката, админ на чужом личном раннере видит плашку владельца, но не флажок, а откат через API получает 403;
- очистка, которую раннер не забрал (контейнер раннера заморожен `docker pause`, долгий опрос команд истёк), отменяется админом: уведомления владельцу нет;
- SIGTERM посреди очистки (рабочие копии-болванки на сотни тысяч файлов удаляются секунды): команда закрыта `cancelled`, а не `lost`, раннер ушёл `/offline` после итога, Анне приходит уведомление «…остановили».

Кэш сборки Docker, старые версии и неиспользуемые образы сценарий не чистит, чтобы не задеть соседние стенды. Висячие образы Docker удаляет все, не только тестовый (`docker image prune`): на машине разработчика это заденет и чужие висячие образы. Свои теги сценарий убирает в конце. Число болванок задают `E2E_SLOW_DIRS` и `E2E_SLOW_FILES` (по умолчанию 8 по 40 000).

```bash
export STACK_PROJECT=hse-doc-studio-sc STACK_PORT=19861 TAG=pr-sc
scripts/dev/server-stack/stack.sh build && scripts/dev/server-stack/stack.sh up
cd e2e && eval "$(../scripts/dev/server-stack/stack.sh env)" && pnpm exec playwright test --project=storage-cleanup
../scripts/dev/server-stack/stack.sh down
```

Сборке нужен образ TeX Live на docker-хосте, иначе задача кончается `image_missing` раньше, чем появится рабочая копия. Скриншоты: `screenshots/{ru,en}/sc-*.png`.

## Журнал писем на стенде deploy/server

`tests/mail-log.spec.ts` (проект Playwright `mail-log`, срез E1 из `docs/design/mail-log.md`) идёт на стенде deploy/server с поддельным SMTP: оверлей `compose.mail.yml`, сервис `fake-smtp` из `fake_smtp/server.py` (только стандартная библиотека). Заглушка принимает письма api на `fake-smtp:2525` без TLS, отвечает `550` на `reject-*@`, `451` на `busy-*@`, по флагу (`POST /config {"auth_fail": true}`) отказывает во входе `535`, а пойманные письма отдаёт по HTTP (`GET /messages?to=`, адрес в `E2E_MAIL_URL` из `stack.sh env`). В CI это шаг `Run mail log e2e` джоба `server-stack-smoke` перед очисткой места; на свежем стенде администратора создаёт сам. Сценарии по порядку:

- почта не настроена: приглашение в Студию из «Пользователей» даёт ссылку на экране и строку «Приглашение в Студию», «Не отправлялось, почта не настроена», вызвал админ; плашка «Почта не настроена»;
- админ настраивает в «Почта (SMTP)» заглушку с логином: при отказе входа тестовое письмо «Не ушло» с `535`, логин в журнале скрыт, под полосой подсказка про логин и пароль; без отказа письмо «Отправлено», Message-ID строки равен пойманному;
- «Забыли пароль» уходит фоном: строка «Запрос без входа», `forgot_password`; токена из пойманной ссылки нет ни в ответе карточки, ни в превью (`srcdoc`) и текстовой части, вместо него «[ссылка скрыта]»;
- приглашение в проект на `reject-x@example.org`: ссылка приглашающему, строка `project_invitation_link`, «Не ушло», `recipient_refused`, `550`, `project_invite`; счётчик в меню и «Не ушло» в полосе равны сводке, клик по «Не ушло» фильтрует журнал;
- маршрут подписания (сборка документов на общем раннере): `signing_request` научруку с автором в «Вызвал», проектом, маршрутом и страницей `/sign/...` в письме и в превью; название проекта в карточке ставит фильтр по проекту;
- запрос доступа к проекту человека, чью почту не подтверждало приглашение без адреса: «Не отправлялось, почта не подтверждена»;
- ссылка сброса, выданная админом: `reset_notice`, `admin_reset_link`, ссылки с экрана нет ни в письме, ни в журнале;
- не админу журнал отвечает 404, анониму 401, админка не открывается.

Люди, проекты и адреса с меткой прогона, числа сверяются со сводкой, поэтому сценарий повторяется на том же стенде. В начале и в конце почта выключается (`host: ""`), как её ждут остальные сценарии стенда. Админ входит один раз: вход ограничен 30 в минуту с адреса.

```bash
export STACK_PROJECT=hse-doc-studio-ml STACK_PORT=19871 TAG=pr-ml
scripts/dev/server-stack/stack.sh build && scripts/dev/server-stack/stack.sh up && scripts/dev/server-stack/stack.sh mail-up
cd e2e && eval "$(../scripts/dev/server-stack/stack.sh env)" && pnpm exec playwright test --project=mail-log
../scripts/dev/server-stack/stack.sh down
```

Скриншоты: `screenshots/ru/ml-*.png`.

`tests/acknowledge.spec.ts` (проект Playwright `acknowledge`) в CI идёт после полного смоука на том же стенде, до бэкапов (пока назначения бэкапов нет, проверка «Бэкапы» даёт предупреждение); на свежем стенде администратора создаёт сам. На ru и en:
