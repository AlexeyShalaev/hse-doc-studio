# Приёмочные e2e на стенде server-lite

Playwright проходит сценарии M1 по настоящему стенду (образ приложения в режиме server и Postgres в compose), а не по демо-миру фронта. Что проверяется, на ru и en:

- аноним попадает на экран входа, неверный пароль отклоняется;
- после входа видны только свои проекты (три демо-пользователя из seed);
- проект создаётся мастером (11 шагов) и остаётся в списке после перезагрузки;
- второй пользователь не видит чужой проект ни в списке, ни по прямой ссылке, ни через API;
- выход закрывает сессию.

Язык интерфейса задаёт локаль браузера, поэтому каждый сценарий идёт дважды. Скриншоты каждого шага лежат в `screenshots/ru` и `screenshots/en`, в CI это артефакт `e2e-screenshots`.

## Запуск

Из корня репозитория:

```bash
make server-lite-up server-lite-seed   # стенд и демо-данные
make e2e-install                       # один раз: зависимости и Chromium
make e2e-m1                            # сценарии
```

Вместо загрузки Chromium можно взять установленный Chrome: `make e2e-m1 E2E_CHANNEL=chrome`.

Против любого другого стенда: `E2E_BASE_URL=http://localhost:8100 E2E_SEED_PASSWORD=... pnpm test` из этого каталога. Пароль это `SERVER_LITE_SEED_PASSWORD` из `scripts/dev/server-lite/.env`.

Сценарии создают проекты `E2E проект ru` и `E2E проект en`: на чистом стенде они единственные новые, при повторном прогоне появляются дубли названий, список от этого не ломается. Чистый стенд: `make server-lite-reset`, затем up и seed.

## Полный смоук на стенде deploy/server

`tests/full.spec.ts` (проект Playwright `full`) идёт по полному серверному набору: api, раннер, Postgres и MinIO. Сценарии по порядку на одной базе:

- мастер первого запуска (язык, администратор по токену из журнала api, регистрация, входы, окружение, готово) создаёт администратора и открывает регистрацию, после завершения его ручки закрыты;
- регистрация без SMTP по приглашению админа: ссылка подтверждения в ответ не попадает, почту подтверждает приглашение, вход;
- изоляция: чужой проект не виден в списке, по ссылке и через API, `/api/admin` не-админу отвечает 404;
- сборка через раннер, PDF отдаётся владельцу временной ссылкой на хранилище, чужому 404;
- квота один запуск на пользователя и справедливая очередь: 15 сборок одного пользователя не задерживают сборку другого (раннер на паузе новые сборки не принимает, поэтому очередь копится квотой);
- раннер убит посреди сборки, сборка заканчивается после его возвращения;
- рестарт api посреди сборки: сессия жива, запись доведена до конца;
- админка, раннеры, на ru и en;
- люди в админке: приглашение со ссылкой (её открывает гость без сессии) и журнал аудита, на ru и en.

```bash
make server-stack-build server-stack-up   # образ с extra server и стенд на 127.0.0.1:17251
make e2e-install                          # один раз
make e2e-full                             # сценарии, скриншоты в screenshots/{ru,en}/full-*.png
make server-stack-down                    # стереть стенд
```

Сборка тянет образ TeX Live (несколько гигабайт) при первом прогоне. В CI то же делает джоб `server-stack-smoke` в deploy-smoke. Раннер запускает TeX в соседнем контейнере `texlive/texlive:TL2024-historic`: образ должен быть на docker-хосте заранее, иначе сборка заканчивается `image_missing`. Порт и тег образа задают `STACK_PORT` и `TAG`.

## Личные раннеры на том же стенде

`tests/personal.spec.ts` (проект Playwright `personal`) идёт после полного смоука на том же стенде: к нему добавлен оверлей `deploy/server/compose.personal.yml` с личным раннером Анны (`runner-personal`, профиль `personal`) и поддельной OpenAI-совместимой моделью (`fake-openai`, сеть `personal-net`, api её не видит). Сценарии по порядку:

- Анна создаёт токен в «Мои раннеры», тест поднимает её раннер (`stack.sh personal-up TOKEN`), строка раннера «В сети»;
- сборка Анны идёт на её раннере (`placement.state = personal`, в очереди админа `runner_scope = personal`) и проходит при квоте в одну сборку и общем раннере на паузе;
- сборка соавтора Бориса идёт на общем, пока Анна не выберет «На моих раннерах», затем на раннере владельца; своих раннеров у Бориса нет, раннер Анны по id ему 404;
- мягкая остановка (`stack.sh personal-stop`): сборка сразу на общем с пометкой «не в сети»; убийство без ухода (`stack.sh personal-kill`): окно ожидания, затем общий с пометкой «не взял за 5 с»;
- ИИ через раннер: провайдер «через мой раннер» загружает модели поддельного сервера, Борис его не видит и не может создать такой же; api до модели напрямую не достаёт;
- админ видит личный раннер с владельцем и выключает личные раннеры (раннер «Выключен», сборка на общем с пометкой), затем включает;
- Анна отзывает раннер: процесс раннера завершается, сборки идут на общих.

```bash
make server-stack-build server-stack-up
make e2e-full                                   # сначала полный смоук: он создаёт администратора
cd e2e && pnpm exec playwright test --project personal   # скриншоты screenshots/{ru,en}/full-personal-*.png
```

## Личные раннеры: самостоятельный прогон

`tests/personal-runners.spec.ts` (проект Playwright `personal-runners`) не зависит от полного смоука: на свежем стенде сам создаёт администратора через мастер, людей заводит с меткой прогона, поэтому его можно гонять повторно. Почти всё проходит через интерфейс:

- Анна подключает раннер из «Мои раннеры» (токен в диалоге), тест поднимает его вторым контейнером раннера (`stack.sh personal-reset`, `personal-up TOKEN`), строка «В сети»;
- сборка Анны на её раннере (чип `build-placement` во вкладке сборки), при квоте одна сборка и общем раннере на паузе; две сборки разом: вторая сразу на общем с пометкой «занят» и берётся, пока первая ещё идёт (личная не в счёте квоты);
- Борис (соавтор из общей организации): по умолчанию на общем, после «На моих раннерах» в настройках проекта на раннере Анны, после «На общих» снова на общем; раннер Анны ему 404;
- провайдер «Через мой раннер» создаётся в настройках, модели приходят через раннер, ответ чата идёт потоком событий; Борис провайдера не видит, своего на раннер Анны не заведёт, чужим провайдером в чате не воспользуется, поддельная модель его запроса не получает; api до модели напрямую не достаёт;
- админ выключает личные раннеры в `/admin/instance` (раннер «Выключен», сборка на общем с пометкой, провайдер «выключено админом») и включает обратно;
- мягкая остановка: сборка сразу на общем; убийство без ухода: общий берёт сборку через окно ожидания (5 с) плюс не больше 1,5 с;
- админ видит раннер в `/admin/runners` с владельцем и отзывает его через меню и подтверждение по имени: процесс раннера завершается.

Второй стенд рядом с первым задают `STACK_PROJECT` и `STACK_PORT` (свои `.env`, каталоги раннеров и тома):

```bash
export STACK_PROJECT=hse-doc-studio-pr-e2e STACK_PORT=19805 TAG=pr-personal
scripts/dev/server-stack/stack.sh build && scripts/dev/server-stack/stack.sh up
cd e2e && eval "$(../scripts/dev/server-stack/stack.sh env)" && pnpm exec playwright test --project personal-runners
../scripts/dev/server-stack/stack.sh down
```

Очередь на настоящем Postgres дополнительно проверяет soak `services/api/tests/integration/e2e/test_queue_soak_pg.py`: 200 задач, случайные сбои раннеров, ни дублей закрытия, ни потерянных задач.
