# Бэкап, обновление, потеря ключа

## Что копировать

| Что | Как |
|---|---|
| база | `docker compose exec postgres pg_dump -U studio studio > studio.sql` |
| исходники проектов | том `api-data` (`projects_root`) |
| блобы, входы и выходы задач | бакет S3 или том `minio-data` |
| ONLYOFFICE | том `onlyoffice-data`, если сервис включён |
| ключ `SECRETS_KEY` | **отдельно** от дампов, в менеджере секретов |

База и том проектов должны копироваться согласованно: сначала остановите запись или снимите снимок обоих. Периодически проверяйте восстановление на пустой машине.

## Обновление

compose: смените `TAG`, затем `docker compose pull && docker compose up -d`. Миграции базы выполняет api на старте под advisory-блокировкой.

Helm: `helm upgrade`; Job миграций запускается перед обновлением. Задавайте `secrets.existingSecret`, чтобы Job видел актуальные секреты.

Перед обновлением снимите бэкап. Раннеры обновляйте вместе с api: несовместимая версия отклоняется при регистрации. Проверка схемы: `hse-doc-studio db current` и `hse-doc-studio db check`.

Одновременно работает одна реплика api; обновление кратко прерывает доступ.

## Совместимость версий и откат

Миграции пишутся по схеме expand/contract: выпуск N только добавляет (таблицы, колонки с значением по умолчанию, индексы), а удаление и ужесточение откладывается на выпуск N+1. Поэтому образ N-1 продолжает работать на базе, уже обновлённой до N. Это проверяют тесты: миграция N-1 к N на заполненной базе и запрет разрушающих шагов в `upgrade()`.

- **Раннер и api.** При регистрации раннер называет версию протокола; несовпадение отклоняется кодом `runner_protocol_unsupported`. Обновляйте api первым, затем раннеры того же выпуска.
- **Откат образа.** Верните прежний `TAG` (или `helm rollback`). Схему назад не откатывайте: образ N-1 работает с базой N. Если выпуск менял данные необратимо, восстановите бэкап, снятый перед обновлением (см. ниже).
- **База новее образа.** Если старый образ видит неизвестную ему ревизию, он отказывается стартовать с ошибкой `db_ahead`. Это защита: поднимите образ того же или более нового выпуска.
- **База старше образа.** Бэкап прошлого выпуска, поднятый новым образом, догоняется миграциями на старте.

## Восстановление из бэкапа

Три хранилища (база, том проектов, S3) должны быть с одного момента времени. Порядок:

1. Остановите api и раннеры: `docker compose stop api runner`.
2. Верните ключ `SECRETS_KEY` из менеджера секретов. Без него секреты в базе нечитаемы (см. ниже).
3. Восстановите базу в пустую: `docker compose exec -T postgres psql -U studio studio < studio.sql`.
4. Восстановите том `api-data` и бакет S3 (или том `minio-data`) из снимков того же момента.
5. Запустите api образом того же или более нового выпуска, чем бэкап. Миграции выполнятся на старте.
6. Раннеры запускайте после api.

Проверка после восстановления:

- `hse-doc-studio db current` и `hse-doc-studio db check` показывают head без дрейфа;
- `GET /health/ready` с `HEALTH_TOKEN` зелёный по всем проверкам;
- войдите администратором, откройте проект, соберите PDF: сборка читает блобы из S3 и подтверждает их хеши;
- если база новее бакета (блобы из реестра отсутствуют в S3), сборка с недостающим файлом завершится ошибкой манифеста. Лишние блобы в бакете безвредны: их уберёт очистка.

Если база новее тома проектов, откройте затронутые проекты и пересохраните файлы из рабочей копии пользователей; если тома новее базы, новые проекты в базе отсутствуют и их нужно импортировать заново.

## Потеря ключа

`SECRETS_KEY` (Fernet) шифрует секреты в базе: токены git, пароль SMTP, секреты OIDC, ключи провайдеров ИИ и подпись. Ключ нигде не хранится рядом с базой, чтобы украденный дамп не раскрывал секреты.

**Если ключ потерян, секреты восстановить нельзя.** Что происходит:

- пользователи, проекты, права, сборки и сами документы **не страдают**: они не зашифрованы этим ключом;
- сохранённые секреты нечитаемы: SMTP, OIDC, токены git, ключи ИИ.

Как восстановиться:

1. Сгенерируйте новый ключ и задайте его в `SECRETS_KEY`.
2. Заново введите пароль SMTP и секреты OIDC в админке.
3. Пользователям нужно заново ввести токены git и ключи ИИ в настройках.
4. Храните копию нового ключа вне бэкапа базы.

## Смена ключа

Если ключ нужно заменить, а старый известен:

1. Задайте новый ключ как первичный, а прежний передайте в `HSE_STUDIO__SECRETS__RETIRED_KEYS`.
2. Проверьте объём: `hse-doc-studio secrets reencrypt --dry-run`.
3. Выполните `hse-doc-studio secrets reencrypt`. Команда выводит число перешифрованных записей и нечитаемых. При сообщении «изменилась во время работы» запустите её ещё раз.
4. Когда нечитаемых нет, уберите прежний ключ из `RETIRED_KEYS`.

## Перенос из локальной Студии

Оператор переносит данные человека командами на сервере (нужен extra server и миграции до head). Запись принадлежит пользователю по e-mail, как если бы он перенёс её сам.

- `hse-doc-studio server import --data-dir <каталог локальной Студии> --user <почта> [--dry-run] [--include-instance]` переносит пользовательские настройки и ИИ-провайдеров (ключи шифруются серверным ключом). Уже существующее на сервере не затирается, повторный запуск ничего не дублирует. Токены git, ключи подписи и роли агента не переносятся: команда перечисляет их в отчёте, добавьте их на сервере заново.
- `hse-doc-studio server import-project <папка или zip> --user <почта> [--dry-run]` создаёт проект с историей версий и чатами агента. Занятый id заменяется новым, архив с путём наружу, симлинком, шифрованием или превышением размера отвергается целиком.

Сам человек может загрузить zip папки проекта (вместе со скрытой `.hse-studio`) на главной: «Импорт из zip». Размер ограничен `HSE_STUDIO__SERVER__PROJECT_IMPORT_MAX_BYTES` и пределом проекта.

## Если что-то пошло не так

- старт без БД перечисляет, чего не хватает; смотрите журнал api;
- `GET /health/ready` с `HEALTH_TOKEN` показывает, какая проверка красная;
- раннер не берёт задачи: проверьте раздел раннеров в админке, паузу, версию и доступ к `API_URL`; за прокси убедитесь в таймауте не меньше 60 секунд.
