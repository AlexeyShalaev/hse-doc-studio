# Раннеры

<p class="hds-lede">Раннер выполняет задачи сборки, упаковки сдачи, проверки подписей и конвертации офисных файлов. Он сам опрашивает api по HTTPS: входящих соединений к раннеру не нужно.</p>

## Как работает задача

1. api кладёт задачу в очередь Postgres: справедливо по пользователям, одинаковые ожидающие задачи вытесняют друг друга.
2. Раннер забирает задачу долгим опросом и получает аренду на 45 секунд; пока он жив, он продлевает её каждые 10 секунд. Умерший раннер теряет задачу, она возвращается в очередь до двух повторов.
3. Входом служит манифест файлов и блобы по sha256. Раннер скачивает недостающее в свой кэш и проверяет хеши.
4. Результат раннер отправляет api, тот проверяет и применяет его. Раннер не пишет в базу и том проектов напрямую.

## Подключение раннера

1. В админке откройте «Раннеры» и выпустите **токен регистрации**: подпись, срок (по умолчанию 24 часа) и число использований.
2. На машине раннера задайте окружение:

   | Переменная | Значение |
   |---|---|
   | `HSE_RUNNER__API_URL` | адрес Студии, `https://studio.example.org` |
   | `HSE_RUNNER__TOKEN` | токен регистрации |
   | `HSE_RUNNER__NAME` | имя в списке (по умолчанию имя хоста) |
   | `HSE_RUNNER__CONCURRENCY` | сколько задач одновременно |
   | `HSE_RUNNER__DATA_DIR` | рабочие папки и кэш блобов |
   | `HSE_RUNNER__OFFICE_URL` | адрес Gotenberg; без него офисные задачи не берутся (в кластере: [встроенный Gotenberg чарта](#office-gotenberg)) |

3. Запустите `hse-doc-studio runner` (в образе это та же команда).
4. Раннер меняет токен регистрации на собственный и сохраняет его в `data_dir/identity.json`. После этого `HSE_RUNNER__TOKEN` можно убрать из окружения.

В compose первый раннер регистрируется токеном `RUNNER_BOOTSTRAP_TOKEN`.

## Установка одной командой

После создания токена (и после «Выпустить новый токен» у раннера) окно показывает секрет один раз и готовые команды в трёх вкладках. Адрес Студии берётся из `public_url` инстанса, а без него из адреса, по которому админ открыл страницу.

| Вкладка | Что делает |
|---|---|
| Docker | одна строка `docker run -d --restart unless-stopped …` с образом той же версии, что у Студии, адресом и токеном |
| Скрипт (служба) | `curl -fsSL <адрес>/api/runner/v1/install.sh \| sudo env … sh -s -- install`: ставит раннер службой systemd на Linux или launchd на macOS |
| Переменные | строка с переменными окружения для машины, где уже есть команда `hse-doc-studio` |

Кнопка «Скопировать» стоит у каждой команды. Для скрипта выбирается система: на Linux команда идёт через `sudo`, на macOS ставится пользовательская служба без `sudo`.

Скрипт устроен так, чтобы его можно было проверить до запуска:

- он одинаков для всех и не содержит секретов: токен и адрес Студии приходят окружением команды. Прочитать его можно по ссылке «Показать скрипт, который выполнится» или командой `curl -fsSL <адрес>/api/runner/v1/install.sh -o install.sh`;
- `sh install.sh plan` (или `HSE_RUNNER_DRY_RUN=1`) печатает все действия и ничего не меняет, токен в плане маскируется;
- `install` перед работой печатает план: образ, адрес Студии, каталог данных, путь службы и файла окружения; токен лежит в файле окружения с правами 0600, а не в описании службы;
- повторный запуск идемпотентен: файлы перезаписываются теми же значениями, служба перезапускается, сохранённая личность раннера в каталоге данных не трогается;
- `sh install.sh uninstall` останавливает и убирает службу и файл окружения; с `--purge` ещё образ и каталог данных. Раннер в списке админки после этого нужно отозвать.

Раннер на хосте работает контейнером, поэтому скрипту нужен Docker. Если его нет, скрипт останавливается с понятным текстом и ссылкой на установку. Имя службы (`HSE_RUNNER_SERVICE`), образ (`HSE_RUNNER_IMAGE`) и каталог данных (`HSE_RUNNER_DATA_DIR`) можно переопределить окружением; по ним на одной машине ставятся несколько раннеров.
## Установка из админки на этой же машине

Кнопка «Установить раннер» на странице «Раннеры» ставит раннер там, где работает сама Студия. Способ показывается, только если он технически возможен; иначе вместо кнопки стоит причина.

| Способ | Когда доступен | Что делает Студия |
|---|---|---|
| Docker рядом | Студия видит `docker.sock` и Docker отвечает (тот же доступ, что у страницы «Диск») | запускает контейнер `hse-runner-<имя>` из образа своей версии с `--restart unless-stopped`; токен передаёт файлом окружения с правами 0600, который удаляет сразу после запуска |
| Deployment в кластере | Студия работает в Kubernetes, в чарте включено `runner.installFromUi.enabled`, ServiceAccount Студии может создавать ресурсы | создаёт Secret с токеном, том данных и Deployment с исполнителем `kubernetes` под отдельным ServiceAccount |

Ход виден по шагам (токен, образ, запуск, подключение к Студии), у каждой ошибки есть понятная причина и кнопка «Повторить». Токен регистрации создаётся одноразовым на час и при неудаче сразу отзывается; в журнал аудита пишутся начало, итог и удаление без секретов.

Поставленными отсюда раннерами управляют на самой странице «Раннеры». В меню «Действия» строки такого раннера есть «Обновить» и «Удалить установку»; раннер узнаётся по имени пода из его отчёта, иначе по имени Deployment или контейнера. Установки, чьего раннера в таблице нет (отозван, ещё не подключился или не может подключиться, например Deployment падает в CrashLoop), собраны в блоке «Установки без раннера» под таблицей, оттуда их можно удалить. Удаление установки сразу отзывает её раннер тем же действием, что «Отозвать раннер» (задачи, которые он выполнял, передаются другому раннеру, его токен перестаёт работать), отзывает токен регистрации установки, если он ещё действует, и убирает Secret, том и Deployment (у Docker только контейнер, каталог данных на хосте остаётся). Отдельно отзывать раннер не нужно; установку без раннера Студия просто удаляет.

Порядок выбран так, чтобы сбой на середине ничего не ломал. Сначала отзываются токен регистрации и раннер, потом удаляется установка: иначе под Deployment, который после удаления ещё до 10 минут доделывает сборки, успел бы взять новые задачи без установки. Если отзыв не удался, установка не тронута и удаление можно повторить. Если не удалось удалить на хосте (ответ 502 `remove_failed`), раннер уже отозван, а установка осталась в блоке «Установки без раннера»; Deployment удаляется последним, поэтому она видна, пока не удалена до конца, и повторное удаление доделывает остальное. Пока установку обновляют, удалить её нельзя (409 `install_busy`). В журнал аудита пишется `runner_install.local.remove` с id отозванного раннера (`revoked_runner`) и отозванных токенов регистрации, при сбое на хосте `runner_install.local.remove_failed`; сам отзыв раннера, как обычно, `runner.revoke`.

### Обновление раннера из админки { #runner-upgrade }

«Обновить» ставит раннеру образ текущей версии Студии на месте, без удаления и повторной установки. Имя, Secret с токеном, том данных и запись раннера в Студии сохраняются, новый токен не выпускается. Если раннер старше Студии, в его строке есть акцентная кнопка «Обновить до vX», такая же есть в окне «Как развёрнут» рядом с пометкой «Старше Студии». Раннеру на версии Студии обновление тоже доступно (в меню): оно заново применяет настройки по нынешним правилам и перезапускает его.

- **Kubernetes.** Студия читает живой Deployment, берёт из него адрес Студии, каталог данных, число слотов и лимиты, с которыми раннер ставили (аннотация `hse-doc-studio/runner-resources`; у установок до неё лимиты, отличные от нынешних умолчаний, читаются из самого манифеста), и заменяет Deployment целиком манифестом по нынешним правилам: образ, лимиты, securityContext, ServiceAccount, адрес Gotenberg Студии (`HSE_STUDIO__RUNNER_INSTALL__OFFICE_URL`). Лимит, который вышел за нынешние границы Helm, уступает умолчанию (это видно в шаге «Манифест»). Стратегия `Recreate`: старый под уходит раньше, чем новый смонтирует том `ReadWriteOnce`. Шаги: образ и текущие настройки, манифест, перезапуск пода (Студия ждёт выкатку до 15 минут), раннер снова на связи.
- **Docker.** Студия тянет новый образ заранее, затем останавливает контейнер (`docker stop`, до 60 секунд), удаляет его и запускает заново с тем же именем, окружением раннера (токен, адрес, каталог данных) и томом. Если новый контейнер не стартовал, Студия возвращает прежний (см. «Откат» ниже).

Последний шаг ждёт до трёх минут, пока раннер выйдет на связь с версией Студии. Сборки, которые раннер выполнял в момент перезапуска, он доделывает до 30 секунд, остальные прерываются с ошибкой «Раннер остановили во время сборки» и собираются заново; задачи из очереди ждут другой раннер или этот после перезапуска. Обновление и установка одним способом не идут одновременно (409 `install_busy`). В журнал аудита пишутся `runner_install.local.upgrade`, `upgrade_succeeded` и `upgrade_failed` с именем раннера, версией до и после и образами.

**Откат.** Если установку уже заменили, а обновление не удалось (выкатка застряла с `ProgressDeadlineExceeded`, под не стал готов за 15 минут, новый контейнер не стартовал или раннер не вышел на связь с новой версией), Студия сама возвращает прежнюю версию отдельным шагом «Откат на прежнюю версию». В Kubernetes перед заменой запоминается прежний Deployment целиком (метки, аннотации и spec: образ, env, ресурсы, шаблон пода), при неудаче он ставится назад тем же PUT с актуальным `resourceVersion` (конфликт версий повторяется), и Студия ждёт выкатку прежней версии. В Docker прежний контейнер пересоздаётся с прежним образом и тем же окружением раннера. Затем Студия, как в шаге «Раннер снова на связи», до трёх минут ждёт, что раннер выйдет на связь с прежней версией. Итог говорит, что раннер возвращён на vX, что он возвращён, но не вышел на связь (тогда шаг отката помечен ошибкой: проверьте под или контейнер), или что откат тоже не удался, с причиной.

Потерянный ответ не принимается за отказ. Каждая замена Deployment несёт свою метку `hse-doc-studio/replace-id`; если ответ на PUT потерян (обрыв связи или 5xx), Студия перечитывает Deployment: метка на месте, значит замена применилась и дальше всё как после успешного PUT (ожидание выкатки, при неудаче откат); метки нет, значит не применилась, и откатывать нечего. Если перечитать не удалось, Студия на всякий случай откатывает: вернуть прежний Deployment безопасно и тогда, когда он не менялся. В Docker после ошибки `docker rm` или `docker run` Студия смотрит `docker inspect`: если контейнер уже работает с нужным образом, шаг считается выполненным. Если сбой случился до замены (образ не скачался, нет прав `update`), откатывать нечего и шага нет. В `upgrade_failed` есть признак `rolled_back`, при неудачном откате `rollback_error`, а если раннер есть в Студии, ещё `rollback_reconnected`. Пока идёт откат, задача держит ту же блокировку, что установка и обновление.

Причины, по которым способ скрыт:

- Docker: нет `docker.sock`, Docker не отвечает, способ отключён `HSE_STUDIO__RUNNER_INSTALL__DOCKER_ENABLED=false`. В наборе `deploy/server` у api доступа к Docker нет намеренно (сокет равен root на хосте), поэтому там вместо кнопки пояснение: используйте установку по SSH или команду у токена.
- Kubernetes: Студия не в кластере, значение чарта не включено или у её ServiceAccount нет прав.

### Kubernetes: что включает чарт

`runner.installFromUi.enabled` по умолчанию `false`, и на проде, где общие раннеры включены не были, так и остаётся. Включение добавляет:

- ServiceAccount и Role для самих раннеров `<релиз>-runner-ui`: только поды сборки (`pods` create, get, list, delete; `pods/log` get; `pods/exec` create, get) в namespace подов сборки (`runner.installFromUi.buildNamespace`, по умолчанию namespace релиза), как у встроенного раннера;
- ServiceAccount `<релиз>-api` и Role для Студии: Deployment (create, list, update, delete; `update` нужен обновлению на месте), Secret (только create и delete, без чтения) и PersistentVolumeClaim (create, delete) в namespace релиза. Role и RoleBinding Студия создавать не может, поэтому выдать себе или раннеру лишнее не способна; ClusterRole нет.

Раннер из админки живёт в namespace релиза, тома данных он получает свои (`runner.installFromUi.storageSize`, `storageClassName`), чтобы выданный раннеру токен переживал перезапуск пода. Адрес Студии для такого раннера внутренний (Service чарта).

#### Свой namespace подов сборки { #build-namespace }

По умолчанию раннеры из админки создают поды сборки в namespace релиза, рядом с api. Квоту туда чарт не ставит (она ограничила бы и саму Студию), поэтому для общих раннеров поды сборки лучше вынести в отдельный namespace:

```yaml
runner:
  installFromUi:
    enabled: true
    buildNamespace: hds-builds   # тот же, что runner.kubernetes.namespace, если он задан
  kubernetes:
    quota: {enabled: true}
    limitRange: {enabled: true}
```

- Сам раннер (Deployment, Secret с токеном, том данных) остаётся в namespace релиза. Поды сборки он создаёт в `buildNamespace`: Студия передаёт его раннеру в `HSE_RUNNER__K8S__NAMESPACE` при установке и при «Обновить».
- Role и RoleBinding `<релиз>-runner-ui-builds` переезжают в `buildNamespace`; в namespace релиза у раннеров из админки прав больше нет. Права Студии не меняются.
- В `buildNamespace` ставятся запрет сети подов сборки (`runner.kubernetes.networkPolicy`), ResourceQuota и LimitRange (`runner.kubernetes.quota`, `limitRange`). Значения общие с раннером чарта: если namespace у обоих один, объект в нём один и потолок общий, если разные, у каждого namespace своя квота с этими значениями.
- Namespace чарт не создаёт, как и `runner.kubernetes.namespace`: такой namespace общий для раннеров чарта и раннеров из админки и не должен пропасть вместе с подами сборки при `helm uninstall`. Создайте его заранее с меткой restricted:

```sh
kubectl create namespace hds-builds
kubectl label namespace hds-builds \
  pod-security.kubernetes.io/enforce=restricted pod-security.kubernetes.io/enforce-version=latest
```

Порядок переключения работающей установки: дождитесь, пока у раннеров из админки нет сборок, выполните `helm upgrade` с `buildNamespace`, затем нажмите «Обновить» у каждого такого раннера. До обновления раннер создаёт поды сборки в namespace релиза, где прав у него уже нет, и сборки на нём падают с `build_backend_unavailable` (403 Kubernetes в деталях).

### Офисные задачи в кластере (Gotenberg) { #office-gotenberg }

Задачи с тегом `office` (презентации pptx, документы docx, odt, xlsx в PDF) раннер отправляет в постоянный Gotenberg по адресу `HSE_RUNNER__OFFICE_URL`; без адреса раннер этот тег не объявляет, и такие задачи ждут раннер, у которого он есть (например, личный). Чарт может поставить Gotenberg сам:

```yaml
services:
  officeConvert:
    enabled: true
```

- В namespace релиза появляются Deployment и Service `<релиз>-office-convert` (порт 3000) с образом `gotenberg/gotenberg:8.39.0-libreoffice` (вариант только с LibreOffice, без Chromium). Ресурсы по умолчанию: requests 250m CPU и 512Mi, limits 2 CPU и 2Gi, эфемерный диск 256Mi/2Gi; число реплик `services.officeConvert.replicas`, предел одной конвертации `timeout` (180s).
- Под проходит Pod Security restricted: uid 1001 образа, `runAsNonRoot`, `drop: [ALL]`, seccomp `RuntimeDefault`, без повышения привилегий и с корнем только для чтения. Gotenberg и LibreOffice пишут только во временный каталог (загруженный файл, профиль LibreOffice, результат) и в домашний (кэш fontconfig), поэтому `/tmp` и `/home/gotenberg` смонтированы как emptyDir (`tmpSizeLimit`, 1Gi). Пробы идут на `/health`. Webhook и загрузка файлов по ссылке в Gotenberg выключены.
- NetworkPolicy `<релиз>-office-convert`: вход только от подов раннеров релиза (раннер чарта и раннеры из админки) на порт 3000, выход закрыт целиком. Отключается `services.officeConvert.networkPolicy.enabled: false`. Сам api в кластере офисные файлы не конвертирует, ему доступ не нужен.
- Адрес получают раннер чарта (`HSE_RUNNER__OFFICE_URL`, если `runner.officeUrl` пуст) и раннеры из админки: чарт пишет его Студии в `HSE_STUDIO__RUNNER_INSTALL__OFFICE_URL`, Студия передаёт раннеру при установке и при «Обновить». Уже поставленные раннеры получают тег `office` после «Обновить». Заданный `runner.officeUrl` (внешний Gotenberg) перекрывает встроенный для обоих видов раннеров.
- Исходящая политика раннеров (`runner.networkPolicy.enabled`) сама разрешает встроенный Gotenberg; внешний адрес из `runner.officeUrl` добавьте в `extraEgress`.
- Установка Docker рядом (не Kubernetes) берёт тот же `HSE_STUDIO__RUNNER_INSTALL__OFFICE_URL`, если он задан Студии: адрес должен быть доступен из контейнера раннера. Без него при «Обновить» у контейнера остаётся прежний адрес.

Где раннер берёт офисные задачи и куда ходит, видно в админке: в окне «Изоляция раннеров» строка «Офисные задачи (Gotenberg)» у раннера чарта и у установки из админки, правило «Gotenberg Студии» в исходящей сети и отдельный блок с образом, ресурсами и сетью Gotenberg.

## Установка по SSH на другую машину

«Установить раннер» → «По SSH» ставит раннер на машину с Linux (macOS при залогиненном пользователе, без гарантий). Студия сама заходит по SSH, так что машина должна быть доступна с сервера Студии.

1. **Форма.** Адрес и порт, логин, способ входа (пароль либо приватный ключ с необязательной passphrase), нужен ли `sudo`, имя раннера.
2. **Защита адреса.** Прежде чем куда-то подключаться, Студия разрешает имя и проверяет каждый адрес. Закрыты loopback, частные сети (в том числе адреса подов и сервисов кластера), link-local и адреса метаданных облака. Внутренний хост открывается только явной записью в `HSE_STUDIO__RUNNER_INSTALL__SSH_ALLOWLIST` (или в общем `HSE_STUDIO__EGRESS__ALLOWLIST`): имя, `*.corp.example`, IP или CIDR. Адреса метаданных облака и link-local закрыты всегда, даже если их вписать. Подключение идёт по проверенному IP, а не по имени повторно, поэтому подмена DNS между проверкой и входом не работает.
3. **Отпечаток.** Студия получает только ключ хоста, пароль и ключ ещё не отправлены. Вы сверяете отпечаток SHA256 с тем, что показывает сам хост (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), и подтверждаете. Дальше вход идёт с закреплённым ключом: если хост ответил другим ключом, соединение рвётся до отправки учётных данных. Молчаливого доверия нет.
4. **План.** Студия определяет ОС, архитектуру, наличие Docker и systemd и показывает шаги: подключение, токен, Docker, служба, проверка, подключение раннера к Студии. Если Docker нет, предлагается поставить его официальным скриптом get.docker.com (включается явным переключателем); без Docker установка не начнётся. Если логин не root и `sudo` не включён, шаг службы помечен невозможным.
5. **Ход.** Шаги идут в реальном времени, у каждой ошибки понятная причина. Сессия живёт 15 минут, поэтому «Повторить» не просит ввести данные заново. Раннер ставится тем же скриптом, что и в разделе «Установка одной командой»: он приходит на хост через stdin (токен и пароль sudo не попадают в аргументы команд и в `ps`).

### Учётные данные

По умолчанию данные **одноразовые**: пароль, ключ и passphrase хранятся только в памяти процесса api на время установки и стираются после успеха, отмены или по истечении сессии. Они не пишутся ни в базу, ни в журнал, ни в журнал аудита, ни в ответы API; тексты ошибок очищаются от них.

Галочка **«Сохранить доступ зашифрованно»** кладёт их в таблицу `runner_ssh_credentials` под ключом шифрования секретов Студии (как токены git; смена ключа перешифровывает и их). Сохранённый доступ виден как факт наличия (название, хост, способ входа, отпечаток), значение показать нельзя, только удалить. По нему работают:

- **Обновить**: заново запускает скрипт на хосте (образ подтягивается, служба перезапускается), личность раннера сохраняется;
- **Переустановить**: убирает службу с данными (`uninstall --purge`) и ставит заново с новым токеном.

Ключ хоста при этом закреплён сохранённый: если он изменился, установка останавливается с ошибкой «ключ хоста не совпадает» до отправки пароля. Сохранение можно запретить `HSE_STUDIO__RUNNER_INSTALL__SSH_SAVE_CREDENTIALS=false`, а установку по SSH целиком `HSE_STUDIO__RUNNER_INSTALL__SSH_ENABLED=false`.

### Ограничения и аудит

Ход установок (шаги, сессии подтверждения отпечатка) хранится в памяти одного процесса api. Это рассчитано на одну реплику, как в чарте (`Recreate`): при нескольких репликах запрос о ходе может попасть на другую и получить 404. Для нескольких реплик нужно общее хранилище, сейчас его нет.

Только администратор установки; чужому ответ 404. Попытки подключения ограничены: 10 в минуту на администратора и 5 в минуту на хост и порт (429), одновременно идут не больше трёх установок. В журнал аудита пишутся `runner_install.ssh.probe`, `confirm`, `start`, `succeeded`, `failed`, `cancel`, `credentials_save`, `credentials_delete`, `run_saved` с адресом, логином и отпечатком, без секретов.

## Управление

В списке видны версия, теги, ёмкость и время последнего опроса.

- **Пауза** останавливает выдачу новых задач, текущие дорабатываются.
- **Ротация токена** выдаёт новый токен раннера; старый перестаёт работать. Новый токен задайте переменной `HSE_RUNNER__RUNNER_TOKEN`: она перекрывает `identity.json`.
- **Отзыв** навсегда закрывает раннеру доступ. Токен регистрации тоже можно отозвать до использования.
- Версии api и раннера проверяются при регистрации; несовместимый раннер отклоняется.
- Новый раннер после регистрации согласует с api возможности (`/announce`): ретрансляцию ИИ, отдельные слоты под неё, сообщение об остановке, канал команд и диск ([Диск раннера](#runner-disk)). Со старым api, который такого вызова не знает, раннер работает по-прежнему, без ретрансляции; старый раннер с новым api тоже работает.

## Зачем обновлять раннеры до 0.27.0 { #runner-version }

Раннер прежней версии с новой Студией работает, но две вещи сборки дают только раннеры 0.27.0 и новее. Раннер, поставленный из админки, обновляется кнопкой «Обновить до vX» ([Обновление раннера из админки](#runner-upgrade)), остальные обновите новым образом. Личный раннер в локальной Студии обновляется вместе с ней.

- **Места подписей по строкам шаблона.** Шаблон может отмечать при сборке, где на странице стоят линии подписей и строки даты, и Студия ставит рамки на них ([Места подписей по строкам шаблона](../workbench/send-for-signing.md#anchors)); так устроен курсовой проект магистратуры СПИ с версии 2026.1.5. Файл с позициями строк (`<документ>.hsepos`) раннер выгружает вместе с PDF, только если и он, и сервер объявили возможность `build_anchors` при согласовании (`/announce`). Раннер прежней версии этот файл не присылает: строки сборки для Студии неизвестны, рамки встают на запасное место шаблона в миллиметрах, метки даты не ставятся, а после правки текста места за строками не переезжают. Сборка при этом не падает.
- **Воспроизводимый PDF.** Раннер 0.27.0 зовёт latexmk с `-latexoption=-output-comment=hse-doc-studio`. Раньше TeX писал в PDF документа без hyperref дату и минуту сборки (поле `/Creator`), поэтому документ, пересобранный без правок в другую минуту, давал другой PDF. У документов на подписании от этого появлялось ложное «Есть изменения после отправки на подпись». Так было, например, с «Заявлением о выборе темы».

Версию каждого раннера видно в колонке «Версия» на странице «Раннеры»; у раннера старше Студии там кнопка «Обновить до vX» (если он поставлен из админки).

## Диск раннера { #runner-disk }

На машине раннера копятся образы Студии прежних версий, старые теги TeX Live и сервисов, кэш сборки Docker: каждое обновление качает новый образ на 1..2 ГБ. Пункт «Диск» в меню строки раннера (страница «Раннеры», общие и личные раннеры) показывает, сколько места занято и что можно освободить, и запускает очистку. Раннер меряет и чистит сам, тем же кодом, что раздел «Диск» в локальной Студии. Под именем общего раннера стоит ссылка «можно освободить N», если по последнему замеру освобождается от 1 ГБ.

| Блок | Что удаляет | Цель |
|---|---|---|
| Старые версии | образы прежних версий Студии, устаревшие теги сервисов и контейнеры на них | `old_versions` |
| Неиспользуемые образы | образы Студии, которые не нужны раннеру и не заняты ни одним контейнером | `unused_images` |
| Кэш сборки Docker | `docker builder prune` | `build_cache` |
| Висячие образы | `docker image prune` | `dangling_images` |
| Остановленные контейнеры Студии | контейнеры с меткой `com.hse-studio.managed`; только в «Очистить всё» | `stopped_containers` |
| Кэш раннера | кэш файлов (`data_dir/blobs`) и рабочие копии проектов (`data_dir/workspaces`) | `runner_cache` |

«Очистить всё» выполняет все цели, кроме отката. Каждая кнопка спрашивает подтверждение со списком того, что удалится, и размерами из последнего замера. Ход виден по шагам, очистку можно остановить после текущего шага. После итога раннер сам присылает новый замер.

Что не трогается:

- текущая версия: образ Студии версии раннера, `image_base:latest`, образ TeX раннера (`HSE_RUNNER__TEX_IMAGE`) и любой образ, на котором стоит контейнер, даже остановленный;
- предыдущая версия, нужная для отката. Её удаляет только флажок «Удалить и предыдущую версию» в подтверждении «Удалить старые версии»;
- тома Docker: кэш TeX Live и модели Ollama. Без них следующие сборки заметно дольше;
- всё вне категорий Студии: Postgres, MinIO, образы и контейнеры других проектов на том же хосте. «Диск» их не показывает;
- в кэше раннера файлы, тронутые за последние 10 минут, и рабочие копии, занятые сборками: идущие сборки не падают.

Сервер передаёт раннеру только цели очистки, а не имена образов. План раннер строит сам по свежему замеру, поэтому даже взломанный сервер может удалить на раннере только неиспользуемые образы Студии, её остановленные контейнеры и кэши. Отчёт о диске не содержит путей и id проектов.

| Раннер | Что в «Диске» |
|---|---|
| Docker (`HSE_RUNNER__EXECUTOR=docker`) | все блоки |
| Kubernetes (`executor=kubernetes`) | только кэш раннера и том данных. Образы TeX Live на узлах удаляет сборщик мусора kubelet (`imageGCHighThresholdPercent`); доступа к узлам у Студии нет, и он ей не нужен |
| локальная Студия, подключённая раннером | только кэш раннера. Docker этого компьютера чистится в самой Студии: Настройки, раздел «Диск» |
| Docker не ответил | только кэш раннера, вместо образов строка «Раннер не достучался до Docker» |
| версия раннера ниже 0.22.0 | заглушка «Обновите раннер, чтобы видеть диск»; у раннера, установленного из админки, кнопка «Обновить раннер» |
| не на связи | последний замер, очистка выключена до возвращения раннера |

Личный раннер видит и чистит владелец (Настройки, «Мои раннеры», пункт «Диск») и администратор установки. Предыдущую версию личного раннера удаляет только владелец. Об очистке, которую запустил администратор, владелец получает уведомление во «Входящих». В журнал аудита пишутся `runner.disk_cleanup`, `runner.disk_cleanup_cancel` и `runner.disk_cleaned`; замер не пишется.

Сервер и общий раннер на одном хосте (`deploy/server`) держите на одной версии. Образ сервера, на котором нет контейнера и который старше версии раннера, раннер посчитает старой версией. Подтверждение перечисляет такие образы поимённо.

### Канал команд { #control-channel }

Протокол раннера тянущий, а опрос задач `/poll` открыт, только пока у раннера есть свободный слот. Поэтому команды диска идут отдельным долгим опросом, который от слотов сборки не зависит. Входящих соединений к раннеру по-прежнему не нужно.

| Вызов | Что делает |
|---|---|
| `POST /api/runner/v1/control/poll` | долгий опрос команд (`disk.measure`, `disk.cleanup`), до 25 секунд |
| `POST /api/runner/v1/control/{id}/progress` | ход и итог команды; в ответе раннер узнаёт об остановке |
| `POST /api/runner/v1/disk` | последний замер диска, до 64 КБ |

- Канал открывается после `/announce`, если сервер согласовал обе возможности, `control` и `disk`. Старый раннер с новым сервером работает как раньше, без «Диска»; новый раннер со старым сервером канал не открывает.
- Замер раннер шлёт сам: после `/announce`, раз в 6 часов, после каждой очистки и по кнопке «Обновить».
- Команду, которую раннер не забрал за 10 минут, сервер помечает просроченной. Очистку, по которой 3 минуты нет хода или раннер ушёл (`/offline`, отзыв), сервер считает потерянной.
- У раннера идёт не больше одной очистки; повторный запуск отвечает 409 `runner_disk_busy`.
- Команды и последний замер хранятся в Postgres, поэтому канал работает при нескольких репликах api. Команды ограничены 20 последними на раннер.

Минимальная версия раннера для «Диска» 0.22.0. Раннер ниже обновите: установленный из админки кнопкой «Обновить» (раздел «Обновление раннера из админки» выше), остальные новым образом.

| Переменная | Значение |
|---|---|
| `HSE_RUNNER__IMAGE_BASE` | репозиторий образов Студии без тега, по умолчанию `ghcr.io/alexeyshalaev/hse-doc-studio`; то же, что `HSE_STUDIO__IMAGE_BASE` у сервера. По нему «Диск» узнаёт образы Студии и её старые версии. Задайте, если образы идут из своего реестра: иначе раннер их не видит и ничего из них не удаляет |
| `HSE_RUNNER__CACHE_MAX_BYTES` | предел кэша файлов (2 ГиБ); лишнее раннер вытесняет сам |
| `HSE_RUNNER__WORKSPACES_MAX_BYTES` | предел рабочих копий (20 ГиБ); давно не нужные раннер удаляет сам |
| `HSE_RUNNER__DATA_DIR` | том данных; «Диск» показывает свободное место на нём |

Метрики в `/metrics`: `hse_runner_disk_cleanable_bytes{scope="shared"|"personal"}` (сколько можно освободить по последним замерам) и `hse_runner_disk_cleanups_total{state}`. Устройство и решения: `docs/design/storage-cleanup.md`.

## Если раннеров нет

Сборка документов на сервере идёт только на раннерах. Интерфейс заранее узнаёт, для каких тегов (`tex`, `office`) сейчас есть живой раннер, общий или личный раннер владельца проекта, и перечитывает это сам, без перезагрузки страницы (`GET /api/v1/projects/{id}/build-availability`).

- Нет ни одного раннера: кнопки «Собрать», «Собрать всё» и пересборка неактивны, рядом пояснение. Документ можно собрать локально в Студии на компьютере (проект синхронизируется, готовый PDF выгружается на сервер) или попросить администратора подключить раннер; администратору показана ссылка на «Раннеры».
- Раннеры есть, но без нужного тега (например, нет раннера с `office`): блокируются только такие документы, «Собрать всё» собирает остальные.
- Если раннер пропал между проверкой и нажатием, сервер отвечает 409 с кодом `no_runners` или `no_runner_for_tags`, списком тегов `tags` и причиной `reason`, интерфейс показывает одно сообщение. «Собрать всё» ставит остальные документы и перечисляет пропущенные с причиной.
- Причина различает «все подходящие раннеры заняты» (сборка ждёт в очереди, как обычно) и «подходящих нет»: `personal_paused` и `shared_paused` (раннер с нужным тегом на паузе), `personal_offline` и `shared_offline` (не в сети), `no_runner` (раннера с тегом нет совсем). Интерфейс так и пишет: «Личный раннер для офисных документов на паузе».
- Уже стоящая сборка, которую после постановки некому взять (раннер отозвали, поставили на паузу или он выключился), не висит вечно: сервер снимает её итогом `failed` с кодом `no_runner_for_tags` (раннера с тегом нет, через минуту), `runner_offline` (подходящий раннер не в сети, через 5 минут) или `runner_paused` (на паузе, через 30 минут; пока ждёт, в документе видно «Ждём раннер: он на паузе»). Если хоть один подходящий раннер в сети, пусть и занят, сборка ждёт своей очереди.

В локальном режиме раннеры не нужны, сборка не блокируется.

## ИИ через свой раннер

Сервер не ходит во внутреннюю сеть пользователей. Чтобы пользоваться моделью на своём железе (Ollama, vLLM, LM Studio, любой OpenAI-совместимый адрес), хозяин личного раннера объявляет адреса в окружении раннера, а на сайте заводит провайдера «Через мой раннер». Сервер знает только имя адреса, URL и ключ остаются у раннера.

| Переменная | Значение |
|---|---|
| `HSE_RUNNER__AI_ENDPOINTS` | JSON-список адресов: `[{"name":"ollama","url":"http://localhost:11434/v1","flavor":"ollama"},{"name":"vllm","url":"http://gpu.lan:8000/v1","key_env":"VLLM_API_KEY"}]` |
| `HSE_RUNNER__AI_CONCURRENCY` | сколько запросов к моделям раннер ведёт сразу (по умолчанию 2), отдельно от сборок |
| `HSE_RUNNER__RELAY_MAX_RESPONSE_BYTES` | предел ответа модели (по умолчанию 64 MiB) |

- `name`: латиница в нижнем регистре, цифры, `-` и `_`, до 32 символов; так адрес называется в форме провайдера.
- `flavor`: `openai` (по умолчанию) или `ollama` (без `tool_choice` и `stream_options`, как требует Ollama).
- `key_env`: имя переменной окружения раннера с ключом модели; ключ на сервер не уходит. Логин и пароль в самом `url` раннер не принимает: адреса пишутся в журнал при старте.
- Раннер ходит только на объявленные адреса и только по путям `models`, `chat/completions`, `completions`, `embeddings`; заголовки сервера не пересылаются, редиректы не следуются.
- Ретрансляцией пользуется только хозяин раннера. Без объявленных адресов раннер ретрансляцию не берёт.

Объявить адрес мало: облако само провайдера не заводит. Человек один раз добавляет в облаке провайдера «Через мой раннер» (или нажимает «Добавить в облаке» в панели подключённых Студий), и только после этого модель появляется в выборе чата. Состояние каждого адреса сервер считает сам и показывает в панели Студии и в «Мои Студии»: провайдер не добавлен, ничего не открыто, раннер не сопряжён, не в сети, на паузе, отозван или личные раннеры выключены, модель на машине не отвечает, моделей нет. Подробнее: [Локальная версия из облака](../start/local-from-cloud.md). Когда модель за раннером не отвечает, чат пишет об этом прямо («модель на его компьютере не отвечает», «Раннер не в сети»), а переполнение окна Ollama (по умолчанию 4096 токенов) объясняет с числами и советом увеличить `num_ctx`.

Пределы на стороне api: `HSE_STUDIO__JOBS__RELAY_PICKUP_S` (сколько ждать, пока раннер возьмёт запрос), `HSE_STUDIO__JOBS__RELAY_MAX_REQUEST_BYTES`, `HSE_STUDIO__JOBS__RELAY_MAX_RESPONSE_BYTES`, `HSE_STUDIO__JOBS__RELAY_MAX_PENDING_PER_USER`, `HSE_STUDIO__JOBS__RELAY_MAX_DURATION_S` и бюджет памяти api под тела запросов: `HSE_STUDIO__JOBS__RELAY_MAX_PENDING_BYTES_PER_USER` (на человека), `HSE_STUDIO__JOBS__RELAY_MAX_PENDING_TOTAL` и `HSE_STUDIO__JOBS__RELAY_MAX_PENDING_BYTES_TOTAL` (на весь процесс). Сверх бюджета чат получает `relay_busy`. Раннер, который не ответил, в чате видно сообщением «Раннер «…» не ответил» с выбором другой модели.

## Раннеры вне сети сервера

Результат сборки раннер отправляет в объектное хранилище (S3) по подписанной ссылке, которую выдаёт api; исходники проекта он берёт у самого api. Ссылку открывает тот, кто её получил, поэтому у адреса должен быть маршрут с его машины. Внутренний адрес S3 (`http://minio.<namespace>.svc`, `http://minio:9000`) виден только внутри сети сервера.

| Кто | Что делает | Адрес S3 |
|---|---|---|
| api | все операции с хранилищем | внутренний, `HSE_STUDIO__S3__ENDPOINT` |
| общий раннер в сети сервера (под в кластере, контейнер compose) | выгрузка результата по ссылке | внутренний |
| личный раннер, локальная Студия, раннер на другой машине | выгрузка результата по ссылке | публичный, `HSE_STUDIO__S3__PUBLIC_ENDPOINT` |
| браузер | PDF сборки и сдачи по ссылке (редирект с api) | публичный |

Подпись запроса S3 (v4) включает хост, поэтому ссылка подписывается сразу для того адреса, по которому её откроют. Подменить хост в готовой ссылке нельзя: хранилище ответит 403. Без `PUBLIC_ENDPOINT` внешние получатели получают внутренний адрес (как до этой настройки). Тогда сборка на личном раннере завершается ошибкой `storage_unreachable` с текстом «object storage at … is not reachable from this machine» и названием настроек, а страница «Самодиагностика» в админке предупреждает: «Раннеров вне сети сервера: N, а публичного адреса хранилища нет».

### Как опубликовать хранилище

1. Откройте наружу только S3 API (порт 9000 у MinIO) под отдельным именем, например `files.example.org`, с TLS. Консоль MinIO (9001) и метрики (`/minio/v2/metrics`) не публикуйте. Имя должно вести на корень хранилища: адрес с префиксом пути не поддерживается.
2. Прокси должен передавать заголовок `Host` как есть: по нему хранилище проверяет подпись.
3. Задайте адрес: `s3.publicEndpoint` в Helm, `S3_PUBLIC_ENDPOINT` в `.env` compose или `HSE_STUDIO__S3__PUBLIC_ENDPOINT`. Значение это схема, хост и порт без пути: `https://files.example.org`.
4. Перезапустите api и откройте «Самодиагностику»: предупреждение о хранилище должно исчезнуть.

Kubernetes, Ingress (ingress-nginx; хост, имя сервиса и пространство имён подставьте свои):

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: studio-s3
  namespace: <namespace-minio>
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "0"
    nginx.ingress.kubernetes.io/proxy-request-buffering: "off"
    nginx.ingress.kubernetes.io/configuration-snippet: |
      limit_except GET HEAD PUT { deny all; }
spec:
  ingressClassName: nginx
  tls:
    - hosts: [files.example.org]
      secretName: files-tls
  rules:
    - host: files.example.org
      http:
        paths:
          - path: /<bucket>/
            pathType: Prefix
            backend:
              service:
                name: <minio-service>
                port: {number: 9000}
```

Аннотация `configuration-snippet` в новых версиях ingress-nginx по умолчанию выключена (`allow-snippet-annotations`): если её нет, ограничьте методы политикой контроллера или используйте Gateway API.

Kubernetes, Gateway API (`HTTPRoute` к существующему Gateway с HTTPS-слушателем на этом имени):

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: studio-s3
  namespace: <namespace-minio>
spec:
  parentRefs:
    - name: <gateway>
      namespace: <namespace-gateway>
  hostnames: [files.example.org]
  rules:
    - matches:
        - path: {type: PathPrefix, value: /<bucket>/}
          method: GET
        - path: {type: PathPrefix, value: /<bucket>/}
          method: HEAD
        - path: {type: PathPrefix, value: /<bucket>/}
          method: PUT
      backendRefs:
        - name: <minio-service>
          port: 9000
```

Если Gateway и MinIO в разных пространствах имён, добавьте `ReferenceGrant`. Compose: обратный прокси на хосте (nginx, Caddy) с TLS перед портом 9000 MinIO; порт в `docker-compose.yml` не публикуется, поэтому прокси подключите к сети compose или опубликуйте порт на `127.0.0.1` оверлеем.

### Безопасность

- Бакет остаётся закрытым. Анонимного доступа нет: открыть объект можно только по ссылке, подписанной ключами api, и только тем методом и для того ключа, для которых она выдана. Ссылка на чтение не годится для записи.
- Ключи доступа к S3 раннерам и браузерам не передаются. Раннер получает ссылку на запись одного выхода своей задачи (префикс `artifacts/<проект>/jobs/<задача>/`), размер и sha256 api сверяет при завершении.
- Срок ссылки: на выгрузку результата 15 минут, на скачивание PDF 2 минуты. Подпись лежит в адресе, поэтому TLS на публичном имени обязателен, а прокси не должен писать query в журнал доступа.
- Наружу достаточно методов `GET`, `HEAD` и `PUT` на путях бакета. `DELETE`, `POST`, листинг и другие бакеты закройте на прокси, как в примерах выше.
- CORS нужен только браузеру (pdf.js читает PDF по ссылке с заголовком `Range` из другого источника), раннерам он не нужен. MinIO по умолчанию отвечает на CORS любому источнику; сузить до адреса Студии можно переменной MinIO `MINIO_API_CORS_ALLOW_ORIGIN`. Для AWS, Yandex Object Storage и Ceph задайте `HSE_STUDIO__S3__CORS_ORIGINS=["https://studio.example.org"]` (в Helm `s3.corsOrigins`): api выставит CORS бакета при старте.

### Если хранилище публиковать нельзя

`HSE_STUDIO__S3__OUTSIDE_RUNNER_ACCESS=proxy` (Helm `s3.outsideRunnerAccess: proxy`, compose `S3_OUTSIDE_RUNNER_ACCESS=proxy`) выключает ссылки для раннеров вне сети: результат они отправляют самому api (`PUT /api/runner/v1/jobs/{id}/artifacts/{sha256}`), а api кладёт его в хранилище. Токены раннера и задачи проверяются, размер не может превысить заявленный, заявленный не больше `HSE_STUDIO__JOBS__MAX_ARTIFACT_BYTES` (512 МиБ), sha256 сверяется до записи в хранилище.

Цена режима: весь трафик результатов таких раннеров идёт через api. Тело принимается во временный файл (до 8 МиБ в памяти, остальное на диске), так что на диске api нужно место под число одновременных выгрузок умноженное на размер результата, а ingress перед api должен пропускать большие тела (для ingress-nginx `proxy-body-size`) и не обрывать долгие запросы. Для браузера режим ничего не меняет: PDF по ссылке по-прежнему требует публичного адреса.

Общий раннер, который стоит вне сети сервера (другая ВМ), считается внутренним. Объявите его внешним: `HSE_STUDIO__S3__SHARED_RUNNERS_OUTSIDE=true` (Helm `s3.sharedRunnersOutside`). Устройство и решения: `docs/design/s3-public-endpoint.md`.

## Подключённые Студии и присутствие

Локальная Студия раз в минуту шлёт серверу по своему входу кодом устройства сигнал присутствия: имя компьютера, версию, что она делает, состояние раннера и моделей, синхронизацию облачных проектов. Сервер держит свежее время в памяти и пишет строку в БД, когда состояние изменилось или раз в две минуты; «в сети» значит сигнал не старше трёх минут. Устройство забывается через 60 дней молчания, у человека не больше 20 устройств. Интервалы задают `HSE_STUDIO__DEVICES__INTERVAL_S`, `ONLINE_WINDOW_S`, `PERSIST_INTERVAL_S`, `RETENTION_DAYS` ([справочник](env-reference.md)). Человек видит свои устройства целиком, другие участники проекта только «работает локально», администратор установки видит столько же, сколько любой человек. Решения: `docs/design/connected-devices.md`.

## Исполнители сборки

Задачи проверки подписей, упаковки сдачи, проверок и ретрансляции ИИ раннер выполняет сам, офисные файлы конвертирует постоянный Gotenberg. Отдельный исполнитель нужен только сборке TeX. Его выбирает `HSE_RUNNER__EXECUTOR`:

| Значение | Как идёт сборка | Где подходит |
|---|---|---|
| `docker` (по умолчанию) | соседний контейнер TeX Live через `/var/run/docker.sock` | машина или ВМ с Docker, compose |
| `kubernetes` | отдельный под на каждую сборку в namespace раннера через Kubernetes API | кластер Kubernetes, в том числе с containerd без Docker |

Исполнитель `kubernetes` не требует ни `docker.sock`, ни `hostPath`, ни привилегий: под раннера и поды сборки проходят Pod Security Standard restricted. Исходники уходят в под и результат возвращается через `exec` Kubernetes API (tar-поток), поэтому общий том между раннером и подами не нужен, а подам сборки не нужна сеть. Раннер ставит каждому поду лимиты процессора и памяти, `activeDeadlineSeconds`, удаляет под при отмене задачи и убирает поды, оставшиеся от прошлого запуска. Лог сборки идёт в журнал задачи как обычно.

| Переменная | Значение |
|---|---|
| `HSE_RUNNER__K8S__NAMESPACE` | namespace подов сборки (по умолчанию namespace раннера) |
| `HSE_RUNNER__K8S__IMAGE` | образ TeX; по умолчанию `HSE_RUNNER__TEX_IMAGE` |
| `HSE_RUNNER__K8S__CPU_REQUEST`, `…CPU_LIMIT`, `…MEMORY_REQUEST`, `…MEMORY_LIMIT`, `…EPHEMERAL_STORAGE_REQUEST`, `…EPHEMERAL_STORAGE_LIMIT` | ресурсы пода сборки (500m/2, 1Gi/4Gi, 1Gi/4Gi); под, убитый по памяти, заканчивается кодом `build_out_of_memory` |
| `HSE_RUNNER__K8S__ACTIVE_DEADLINE_S` | предел жизни пода, секунды (1800) |
| `HSE_RUNNER__K8S__POD_START_TIMEOUT_S` | сколько ждать запуска пода с pull образа (300) |
| `HSE_RUNNER__K8S__NODE_SELECTOR`, `…TOLERATIONS` | размещение подов сборки, JSON |
| `HSE_RUNNER__K8S__RUNTIME_CLASS_NAME` | RuntimeClass подов сборки, например `gvisor` |
| `HSE_RUNNER__K8S__TEX_CACHE_CLAIM` | необязательный PVC с кэшем шрифтов TeX |
| `HSE_RUNNER__K8S__FONTS_CLAIM` | необязательный PVC со шрифтами (`.ttf`, `.otf`, `.ttc`), монтируется в поды сборки только для чтения |
| `HSE_RUNNER__POD__NAMESPACE`, `…NAME`, `…SERVICE_ACCOUNT`, `…CPU_REQUEST_M`, `…CPU_LIMIT_M`, `…MEMORY_REQUEST_MI`, `…MEMORY_LIMIT_MI`, `…EPHEMERAL_REQUEST_MI`, `…EPHEMERAL_LIMIT_MI` | свой под из downward API (милликоры и МиБ); раннер только сообщает это в админку, на работу не влияет. Чарт и установка из админки задают их сами ([что видно в админке](runner-isolation.md)) |

В Helm-чарте это `runner.executor: kubernetes` и блок `runner.kubernetes` (см. README чарта): чарт создаёт ServiceAccount раннера, Role только на поды своего namespace (`pods`, `pods/log`, `pods/exec`), NetworkPolicy, запрещающую подам сборки сеть, и том данных раннера. Если сборка падает с кодом `image_missing`, узел не смог скачать образ TeX; `build_backend_unavailable` значит, что Kubernetes отказал в поде (права, квота, нет подходящего узла), подробность в журнале задачи. Лимиты, сетевые политики, квота и проверка: [Изоляция и лимиты раннеров](runner-isolation.md). Устройство и развилки: `docs/design/k8s-runner.md`.

## Шрифты сборки { #build-fonts }

Шаблоны по ГОСТ просят Times New Roman, Arial и Consolas, а в образе TeX Live их нет, и Studio не поставляет их ни в образах, ни в репозитории (лицензия Microsoft). Без них шаблоны с `\IfFontExistsTF` берут свободную замену и собираются, а шаблон с прямым `\setmainfont{Arial}` падает с кодом `font_missing` и именем шрифта в подробностях. Строки `kpathsea: Running mktextfm Arial` в журнале сами не ошибка: так XeTeX ищет шрифт по имени.

Чтобы сборки на раннере видели ваши шрифты, положите лицензионные файлы в папку и подключите её:

| Исполнитель | Как |
|---|---|
| `docker` | `HSE_RUNNER__FONTS_DIR` указывает на папку (в ней `.ttf`, `.otf`, `.ttc`); раннер монтирует её в контейнер сборки только для чтения в `HSE_RUNNER__FONTS_MOUNT_TARGET` (по умолчанию `/usr/local/share/fonts/hse`), где её видит fontconfig. Если раннер сам работает в контейнере, а `docker.sock` хостовый, папка должна лежать на хосте: путь на хосте задаёт `HSE_RUNNER__FONTS_HOST_DIR` (без него путь переводится так же, как путь папок проектов). Пустая папка или переменная не заданы: ничего не монтируется |
| `kubernetes` | `HSE_RUNNER__K8S__FONTS_CLAIM` называет PVC со шрифтами в namespace подов сборки; он монтируется в поды только для чтения (`HSE_RUNNER__K8S__FONTS_MOUNT_TARGET`) |

Другой путь: собрать свой образ TeX Live со шрифтами (`FROM texlive/texlive`, `COPY fonts/ /usr/local/share/fonts/hse/`, `RUN fc-cache -f`) и указать его в `HSE_RUNNER__TEX_IMAGE`. Личный раннер (локальная Студия) настраивать не нужно: он берёт шрифты из «Настройки, Шрифты» вашей Студии, см. [Шрифты в облачных сборках](../workbench/compile.md#cloud-fonts).

## Масштабирование

Несколько раннеров на разных машинах работают сообща. Две реплики на одной машине должны иметь разные каталоги данных. Кроме раннеров установки бывают личные раннеры пользователей; раннеров организаций пока нет.
