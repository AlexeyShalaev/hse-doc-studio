# Автообновление сервера

<p class="hds-lede">Студия сама узнаёт о новых релизах и, если вы разрешите, ставит их ночью: снимает снимок базы, проверяет образ, применяет миграции, перезапускает сервисы и сама возвращается на прежнюю версию, если новая не поднялась. Настраивается всё в админке, в разделе «Обновления».</p>

Устройство и принятые решения: `docs/design/auto-update.md` в репозитории.

## Что нужно включить

Проверка релизов и уведомления работают сразу. Установку делает отдельный сервис `updater`: в compose ему нужен доступ к docker, в Kubernetes права на Deployment api (раздел «Kubernetes» ниже). Включение для compose:

```bash
# в .env: общий секрет api и апдейтера
UPDATER_TOKEN=$(openssl rand -hex 32)
# файл .env должен быть доступен на запись пользователю app (uid 10001), чтобы апдейтер продвигал TAG
chmod o+w .env
docker compose --profile updater up -d
```

Через минуту в разделе «Обновления» появится строка «Апдейтер: работает». Без токена сервис не запускается, а Студия только сообщает о версиях.

!!! danger "Сокет docker равен root"
    У `updater` есть `/var/run/docker.sock`, как у раннера. Порты он не публикует и берёт работу только у api по общему секрету, но компрометация хоста или секрета даёт права root. Сервис выключен, пока вы не включите профиль. Если это неприемлемо, оставьте режим «Уведомлять» и обновляйте вручную.

## Политика

| Режим | Что делает |
|---|---|
| Выключено | релизы не проверяются |
| Уведомлять (по умолчанию) | раз в 6 часов спрашивает канал stable и сообщает администраторам; ставите вы кнопкой |
| Ставить автоматически | ставит сам в окно обслуживания |

Для автоустановки задаются: самый крупный шаг без человека (только патчи или патчи и минорные; новая мажорная версия всегда только уведомление), дни и время окна в UTC (по умолчанию каждый день с 02:00 на 3 часа), нужен ли полный бэкап перед обновлением, проверка образа. Версия, которая уже откатывалась, повторно сама не ставится: ждём следующий релиз.

## Как идёт обновление (compose)

1. Если в разделе «Бэкапы» есть назначение, запускается полный бэкап и обновление ждёт его успеха. Бэкап не удался: обновление отменено, ничего не тронуто.
2. Апдейтер снимает снимок базы и закрепляет прежний образ.
3. Скачивает новый образ и проверяет его: дайджест совпадает с опубликованным в релизе (`image-digest.json`), при выборе «Дайджест и подпись» ещё и подпись cosign.
4. Останавливает раннер и api (с этого момента Студия недоступна, обычно 1–3 минуты), применяет миграции, запускает сервисы на новом образе.
5. Ждёт здоровья: контейнеры работают, не перезапускаются, `/health/ready` отвечает 200 двадцать секунд подряд.

Что-то пошло не так на шагах 4–5: прежние образы возвращаются автоматически. Если миграции успели изменить схему базы, сначала база восстанавливается из снимка (старый образ на новой схеме не запустится), данные при этом не теряются, потому что api был остановлен. Администраторы получают уведомление, в истории виден ход запуска.

## Откатить вручную

Кнопка «Откатить на X» доступна, пока стоит версия последнего успешного обновления. Если обновление меняло схему базы, откат восстанавливает снимок, снятый перед ним: **всё записанное после обновления будет потеряно**, поэтому нужно явное подтверждение. Без изменения схемы откат возвращает только образы.

## Kubernetes

Есть два пути, выбирайте один.

### Кнопки в админке: исполнитель `kubernetes`

Включается флагом чарта (по умолчанию выключено):

```bash
helm upgrade hse-doc-studio deploy/helm/hse-doc-studio --reset-then-reuse-values \
  --set updater.enabled=true --set updater.token=$(openssl rand -hex 32)
```

Токен можно не класть в values, а завести ключ `updater-token` в `secrets.existingSecret`. Чарт добавит под `updater` и переключит api на исполнитель `kubernetes` (`HSE_STUDIO__SERVER_UPDATE__EXECUTOR=kubernetes`). Через минуту в разделе «Обновления» появится «Апдейтер: работает», а «Обновить сейчас» и «Откатить» заработают.

Что он делает: проверяет образ (дайджест из релиза записывается в Deployment, при выборе «Дайджест и подпись» подпись cosign проверяется отдельным Job), запускает Job `db current` на новом образе, останавливает api (`replicas: 0`), применяет миграции Job’ом `db upgrade`, меняет образ Deployment `api` и ждёт здоровья. Опирается на Deployment и Job, а не на запись релиза Helm: работает и у установок без Helm (Kustomize, свои манифесты). Студия недоступна от остановки api до готовности новой версии, обычно 1–3 минуты плюс время миграций.

Права апдейтера ограничены его namespace: `get` и `patch` одного Deployment api по имени, Job (создать, читать, удалять), чтение подов и их логов. Секретов, других namespace и `ClusterRole` у него нет. Под и Job проходят Pod Security `restricted`.

!!! warning "Снимка базы в Kubernetes нет"
    Образ старше схемы не стартует, поэтому откатить образ можно, только пока миграции не менялись. Защита такая:

    - если в «Бэкапах» настроено назначение, перед обновлением идёт полный бэкап и обновление ждёт его успеха;
    - иначе ручное обновление просит подтвердить риск («Я понимаю: полного бэкапа не будет и базу откатить нельзя»), а автоустановка не стартует: администраторы получают уведомление;
    - новая версия не поднялась, а миграции схему не меняли: образ и реплики возвращаются сами, итог «Откачено»;
    - новая версия не поднялась, а **миграции схему изменили**: образ не откатывается (старый на новой схеме не запустится), статус «Нужны руки». В ходе запуска (кнопка «Ход») написано, что стоит в Deployment, как диагностировать и два пути: исправить причину и дать поду перезапуститься либо восстановить базу из бэкапа и вернуть прежний образ командами `kubectl set image` и `kubectl scale` (имена уже подставлены);
    - кнопка «Откатить» доступна, пока последнее обновление не меняло схему; иначе страница объясняет, почему её нет.

После обновления из админки зафиксируйте версию в values (или в GitOps-репозитории): следующий `helm upgrade` без `--set image.tag=<версия>` вернёт образ из values. Раннер задач (если включён) и сам апдейтер обновляются `helm upgrade` вместе с чартом: из админки меняется только Deployment api, а несовместимая версия раннера отклоняется при регистрации.

### Команда оператора: Helm и GitOps

Если исполнитель выключен (`HSE_STUDIO__SERVER_UPDATE__EXECUTOR=none`, по умолчанию), Студия проверяет релизы и сообщает о них, страница показывает готовую команду, а откат делает сам Helm:

```bash
helm upgrade hse-doc-studio deploy/helm/hse-doc-studio --reuse-values --set image.tag=0.4.0 --atomic --wait
```

Миграции идут отдельным Job перед обновлением. Чтобы не получать уведомления, задайте `api.extraEnv.HSE_STUDIO__SERVER_UPDATE__ENABLED=false`. Образ можно проверить заранее: `cosign verify` с идентичностью workflow `publish.yml`.

## Если что-то не так

| Симптом | Что делать |
|---|---|
| «Апдейтер не отвечает» | `docker compose --profile updater ps`, `docker compose logs updater`; токен в `.env` и в api должен совпадать |
| «У релиза нет дайджеста» | релиз вышел до автообновления; поставьте его вручную или выберите проверку «Без проверки» |
| Статус «Нужны руки» (compose) | откат не удался; в ходе запуска написано, где лежит снимок (`snapshots/…` в томе `updater-data`), затем `docker compose up -d` |
| Статус «Нужны руки» (Kubernetes) | миграции изменили схему, а новая версия не поднялась; образ не откачен, шаги в ходе запуска (диагностика, исправить причину или восстановить базу и вернуть образ) |
| «Апдейтер не отвечает» (Kubernetes) | `kubectl get pods -l app.kubernetes.io/component=updater`, его журнал; токен `updater.token` и ключ `updater-token` в Secret api должны совпадать, у Role должны быть права на Deployment api |
| Запуск отменён `precheck_failed` (Kubernetes) | новый образ не потянулся или база не читается: `kubectl describe job` с меткой `hse-doc-studio/update-run`; api не останавливали |
| Обновление отменено `unsupported_container_options` | у контейнера есть опции, которые апдейтер не переносит; обновите вручную |
| TAG в `.env` не меняется | файл недоступен на запись пользователю app: `chmod o+w .env` |

Метрики для алертов: `hse_update_available`, `hse_update_updater_up`, `hse_update_last_run_success`, `hse_update_runs_total{result}`. Настройки процесса: `HSE_STUDIO__SERVER_UPDATE__*` в [справочнике](env-reference.md).
