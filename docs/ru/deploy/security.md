# Безопасность и персональные данные

## Модель угроз раннера

Исходники и сборочные настройки пишут пользователи, то есть код раннера обрабатывает **недоверенный ввод**. Сборка LaTeX умеет вызывать внешние программы и читать файлы, поэтому раннер строится так:

| Угроза | Мера |
|---|---|
| Сборка читает или портит соседние проекты | каждая задача получает свой воркспейс; входные файлы копируются, не линкуются, хеш проверяется повторно; кэш блобов только для чтения |
| Выход сборки подменяет файлы или ссылается наружу | сборщик выходов принимает только обычные файлы, симлинки отвергаются |
| Сборка ходит в сеть и во внутренние службы | контейнер сборки запускается без секретов раннера и без токенов задач |
| Украденный токен раннера | токен хранится в базе хешем, ротируется и отзывается в админке; раннер получает только то, что лежит в очереди |
| Чужой раннер подсовывает артефакты | результат применяет api после проверки; подпись токена задачи (HMAC) ограничена задачей и попыткой |
| Выход из контейнера сборки | см. остаточный риск ниже |

### Остаточный риск: сокет Docker

Раннер управляет соседними контейнерами через `/var/run/docker.sock`. Это равно root на хосте раннера. Поэтому:

- раннер-хост считайте доверенной инфраструктурой отдельно от api и базы;
- лучше rootless Docker, sysbox или выделенная виртуальная машина;
- у api доступа к Docker нет и быть не должно;
- под Kubernetes пока работает раннер на hostPath; под на задачу с gVisor или Kata в плане следующих этапов.

## Границы доверия

- **Участники проекта** видят только свои проекты. Чужой проект отвечает как несуществующий (404), нехватка роли даёт 403.
- **Администратор установки** управляет людьми и настройками, но не получает неявного доступа к содержимому проектов. Два пути обхода (ссылка сброса пароля и самодобавление в организацию) оформлены как break-glass: с подтверждением, записью в аудит и уведомлением.
- **Права проекта** хранятся только в базе. Файл `project.json` содержит их как подсказку, и значение базы всегда перезаписывает файл; пришедший по git `project.json` права не меняет.
- **Исходящие запросы** пользователей (git, OIDC, провайдеры ИИ) проходят политику: loopback, link-local, приватные сети и адреса метаданных облака закрыты; внутренние узлы открываются списком `HSE_STUDIO__EGRESS__ALLOWLIST`.
- **Пользовательские файлы** отдаются с `nosniff`, ограничением типов и песочницей CSP.
- **Секреты в базе** (токены git, пароль SMTP, секрет OIDC, ключи ИИ) зашифрованы и привязаны к записи; без `SECRETS_KEY` не читаются.
- **Админка** может быть ограничена по имени хоста и сети.
- **Связка OpenPGP общая.** Секретные и загруженные открытые ключи OpenPGP лежат в одной связке сервера (`data_dir/gnupg`), а не по людям: записи о ключах привязаны к владельцу в базе, но сама связка общая, и проверка подписи видит ключи всех. Хотите разделения, не разрешайте хранить секретные ключи на сервере (`settings/signing`). Роли агента, наоборот, раздельные: `data_dir/users/<хеш id>/`.

## Персональные данные

!!! note "Оператор это вы"
    Публичного сервиса автора нет. Тот, кто развернул сервер, является оператором персональных данных своих пользователей и отвечает за их обработку.

Что хранится:

| Данные | Где |
|---|---|
| имя, адрес почты, хеш пароля, сведения об организации | Postgres |
| сессии (адрес клиента, устройство), журнал аудита | Postgres, срок аудита настраивается |
| тексты работ, вложения, сборки | том проектов и S3 |
| переписка с ИИ-агентом, настройки, ключи | Postgres, ключи зашифрованы |

Что нужно сделать оператору:

1. Уведомить пользователей о составе и целях обработки и назначить ответственного. В российской практике это требования 152-ФЗ; проверьте применимость к вашему случаю с юристом.
2. Хранить данные там, где это допустимо для вашей организации; Postgres и S3 разворачиваются у вас.
3. Задать сроки хранения: `AUDIT_RETENTION_DAYS`, `PROJECT_RETENTION_DAYS` (удалённый проект стирается с тома и из каталога через заданный срок).
4. Закрыть доступ к бэкапам так же, как к самим данным.
5. Ответственно выбрать провайдеров ИИ: текст проекта уходит выбранному провайдеру. Локальная Ollama оставляет данные у вас. Список внешних обращений: [Что уходит в сеть](../reference/privacy.md).

Аккаунт отключается в админке; проекты удаляются владельцем или по сроку хранения.
