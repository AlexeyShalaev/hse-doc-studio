# Предложить изменения

<p class="hds-lede">В пространстве над git правки уходят в рабочую ветку и запросом на слияние в базовую: PR на GitHub, MR на GitLab. Решение о слиянии принимает хостинг и сопровождающие репозитория, Студия только готовит предложение.</p>

## Ветка и версии

Под заголовком пространства панель git: ветка, правки после последнего коммита, на сколько коммитов ветка впереди и позади базы, открытый PR и статус проверок.

- **Сохранить версию**: коммит в рабочую ветку от вашего имени. Ветки ещё нет: Студия создаст её сама. Сообщение можно оставить пустым, Студия составит его по изменённым версиям (`fix(packs): ...` для patch, `feat(packs): ...` иначе).
- **Ветка**: новая ветка с именем от Студии, своё имя или переход на существующую ветку (только без несохранённых правок).
- **Изменения**: что отличается от базовой ветки, по файлам.
- **Подтянуть** базовую ветку в рабочую. Если основная ветка правит те же места, слияние отменяется, Студия называет файлы: поправьте их в своей ветке, сохраните версию и подтяните снова.
- **Начать заново**: дерево на свежей базе без ветки. Несохранённые правки отбрасываются только по отдельной галочке; ветка и запрос на хостинге остаются как есть.

## Запрос на слияние

**Предложить изменения**:

1. Студия проверяет изменённые паки тем же кодом, что `hse-doc-studio pack check --base`: линтер, неизменность выпущенных версий, схемы, класс версий. Ошибки останавливают отправку и появляются в «Проблемах»; чужие ошибки в нетронутых паках не мешают.
2. Несохранённые правки коммитятся, ветка уходит на хостинг.
3. Открывается PR или MR в базовую ветку. Заголовок и описание можно написать или оставить Студии: описание она дополнит сводкой (версии, класс изменения, заметки, итоги проверок). Если запрос из этой ветки уже открыт, ветка просто обновится.

Если хостинг не дал открыть запрос через API, будет ссылка **Открыть PR в браузере** со страницей сравнения.

**Нет права писать в репозиторий.** Студия предложит **Отправить в форк**: **Создать форк моим токеном** (GitHub) или **Указать свой форк** на том же сервере. Форк запоминается для пространства.

## Проверки хостинга { #hosting-checks }

После отправки панель показывает статус проверок по отправленной вершине: GitHub (check runs и статусы коммита) или GitLab (конвейер, нужен токен с `read_api`). Пока проверки идут, статус обновляется раз в 30 секунд. **Проверки хостинга** раскрывают список со ссылками. Если хостинг не отдаёт статус этому токену, ссылка ведёт на страницу проверок.

Готовый CI для своего репозитория паков: [Командная строка и CI](ci.md#ci).

## Официальные паки { #official }

Паки самой Студии лежат в её репозитории (`packs/`). Предложить исправление в них может любой, у кого есть аккаунт GitHub:

1. Карточка **Официальные паки**, кнопка **Начать**. Нужен ваш токен GitHub: классический, с правом `public_repo` (форк, ветка в форке и PR в открытый репозиторий). Если токена нет, окно даст ссылку на его создание и поле, куда его вставить: Студия проверит токен, сохранит его в «Доступе к репозиториям» и сразу выберет. Студия скачает только папку паков.
2. Правки и новая версия как обычно.
3. **Предложить изменения**: ветка уходит в ваш форк, PR открывается от вашего аккаунта. Других путей нет: бота установки для официальных паков нет, так безопаснее. Коммиты могут трогать только папку паков.
4. Перед первой отправкой отметьте согласие: вклад публичен и распространяется под лицензией репозитория. Правила вклада: раздел «Contributing to the official packs» в [CONTRIBUTING.md](https://github.com/AlexeyShalaev/hse-doc-studio/blob/master/CONTRIBUTING.md#contributing-to-the-official-packs).

У PR из форка нового участника GitHub не запускает проверки, пока сопровождающий не разрешит запуск. Студия покажет **Ждут одобрения**: это не ошибка. Официальные паки выходят вместе со Студией: после слияния PR новая версия появится у пользователей со следующим выпуском.
