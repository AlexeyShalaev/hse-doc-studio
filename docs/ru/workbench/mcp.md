# ИИ-клиенты (MCP)

<p class="hds-lede">Студия умеет работать сервером Model Context Protocol. Внешний ИИ-клиент (Claude Code, Claude Desktop, Codex, OpenCode, Gemini CLI, Cursor, VS Code, Windsurf, Zed, Cline, JetBrains) видит ваши проекты и работает в них инструментами Студии: читает и правит файлы, собирает PDF, разбирает замечания, сохраняет снимки. Он действует от вашего имени и не может больше, чем вы.</p>

## Включить

=== "Локальная Студия"

    **Настройки → ИИ-клиенты (MCP) → «Включить MCP-сервер»**. Адрес сервера `http://127.0.0.1:17240/mcp`: порт тот же, что у Студии. Токен не нужен: сервер отвечает только программам на этом компьютере и отклоняет запросы, где `Host` или `Origin` называют чужой сайт.

=== "Облачная Студия"

    MCP включает администратор: **Админка → MCP-сервер → «Включить MCP-сервер»**. Затем каждый выпускает себе токен: **Настройки → Аккаунт → Токены → Новый токен**, право **MCP**. Адрес сервера `https://<адрес Студии>/mcp`, токен передаётся заголовком `Authorization: Bearer <токен>`.

## Подключить клиента

Готовые конфиги с вашим адресом есть в Студии: **Настройки**, раздел **ИИ-клиенты (MCP)**, клиент выбирается в списке. Ниже те же конфиги для облака с адресом `https://studio.example.org/mcp`. Для локальной Студии адрес `http://127.0.0.1:17240/mcp`, а заголовок `Authorization`, переменную с токеном и `bearer_token_env_var` уберите.

### Токен в переменной окружения

Где клиент умеет подставлять переменную окружения, конфиг ссылается на `HSE_STUDIO_TOKEN`, и токен не лежит в файле открытым текстом. Задайте переменную до запуска клиента:

=== "macOS, Linux"

    ```bash
    # в ~/.zshrc или ~/.bashrc
    export HSE_STUDIO_TOKEN=hsd_pat_...
    ```

    Редактор, запущенный из Dock или меню, переменные оболочки не видит: запускайте его из терминала (`cursor .`, `code .`).

=== "Windows"

    ```powershell
    setx HSE_STUDIO_TOKEN hsd_pat_...
    ```

    `setx` действует на новые окна и программы: перезапустите терминал и редактор.

### Агенты в терминале

=== "Claude Code"

    ```bash
    # локально
    claude mcp add --transport http hse-doc-studio http://127.0.0.1:17240/mcp
    # облако
    claude mcp add --transport http hse-doc-studio https://studio.example.org/mcp \
      --header "Authorization: Bearer hsd_pat_..."
    ```

    [Документация Claude Code](https://code.claude.com/docs/en/mcp)

=== "Codex"

    CLI, расширение для IDE и приложение для компьютера читают общий `~/.codex/config.toml` (на Windows он в папке пользователя, `%USERPROFILE%\.codex\config.toml`).

    ```bash
    codex mcp add hse-doc-studio --url https://studio.example.org/mcp \
      --bearer-token-env-var HSE_STUDIO_TOKEN
    ```

    То же вручную в `config.toml`:

    ```toml
    [mcp_servers.hse-doc-studio]
    url = "https://studio.example.org/mcp"
    bearer_token_env_var = "HSE_STUDIO_TOKEN"
    ```

    Проверка: `codex mcp list`, в сессии `/mcp`. [Документация Codex](https://developers.openai.com/codex/mcp), [флаги `codex mcp add`](https://developers.openai.com/codex/cli/reference).

=== "OpenCode"

    Файл `opencode.json` в корне проекта или `~/.config/opencode/opencode.json` для всех проектов.

    ```json
    {
      "$schema": "https://opencode.ai/config.json",
      "mcp": {
        "servers": {
          "hse-doc-studio": {
            "type": "remote",
            "url": "https://studio.example.org/mcp",
            "oauth": false,
            "headers": { "Authorization": "Bearer {env:HSE_STUDIO_TOKEN}" }
          }
        }
      }
    }
    ```

    Команда пишет то же в конфиг проекта (`--global` в общий):

    ```bash
    opencode mcp add hse-doc-studio --url https://studio.example.org/mcp \
      --header 'Authorization=Bearer {env:HSE_STUDIO_TOKEN}'
    ```

    `oauth: false` выключает попытку входа через OAuth: Студия принимает токен. В OpenCode 1.x сервер лежит прямо под `mcp`, без `servers`. [Документация OpenCode](https://opencode.ai/docs/mcp-servers/)

=== "Gemini CLI"

    ```bash
    gemini mcp add --scope user --transport http \
      --header 'Authorization: Bearer ${HSE_STUDIO_TOKEN}' \
      hse-doc-studio https://studio.example.org/mcp
    ```

    Или вручную в `~/.gemini/settings.json` (для проекта `.gemini/settings.json`):

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "httpUrl": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    Нужен именно `httpUrl`: поле `url` у Gemini CLI означает старый транспорт SSE. Одинарные кавычки в команде не дают оболочке подставить токен в файл. [Документация Gemini CLI](https://geminicli.com/docs/tools/mcp-server/)

### Редакторы

=== "Cursor"

    Файл `~/.cursor/mcp.json` или `.cursor/mcp.json` в проекте.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${env:HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    [Документация Cursor](https://cursor.com/docs/mcp)

=== "VS Code"

    Copilot читает `~/.copilot/mcp-config.json` или `.mcp.json` в корне проекта. Удобнее всего добавить сервер командой **MCP: Add Server**.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "type": "http",
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${HSE_STUDIO_TOKEN}" },
          "tools": ["*"]
        }
      }
    }
    ```

    Старый формат `.vscode/mcp.json` с ключом `servers` VS Code ещё понимает, но для новых настроек не советует. [Документация VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)

=== "Windsurf"

    Windsurf теперь называется Devin Desktop. Файл `~/.config/devin/mcp_config.json`, на Windows `%APPDATA%\devin\mcp_config.json`; открывается кнопкой **Open MCP config file** в меню MCP. У прежних версий Windsurf файл `~/.codeium/windsurf/mcp_config.json`.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "serverUrl": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${env:HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    После правки нажмите обновление списка серверов. [Документация Windsurf](https://docs.devin.ai/windsurf/plugins/cascade/mcp)

=== "Zed"

    Файл настроек `~/.config/zed/settings.json`, на Windows `%APPDATA%\Zed\settings.json`. То же можно ввести в **Settings | AI | MCP Servers**, кнопка **Add Remote Server**.

    ```json
    {
      "context_servers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    Подстановку переменных в `headers` документация Zed не описывает, поэтому токен вписывается в файл. [Документация Zed](https://zed.dev/docs/ai/mcp)

=== "Cline"

    В расширении: вкладка **Configure**, кнопка **Configure MCP Servers**. У Cline CLI файл `~/.cline/data/settings/cline_mcp_settings.json`.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "type": "streamableHttp",
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    Без `"type": "streamableHttp"` Cline подключается по старому SSE и к Студии не подключится. Из терминала:

    ```bash
    cline mcp add hse-doc-studio https://studio.example.org/mcp --transport http \
      --header "Authorization: Bearer hsd_pat_..." --yes
    ```

    Переменные в `headers` документация Cline не описывает. [Документация Cline](https://docs.cline.bot/mcp/adding-and-configuring-servers)

=== "JetBrains"

    **Junie** (плагин и CLI) читает `~/.junie/mcp/mcp.json` или `.junie/mcp/mcp.json` в проекте:

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    **AI Assistant**: **Settings | Tools | AI Assistant | Model Context Protocol (MCP)**, кнопка **Add**. Для удалённого сервера его документация описывает только `url`, без заголовков. Локальной Студии этого хватает (`{"mcpServers": {"hse-doc-studio": {"url": "http://127.0.0.1:17240/mcp"}}}`), к облаку подключайтесь через мост stdio из раздела ниже. [Документация Junie](https://junie.jetbrains.com/docs/junie-cli-mcp-configuration.html), [документация AI Assistant](https://www.jetbrains.com/help/ai-assistant/configure-an-mcp-server.html)

### Клиенты с запуском процесса (stdio)

Claude Desktop и клиенты, которые запускают сервер процессом, используют мост `hse-doc-studio mcp`: он пересылает запросы работающей Студии.

```json
{
  "mcpServers": {
    "hse-doc-studio": {
      "command": "hse-doc-studio",
      "args": ["mcp", "--url", "https://studio.example.org"],
      "env": { "HSE_STUDIO_TOKEN": "hsd_pat_..." }
    }
  }
}
```

Без `--url` мост подключается к локальной Студии, она должна быть запущена. Если команды `hse-doc-studio` на компьютере нет, то же делает [`mcp-remote`](https://github.com/geelen/mcp-remote) (нужен Node.js): `"command": "npx"`, `"args": ["-y", "mcp-remote", "https://studio.example.org/mcp", "--header", "Authorization:${AUTH_HEADER}"]`, `"env": { "AUTH_HEADER": "Bearer hsd_pat_..." }`.

### Клиенты, которым нужен OAuth

ChatGPT (приложения и коннекторы), Claude в браузере и на телефоне (коннекторы) и другие облачные клиенты ходят к серверу со своих серверов и входят только через OAuth или без авторизации. Студия пока принимает только токен в заголовке, поэтому такие клиенты к ней не подключаются, а локальная Студия им вообще не видна.

Что можно сделать:

- **ChatGPT**: подключите Студию к Codex. Его конфиг `~/.codex/config.toml` общий для CLI, расширения IDE и приложения ChatGPT для компьютера.
- **Claude**: Claude Desktop работает через мост stdio, Claude Code напрямую.

## Что доступно

- **Инструменты.** Проекты (список, карточка, создание, метаданные, руководитель и авторы, обновление шаблона, доступ и приглашения в облаке), файлы (дерево, чтение, поиск, правка, запись, перенос), сборка (запуск с ожиданием результата, история, лог, отмена), проверки и отчёт нормоконтроля, требования, ревью-комментарии (облако), история и git-синхронизация, профили и пакеты сдачи, состояние подписей, маршрут подписания (облако). Инструменты проекта принимают `project_id`; начните с `list_projects`.
- **Ресурсы.** `studio://projects`, карточка проекта `studio://projects/<id>`, файлы `studio://projects/<id>/files/<путь>` и PDF сборок.
- **Сценарии (prompts).** `fix_build` (починить сборку), `normcontrol` (разобрать замечания), `review_changes` (описать изменения перед снимком).

### Проекты: создание, люди, проект из облака

- **`create_project`** создаёт проект из шаблона (`pack_id`, `template_id`, `version` из `list_templates`). В локальной Студии нужен `folder`, полный путь к новой папке. В облаке папку выбирает сервер: поля `folder` в схеме нет, а присланное значение не используется.
    - Работает тот же сценарий, что у мастера создания в вебе, с теми же проверками. Авторы передаются в `authors`: `name` (ФИО, обязательно), `group`, `email`, а для командного проекта ещё `topic` (тема автора), `slug` (папка автора) и `managed` (вести ли его комплект здесь, по умолчанию да). Для одного автора по-прежнему хватит `author_name`.
    - Больше одного автора означает командный проект (`staffing: "team"`), как в мастере. `list_templates` показывает, поддерживает ли шаблон команду (`staffing=solo,team`). У каждого ведомого автора нужна тема, ведомым должен быть хотя бы один, `slug` по умолчанию выводится из фамилии и должен быть уникальным. Каждый ведомый автор получает свои экземпляры личных документов (`<документ>--<slug>`) в своей папке; общие документы команды ведутся, пока `shared_enabled` не равно `false`.
    - Руководители `supervisor`, `co_supervisor`, `academic_supervisor` необязательны, поля те же, что у `set_project_people`; задать их можно и позже. Группа первого автора, у которого она указана, попадает в `meta.group`, как в мастере.
    - В ответе id проекта, а у командного проекта ещё `slug` авторов: по ним `set_project_people` выбирает автора.
    - Пример: `{"name": "Система учёта", "pack_id": "hse-cs-se", "template_id": "vkr", "version": "2026.1", "kind": "project", "authors": [{"name": "Смирнова Анна", "topic": "Серверная часть"}, {"name": "Петров Борис", "topic": "Клиент"}], "supervisor": {"name": "С. А. Шершаков"}}`.
- **`set_project_people`** меняет научного руководителя (`supervisor`), соруководителя (`co_supervisor`), академического руководителя программы (`academic_supervisor`) и авторов, то есть то, что попадает на титульный лист, в заявку и заявление. Права те же, что в настройках проекта: нужна роль, которой можно менять настройки, а проект должен быть доступен для записи. Значения доходят до PDF при следующей сборке: `common/meta.tex` перегенерируется перед каждой сборкой.
    - У руководителей поля `name` (ФИО), `title` (должность), `degree` (степень или звание), `role` (`university` или `company`). Переданные поля заменяют текущие, остальные остаются; пустая строка очищает должность или степень, пустое `name` убирает человека из проекта.
    - `author` меняет одного автора, не трогая остальных: `name`, `group`, `email`, `topic` (тема в командном проекте), пустая строка очищает группу, e-mail или тему. В командном проекте автора выбирают по `slug` из `get_project`, в одиночном меняется первый автор.
    - `authors` заменяет список целиком: `name`, `group`, `email` и `topic` каждого автора, первый идёт на титульный лист. Чтобы у существующих авторов сохранились тема и комплект командного проекта, передайте их `slug` из `get_project`. Новый автор командного проекта появляется без комплекта (`managed: false`), как при добавлении автора в настройках; комплект включается в настройках проекта.
    - `clear: ["co_supervisor"]` убирает соруководителя (так же `supervisor` и `academic_supervisor`).
    - Пример: `{"supervisor": {"name": "С. А. Шершаков", "degree": "канд. техн. наук"}, "author": {"group": "МПИ251", "email": "ivanov@edu.hse.ru"}}`.
    - Каждое изменение попадает в аудит: в облаке событие `project.people_update` с тем, что было и что стало; локально вызов виден в журнале MCP.
- **`clone_cloud_project`** (только локальная Студия) скачивает проект облачной Студии, как кнопка «Открыть» у облачного проекта в списке. Передайте `url` проекта, например `https://studio.example.org/projects/<id>/`, или `project_id`, если сервер уже подключён (`server` нужен, только когда подключено несколько серверов). Студия использует сохранённый вход на сервер ([подключение](../start/local-from-cloud.md#connect)), токен в аргументах не нужен и в ответ не попадает; адрес с логином или токеном отклоняется. Проект ложится в папку проектов из облака и остаётся связан с сервером. Скачивание идёт в фоне: инструмент ждёт до `wait_s` секунд (по умолчанию 45, меньше таймаута клиентов MCP), а если не дождался, повторный вызов с теми же аргументами подхватит ту же загрузку. Если проект уже на компьютере, он не скачивается заново.
- **`list_project_fields`** показывает поля проекта из описания шаблона, те же, что в настройках проекта: ключ, подпись, текущее значение, допустимые значения (`options`) или подсказку (`hint`, `example`), обязательность (`required_at`: `create` при создании, `finalize` к сдаче) и документы, где поле печатается (`printed_in`, по исходникам шаблона). В `set_with` указано, каким инструментом поле менять. В командном проекте у полей автора есть `author_values` по `slug`. В `unknown_meta` ключи метаданных, которых шаблон не описывает и не печатает (например группа, записанная в метаданные вместо карточки автора).
- **`set_project_meta`** задаёт поля (`entries`) и удаляет ключи (`unset`): удалённое поле снова берёт значение из шаблона. Пример: `{"entries": {"year": "2027"}, "unset": ["udc"]}`. Права те же, что в настройках проекта.
- **Обновление шаблона** идёт так же, как окно «Обновить шаблон» в настройках проекта.
    - `template_update_status` показывает версию шаблона проекта и доступные обновления: класс (`patch`, `minor`, `major`), что нового и что ломает, например `2026.1.1` и рекомендованное `2026.1.2`.
    - `plan_template_update` с `to_version` показывает, что станет с каждым файлом (`update`, `add`, `delete`, `merge`, `conflict`), и отдаёт `fingerprint`. Файлы проекта не меняются.
    - `apply_template_update` с `to_version` и `fingerprint` применяет ровно этот план; если проект за это время изменился, нужен новый план. Конфликты решает `resolutions` (`{"путь": "mine" | "theirs" | "markers"}`), по умолчанию файл остаётся вашим. Перед записью Студия делает снимок истории, отменить обновление можно в настройках проекта.
    - План и применение доступны тому, кто может управлять шаблоном проекта (владелец), и только в проекте, доступном для записи. В облаке применение попадает в аудит (`project.template_update`).

### Синхронизация с git-remote

**`git_sync`** делает то же, что кнопка синхронизации проекта: сохраняет снимок, забирает чужие изменения и отправляет свои. В локальной Студии это синхронизация с облачным сервером (проект из облака) или с подключённым репозиторием, в облаке с подключённым репозиторием. Инструмент ждёт итог до `wait_s` секунд (по умолчанию 45); если не дождался, ответ `status: running`, а повторный вызов присоединится к той же синхронизации, как и кнопка, нажатая во время идущей. В ответе `outcome` (`up_to_date`, `pushed`, `fast_forwarded`, `merged`, `conflicts`), число полученных и отправленных версий и файлы, слитые автоматически. При конфликтах ничего не отправляется и файлы на диске не меняются: в ответе список файлов с конфликтами, а решаются они в Студии кнопкой «Разобрать». Адрес репозитория и доступ к нему в ответ не попадают. Права те же, что у кнопки: нужна роль редактора, а в командном проекте ещё право править весь проект. Инструмент опасный, поэтому по умолчанию выключен.

### Документы: вариант

- **`set_document_variant`** выбирает вариант документа, как переключатель «Форматы документов» в настройках проекта: например, у презентации `pptx`, `beamer` или `reveal`. Передайте `doc_id` из `list_documents` и `variant`; без `variant` инструмент только покажет текущий вариант и допустимые для языка проекта. Неизвестный вариант отклоняется с перечнем допустимых. Смена сбрасывает статус документа в черновик, файлы прежнего варианта остаются. Права те же, что в интерфейсе: запись в документ, а проект должен быть доступен для записи. В облаке смена попадает в аудит событием `document.variant_update`.

### Доступ к проекту (облако)

Те же действия, что в панели «Доступ», с теми же правами; в локальной Студии этих инструментов нет.

- **`list_project_access`** показывает владельца, людей и группы с ролями. Тому, кто ведёт приглашения (владелец или редактор с правом делиться), ещё и ожидающие приглашения.
- **`invite_to_project`** приглашает по `email` с ролью `reader`, `reviewer` или `editor` (не выше своей). `persona` привязывает к роли в проекте: например, руководитель-рецензент это `role: "reviewer"`, `persona: "supervisor"`. Доступ появляется, когда человек примет приглашение. Если почта на сервере не настроена, в ответе `link`: перешлите её сами, как из окна приглашения в интерфейсе. Ссылка одноразовая.
- **`revoke_project_invitation`** отзывает ожидающее приглашение по `invitation_id`, ссылка из письма перестаёт работать.
- **`remove_project_member`** снимает доступ с участника (`member` вида `user:<id>` из `list_project_access`); это может только владелец.

Опасные инструменты (удаление проекта и файла, откат истории, синхронизация с git-remote, подписание комплекта `sign_submission`, отправка на подписание `send_for_signing`) по умолчанию выключены: их включает поимённо администратор (облако) или вы сами (локально). `get_signature_plan` показывает план подписей и чего не хватает. У документа, отправленного на подписание, в плане `pinned` (версия на подписи: `sha256` и `pinned_at`) и `working_differs` (текущая сборка от неё отличается); подписи считаются по версии на подписи. `sign_submission` подписывает ваши слоты в документах контрольной точки ключом из Студии: токену нужно отдельное право «подписание», ключ с паролем через MCP не используется (подпишите в интерфейсе), пароли и ключи в ответ не попадают. Документ, отправленный на подписание по маршруту, инструмент не фиксирует и подписывает только в вашу очередь на подпись; иначе пропускает его с причиной «Документ на подписании по маршруту».

### Маршрут подписания (облако)

Маршрут [«Отправить на подписание»](send-for-signing.md) ведёт только сервер, поэтому в локальной Студии этих инструментов нет. Через MCP можно узнать ход маршрута и отправить документы; согласовать, подписать или вернуть на доработку можно только на странице подписи в интерфейсе: это решение человека.

- **`get_signing_route`** показывает ход маршрута контрольной точки (`profile_id` из `list_submission_profiles`): статус и фазу, шаги с людьми и их состояниями, чья очередь сейчас (`waiting_for`), срок, причину остановки (`stop_reason`: версия на подписи изменилась вне маршрута, подписи или итоговый PDF изменены вне маршрута, участник ушёл, возврат на доработку; у маршрутов, остановленных прежней версией Студии, ещё «документ пересобран»), кто остановил и последние события. У каждого документа `sent` (версия на подписи: SHA-256, дата, раунд) и `changed` (есть изменения после отправки), у маршрута `changed_docs`. Если изменения есть, `changed_hint` подсказывает, какие документы изменились и что новую версию отправляет человек в интерфейсе. У остановленного маршрута `stop_text` объясняет, что случилось и что делать, в том числе когда версия на подписи изменилась вне маршрута. Без `profile_id` отдаёт сводку по всем маршрутам проекта. Доступно тем же, кто видит результаты сборки; комментарий возврата видят управляющие маршрутом и его участники.
- **`list_signing_tasks`** показывает ваши задачи «На подпись» по всем проектам: где сейчас нужно ваше действие (`approve`, `approve_and_sign`, `sign`), от кого, по какой точке и к какому сроку. В `signing_page` адрес страницы подписи: откройте её в Студии.
- **`send_for_signing`** отправляет документы контрольной точки (`profile_id`) на подписание, как кнопка «Отправить на подписание». Берёт сохранённый маршрут точки (черновик, остановленный, возвращённый или отменённый: тогда это «Отправить заново»), а если его нет, создаёт из прежнего маршрута или порядка шаблона. Проверки те же, что у кнопки: документы собраны, у каждого слота есть подписант, ваша подпись готова, документы не изменились между проверкой и отправкой. Сверх того все подписанты должны уже быть в проекте: с человеком, который ещё не принял приглашение, отправьте маршрут из интерфейса. Если что-то мешает, инструмент перечисляет помехи и ничего не отправляет. Если вы подписант первого шага, отправка считается вашим согласованием. Ключом инструмент не подписывает: «Отправить и подписать» остаётся в интерфейсе. Нужна роль, которой можно собирать пакет сдачи (владелец, редактор). Инструмент опасный, поэтому по умолчанию выключен; отправка попадает в аудит событием `signing_route.send`. Идущий или завершённый маршрут инструмент не отправляет: отказ `new_version_in_ui`, при этом ничего не меняется и завершённый маршрут остаётся на контроле. Новая версия сбрасывает согласия других людей, поэтому это решение человека: кнопка «Отправить новую версию» на карточке «Подписание».

Необязательные подписи ([Необязательные подписи и пропуск](send-for-signing.md#optional)) через MCP только читаются. `get_signing_route` отдаёт у слота документа `optional` (необязательна на этой точке), `extra` (слот сверх точки) и статус `skipped`, у участника состояние `skipped`, `skipped_at` и `skippable`, у маршрута подсказку `skip_hint`, когда очередь у человека, которого можно пропустить. `get_signature_plan` показывает у слота `optional` и `skipped` (`at`, `route_id`), у плана `optional_pending`; `package_project` перечисляет необязательные неподписанные слоты как `optional_unsigned`. **Пропустить участника и отметить подпись необязательной через MCP нельзя**, инструментов для этого нет: пропуск отменяет требование подписи и пишет человеку, а ошибку можно исправить только новой отправкой, то есть лишним кругом для людей. Это решение автора в интерфейсе, как отправка новой версии.

Метки даты ([Дата подписания](send-for-signing.md#dates)) через MCP только читаются. `get_signature_plan` отдаёт у слота документа `dates` (страница, формат и `text`: что напечатано сейчас, `null` у пустой метки) и `signed_at` (`at` и `source`: `approval`, дата согласования по маршруту, или `manual`, день, указанный автором), `list_signatures` показывает метки в размещениях. **Ставить, двигать и удалять метки и ручную дату через MCP нельзя**: инструмента размещения подписей нет, а правка меток на документе под маршрутом может сбросить электронные подписи и требует подтверждения человека. Это делается в интерфейсе: на вкладке «Подписи» документа или в блоке «Где подписи» редактора маршрута.

Править и собирать документы на подписании через MCP можно: маршрут подписывает версию, снятую при отправке, и правки в неё не попадают. Если инструмент правки или сборки затрагивает документ идущего маршрута, к ответу добавляется `signing_note`: какой документ на подписании, что изменения не попадут в версию на подписи и что новую версию отправляет человек в интерфейсе. Так делают `edit_tex`, `write_file`, `move_file`, `delete_file`, `compile_document`, `set_document_variant`, `set_project_meta`, `set_project_people`, `set_language`, `apply_template_update`, `vcs_restore` и `git_sync`. Общий файл, поля проекта, обновление шаблона, откат истории и синхронизация затрагивают все документы на подписании. Это не отказ, действие выполнено. `package_project` собирает такие документы из версии на подписи и возвращает предупреждение `changed_after_sent`, если текущая сборка новее.

### Сборка

**`compile_document`** запускает сборку, как кнопка «Собрать». По умолчанию (`wait: true`) инструмент ждёт итог до 45 секунд: этого меньше, чем клиенты MCP ждут ответа. Если сборка идёт дольше (например, облачная сборка на личном раннере), ответ приходит без ошибки: `status: in_progress` и `compile_id`, а сборка продолжается. С `wait: false` инструмент сразу возвращает `compile_id`. Итог такой сборки показывает `get_compile` с этим `compile_id`, остановить её можно через `cancel_compile`.

## Безопасность

- Клиент действует от имени владельца токена: те же роли в проектах, квоты и лимиты, что в интерфейсе. Чужой проект для него не существует.
- Токену MCP достаточно права **MCP**; к обычному API он доступа не даёт. Отозвать токен можно там же, где он выпущен; он перестаёт действовать сразу.
- Вход по cookie браузера на `/mcp` не принимается.
- Каждый вызов попадает в журнал: инструмент, проект, исход и время, без содержимого аргументов. В облаке журнал на странице **Админка → MCP-сервер** и в общем аудите, локально в настройках MCP.
- Частота вызовов ограничена (по умолчанию 120 в минуту на человека); сборка, запись файлов и git считаются ещё и по своим лимитам.

## Для администратора

На странице **Админка → MCP-сервер**:

- общий переключатель MCP-сервера;
- группы и отдельные инструменты с переключателями; опасные включаются поимённо;
- группа **Администрирование** (пользователи, очередь, раннеры, аудит, журнал писем) выключена по умолчанию; даже включённой она доступна только администратору установки с токеном, где есть право **MCP: администрирование**;
- журнал вызовов.

**`admin_list_mail_log`** отвечает на вопрос «дошло ли письмо» без страницы **Админка → Письма**: строки журнала писем, новые первыми. Фильтры `recipient` (точный адрес без учёта регистра), `template` (вид письма, например `invite`), `status` (`sent`, `failed`, `not_sent`, `suppressed`) и `since` (дата или момент ISO 8601, без часового пояса считается UTC), не больше 50 строк (`limit`, по умолчанию 20). В строке время, вид письма, адрес и тема, итог, причина, код ответа SMTP и кто вызвал письмо (`cause`: человек, запрос без входа или фоновая задача, и `actor_id`); получатель и проект только своими id. Превью письма, имён, ссылок и текста сбоя в ответе нет. Инструмент только читает, и чтение не попадает в аудит.
