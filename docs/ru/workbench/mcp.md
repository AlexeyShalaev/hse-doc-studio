# ИИ-клиенты (MCP)

<p class="hds-lede">Студия умеет работать сервером Model Context Protocol. Внешний ИИ-клиент (Claude Code, Claude Desktop, Codex, OpenCode, Gemini CLI, Cursor, VS Code, Windsurf, Zed, Cline, JetBrains) видит ваши проекты и работает в них инструментами Студии: читает и правит файлы, собирает PDF, разбирает замечания, сохраняет снимки. Он действует от вашего имени и не может больше, чем вы.</p>

## Включить

=== "Локальная Студия"

    **Настройки → ИИ-клиенты (MCP) → «Включить MCP-сервер»**. Адрес сервера `http://127.0.0.1:17240/mcp`: порт тот же, что у Студии. Токен не нужен: сервер отвечает только программам на этом компьютере и отклоняет запросы, где `Host` или `Origin` называют чужой сайт.

=== "Облачная Студия"

    MCP включает администратор: **Админка → MCP-сервер → «Включить MCP-сервер»**. Затем каждый выпускает себе токен: **Настройки → Аккаунт → Токены → Новый токен**, право **MCP**. Адрес сервера `https://<адрес Студии>/mcp`, токен передаётся заголовком `Authorization: Bearer <токен>`.

    Если токен уже есть, новый выпускать не нужно: **Настройки → Аккаунт → Токены → «Изменить права»** у нужного токена (подробнее в разделе [Права токена](#scopes)).

### Права токена { #scopes }

Что умеет токен, решают его права. Для MCP нужно право **MCP**; **Подпись через MCP** даёт инструменту `sign_submission` подписывать комплект, **Студия шаблонов** открывает инструменты `pack_*`, **MCP: администрирование** открывает админские инструменты (только администратору установки).

Права можно поменять у готового токена: **Настройки → Аккаунт → Токены → «Изменить права»**. Отметьте нужные права, проверьте сводку «Добавится» и «Уберётся» и сохраните. Сам токен остаётся прежним, поэтому в CLI, скриптах и ИИ-клиентах ничего менять не нужно.

- Новые права действуют сразу, со следующего запроса с этим токеном. Снятое право перестаёт работать тоже сразу.
- ИИ-клиент запоминает список инструментов, когда подключается. Чтобы он увидел новые инструменты (или перестал показывать снятые), переподключите сервер Студии в клиенте (в Claude Code команда `/mcp`, в Cursor и VS Code кнопка перезапуска сервера) или перезапустите клиент. Студия работает без сессий MCP, поэтому сама сообщить клиенту об изменении не может.
- Права меняет только вошедший в Студию человек в браузере. Сам токен свои и чужие права не меняет, через MCP или API это сделать нельзя.
- Дать можно те же права, что при выпуске: **MCP: администрирование** только администратору установки, токену устройства (вход по коду) только права git. Убрать можно любое право.
- У истёкшего токена права не поменять, нужен новый. Отозванного токена больше нет.
- Каждая смена прав попадает в аудит: что добавлено и что убрано.

## Подключить клиента

Готовые конфиги с вашим адресом есть в Студии: **Настройки**, раздел **ИИ-клиенты (MCP)**, клиент выбирается в списке. Ниже те же конфиги для облака с адресом `https://studio.example.org/mcp`. Для локальной Студии адрес `http://127.0.0.1:17240/mcp`, а заголовок `Authorization`, переменную с токеном и `bearer_token_env_var` уберите.

### Токен в переменной окружения

Где клиент умеет подставлять переменную окружения, конфиг ссылается на `HSE_STUDIO_TOKEN`, и токен не лежит в файле открытым текстом. Задайте переменную до запуска клиента:

=== "macOS, Linux"

    ```bash
    # в ~/.zshrc или ~/.bashrc
    export HSE_STUDIO_TOKEN=hsd_pat_...
    ```

    Редактор, запущенный из Dock или меню, переменные оболочки не видит: запускайте его из терминала (`cursor .`, `code .`).

=== "Windows"

    ```powershell
    setx HSE_STUDIO_TOKEN hsd_pat_...
    ```

    `setx` действует на новые окна и программы: перезапустите терминал и редактор.

### Агенты в терминале

=== "Claude Code"

    ```bash
    # локально
    claude mcp add --transport http hse-doc-studio http://127.0.0.1:17240/mcp
    # облако
    claude mcp add --transport http hse-doc-studio https://studio.example.org/mcp \
      --header "Authorization: Bearer hsd_pat_..."
    ```

    [Документация Claude Code](https://code.claude.com/docs/en/mcp)

=== "Codex"

    CLI, расширение для IDE и приложение для компьютера читают общий `~/.codex/config.toml` (на Windows он в папке пользователя, `%USERPROFILE%\.codex\config.toml`).

    ```bash
    codex mcp add hse-doc-studio --url https://studio.example.org/mcp \
      --bearer-token-env-var HSE_STUDIO_TOKEN
    ```

    То же вручную в `config.toml`:

    ```toml
    [mcp_servers.hse-doc-studio]
    url = "https://studio.example.org/mcp"
    bearer_token_env_var = "HSE_STUDIO_TOKEN"
    ```

    Проверка: `codex mcp list`, в сессии `/mcp`. [Документация Codex](https://developers.openai.com/codex/mcp), [флаги `codex mcp add`](https://developers.openai.com/codex/cli/reference).

=== "OpenCode"

    Файл `opencode.json` в корне проекта или `~/.config/opencode/opencode.json` для всех проектов.

    ```json
    {
      "$schema": "https://opencode.ai/config.json",
      "mcp": {
        "servers": {
          "hse-doc-studio": {
            "type": "remote",
            "url": "https://studio.example.org/mcp",
            "oauth": false,
            "headers": { "Authorization": "Bearer {env:HSE_STUDIO_TOKEN}" }
          }
        }
      }
    }
    ```

    Команда пишет то же в конфиг проекта (`--global` в общий):

    ```bash
    opencode mcp add hse-doc-studio --url https://studio.example.org/mcp \
      --header 'Authorization=Bearer {env:HSE_STUDIO_TOKEN}'
    ```

    `oauth: false` выключает попытку входа через OAuth: Студия принимает токен. В OpenCode 1.x сервер лежит прямо под `mcp`, без `servers`. [Документация OpenCode](https://opencode.ai/docs/mcp-servers/)

=== "Gemini CLI"

    ```bash
    gemini mcp add --scope user --transport http \
      --header 'Authorization: Bearer ${HSE_STUDIO_TOKEN}' \
      hse-doc-studio https://studio.example.org/mcp
    ```

    Или вручную в `~/.gemini/settings.json` (для проекта `.gemini/settings.json`):

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "httpUrl": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    Нужен именно `httpUrl`: поле `url` у Gemini CLI означает старый транспорт SSE. Одинарные кавычки в команде не дают оболочке подставить токен в файл. [Документация Gemini CLI](https://geminicli.com/docs/tools/mcp-server/)

### Редакторы

=== "Cursor"

    Файл `~/.cursor/mcp.json` или `.cursor/mcp.json` в проекте.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${env:HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    [Документация Cursor](https://cursor.com/docs/mcp)

=== "VS Code"

    Copilot читает `~/.copilot/mcp-config.json` или `.mcp.json` в корне проекта. Удобнее всего добавить сервер командой **MCP: Add Server**.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "type": "http",
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${HSE_STUDIO_TOKEN}" },
          "tools": ["*"]
        }
      }
    }
    ```

    Старый формат `.vscode/mcp.json` с ключом `servers` VS Code ещё понимает, но для новых настроек не советует. [Документация VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)

=== "Windsurf"

    Windsurf теперь называется Devin Desktop. Файл `~/.config/devin/mcp_config.json`, на Windows `%APPDATA%\devin\mcp_config.json`; открывается кнопкой **Open MCP config file** в меню MCP. У прежних версий Windsurf файл `~/.codeium/windsurf/mcp_config.json`.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "serverUrl": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer ${env:HSE_STUDIO_TOKEN}" }
        }
      }
    }
    ```

    После правки нажмите обновление списка серверов. [Документация Windsurf](https://docs.devin.ai/windsurf/plugins/cascade/mcp)

=== "Zed"

    Файл настроек `~/.config/zed/settings.json`, на Windows `%APPDATA%\Zed\settings.json`. То же можно ввести в **Settings | AI | MCP Servers**, кнопка **Add Remote Server**.

    ```json
    {
      "context_servers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    Подстановку переменных в `headers` документация Zed не описывает, поэтому токен вписывается в файл. [Документация Zed](https://zed.dev/docs/ai/mcp)

=== "Cline"

    В расширении: вкладка **Configure**, кнопка **Configure MCP Servers**. У Cline CLI файл `~/.cline/data/settings/cline_mcp_settings.json`.

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "type": "streamableHttp",
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    Без `"type": "streamableHttp"` Cline подключается по старому SSE и к Студии не подключится. Из терминала:

    ```bash
    cline mcp add hse-doc-studio https://studio.example.org/mcp --transport http \
      --header "Authorization: Bearer hsd_pat_..." --yes
    ```

    Переменные в `headers` документация Cline не описывает. [Документация Cline](https://docs.cline.bot/mcp/adding-and-configuring-servers)

=== "JetBrains"

    **Junie** (плагин и CLI) читает `~/.junie/mcp/mcp.json` или `.junie/mcp/mcp.json` в проекте:

    ```json
    {
      "mcpServers": {
        "hse-doc-studio": {
          "url": "https://studio.example.org/mcp",
          "headers": { "Authorization": "Bearer hsd_pat_..." }
        }
      }
    }
    ```

    **AI Assistant**: **Settings | Tools | AI Assistant | Model Context Protocol (MCP)**, кнопка **Add**. Для удалённого сервера его документация описывает только `url`, без заголовков. Локальной Студии этого хватает (`{"mcpServers": {"hse-doc-studio": {"url": "http://127.0.0.1:17240/mcp"}}}`), к облаку подключайтесь через мост stdio из раздела ниже. [Документация Junie](https://junie.jetbrains.com/docs/junie-cli-mcp-configuration.html), [документация AI Assistant](https://www.jetbrains.com/help/ai-assistant/configure-an-mcp-server.html)

### Клиенты с запуском процесса (stdio)

Claude Desktop и клиенты, которые запускают сервер процессом, используют мост `hse-doc-studio mcp`: он пересылает запросы работающей Студии.

```json
{
  "mcpServers": {
    "hse-doc-studio": {
      "command": "hse-doc-studio",
      "args": ["mcp", "--url", "https://studio.example.org"],
      "env": { "HSE_STUDIO_TOKEN": "hsd_pat_..." }
    }
  }
}
```

Без `--url` мост подключается к локальной Студии, она должна быть запущена. Если команды `hse-doc-studio` на компьютере нет, то же делает [`mcp-remote`](https://github.com/geelen/mcp-remote) (нужен Node.js): `"command": "npx"`, `"args": ["-y", "mcp-remote", "https://studio.example.org/mcp", "--header", "Authorization:${AUTH_HEADER}"]`, `"env": { "AUTH_HEADER": "Bearer hsd_pat_..." }`.

### Клиенты, которым нужен OAuth

ChatGPT (приложения и коннекторы), Claude в браузере и на телефоне (коннекторы) и другие облачные клиенты ходят к серверу со своих серверов и входят только через OAuth или без авторизации. Студия пока принимает только токен в заголовке, поэтому такие клиенты к ней не подключаются, а локальная Студия им вообще не видна.

Что можно сделать:

- **ChatGPT**: подключите Студию к Codex. Его конфиг `~/.codex/config.toml` общий для CLI, расширения IDE и приложения ChatGPT для компьютера.
- **Claude**: Claude Desktop работает через мост stdio, Claude Code напрямую.

## Что доступно

- **Инструменты.** Проекты (список, карточка, создание, метаданные, руководитель и авторы, обновление шаблона, доступ и приглашения в облаке), файлы (дерево, чтение, поиск, правка, запись, перенос), сборка (запуск с ожиданием результата, история, лог, отмена), проверки и отчёт нормоконтроля, требования, ревью-комментарии (облако), история и git-синхронизация, профили и пакеты сдачи, состояние подписей, маршрут подписания (облако), паки в Студии шаблонов. Инструменты проекта принимают `project_id`; начните с `list_projects`.
- **Ресурсы.** `studio://projects`, карточка проекта `studio://projects/<id>`, файлы `studio://projects/<id>/files/<путь>` и PDF сборок.
- **Сценарии (prompts).** `fix_build` (починить сборку), `normcontrol` (разобрать замечания), `review_changes` (описать изменения перед снимком).

### Проекты: создание, люди, проект из облака

- **`create_project`** создаёт проект из шаблона (`pack_id`, `template_id`, `version` из `list_templates`). В локальной Студии нужен `folder`, полный путь к новой папке. В облаке папку выбирает сервер: поля `folder` в схеме нет, а присланное значение не используется.
    - Работает тот же сценарий, что у мастера создания в вебе, с теми же проверками. Авторы передаются в `authors`: `name` (ФИО, обязательно), `group`, `email`, а для командного проекта ещё `topic` (тема автора), `slug` (папка автора) и `managed` (вести ли его комплект здесь, по умолчанию да). Для одного автора по-прежнему хватит `author_name`.
    - Больше одного автора означает командный проект (`staffing: "team"`), как в мастере. `list_templates` показывает, поддерживает ли шаблон команду (`staffing=solo,team`). У каждого ведомого автора нужна тема, ведомым должен быть хотя бы один, `slug` по умолчанию выводится из фамилии (в проекте на `ru` это первое слово ФИО, на `en` последнее, инициалы не в счёт; «Surname, Given» читается по запятой) и должен быть уникальным. У созданного проекта слаг не меняется. Каждый ведомый автор получает свои экземпляры личных документов (`<документ>--<slug>`) в своей папке; общие документы команды ведутся, пока `shared_enabled` не равно `false`.
    - Руководители `supervisor`, `co_supervisor`, `academic_supervisor` необязательны, поля те же, что у `set_project_people`; задать их можно и позже. Группа первого автора, у которого она указана, попадает в `meta.group`, как в мастере.
    - В ответе id проекта, а у командного проекта ещё `slug` авторов: по ним `set_project_people` выбирает автора.
    - Пример: `{"name": "Система учёта", "pack_id": "hse-cs-se", "template_id": "vkr", "version": "2026.1", "kind": "project", "authors": [{"name": "Смирнова Анна", "topic": "Серверная часть"}, {"name": "Петров Борис", "topic": "Клиент"}], "supervisor": {"name": "С. А. Шершаков"}}`.
- **`set_project_people`** меняет научного руководителя (`supervisor`), соруководителя (`co_supervisor`), академического руководителя программы (`academic_supervisor`) и авторов, то есть то, что попадает на титульный лист, в заявку и заявление. Права те же, что в настройках проекта: нужна роль, которой можно менять настройки, а проект должен быть доступен для записи. Значения доходят до PDF при следующей сборке: `common/meta.tex` перегенерируется перед каждой сборкой.
    - У руководителей поля `name` (ФИО), `title` (должность), `degree` (степень или звание), `role` (`university` или `company`). Переданные поля заменяют текущие, остальные остаются; пустая строка очищает должность или степень, пустое `name` убирает человека из проекта.
    - `author` меняет одного автора, не трогая остальных: `name`, `group`, `email`, `topic` (тема в командном проекте), пустая строка очищает группу, e-mail или тему. В командном проекте автора выбирают по `slug` из `get_project`, в одиночном меняется первый автор.
    - `authors` заменяет список целиком: `name`, `group`, `email` и `topic` каждого автора, первый идёт на титульный лист. Чтобы у существующих авторов сохранились тема и комплект командного проекта, передайте их `slug` из `get_project`. Новый автор командного проекта появляется без комплекта (`managed: false`), как при добавлении автора в настройках; комплект включается в настройках проекта.
    - `clear: ["co_supervisor"]` убирает соруководителя (так же `supervisor` и `academic_supervisor`).
    - Пример: `{"supervisor": {"name": "С. А. Шершаков", "degree": "канд. техн. наук"}, "author": {"group": "МПИ251", "email": "ivanov@edu.hse.ru"}}`.
    - Каждое изменение попадает в аудит: в облаке событие `project.people_update` с тем, что было и что стало; локально вызов виден в журнале MCP.
- **`clone_cloud_project`** (только локальная Студия) скачивает проект облачной Студии, как кнопка «Открыть» у облачного проекта в списке. Передайте `url` проекта, например `https://studio.example.org/projects/<id>/`, или `project_id`, если сервер уже подключён (`server` нужен, только когда подключено несколько серверов). Студия использует сохранённый вход на сервер ([подключение](../start/local-from-cloud.md#connect)), токен в аргументах не нужен и в ответ не попадает; адрес с логином или токеном отклоняется. Проект ложится в папку проектов из облака и остаётся связан с сервером. Скачивание идёт в фоне: инструмент ждёт до `wait_s` секунд (по умолчанию 45, не больше 50: больший `wait_s` урезается, иначе клиент MCP оборвёт вызов по своему таймауту), а если не дождался, повторный вызов с теми же аргументами подхватит ту же загрузку. Если проект уже на компьютере, он не скачивается заново.
- **`list_project_fields`** показывает поля проекта из описания шаблона, те же, что в настройках проекта: ключ, подпись, текущее значение, допустимые значения (`options`) или подсказку (`hint`, `example`), обязательность (`required_at`: `create` при создании, `finalize` к сдаче) и документы, где поле печатается (`printed_in`, по исходникам шаблона). В `set_with` указано, каким инструментом поле менять. В командном проекте у полей автора есть `author_values` по `slug`. В `unknown_meta` ключи метаданных, которых шаблон не описывает и не печатает (например группа, записанная в метаданные вместо карточки автора).
- **`set_project_meta`** задаёт поля (`entries`) и удаляет ключи (`unset`): удалённое поле снова берёт значение из шаблона. Пример: `{"entries": {"year": "2027"}, "unset": ["udc"]}`. Права те же, что в настройках проекта.
- **Обновление шаблона** идёт так же, как окно «Обновить шаблон» в настройках проекта.
    - `template_update_status` показывает версию шаблона проекта и доступные обновления: класс (`patch`, `minor`, `major`), что нового и что ломает, например `2026.1.1` и рекомендованное `2026.1.2`.
    - `plan_template_update` с `to_version` показывает, что станет с каждым файлом (`update`, `add`, `delete`, `merge`, `conflict`), какие места подписей из шаблона перейдут на новую версию (`signature_presets`: `updated` и `kept` с причиной `manual`, `route` или `signed`), и отдаёт `fingerprint`. Файлы проекта не меняются.
    - `apply_template_update` с `to_version` и `fingerprint` применяет ровно этот план; если проект за это время изменился, нужен новый план. Конфликты решает `resolutions` (`{"путь": "mine" | "theirs" | "markers"}`), по умолчанию файл остаётся вашим. Перед записью Студия делает снимок истории, отменить обновление можно в настройках проекта.
    - План и применение доступны тому, кто может управлять шаблоном проекта (владелец), и только в проекте, доступном для записи. В облаке применение попадает в аудит (`project.template_update`).

### Синхронизация с git-remote

**`git_sync`** делает то же, что кнопка синхронизации проекта: сохраняет снимок, забирает чужие изменения и отправляет свои. В локальной Студии это синхронизация с облачным сервером (проект из облака) или с подключённым репозиторием, в облаке с подключённым репозиторием. Инструмент ждёт итог до `wait_s` секунд (по умолчанию 45, не больше 50: больший `wait_s` урезается, иначе клиент MCP оборвёт вызов по своему таймауту); если не дождался, ответ `status: running` с `operation_id`, а повторный вызов присоединится к той же синхронизации, как и кнопка, нажатая во время идущей. Долгую синхронизацию начните с `wait_s: 0` или коротким ожиданием и вызывайте снова. В ответе `outcome` (`up_to_date`, `pushed`, `fast_forwarded`, `merged`, `conflicts`), число полученных и отправленных версий и файлы, слитые автоматически. При конфликтах ничего не отправляется и файлы на диске не меняются: в ответе список файлов с конфликтами, а решаются они в Студии кнопкой «Разобрать». Адрес репозитория и доступ к нему в ответ не попадают. Права те же, что у кнопки: нужна роль редактора, а в командном проекте ещё право править весь проект. Инструмент опасный, поэтому по умолчанию выключен.

### Документы: вариант

- **`set_document_variant`** выбирает вариант документа, как переключатель «Форматы документов» в настройках проекта: например, у презентации `pptx`, `beamer` или `reveal`. Передайте `doc_id` из `list_documents` и `variant`; без `variant` инструмент только покажет текущий вариант и допустимые для языка проекта. Неизвестный вариант отклоняется с перечнем допустимых. Смена сбрасывает статус документа в черновик, файлы прежнего варианта остаются. Права те же, что в интерфейсе: запись в документ, а проект должен быть доступен для записи. В облаке смена попадает в аудит событием `document.variant_update`.

### Доступ к проекту (облако)

Те же действия, что в панели «Доступ», с теми же правами; в локальной Студии этих инструментов нет.

- **`list_project_access`** показывает владельца, людей и группы с ролями. Тому, кто ведёт приглашения (владелец или редактор с правом делиться), ещё и ожидающие приглашения.
- **`invite_to_project`** приглашает по `email` с ролью `reader`, `reviewer` или `editor` (не выше своей). `persona` привязывает к роли в проекте: например, руководитель-рецензент это `role: "reviewer"`, `persona: "supervisor"`. Доступ появляется, когда человек примет приглашение. Если почта на сервере не настроена, в ответе `link`: перешлите её сами, как из окна приглашения в интерфейсе. Ссылка одноразовая.
- **`revoke_project_invitation`** отзывает ожидающее приглашение по `invitation_id`, ссылка из письма перестаёт работать.
- **`remove_project_member`** снимает доступ с участника (`member` вида `user:<id>` из `list_project_access`); это может только владелец.

Опасные инструменты (удаление проекта и файла, откат истории, синхронизация с git-remote, подписание комплекта `sign_submission`, отправка на подписание `send_for_signing`) по умолчанию выключены: их включает поимённо администратор (облако) или вы сами (локально). `get_signature_plan` показывает план подписей и чего не хватает. У документа, отправленного на подписание, в плане `pinned` (версия на подписи: `sha256` и `pinned_at`) и `working_differs` (текущая сборка от неё отличается); подписи считаются по версии на подписи. `sign_submission` подписывает ваши слоты в документах контрольной точки ключом из Студии: токену нужно отдельное право «подписание», ключ с паролем через MCP не используется (подпишите в интерфейсе), пароли и ключи в ответ не попадают. Документ, отправленный на подписание по маршруту, инструмент не фиксирует и подписывает только в вашу очередь на подпись; иначе пропускает его с причиной «Документ на подписании по маршруту».

### Сроки контрольных точек

Срок сдачи точки ([Срок сдачи](submit.md#deadline)) задаёт человек или агент, шаблон его не знает.

- **`list_submission_profiles`** отдаёт у каждой точки `deadline` (момент с поясом, по Москве), `deadline_state` (`none`, `upcoming`, `soon`, `today`, `packaged`, `overdue`; `overdue` значит, что пакет точки не собран к сроку), `deadline_hint` (подсказка шаблона, когда срок обычно бывает) и `packaged_at` (последняя сборка пакета к сроку). `get_project` отдаёт сроки всех точек в `deadlines`.
- **`set_checkpoint_deadline`** ставит или снимает срок: `profile_id` из `list_submission_profiles` и `deadline` в ISO 8601 с поясом, например `ГГГГ-ММ-ДДT23:59:00+03:00`; `null` снимает срок. Срок в прошлом поставить можно. Права те же, что у кнопки «Указать срок»: владелец и редактор. Срок маршрута подписания инструмент не меняет. Срок не вход сборки, поэтому `signing_note` к ответу не добавляется. Изменение попадает в аудит (`project.deadline`).

### Маршрут подписания (облако)

Маршрут [«Отправить на подписание»](send-for-signing.md) ведёт только сервер, поэтому в локальной Студии этих инструментов нет. Через MCP можно узнать ход маршрута и отправить документы; согласовать, подписать или вернуть на доработку можно только на странице подписи в интерфейсе: это решение человека.

- **`get_signing_route`** показывает ход маршрута контрольной точки (`profile_id` из `list_submission_profiles`): статус и фазу, шаги с людьми и их состояниями, чья очередь сейчас (`waiting_for`), срок, причину остановки (`stop_reason`: версия на подписи изменилась вне маршрута, подписи или итоговый PDF изменены вне маршрута, участник ушёл, возврат на доработку; у маршрутов, остановленных прежней версией Студии, ещё «документ пересобран»), кто остановил и последние события. У каждого документа `sent` (версия на подписи: SHA-256, дата, раунд) и `changed` (есть изменения после отправки), у маршрута `changed_docs`. Если изменения есть, `changed_hint` подсказывает, какие документы изменились и что новую версию отправляет человек в интерфейсе. У остановленного маршрута `stop_text` объясняет, что случилось и что делать, в том числе когда версия на подписи изменилась вне маршрута. Без `profile_id` отдаёт сводку по всем маршрутам проекта. Доступно тем же, кто видит результаты сборки; комментарий возврата видят управляющие маршрутом и его участники.
- **`list_signing_tasks`** показывает ваши задачи «На подпись» по всем проектам: где сейчас нужно ваше действие (`approve`, `approve_and_sign`, `sign`), от кого, по какой точке и к какому сроку. В `signing_page` адрес страницы подписи: откройте её в Студии.
- **`send_for_signing`** отправляет документы контрольной точки (`profile_id`) на подписание, как кнопка «Отправить на подписание». Берёт сохранённый маршрут точки (черновик, остановленный, возвращённый или отменённый: тогда это «Отправить заново»), а если его нет, создаёт из прежнего маршрута или порядка шаблона. Проверки те же, что у кнопки: документы собраны, у каждого слота есть подписант, ваша подпись готова, документы не изменились между проверкой и отправкой. Сверх того все подписанты должны уже быть в проекте: с человеком, который ещё не принял приглашение, отправьте маршрут из интерфейса. Если что-то мешает, инструмент перечисляет помехи и ничего не отправляет. Если вы подписант первого шага, отправка считается вашим согласованием. Ключом инструмент не подписывает: «Отправить и подписать» остаётся в интерфейсе. Нужна роль, которой можно собирать пакет сдачи (владелец, редактор). Инструмент опасный, поэтому по умолчанию выключен; отправка попадает в аудит событием `signing_route.send`. Идущий или завершённый маршрут инструмент не отправляет: отказ `new_version_in_ui`, при этом ничего не меняется и завершённый маршрут остаётся на контроле. Новая версия сбрасывает согласия других людей, поэтому это решение человека: кнопка «Отправить новую версию» на карточке «Подписание».

Необязательные подписи ([Необязательные подписи и пропуск](send-for-signing.md#optional)) через MCP только читаются. `get_signing_route` отдаёт у слота документа `optional` (необязательна на этой точке), `extra` (слот сверх точки) и статус `skipped`, у участника состояние `skipped`, `skipped_at` и `skippable`, у маршрута подсказку `skip_hint`, когда очередь у человека, которого можно пропустить. `get_signature_plan` показывает у слота `optional` и `skipped` (`at`, `route_id`), у плана `optional_pending`; `package_project` перечисляет необязательные неподписанные слоты как `optional_unsigned`. **Пропустить участника и отметить подпись необязательной через MCP нельзя**, инструментов для этого нет: пропуск отменяет требование подписи и пишет человеку, а ошибку можно исправить только новой отправкой, то есть лишним кругом для людей. Это решение автора в интерфейсе, как отправка новой версии.

Метки даты ([Дата подписания](send-for-signing.md#dates)) через MCP только читаются. `get_signature_plan` отдаёт у слота документа `dates` (страница, формат и `text`: что напечатано сейчас, `null` у пустой метки) и `signed_at` (`at` и `source`: `approval`, дата согласования по маршруту, или `manual`, день, указанный автором), `list_signatures` показывает метки в размещениях. **Ставить, двигать и удалять метки и ручную дату через MCP нельзя**: инструмента размещения подписей нет, а правка меток на документе под маршрутом может сбросить электронные подписи и требует подтверждения человека. Это делается в интерфейсе: на вкладке «Подписи» документа или в блоке «Где подписи» редактора маршрута.

Маршрут из шаблона ([Маршрут из шаблона](send-for-signing.md#preset)) через MCP только читается. `get_signing_route` отдаёт у маршрута `preset`: версию шаблона, шаги шаблона персонами, подписи сверх точки с условием (`extra_slots`), отметки «необязательна» (`optional`), подписи, которые шаблон не добавил по условию (`skipped_by_condition`), и чем маршрут отличается (`differs`: `order`, `slots`, `optional`); `null`, если шаблон маршрута не задаёт. Если маршрут можно править и он отличается, `preset_hint` подсказывает, что вернуть как в шаблоне может автор в интерфейсе. У слота документа `added_by` (`pack`: добавил шаблон, `author`: автор) и `preset_optional`. `get_signature_plan` показывает у слота `place`: `pack` (место из шаблона), `seed` (место, которое Студия поставила из шаблона, а вы не трогали), `manual` (изменено) или `none`. Места по строкам шаблона ([Места подписей по строкам шаблона](send-for-signing.md#anchors)) тоже только читаются: `get_signature_plan` отдаёт у слота `place_source` (`anchor`: место шаблона задано по строке, `mm`: в мм, `null`: ручное или места нет; встало ли место на строку, видно по `anchor_missing` и пометке места в `list_signatures`) и подсказку `anchor_missing`, если в собранном документе нет строки для подписи; `list_signatures` отдаёт пометку места из шаблона целиком, с якорем и сборкой; `get_compile` и `list_compiles` отдают `signature_places_moved`, сколько мест из шаблона сборка подвинула по новой вёрстке, а `compile_document` пишет это строкой в ответе; у `plan_template_update` пункт `after_build: true` значит, что место встанет по строкам шаблона после сборки. `list_submission_profiles` отдаёт у точки `route_preset` с `signing_slots` и тем, выполнено ли условие на людях проекта (`met`). **Вернуть маршрут или место как в шаблоне через MCP нельзя**: это правка маршрута и мест, она делается в интерфейсе. `send_for_signing` применяет шаблон к новому маршруту так же, как кнопка.

Править и собирать документы на подписании через MCP можно: маршрут подписывает версию, снятую при отправке, и правки в неё не попадают. Если инструмент правки или сборки затрагивает документ идущего маршрута, к ответу добавляется `signing_note`: какой документ на подписании, что изменения не попадут в версию на подписи и что новую версию отправляет человек в интерфейсе. Так делают `edit_tex`, `write_file`, `move_file`, `delete_file`, `compile_document`, `set_document_variant`, `set_project_meta`, `set_project_people`, `set_language`, `apply_template_update`, `vcs_restore` и `git_sync`. Общий файл, поля проекта, обновление шаблона, откат истории и синхронизация затрагивают все документы на подписании. Это не отказ, действие выполнено. `package_project` собирает такие документы из версии на подписи и возвращает предупреждение `changed_after_sent`, если текущая сборка новее.

### Студия шаблонов (паки)

Инструменты группы **Студия шаблонов** работают с [паками](../reference/pack.md) в Студии шаблонов: пространства, файлы, проверки, предпросмотр, копия версии и отправка на рассмотрение. Клиент видит их, только если раздел включён и у вас есть доступ к Студии шаблонов (его выдаёт администратор, раздел «Кто может править шаблоны»); в облаке токену нужно ещё право **Студия шаблонов**. Права те же, что в интерфейсе раздела: только свои пространства, выпущенные версии только для чтения.

- **`pack_list_workspaces`** показывает ваши пространства; их `id` нужен остальным инструментам. Версию называют `<пак>/<шаблон>/<версия>` по именам папок, например `hse-cs-sse/coursework/2026.1.7`.
- **`pack_read`** без `version` показывает дерево (паки, шаблоны, версии со статусом, `released` у выпущенных), с `version` модель версии: документы, поля анкеты, слоты подписей, точки сдачи, анкеты, наборы данных, файлы и блок `preview`: что можно собрать в `pack_preview_build` (документы, переключатели `combination` с допустимыми значениями, наборы данных, умолчания, а в `author` сколько авторов даёт каждый `staffing` и какие документы личные).
- **`pack_read_file`** и **`pack_write_file`** читают и записывают файл целиком. `if_match` (etag из чтения) защищает от чужой правки. Запись в выпущенную версию отвечает `version_released`: сначала создайте новую версию. Здесь и у остальных инструментов с `if_match` etag принимается и без кавычек, сверка та же.
- **`pack_scaffold_options`**, **`pack_create`** и **`pack_new_template`** создают пак с первым шаблоном или шаблон в существующем паке, как окна «Новый пак» и «Новый шаблон»: без `copy_from` заготовка «Минимальный» (отчёт по ГОСТ 7.32, два поля анкеты, подпись автора, одна точка сдачи), с `copy_from` копия выбранной версии с новыми id. Варианты для копии и занятые id показывает `pack_scaffold_options`.
- **`pack_lint`** проверяет версию или манифест: находки с файлом и строкой. **`pack_classify`** показывает класс черновика (patch, minor, major) с причинами и годится ли номер. Файл, разделённый на языковые редакции (`x.tex` стал `x.ru.tex` и `x.en.tex`), слитый обратно или оставшийся без одной редакции, это изменение, а не удаление: путь в проекте тот же.
- **`pack_preview_build`** собирает документ версии на тестовых данных на раннере (TeX у себя не нужен) и ждёт итог до `wait_s` секунд (по умолчанию 45, не больше 50: больший `wait_s` урезается, иначе клиент MCP оборвёт вызов по своему таймауту). Долгую сборку начните с `wait_s: 0` или коротким ожиданием, а потом вызывайте снова с `build_id`: инструмент ждёт уже начатую сборку, новую не запускает. `example` и `combination` выбирают набор данных и комбинацию (язык, состав, руководитель, поля). В командной комбинации (`staffing` `team2`, `team3`) у личного документа свой экземпляр на каждого автора: `author` выбирает, чей собирать, номером автора с единицы (`"2"`) или слагом из `authors` ответа; без `author` собирается документ первого автора. Общий документ команды от `author` не зависит, автора вне комбинации отклоняет `preview_invalid`. В ответе `author` (чей документ собран) и `authors` (авторы комбинации: номер, слаг, имя). `cancel: true` с `build_id` останавливает сборку. **`pack_preview_read`** отдаёт текст PDF или журнал сборки.
- **`pack_outcome_inputs`** показывает вводные версии для `pack_outcome`: id (`lang`, `kind`, `staffing`, `supervisor`, `co_supervisor`, `academic_supervisor`, `nda`, `meta.<поле>`, `answer.<анкета>.<поле>`, `variant.<документ>`), допустимые значения, умолчание, разделы, которые вводная меняет (`affects`), число правил, которые её читают (`rules`), и наборы данных. **`pack_outcome`** отвечает, что получится у версии при заданных вводных, без сборки PDF: документы в комплекте с итоговыми именами файлов (у выключенных причина: первое невыполненное условие с фактическим значением), участники, пункты точек сдачи, шаги маршрута и пары «документ и слот», предупреждения (например, шаг ждёт человека, которого нет). Аргумент `scenario` (id файла `scenarios/<id>.yaml` шаблона) кладёт вводные и набор данных сценария под `inputs`. Вводные `inputs` кладутся поверх умолчаний и сценария (`{"kind": "research", "meta.nda": true}`, `true` и `false` это `yes` и `no`); незнакомая вводная или значение вне списка отвечает `inputs_invalid` с полями `field`, `value`, `reason`. `state` выбирает, что читать: `work_tree` (рабочее дерево с несохранёнными правками, по умолчанию), `head` (последний коммит) или `base` (вершина базовой ветки); у папки без git и у новой версии `head` и `base` отвечают `diff_base_unavailable` с `reason` и подсказкой. По умолчанию ответ компактный текст: сводка по разделам, комплект, участники, точки сдачи, маршруты и предупреждения. `include` выбирает разделы (`documents`, `meta`, `forms`, `participants`, `points`, `route`, `checks`, `branches` или `all`); `checks` и `branches` считаются только по запросу. `trace: true` добавляет решения, на которые ссылаются показанные элементы: правило (файл и указатель в манифесте или зашитое в движок), условие, фактические значения и исход. `detail: full` добавляет поля, языки, подписи пунктов, условия пар и правила проверок. `format` выбирает вид ответа: `text` (по умолчанию), `json` (те же разделы структурой) или `both`. Оба инструмента только читают: ничего не записывают, не собирают и не отправляют. Частота та же, что у экрана «Результат»: 20 вызовов в секунду на человека (общий счётчик с интерфейсом), при `outcome_busy` повторите через `retry_after_s`. **`pack_outcome_compare`** сравнивает два результата без сборки PDF: стороны `left` и `right` (каждая: `state`, `scenario`, `example`, `inputs`; не названное берётся из одноимённых верхнеуровневых аргументов) могут быть на одном состоянии (два сценария, два набора вводных) или на двух (рабочее дерево против `head` или `base`: «что я наменял»). Ответ: изменения со знаками `+`, `~`, `-` по разделам и главная причина каждого из трассы (правило с файлом и указателем, исход слева и справа, фактические значения); `detail: full` покажет все причины и все изменения, `sections` оставит нужные разделы, `format` выберет текст, структуру или оба. **`pack_outcome_impact`** отвечает «изменится результат в N из M сценариев»: считает сценарии шаблона на `base` (или `head`) и в рабочем дереве, у каждого статус `changed`, `unchanged` или `error` (сценарий не читается на одной из сторон) и изменения со знаками; `include_atlas: true` добавляет, у скольких строк атласа результат изменится (по умолчанию выключено: на ВКР это секунды). Без базы (`no_git`, `no_base`, `new_version`) оба инструмента отвечают `diff_base_unavailable` с подсказкой. Только чтение; `compare` под тем же правилом частоты, что `pack_outcome` (20 в секунду), `impact` не чаще 6 раз в минуту на человека.
- **`pack_outcome_lint`** запускает линтер результата версии: слоты вне маршрута, шаги без человека, `visible_if` и `when`, которые не выполнятся, обязательные скрытые поля, недостающие переводы и другое (с `jinja: true` на рабочем дереве ещё и шаблоны Jinja, которые падают при рендере). У находки файл, путь, строка, подсказка и комбинация вводных; плюс покрытие правил сценариями и комбинации, которые стоит закрыть новыми. По умолчанию находки названы теми же словами, что на вкладке «Проверка» интерфейса: заголовок, «Как исправить», «Так бывает в n из m сочетаний условий», а в квадратных скобках номер правила, файл и строка; `wording: tech` возвращает тексты правил линтера. `severity` (`error`, `warning`, `info`), `limit`, `state`, `wording`, `format`. Только чтение, частота 6 запросов в минуту ([подробнее](../pack-studio/index.md#outcome-lint)).
- **`pack_set_placement`** ставит места подписей и метки даты в `version.yaml`, как визуальный редактор мест. С `build_id` в ответе якоря сборки: `sign_anchors` и `date_anchors` (id как в шаблоне) и `anchor_views`, те же якоря словами: слот `slot`, часть даты `part`, а у строки автора команды `author__<слаг>` ещё слаг `author` и имя автора `author_name` из набора данных сборки. **`pack_signature_render`** отдаёт картинку страниц PDF сборки предпросмотра с рамками мест поверх (синие подписи, красные с ошибкой, зелёные метки даты, оранжевый пунктир линий якорей, фиолетовые предложенные рамки), **`pack_signature_check`** проверяет места автоматически и предлагает готовые операции для `pack_set_placement` (порядок ниже). Рамка автора команды подписана его именем из набора данных сборки (у старых сборок, которые имён не помнят, слагом).
- **`pack_new_version`**, **`pack_version_notes`** и **`pack_release`** это шаги мастера «Новая версия»: копия базы в черновик, заметки `changes` ru и en, выпуск с записью в реестр. `pack_new_version` с `dry_run: true` ничего не создаёт и показывает версии шаблона, базу по умолчанию и номера по классам. **`pack_version_number`** меняет номер черновика (`action: renumber`, `to` или `update_class`) или переносит правки, сделанные в выпущенной версии мимо Студии, в новую версию (`action: move_edits`), как «Изменить номер» и «Перенести правки в новую версию».
- **`pack_git_status`** показывает рабочую ветку, правки, PR и по `checks: true` статус проверок хостинга. **`pack_propose`** («Отправить на рассмотрение») делает коммит, проверку, push и PR доступом пространства. Инструмент опасный и по умолчанию выключен; без `confirm: true` он ничего не отправляет и только показывает сводку, которую стоит показать человеку.
- **`pack_help`** отвечает, каким инструментом сделать нужное: все `pack_*` по задачам и порядок «создать шаблон и ветку, исправить, проверить, предложить». Начните с него, если не знаете, с чего начать. Остальные инструменты ниже закрывают всё, что есть в разделе «Студия шаблонов», и отвечают компактным текстом или структурой (`format`: `text`, `json`, `both`). Отказы приходят с `code`, `detail` и `hint`: что делать дальше. `topic: team` это раздел формата «Командный проект: строка каждого автора» (якорь `author__<слаг>`), тот же, что в [справочнике пака](../reference/pack.md); на него ссылаются `pack_hints` и предупреждение `pack_lint`.
- **Пространства.** **`pack_list_credentials`** показывает сохранённые доступы git (id, вид, хост, статус; секретов нет). **`pack_workspace_create`** создаёт пространство над репозиторием (`url` и `credential_id` сохранённого доступа; публичный репозиторий без него) или над папкой (`kind: folder`, только локально); клон идёт в фоне, состояние `cloning`, затем `ready`. Токены и пароли через MCP не принимаются ни в аргументах, ни в ответах: новый доступ добавьте в интерфейсе (Настройки, Git). **`pack_workspace_refresh`** это «Обновить базу»: пространство без рабочей ветки и без правок переезжает на свежую базу, при несохранённых правках файлы не трогаются, а в `error` пространства код `refresh_dirty`. **`pack_workspace_delete`** удаляет пространство: без `confirm: true` только описывает последствия. **`pack_official`** и **`pack_official_open`** показывают и открывают официальные паки установки. **`pack_catalog`** подключает папку к каталогу этой Студии (только локально): `check`, `apply` и `disconnect` меняют каталог всей Студии, `apply` и `disconnect` требуют `confirm: true`.
- **Чтение и правка.** **`pack_tree`** дерево файлов (версии со статусом, файлы с `read_only`). **`pack_model`** модель версии с etag манифестов; **`pack_hints`** и **`pack_doc_library`** подсказки редактора и документы-заготовки; **`pack_submission`** профили сдачи, слоты и маршруты подписания: текст показывает записанный маршрут каждой точки сдачи (порядок по шагам, подписи пунктов, слоты сверх точки с условием `when` и отметкой «необязательна»), а с `routes: true` ещё и маршрут в комбинации (шаги людьми из набора данных, кто какую подпись ставит, что условие не пропустило). `profile` (id точки) оставляет в тексте и структуре только одну точку сдачи. **`pack_patch_yaml`** точечно правит YAML по JSON Pointer (`set`, `remove`, `insert` с `-` в конец списка, `move`): комментарии и оформление остаются, `if_match` защищает от чужой правки (`stale_file`), манифесты версии и документов проверяются лоадером и схемой (`model_invalid`, файл не меняется). **`pack_submission_edit`** и **`pack_model_action`** (`rename_field`, `add_document`, `remove_document`, `add_translation`) правят формы версии. **`pack_move_file`** переносит файл, **`pack_delete_file`** удаляет файл или папку (нужен `confirm: true`). **`pack_checks`** правит правила проверки версии формой: без `file` и `config` показывает файлы `checks/*.yaml` с правилами по индексам и `checks_version`; `file` с `ops` (`set_header`, `add_rule`, `set_rule`, `remove_rule`, `move_rule`) правит файл правил, `config` пишет `checks_version` (выключенные категории и правила, `severity_override`). Весь набор правок или ничего, `if_match` по etag. Выпущенная версия отвечает `version_released` с подсказкой `pack_new_version`.
- **Сценарии и результат.** **`pack_scenario_list`**, **`pack_scenario_write`** (создать или поправить, `if_match` по etag, `record_snapshot` принимает снимок), **`pack_scenario_delete`** (мягко, ответ содержит тело удалённого) и **`pack_scenario_run`** (статусы: совпало, изменилось, ошибка, не проверено, и покрытие правил). **`pack_outcome_atlas`** показывает, какие вводные меняют результат (измерения, число исходов, группы; `pin`, `limit`), **`pack_outcome_explain`** отвечает «Почему?» по элементу (цепочка решений, «что если»), **`pack_outcome_matrix`** даёт матрицу сценариев на разделы. Частота: прогон и `explain` как `pack_outcome` (20 в секунду), атлас 6 в минуту, матрица 6 в минуту. `version` у `pack_scenario_write` и `pack_scenario_run` это номер (`2026.2.0`) или `<пак>/<шаблон>/<версия>` того же шаблона. Утверждение `route_pair` с `present: true` может проверять и необязательность подписи: `optional: true` или `false`.
- **Git по шагам.** **`pack_git_branches`**, **`pack_git_branch`** (создать или переключить ветку; `from_base: true` создаёт новую ветку от свежей базовой, а не от текущей вершины: так начинают следующую работу после слияния PR, дерево должно быть чистым, иначе `workspace_dirty`, занятое имя отклоняет `branch_exists`), **`pack_git_commit`** (от профиля человека), **`pack_git_diff`**, **`pack_git_checks`** (ошибки, которые остановят предложение, и CI хостинга), **`pack_git_merge_base`** («Обновить из базы», конфликт отменяет слияние) и **`pack_git_start_over`** («Начать заново»: без `confirm: true` только описывает, что будет потеряно; при несохранённых правках нужен ещё `discard: true`). Полный цикл агента: `pack_git_branch`, правки, `pack_lint`, `pack_outcome` и сценарии, `pack_git_commit`, `pack_git_diff`, `pack_propose`. Длинные списки файлов обрезаются с явной пометкой: `pack_git_status`, `pack_git_commit` и `pack_propose` отдают первые 200 файлов, `files_truncated` и `files_note`; `pack_git_diff` в тексте показывает первые 100, а в `format: json` поле `files` полное.
- **Изменения и следующий шаг.** **`pack_changes`** отвечает то же, что панель «Изменения» и главная кнопка интерфейса: изменённые файлы и версии, ошибки и замечания проверки изменённых мест, нужны ли заметки, запрос на слияние и его проверки, отставание от основной ветки и `next_step` (подпись кнопки, подсказка и инструменты, которые делают шаг, например «Описать изменения» и `pack_version_notes`). `version` выбирает открытую версию, по умолчанию самую новую изменённую. Только чтение.

Отказ приходит ошибкой с полем `code` из списка Студии шаблонов, например `version_released`, `stale_file` (с текущим `etag`), `lint_failed` (с находками) или `fork_required`.

### Места подписей агентом

Агент ставит места подписей пака сам и проверяет, что каждая подпись стоит там, где должна. Человеку остаётся посмотреть на итог.

1. **`pack_preview_build`** собирает документ для нужной ситуации (`scenario` или `combination`): места считаются по этой сборке.
2. **`pack_signature_render`** с `build_id` присылает картинку страниц, где есть места и строки подписей. Мультимодальная модель смотрит на неё сама; в тексте ответа легенда в миллиметрах: слот, страница, рамка, откуда место (своё у документа, общее у слота, на якоре).
3. **`pack_signature_check`** с тем же `build_id` проверяет каждое место: есть ли рамка, на той ли странице, не выходит ли за лист и не ближе 5 мм к краю, не закрывает ли текст (подпись «(подпись)» и подчёркивания можно), не пересекает ли чужие рамки и метки даты, нет ли под ней рисунка или таблицы (доля тёмных пикселей), стоит ли на своей строке подписи. Своя строка это якорь слота из шаблона (`\hseSignAnchor`), иначе линия или ряд подчёркиваний рядом с подписью слота («Научный руководитель ____»). У находок есть текст и числа, у плохих мест предложенная рамка над серединой линии и `suggested_ops`: `bind_anchor`, если у слота есть якорь (место переживёт правку текста), иначе `set_place` с рамкой в миллиметрах.
4. **`pack_set_placement`** с `build_id` применяет `suggested_ops` или своё решение.
5. Снова **`pack_signature_render`** и **`pack_signature_check`**: пересобирать PDF не нужно, места не входят в сборку предпросмотра. Пересборка нужна только после правки текста шаблона.

Проверка видит только то, что есть в PDF: текст, линии, растр. Слот, который в этой ситуации не нужен (например, консультанта нет), проверка всё равно смотрит; соберите предпросмотр для ситуации, где он есть.

### Сборка

**`compile_document`** запускает сборку, как кнопка «Собрать». По умолчанию (`wait: true`) инструмент ждёт итог до 45 секунд: этого меньше, чем клиенты MCP ждут ответа. Если сборка идёт дольше (например, облачная сборка на личном раннере), ответ приходит без ошибки: `status: in_progress` и `compile_id`, а сборка продолжается. С `wait: false` инструмент сразу возвращает `compile_id`. Итог такой сборки показывает `get_compile` с этим `compile_id`, остановить её можно через `cancel_compile`.

## Безопасность

- Клиент действует от имени владельца токена: те же роли в проектах, квоты и лимиты, что в интерфейсе. Чужой проект для него не существует.
- Токену MCP достаточно права **MCP**; к обычному API он доступа не даёт. Отозвать токен можно там же, где он выпущен; он перестаёт действовать сразу. Права токена меняются там же ([Права токена](#scopes)) и тоже действуют сразу.
- Вход по cookie браузера на `/mcp` не принимается.
- Каждый вызов попадает в журнал: инструмент, проект, исход и время, без содержимого аргументов. В облаке журнал на странице **Админка → MCP-сервер** и в общем аудите, локально в настройках MCP.
- Частота вызовов ограничена (по умолчанию 120 в минуту на человека); сборка, запись файлов и git считаются ещё и по своим лимитам.

## Для администратора

На странице **Админка → MCP-сервер**:

- общий переключатель MCP-сервера;
- группы и отдельные инструменты с переключателями; опасные включаются поимённо;
- группа **Администрирование** (пользователи, очередь, раннеры, аудит, журнал писем) выключена по умолчанию; даже включённой она доступна только администратору установки с токеном, где есть право **MCP: администрирование**;
- группа **Студия шаблонов** видна только тем, у кого есть доступ к Студии шаблонов («Кто может править шаблоны»);
- журнал вызовов.

**`admin_runner_fleet`**, **`admin_runner_fleet_upgrade`** и **`admin_runner_fleet_cancel`** дают то же, что окно «Обновить все раннеры» после обновления Студии ([Раннеры](../deploy/runners.md#runner-fleet-upgrade)). `admin_runner_fleet` показывает устаревшие раннеры установки: вид (`docker`, `kubernetes`, `ssh` обновляются отсюда, `manual` только вручную, с причиной в `manual_reason`), версию и число идущих на нём сборок (`running_jobs`); с `batch_id` возвращает ход и итог запуска. `admin_runner_fleet_upgrade` запускает обновление выбранных `runner_ids` или всех, которые можно обновить отсюда (`all: true`), и сразу возвращает запуск; раннеры обновляются по одному, раннер с идущей сборкой ждёт её окончания и пропускается (`busy`), если не освободился за 15 минут. Инструмент опасный: раннеры перезапускаются, поэтому он включается поимённо. `admin_runner_fleet_cancel` останавливает запуск после текущего раннера. Запуск и остановка пишутся в журнал аудита (`runner_fleet.upgrade.start`, `finished`, `cancel`), чтение нет.

**`admin_list_mail_log`** отвечает на вопрос «дошло ли письмо» без страницы **Админка → Письма**: строки журнала писем, новые первыми. Фильтры `recipient` (точный адрес без учёта регистра), `template` (вид письма, например `invite`), `status` (`sent`, `failed`, `not_sent`, `suppressed`) и `since` (дата или момент ISO 8601, без часового пояса считается UTC), не больше 50 строк (`limit`, по умолчанию 20). В строке время, вид письма, адрес и тема, итог, причина, код ответа SMTP, кто вызвал письмо (`cause`: человек, запрос без входа или фоновая задача, и `actor_id`), число попыток (`attempts`), время следующего автоповтора (`next_attempt_at`, пусто, если повторов больше не будет), время последней попытки (`last_attempt_at`) и у ручного повтора id исходного письма (`resent_from_id`); получатель и проект только своими id. Превью письма, имён, ссылок и текста сбоя в ответе нет. Инструмент только читает, и чтение не попадает в аудит.
