# Git-синхронизация

<p class="hds-lede">Проект можно подключить к репозиторию на GitHub, GitLab, Gitea, Bitbucket или своём сервере: версии хранятся и у вас, и там, а коллеги получают их одной кнопкой. Если репозиторий не подключать, ничего не меняется: Студия работает локально, как раньше, и в сеть не ходит.</p>

## Как это устроено { #how }

- **Свой `.git` не трогается.** История Студии живёт в изолированном хранилище `.hse-studio/git`. Репозиторий на сервере подключается именно к нему, ваш собственный `.git` поверх проекта (если он есть) остаётся как был.
- **В репозиторий уходят все версии**, включая автоснимки, которые Студия делает при сборке и перед рискованными действиями. В истории они помечены видом версии, так что отфильтровать их легко.
- **Кнопка «Синхронизировать»** в титлбаре выполняет цикл: снимок ваших правок, получение чужих версий, слияние, отправка. Ничего не перезаписывается силой: ни `force`, ни `rebase`, ни `squash`.
- **Одна ветка.** Синхронизируется одна пара веток: локальная и ветка в репозитории. По умолчанию это главная ветка репозитория, а в пустом репозитории Студия создаёт `main`. Локальная `master` уйдёт в `main`.
- **Теги не отправляются.** Релизы в репозитории вы ставите сами, например для [сборки в CI](#ci).
- **Автор версий — вы.** Перед подключением и клонированием Студия просит представиться: имя и e-mail из этого профиля подписывают версии в репозитории. Раньше версии подписывались общей подписью Студии, такие версии уходят в репозиторий как есть. Если GitHub отклонил адрес как скрытый, укажите в профиле адрес вида `…@users.noreply.github.com`.

## Подключение { #connect }

Откройте значок синхронизации в титлбаре (или Настройки проекта → **Синхронизация**) и нажмите «Подключить репозиторий».

1. **Адрес.** Скопируйте со страницы репозитория: кнопка Code на GitHub, Clone на GitLab. Подходят `https://…` и `git@хост:владелец/репозиторий.git`. Токен внутри адреса не нужен: Студия вырежет его и нигде не сохранит. Ветку можно не указывать.
2. **Доступ.** Токен для https или ключ для ssh, подробно ниже. Рядом с адресом Студия показывает, что за сервер перед ней («GitLab · gitlab.example.org · v17.3»), и дает исправить, если угадала неверно. Выбор запоминается для этого сервера. Открытые репозитории подключаются без токена, только для чтения.
3. **Проверка.** Студия убеждается, что адрес отвечает, доступ принят и репозиторий подходит: он пуст, это тот же проект или проект Студии с общей историей. Другой проект Студии или репозиторий без проекта подключить нельзя.

Перед подключением Студия показывает, что попадёт в репозиторий: число файлов, размер, число версий, подписи, файлы под NDA, самые крупные файлы.

!!! warning "Что окажется в репозитории"
    В репозиторий уходит вся рабочая история: тексты, ответы анкет, PNG подписей, файлы под NDA. Делайте репозиторий **закрытым**. Для проекта с пометкой NDA Студия требует отдельного подтверждения, что репозиторий закрыт и договор разрешает там хранить файлы.

Подключение можно снять в Настройках проекта («Отключить»): локальная история останется, репозиторий на сервере не изменится. Можно заодно удалить сохранённый доступ, если им не пользуются другие проекты.

### Что не попадает в репозиторий { #excluded }

В репозиторий идёт только рабочее: исходники, паспорт проекта, анкеты, подписи, ресурсы. Не отправляются:

- промежуточные файлы LaTeX (`*.aux`, `*.log`, `*.synctex.gz` и другие) и папки `.build/`;
- сгенерированный перед сборкой `common/meta.tex` и другие выходы шаблона, которые пересоздаются сами;
- готовые PDF (если не включено «Хранить готовые PDF в истории» в настройках истории: тогда они едут вместе с проектом);
- журнал документов `.hse-studio/history.json`, метаданные сборок и чатов агента, пакеты сдач, служебные данные обновления шаблона и бэкапы;
- само хранилище `.hse-studio/git`, `.git` и `.gitmodules`.

Файлы Git LFS не поддерживаются: если они есть, Студия отправит только короткие указатели и предупредит. Файл от 95 МБ в истории останавливает подключение заранее, потому что хостинги отказывают около 100 МБ.

## Токены по провайдерам { #tokens }

Токен для https хранится [зашифрованным](#secrets) на вашем компьютере и больше не показывается. Дайте ему **только чтение и запись в репозиторий** и разумный срок. Студия сама определяет провайдера по адресу (самостоятельно установленные серверы распознаются запросом к их API) и открывает страницу выпуска токена в новой вкладке уже с заполненными названием, описанием и правами.

Кнопка **«Создать токен на …»** ведёт на ссылку нужного провайдера, ниже её вид и точные права. Шаги те же: создать, скопировать, вставить в поле токена. Сразу после вставки Студия проверяет токен.

=== "GitHub"

    **Ссылка:** `https://github.com/settings/personal-access-tokens/new` с заполненными названием, описанием, владельцем, сроком (по умолчанию 90 дней) и правом `Contents: Read and write`.

    | Параметр | Значение |
    |---|---|
    | Тип токена | Fine-grained (точный) |
    | Repository access | **Only select repositories** и ваш репозиторий. Эту часть ссылка заполнить не может |
    | Repository permissions | **Contents: Read and write**. `Metadata: Read` включается сам |
    | Для [CI](#ci) дополнительно | **Workflows: Read and write**, иначе файл `.github/workflows` не отправить |

    Если организация требует SSO, откройте токен в настройках GitHub и нажмите Authorize рядом с организацией. Если организация одобряет точные токены, владелец должен одобрить и ваш.

    **Запасная ссылка** (классический токен): `https://github.com/settings/tokens/new?scopes=repo`. Право `repo` широкое, оно открывает все ваши репозитории, поэтому предпочитайте точный токен. Для CI к `repo` нужно `workflow`.

    GitHub Enterprise Server: те же страницы на вашем хосте (`https://<хост>/settings/personal-access-tokens/new`, запасная `/settings/tokens/new`).

=== "GitLab"

    **Ссылка:** `https://<хост>/-/user_settings/personal_access_tokens?scopes=write_repository,read_repository` с заполненными названием и описанием. Работает и для gitlab.com, и для своего сервера.

    | Параметр | Значение |
    |---|---|
    | Права (scopes) | `read_repository` и `write_repository`. **Права `api` не нужно**: оно открывает весь API |
    | Роль в проекте | Developer или выше. В защищённую ветку может писать только Maintainer, если иное не разрешено |
    | Срок | по умолчанию год, администратор сервера может ограничить |

    **Запасная ссылка** для старых серверов GitLab: `https://<хост>/-/profile/personal_access_tokens?scopes=write_repository,read_repository`. Она открывается, если первая вернула «не найдено».

    Своя установка может жить в подпути (`https://хост/gitlab/группа/проект`): Студия берёт корень сайта из адреса репозитория.

=== "Gitea / Forgejo / Codeberg"

    У этих серверов ссылки с заполненными полями нет, шаги такие:

    1. Откройте на сервере Settings → **Applications**.
    2. В блоке Manage Access Tokens введите название, например «HSE Studio».
    3. В выборе прав поставьте **repository: Read and write**. Остальное не нужно.
    4. Нажмите Generate Token и скопируйте значение: позже его не покажут.

    Страница: `https://<хост>/user/settings/applications`. Codeberg тоже распознаётся автоматически.

=== "Bitbucket"

    У Bitbucket Cloud ссылки с заполненными полями нет, шаги такие:

    1. Откройте репозиторий → Repository settings → **Access tokens** (`https://bitbucket.org/<владелец>/<репозиторий>/admin/access-tokens`).
    2. Нажмите Create repository access token, дайте название.
    3. Поставьте право **Repositories: Write** (чтение входит).
    4. Скопируйте токен: Bitbucket показывает его один раз.
    5. В поле токена в Студии откройте «Дополнительно» и впишите имя пользователя `x-token-auth`.

    Токен ограничен одним репозиторием, это удобно. Проверить права токена Студия не может, он покажется «не проверен», а настоящую проверку выполнит первый обмен.

=== "Другой сервер"

    Откройте настройки профиля на сервере и создайте персональный токен (Personal access token) с правом записи в репозиторий. Если сервер требует имя пользователя вместе с токеном, впишите его в «Дополнительно». Студия не угадывает права и проверит доступ настоящим запросом.

### Проверка токена { #token-check }

Кнопка «Проверить» у вставленного (и у сохранённого) токена спрашивает у сервера, чей он, какие у него права и когда истекает. Токен отправляется только на сервер, для которого он создан.

| Результат | Что значит |
|---|---|
| **Достаточно** | Права покрывают чтение и запись. Показываются логин и срок |
| **Слишком узкие** | Отправка не получится. Студия называет, какое право добавить |
| **Слишком широкие** | Например, `api` у GitLab или `admin:*` у GitHub. Работает, но лучше выпустить узкий токен |
| **Не удалось проверить** | Старый сервер, точный токен GitHub (у него нет списка прав в ответе), Bitbucket. Это не ошибка: годность покажет настоящий обмен |

Срок токена, если сервер его назвал, запоминается. В списке доступов видно «истекает через N дней», а просроченный токен переводит синхронизацию в состояние «Нет доступа» с кнопкой «Обновить доступ».

## Ключи ssh { #ssh }

Вместо токена можно подключиться по ssh (`git@хост:владелец/репозиторий.git`). Студия сама создаёт пару Ed25519 на вашем компьютере: закрытая часть хранится [зашифрованной](#secrets) и никуда не отправляется, публичную вы добавляете на сервер. Ваш `~/.ssh`, `ssh-agent` и `~/.ssh/config` Студия не читает и не меняет, поэтому нужен установленный клиент OpenSSH.

Есть два способа добавить публичный ключ:

- **Ключ пользователя**: даёт доступ ко всем репозиториям вашей учётной записи. Проще, но и шире. Страница: GitHub `/settings/keys`, GitLab `/-/user_settings/ssh_keys`, Gitea `/user/settings/keys`, Bitbucket `/account/settings/ssh-keys/`.
- **Deploy key репозитория**: открывает ровно один репозиторий, остальные недоступны. Страница: GitHub `/<владелец>/<репозиторий>/settings/keys/new`, GitLab Settings → Repository → Deploy keys, Gitea Settings → Deploy Keys. **Обязательно включите запись**: «Allow write access» на GitHub, «Grant write permissions to this key» на GitLab, «Enable Write Access» на Gitea. Ключ только для чтения принимает версии, но отправить их не даст. Deploy key GitHub нельзя использовать в двух репозиториях сразу. У Bitbucket ключи репозитория только для чтения, для записи добавьте ключ в профиль.

Публичный ключ и его отпечаток видны в карточке доступа (в Настройках проекта и в Настройки → **Доступ к репозиториям**) в поле с кнопкой копирования, а нужная страница сервера открывается ссылкой.

### Ключ сервера { #host-keys }

При первом ssh-подключении Студия показывает отпечаток ключа сервера (`SHA256:…`). Сверьте его с тем, что публикует сервер: у GitHub и GitLab отпечатки есть в документации, у своего сервера спросите администратора. Кнопка «Доверять серверу» включается с небольшой задержкой, чтобы подтвердить не глядя было труднее. Студия запоминает ключ в **собственном** файле known_hosts, отдельном от системного.

Если ключ позже изменился, подключение останавливается: это может быть подменой сервера. Заменить ключ можно, только если вы сверили новый отпечаток и ввели имя сервера. Список доверенных серверов и кнопка «Забыть» находятся в Настройки → **Доступ к репозиториям**.

## Свой сервер: сертификат TLS { #tls }

Корпоративные серверы часто работают с сертификатом внутреннего центра сертификации или самоподписанным. Студия **не предлагает отключить проверку сертификата**. Вместо этого для каждого сервера есть два безопасных пути, они появляются, когда Студия сообщает «Сертификат сервера не принят» (раздел Настройки → **Доступ к репозиториям**, карточка сервера):

- **Доверять корневому сертификату (CA).** Вставьте сертификат центра сертификации в формате PEM (`-----BEGIN CERTIFICATE-----`) или выберите файл. Допускается до десяти сертификатов цепочки; закрытый ключ вставить нельзя, такой файл отклоняется. Сертификат действует **только для этого сервера** и передаётся git на время его команд, глобальные настройки не меняются. Предпочтительный способ: он переживает продление сертификата самого сервера.
- **Закрепить сертификат сервера.** Студия при первом подключении показывает отпечаток предъявленного сертификата (`SHA256:…`), и вы подтверждаете его, как ключ ssh: сверьте с администратором. Дальше соединение разрешено только с этим сертификатом. После выпуска нового сертификата Студия остановит соединение с сообщением «Сертификат сервера отличается от подтверждённого раньше», и закрепление нужно подтвердить заново.

Обычный `http://` по умолчанию запрещён. Администратор установки может разрешить его переменной `HSE_STUDIO__GIT__ALLOW_INSECURE_HTTP=true`, и тогда каждое подключение отдельно соглашается на него, а в интерфейсе остаётся заметное предупреждение: токен и версии идут по сети открыто.

## Где живут секреты { #secrets }

Всё лежит в [папке данных](../reference/layout.md), в проекте и в репозитории секретов нет.

| Что | Где | Как защищено |
|---|---|---|
| Токены и закрытые ключи ssh | `git/credentials.json` | шифртекст Fernet; название, сервер, срок и отпечаток лежат открыто |
| Ключ шифрования | `secrets/master.keys.json` | файл создаётся при первом сохранённом секрете, права только владельцу (0600). Вместо файла ключ можно дать переменной `HSE_STUDIO__SECRETS__KEY` или `HSE_STUDIO__SECRETS__KEY_FILE` (docker secret): тогда в папке данных его нет |
| Доверенные ключи серверов ssh | `git/known_hosts` | обычный формат OpenSSH, отдельно от системного |
| Свой CA и закреплённые сертификаты | `git/host_settings.json`, `git/trust/` | это публичные сертификаты, но права как у доступов |
| Имя и e-mail автора | `config.json` | обычные настройки |

Токен не попадает в аргументы процессов, логи, настройки хранилища проекта и ответы API. Для git он передаётся переменной окружения одного процесса и привязан к адресу сервера: при подмене адреса или редиректе на другой хост заголовок не уйдёт. Закрытый ключ ssh на время команды лежит во временном файле в новом каталоге с правами только владельца и удаляется сразу после неё.

Шифрование защищает от случайных утечек: копии папки данных, снимка облачной папки, скриншота. От вредоносной программы на этом компьютере и от того, у кого есть вся папка данных вместе с ключом, оно не защищает. Если ключ потерян или заменён, токены станут «не читаются»: введите их заново.

### Что не уходит в экспорт настроек { #export }

Настройки → **Импорт / Экспорт** и файл экспорта (в том числе зашифрованный) **не содержат** токены, ключи ssh, ключ шифрования, доверенные серверы и сертификаты, а также имя и e-mail автора. Файл, отправленный коллеге, не должен нести ваш доступ к репозиториям. При импорте эти данные игнорируются. На новой машине токены вводятся заново.

## Общие папки и облачные диски { #shared-folders }

!!! warning "Не синхронизируйте историю двумя способами сразу"
    Папка проекта внутри Яндекс Диска, Dropbox, OneDrive, Google Диска, iCloud, Nextcloud или под Syncthing живёт под двумя синхронизаторами: диском и git. Диск может разнести по машинам наполовину записанные объекты и блокировки, и история повредится.

Студия узнаёт такие папки по имени каталога и служебным файлам диска, предупреждает при подключении и показывает предупреждение в статусе. Это только предупреждение, подключиться можно. Самое надёжное:

- исключить `.hse-studio/git` из синхронизации диска, **или** хранить проект вне облачной папки, а делиться через git;
- отметить «Понятно», когда вы осознанно оставляете как есть: Студия перестанет напоминать для этого проекта.

Отдельная проблема у **папки данных** в облачном диске: зашифрованные токены и ключ шифрования окажутся в облаке вместе, и шифрование почти ничего не даст. Вынесите файл ключа за пределы диска, путь задаёт `HSE_STUDIO__SECRETS__KEY_FILE`. Раздел Доступ к репозиториям показывает это предупреждение.

## Синхронизация { #sync }

Состояние видно на кнопке синхронизации в титлбаре и в строке состояния:

| Состояние | Значит |
|---|---|
| Синхронизировано | версии у вас и в репозитории совпадают |
| Не отправлено | у вас есть версии, которых нет в репозитории |
| Есть новые изменения | в репозитории появились версии коллег |
| Нужно объединить | новое и у вас, и там: при синхронизации изменения сольются |
| Есть конфликты | одни и те же места изменены у обоих, нужно [выбрать](#conflicts) |
| Нет доступа | токен отозван, просрочен или нет права записи: «Обновить доступ» |
| Нет связи | сервер недоступен, версии на компьютере в безопасности |
| Недоступно | проект только для чтения, не на синхронизируемой ветке, из более новой Студии или нет профиля автора |

- **Фоновая проверка.** Студия сама узнаёт, что коллеги отправили новое, и показывает это на кнопке; в проект при этом ничего не скачивается, пока вы не синхронизируете. По умолчанию раз в пять минут (минимум минута), интервал меняется в Настройки → **Доступ к репозиториям** и для отдельного проекта в его настройках синхронизации; можно выключить. Это личные настройки, коллегам они не передаются. После сбоя связи паузы растут до часа, после отказа в доступе проверки прекращаются, пока вы не обновите доступ.
- **Идущую синхронизацию можно отменить** кнопкой «Отменить» в панели. Идёт она на сервере, окно открытым держать не нужно, итог остаётся в статусе.
- **Идёт сборка документа.** Слияние дожидается окончания сборки (до двух минут), иначе остановится с просьбой повторить.
- **Проект из более новой Студии.** Если версия проекта в репозитории новее вашей Студии, синхронизация ставится на паузу с указанием нужной версии. Обновите Студию.
- **Нет шаблона.** Если после слияния проекту нужен шаблон, которого нет в этой Студии, слияние завершается, а проект открывается только для чтения, как при [обновлении шаблона](../reference/pack.md).

## Конфликты и как они решаются { #conflicts }

Студия сливает файлы сама, и конфликт возникает, только если обе стороны изменили одно и то же место. Правила зависят от типа файла:

| Файл | Как сливается |
|---|---|
| Текст (`.tex`, `.bib`, `.md`, `.sty`, `.cls`) | построчно, по участкам. Правки в разных местах объединяются сами |
| `project.json`, анкеты, подписи, состав шаблона | по полям: конфликт, только если обе стороны изменили одно поле. Личные поля (закрепление проекта, архив, последняя сборка, ваш сертификат подписи) остаются вашими |
| Картинки и другие двоичные файлы | остаётся более новая версия, вторая сохраняется рядом как `имя.conflict-xxxxxxx.расширение`. Конфликтом не считается |
| Готовые PDF | побеждает более новый, копии не остаётся |
| Подписи документа | группой, целиком от одной стороны |
| Файл удалили с одной стороны и изменили с другой | всегда конфликт |

Если без выбора не обойтись, открывается экран «Синхронизация не завершена». В нём список файлов, у каждого видно, что случилось («Одни и те же строки изменены и у тебя, и в репозитории»):

- **Текст** решается по участкам: «Взять моё», «Взять их», «Оба» (в нужном порядке), «Как было» или свой вариант, а также правкой всего файла руками. Видно, как будет выглядеть итог. Метки конфликта (`<<<<<<<`) в файл никогда не попадают, а оставшиеся в ручной правке Студия отклоняет.
- **Поля** (анкеты, паспорт проекта) решаются по полям: моё, их или объединение там, где это имеет смысл.
- **Файл целиком**: моя версия, версия из репозитория или более новая. Для удаления против правки варианты названы прямо: «Оставить файл», «Удалить».

Выбор сохраняется на ходу, окно можно закрыть и вернуться. Пока все файлы не решены, **на диск ничего не пишется**, проект работает как обычно, но отправка заблокирована. Кнопка «Завершить и отправить» включается, когда решено всё: Студия делает слияние и отправляет результат.

- **«Отменить слияние»** возвращает проект к состоянию до синхронизации. Ваши правки не пропадают: они уже сохранены версией в истории.
- Если коллега успел отправить новое в тот же файл, пока вы выбирали, Студия предложит повторить с уже сделанными выборами (по ключам участков). Правки в других файлах этого не вызывают.
- Если слияние сохранилось, а отправить не удалось, конфликтов уже нет: синхронизируйте ещё раз.

## История версий { #history }

В режиме **История** версии из репозитория, отправленные и ещё не отправленные различаются метками. Фильтры: вид версии (в том числе «Синхронизация»), автор, текст, период, а также «не отправлены» и «пришли из репозитория». Слияния показывают файлы относительно вашей ветки. Подробности версии и откат работают так же, как раньше.

## Клонирование { #clone }

Чтобы получить готовый проект с сервера, нажмите «Клонировать проект из git» на экране проектов.

1. **Источник.** Адрес репозитория с доступом или [файл bundle](#bundle). Студия проверяет репозиторий и показывает проект, шаблон, состав и то, как он откроется.
2. **Папка.** Новая или пустая; по умолчанию предлагается в папке проектов. Если папка в облачном диске, будет [предупреждение](#shared-folders).
3. **Загрузка.** История скачивается, шаблон проверяется, проект регистрируется. Операцию можно отменить: скачанное удалится, проект не добавится.

Проект откроется для **полной работы**, **только для чтения** (версия проекта новее Студии или нет шаблона) или **как набор файлов**. Клонирование по адресу сразу подключает репозиторий к проекту, а из файла bundle проект остаётся без удалённого репозитория.

## Сервер HSE Doc Studio как remote { #studio-server }

Проект на сервере HSE Doc Studio можно клонировать в Студию на компьютере или в любой git-клиент. Сервер сам служит репозиторием: отдельный GitHub не нужен.

**Из Студии на компьютере.** «Клонировать проект из git» → **Сервер HSE Doc Studio** → «Войти на сервер». Введите адрес сервера (`https://…`, для своего компьютера подходит `http://localhost`). Студия покажет код вида `BCDF-2345` и откроет страницу подтверждения на сервере: проверьте, что код совпадает, выберите права (чтение или чтение и запись) и нажмите «Разрешить». Студия получит токен сама, покажет ваши проекты на сервере, дальше обычное клонирование. Сервер появится в списке, и следующий проект клонируется без входа.

**Из командной строки.** Настройки проекта на сервере → Синхронизация → **Клонировать с сервера**: там адрес вида `https://studio.hse.ru/git/<id>.git`. Для `git clone` имя пользователя любое, пароль это [токен для git](#git-tokens).

**Что сервер принимает.** Отправлять можно только в текущую ветку проекта и только поверх последних изменений: если на сервере уже есть новые правки (в том числе из браузера), сделайте «Синхронизировать» (fetch и слияние) и отправьте снова. В командном проекте автор отправляет изменения только своей папки и `shared/`, владелец и «правит всё» любые. Служебные файлы `.hse-studio/git`, символьные ссылки, подмодули, файлы больше 95 МБ и проект, сохранённый более новой версией Студии, не принимаются. Отказ виден в Студии блоком «Сервер отклонил отправку» с перечнем путей.

**Права.** Читатель без исходников и гость по ссылке git не получают; ссылка доступа git не открывает вовсе.

### Токены для git { #git-tokens }

Аккаунт на сервере → **Токены** → «Создать токен» → **Для git**: права `git:read` и `git:write` без доступа к API. Такой токен работает только для git: открыть им веб-интерфейс или API нельзя. Токены, выданные Студии при входе по коду, видны там же с пометкой «Устройство» и именем устройства; отзыв закрывает доступ сразу. Срок токена устройства 90 дней, после него войдите заново.

## Обмен файлом без сервера { #bundle }

Когда сервера нет (или нет сети), проектом можно делиться файлом: Настройки проекта → **Обмен файлом**.

- **Выгрузить bundle.** Одна ветка проекта целиком с историей в одном файле `.bundle`. Можно защитить паролем: получится `.bundle.hseenc` (то же шифрование, что у зашифрованного экспорта настроек, файл читается и пишется порциями, подмена или обрезка обнаруживаются). Пароль Студия не хранит и не восстановит, передайте его отдельно от файла. Для проекта с NDA Студия отдельно предупреждает, что без пароля файл прочитает любой.
- **Загрузить bundle.** Версии из файла **объединяются** с проектом так же, как при синхронизации, ваши остаются. Конфликты решаются на том же экране. Ничего никуда не отправляется.
- **Новый проект из файла.** В мастере клонирования выберите вкладку «Файл bundle».

Файл должен содержать полную историю: если он построен на версиях, которых у вас нет, Студия попросит полную выгрузку. Больше двух гигабайт файл не принимается (лимит задаёт администратор установки).

## Сборка документов в CI { #ci }

Студия может подготовить файл для GitHub Actions или GitLab CI, и сервис сам соберёт PDF после изменений. Откройте Настройки проекта → **Обмен файлом** → «Настроить автосборку».

- **Сервис**: GitHub Actions (файл `.github/workflows/hse-studio-build.yml`) или GitLab CI (`.gitlab-ci.yml`).
- **Документы**: все или выбранные.
- **Результат**: артефакты сборки (хранятся ограниченное время) или релиз (PDF прикрепляются к тегу вида `v1.0` и хранятся постоянно).
- **Когда собирать**: на изменения в основной ветке, на тег `v*`, вручную по кнопке.
- **Образ сборки**: по умолчанию тот, что подходит версии вашей Студии, в «Дополнительно» его можно заменить.

Справа виден готовый файл и состояние («новый файл», «уже записан», «отличается»). Нажмите «Записать в проект»: файл попадёт в репозиторий при следующей синхронизации. Существующий отличающийся файл заменяется только с вашей отметкой.

Сборка запускает `hse-doc-studio build` в образе Студии, и ту же команду можно выполнить у себя:

```sh
hse-doc-studio build . --all --out build
hse-doc-studio build . --docs thesis presentation --out build
```

Код выхода 0, если всё собрано, 1 если хотя бы один документ не собрался, 2 при неверных аргументах, не проекте или отсутствии Docker.

!!! note "Что нужно CI"
    - **GitHub.** Для отправки файла в `.github/workflows` токену нужно право Workflows (точный токен) или `workflow` (классический). Публикация релиза отдельного токена не требует, используется встроенный токен запуска.
    - **GitLab.** Раннеру нужен Docker: привилегированный `docker:dind` или проброшенный сокет. Образы Студии и LaTeX скачиваются при первом запуске, он самый долгий.
    - **NDA.** Сборка на внешнем хостинге отправляет содержимое проекта третьим лицам. Студия просит подтвердить это явно.

## Если что-то не так { #troubleshooting }

| Что видите | Что делать |
|---|---|
| «Репозиторий не принял доступ» | токен отозван, просрочен или неверный. Обновите его кнопкой «Обновить доступ» |
| «У доступа нет права записи» | выдайте токену запись (`Contents: Read and write`, `write_repository`) или включите запись для ключа |
| «Нужно разрешить токен для организации» | авторизуйте токен для организации (SSO) в настройках GitHub |
| «Сертификат сервера не принят» | добавьте [свой CA или закрепите сертификат](#tls) |
| «Нужно подтвердить сервер» / «Ключ сервера изменился» | сверьте [отпечаток ключа](#host-keys) с тем, что публикует сервер |
| «Ветка защищена: прямая запись в неё запрещена» | в защищённую ветку писать может не каждая роль. Выберите другую ветку или попросите права |
| «Файл, который сервер не принимает по размеру» | хостинг не принимает файлы около 100 МБ. Уберите такой файл из проекта |
| «Настройки истории выглядят чужими» | в хранилище проекта обнаружены настройки git, созданные не Студией. Подключение остановлено ради безопасности: проверьте происхождение папки |
| «В системе нет ssh» | установите клиент OpenSSH или подключитесь по https с токеном |
