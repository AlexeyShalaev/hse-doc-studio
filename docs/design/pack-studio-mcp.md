# Студия шаблонов целиком через MCP

Статус: дизайн и реализация (22.11.2026), срезы в разделе 8. Основа: `docs/design/mcp.md` (M26, M27),
`docs/design/template-studio.md` (раздел 11), `docs/design/template-studio-outcome.md`, `docs/design/pack-studio-ux.md`.

Цель владельца: ИИ-агент ведёт пак шаблонов от начала до конца без интерфейса, потому что модели так проще. Человеку
остаётся только указать, где стоят подписи, а в идеале и это делает агент: смотрит на картинку страницы с рамками
подписей и проверяет автоматикой, что каждая подпись стоит там, где должна.

## 0. Решения

| № | Решение | Почему |
|---|---|---|
| P1 | Новые тулы идут в ту же группу `packs`, с областью токена `packs`, тем же `PackStudioAccess.require` и `PackStudioToolGate`, что остальные `pack_*` (M26). Запись идёт сценариями маршрутов (`PackVersionService`, `PackChecksFormService`, `PackPreviewService`, `PackPlacesService`): защита выпущенных версий, `If-Match`, замки пространства и коды отказов те же, что у REST. | Агент не получает прав больше человека и не обходит проверки. |
| P2 | Каталог не раздуваем: где можно, новое это параметр существующего тула. Варианты новой версии это `pack_new_version` с `dry_run: true`; что можно собрать (переключатели, наборы данных, варианты) это блок `preview` в `pack_read` с `version`; отмена сборки это `pack_preview_build` с `cancel: true`. Новых тулов пять: `pack_changes`, `pack_checks`, `pack_version_number`, `pack_signature_render`, `pack_signature_check`. | Модель выбирает тул по описанию: пять почти одинаковых тулов путают сильнее одного с понятным параметром. |
| P3 | Находки линтера результата (`pack_outcome_lint`) по умолчанию теми же словами, что вкладка «Проверка, Замечания» интерфейса: заголовок и «Как исправить» по коду правила, названия документов, подписей и точек сдачи из пака, «Так бывает в n из m сочетаний условий». Тексты лежат в `use_cases/mcp/tools/pack_plain_texts.json` (ru, en); тест сверяет их со строками интерфейса (`packSpace/plain.json`, `check.json`, `changes.json`), поэтому слова не разойдутся. `wording: "tech"` возвращает прежний технический вид. Файл, строка и указатель остаются в ответе (агенту они нужны для правки). | Владелец хочет, чтобы агент объяснял человеку то же, что тот видит на экране. |
| P4 | `pack_changes` повторяет панель «Изменения» и главную кнопку (`deriveChangesStatus` и `resolveNextStep` интерфейса) на сервере: подключение, изменённые файлы и версии, ошибки и замечания проверки изменённых мест (не больше трёх), нужны ли заметки, запрос на слияние и его проверки, отставание от основной ветки и следующий шаг с подписью кнопки и тулом, который его делает. «Что изменится у студентов» остаётся отдельным `pack_outcome_impact`: он дорогой (6 в минуту). | Агенту нужен один вызов «что дальше», а не шесть чтений. Сверка копии с основой (`useCopyScan`) не повторяется: изменённые файлы считаются по git как есть (раздел 7). |
| P5 | Картинки: `ToolResult` получает необязательный список `images` (PNG, `mime`), MCP-сервер отдаёт их как `ImageContent` после текста. Встроенный агент картинки пока игнорирует. | Мультимодальный агент смотрит на страницу сам; текст ответа остаётся главным (координаты, находки). |
| P6 | Растровая страница PDF через `pypdfium2` (новая зависимость, раздел 5.4), рисование рамок через Pillow (уже есть через `pyHanko[image-support]`). Текстовый слой и линии страницы тоже из `pypdfium2`. | Других растеризаторов в бэкенде нет; pypdf не рисует страницы. |
| P7 | Места подписей ставятся существующим `pack_set_placement` (те же операции, что визуальный редактор: `set_place`, `bind_anchor`, `make_default`, метки даты). Нового тула записи нет. Проверка (`pack_signature_check`) только читает и предлагает операции для `pack_set_placement` готовым JSON. | Одна запись мест на интерфейс и агента; агент применяет предложение явно. |
| P8 | Чего MCP не делает: админка раздела (включение, выдача права, служебные доступы, официальные паки установки) и включение раздела локально (`PUT /pack-studio/section`). Добавление токена git тоже только в интерфейсе. | M7: админка только сессией; агент не включает себе инструменты; секреты через модель не ходят (M27). |

## 2. Новые и изменённые тулы

Обозначения как в `mcp.md`, раздел 5. Все в группе `packs`, область токена `packs`.

| Тул | Вид | Частота | Что делает |
|---|---|---|---|
| `pack_changes` | R | `git_sync` | Свод панели «Изменения»: подключение, `changed_files`, `changed_in_version`, `changed_elsewhere`, `errors`, `warnings`, `notes_needed`, запрос (`none`, `open` с проверками и прогрессом, `merged`, `closed`), `behind`, `next_step` (`kind`, подпись кнопки, подсказка интерфейса, `tool`). `version`: открытая версия (по умолчанию самая новая изменённая, иначе самый новый черновик). |

| `pack_signature_check` | R | — | Проверка мест подписей сборки (раздел 4) с находками и предложенными операциями для `pack_set_placement`. |

## 3. Жизненный цикл пака агентом

1. Найти: `pack_list_workspaces`, `pack_read` (дерево), `pack_read` с `version` (модель и `preview`).
2. Править копию: `pack_new_version` (`dry_run` покажет номера), `pack_git_branch`.
3. Править: `pack_read_file`, `pack_write_file`, `pack_patch_yaml`, `pack_move_file`, `pack_delete_file`,
   `pack_model_action`, `pack_submission_edit`, `pack_checks`.
4. Результат: `pack_outcome_inputs`, `pack_outcome`, `pack_outcome_explain`, `pack_outcome_compare`.
5. Готовые случаи: `pack_scenario_list`, `pack_scenario_write` (`record_snapshot`: принять текущий результат как
   ожидаемый), `pack_scenario_delete`, `pack_scenario_run`, `pack_outcome_matrix`.
6. Проверка: `pack_lint`, `pack_outcome_lint` (словами интерфейса), `pack_classify`.
7. PDF: `pack_preview_build`, `pack_preview_read`, места подписей (раздел 4).
8. Изменения: `pack_changes` называет следующий шаг; `pack_version_notes`, `pack_version_number`, `pack_release`,
   `pack_git_commit`, `pack_propose` (опасный, сначала `confirm: false`).

## 4. Места подписей агентом

### 4.1. Как места устроены сейчас

Место подписи это запись `version.yaml` версии (template-studio.md, 5.6; signing-route.md, 15.17):

- у слота `signatures.slots[]` общее место `default_placement` и места документов `placements` (документ: место);
- место в мм (`page`, `x_mm`, `y_mm` верх рамки от левого верхнего угла, `width_mm`; высота рамки картинки подписи
  это ширина на пропорцию картинки, по умолчанию 0,4) или на якоре (`anchor`, `align`, `dx_mm`, `dy_mm`,
  `width_mm`, запасное место `fallback` в мм);
- якорь ставит шаблон макросом `\hseSignAnchor{<слот>}` (`common/anchors.tex`), сборка пишет `<doc>.hsepos`,
  Студия переводит его в `anchors.json` рядом с PDF (линии подписей и дат в мм);
- метки даты `default_dates` документа: рамка в мм или на якоре даты `<слот>.<часть>`.

Человек ставит рамки мышкой в редакторе мест («Содержимое», документ, «Подписи»), запись идёт `PATCH .../signatures`
(`PackPlacesService.edit`); у MCP тот же путь: `pack_set_placement`.

### 4.2. Порядок работы агента

1. `pack_preview_build` документа для нужной ситуации (`scenario` или `combination`), дождаться `succeeded`.
2. `pack_signature_render` с `build_id`: страницы, где есть места и строки подписей, с рамками. Агент смотрит
   на картинку.
3. `pack_signature_check` с тем же `build_id`: находки по каждому месту и `suggested_ops`.
4. `pack_set_placement`: применить предложение (`bind_anchor`, если у слота есть якорь в сборке; иначе
   `set_place` с предложенной рамкой) или своё решение.
5. Повторить 2 и 3 (сборку пересобирать не нужно: места не входят в PDF предпросмотра, рамки считаются по той же
   сборке). Пересобрать только после правки текста шаблона.

### 4.3. `pack_signature_render`

Вход: `workspace_id`, `version`, `build_id` (сборка этой версии), `pages` (по умолчанию страницы с рамками и
якорями, не больше четырёх), `slot` (только один слот), `dpi` (по умолчанию 80, от 50 до 150).

Выход: текст с легендой (страница, слот и подпись слота, рамка в мм, откуда место: место документа, общее место
слота, якорь, запасное) и по картинке PNG на страницу. Рамки подписей синие с подписью «<слот>: <подпись>»,
метки даты зелёные, линии якорей пунктиром. Размер картинки ограничен (страница A4 при 80 dpi около 660 на 935 px,
до 250 КБ), чтобы не съедать контекст.

### 4.4. `pack_signature_check`: что проверяется

Для каждого слота, который применим к документу сборки (`applies_to`), по рамке этой сборки (как её посчитала
модель мест, `DocFrame.box`):

| Код | Уровень | Проверка |
|---|---|---|
| `no_place` | ошибка | У слота нет рамки в этой сборке: якорь записи не найден, рамка за краем листа, места нет совсем. |
| `page_out_of_range` | ошибка | Страница рамки больше числа страниц PDF. |
| `outside_page` | ошибка | Рамка выходит за лист. |
| `near_edge` | замечание | Рамка ближе 5 мм к краю листа (поле печати). |
| `overlaps_text` | ошибка (замечание, если закрыт только мелкий текст до 2,6 мм, например «И.О. Фамилия» под строкой) | Рамка закрывает не меньше 40 % площади знаков текстового слоя, кроме подчёркиваний, пробелов и подписей у линии («(подпись)», «Подпись, Дата», «М.П.»). В находке закрытый текст. |
| `overlaps_place` | ошибка | Рамка пересекает рамку другого слота или метку даты на той же странице. |
| `busy_area` | замечание | Растр рамки (страница без рамок): доля не белых пикселей без строк-линий больше 6 %: под подписью картинка, таблица или рисунок, которых нет в текстовом слое. |
| `far_from_line` | замечание | Рядом нет строки подписи: якорь слота, линия рисунка (горизонтальный отрезок от 15 мм тоньше 1 мм), ряд подчёркиваний от 5 знаков, слово «подпись» под линией. Ожидание: линия проходит через нижнюю половину рамки, центр рамки над линией (до половины ширины рамки в сторону). |
| `anchor_available` | подсказка | Место в мм, а в сборке есть якорь с id слота: предлагается `bind_anchor`. |

Какая линия «своя» у слота: сначала якорь с id слота (якорь уже 5 мм это точка отсчёта, а не строка: место на нём
не сверяется с линией, рамку там ставит смещение записи); иначе линия с наибольшим счётом: по два очка за основу
слова из `label` слота рядом (на той же строке левее, выше до 14 мм или в заголовке колонки над линией до 60 мм:
«Научный руководитель» над столбцом строк титула) и очко за подпись «Подпись» под линией; при равном счёте ближняя
к рамке. Без совпадений с подписью слота берётся ближайшая к рамке линия не дальше 60 мм, которую не занимает
рамка другого слота. Пропуск месяца в строке даты («« __ » ______ 2026 г.»: сразу справа год или «г.», сразу слева
«»») строкой подписи не считается, даже если над колонкой подпись слота. Предложение: рамка той же ширины (не шире
линии плюс 10 мм), центр над серединой линии, верх на 10 мм выше линии (как у места на якоре по умолчанию,
`ANCHOR_DEFAULT_DY_MM`). Предложенная рамка сама проверяется на текст и другие рамки; если чисто она не встаёт,
годится рамка, которая закрывает только мелкий текст (это замечание `overlaps_text`, а не ошибка); если и такой нет,
предложения нет.

Ответ: `ok` (нет ошибок), по слоту `status` (`ok`, `warning`, `error`), находки с кодом, текстом и числами,
`suggested_ops` (готовые операции для `pack_set_placement`), общий список `suggested_ops`. Находок текста, не
относящихся к слоту, нет: это не линтер шаблона.

### 4.5. Реализация

- `core/pack_studio/sign_check.py`: чистые типы (`PageLayout`: размер страницы, слова с рамками, линии) и функция
  `check_places` (находки и предложения). Тестируется таблицами без PDF.
- `core/pack_studio/protocols.py`: порт `IPdfPages` (`layout(pdf, page)`, `render(pdf, page, dpi)`, `ink(pdf, page,
  box, dpi)`), адаптер `infra/pack_studio/pdf_pages.py` на `pypdfium2`; рисование рамок `infra/pack_studio/
  place_overlay.py` на Pillow.
- `use_cases/pack_studio/place_check.py`: `PackPlaceCheckService` берёт места и якоря сборки
  (`PackPlacesService.get` с `build_id`, тот же путь, что `GET .../signatures`), PDF сборки (`PackPreviewService.pdf`),
  страницы через порт и собирает ответ.
- Тулы в `use_cases/mcp/tools/pack_signatures.py`.

### 4.6. Новая зависимость `pypdfium2`

`pypdfium2` (Apache-2.0 и BSD-3-Clause, движок PDFium из Chromium) это колёса под Linux x86_64 и aarch64, macOS
и Windows без системных библиотек, около 3 МБ. Даёт растр страницы, текстовый слой с рамками знаков и объекты
страницы (отрезки, прямоугольники). Альтернативы: pypdf не растрирует; Ghostscript и poppler это системные пакеты
(образ, Windows, локальная Студия); PyMuPDF под AGPL. Импорт ленивый, только в адаптере.

### 4.7. Пример на настоящем паке

`hse-cs-sse/coursework/2026.1.6`, сборка в Docker (`texlive/texlive:TL2024-historic`), ситуация «руководитель из
компании, есть консультант»:

- «Заявление о выборе темы» (`topic_application`): четыре места на якорях (`author`, `supervisor`, `co_supervisor`,
  `academic_supervisor`), проверка: ошибок 0, замечаний 0. В черновике 2026.1.7 рамка научного руководителя сдвинута на
  (120, 160) мм, рамка автора на (30, 250) мм: проверка находит `far_from_line` у обоих и `overlaps_text` у автора
  (закрыт текст «руководителя (при внешнем научном руководителе)»), предлагает `set_place` над своими якорями;
  после применения ошибок 0, замечаний 0.
- «Описание проекта» (`project_proposal`): место научного руководителя на якоре-точке в ячейке над строкой даты:
  ошибок 0, замечаний 0.
- Титул отчёта (`report`): у слота `supervisor` нет места для отчёта, поэтому берётся общее место слота (110, 130) мм,
  а оно на названии работы: `overlaps_text` и `far_from_line`, предложена рамка над строкой «Подпись, Дата» в колонке
  «Научный руководитель». В сдачах версии отчёт подписывает только автор, поэтому это скрытый дефект пака: он
  проявится, если руководителя добавят в маршрут. Рамка автора задевает мелкую подпись «И.О. Фамилия» строки выше:
  замечание.

## 5. Права, ошибки, журнал

- Все тулы проходят `CallMcpToolUC`: включение и выключение группы и тула, область `packs`, журнал `mcp.call`,
  частота. Права раздела и защиту выпущенных проверяют сценарии (P1); чужое пространство неотличимо от
  несуществующего.
- Отказы сценариев это ответ с ошибкой `{code, detail, ..., hint}` (`refusal`), коды из
  `contracts/pack-studio/error_codes.json`.
- Новых опасных тулов нет: `pack_version_number` и `pack_checks` правят только черновик в рабочей ветке
  (откат: git или «Сбросить все мои изменения»), рисование и проверка только читают.

## 7. Ограничения

- `pack_changes` не сверяет копию с версией-основой (интерфейс не считает правкой файлы копии, совпавшие с основой):
  сразу после «Править копию» в git число изменённых файлов больше, чем на кнопке интерфейса. Следующий шаг от этого
  не меняется: в черновике без заметок он «Описать изменения».
- Проверка мест знает только то, что видно в PDF: текст, линии, растр. Подпись «не тому человеку» (рамка слота
  руководителя на строке консультанта) ловится только по словам подписи слота рядом с линией.
- Названия условий в словах интерфейса берутся из пака; у встроенных условий без подписи стоит нейтральное «…», как
  у интерфейса без словаря.
