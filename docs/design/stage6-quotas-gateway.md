# Этап 6: полные квоты, ИИ-шлюз, автомасштабирование

Статус: дизайн и реализация на ветке `feat/stage6-quotas-gateway` (от `feat/admin-design`, 01.11.2026). Основа: `docs/design/collaboration.md`, разделы 14.6, 15 и 18 (этап 6); решения личных раннеров: S7 (ключи ИИ личных провайдеров остаются на раннере, сервер не считает их токены).

В этот этап входят три части: квоты по всем видам ресурсов (раздел 2), ИИ-шлюз (раздел 3), автомасштабирование раннеров (раздел 4). Бэкап, мониторинг и несколько реплик api остаются за рамками.

## 0. Решения

| № | Решение | Почему |
|---|---|---|
| Q1 | Виды ресурсов: `storage` (байты), `builds` (сборки за месяц), `ai_tokens_day`, `ai_tokens_month`, `members` (участников в проекте). Одновременность и предел длительности задач остаются как есть (`jobs.*`). | Список из задачи этапа; пара «одновременность и длительность» уже в работе. |
| Q2 | Уровни: умолчание установки, переопределение организации, переопределение пользователя. Приоритет user > org > установка. Для организации два значения, как у `jobs.concurrent_*`: «на участника» (`*_user`, умолчание для её людей) и «на всю организацию» (`*_org`, общий потолок). | Не меняем уже принятую форму `quotas`. |
| Q3 | Платит пользователь и, если проект принадлежит организации, ещё и организация. Списание проходит, только если оба счётчика в пределе. Место и участники считаются по владельцу проекта: личный проект на пользователе, проект организации на организации. | Совпадает с тем, как очередь делит `jobs.org_id` и `user_id`. |
| Q4 | Периоды: календарные сутки и календарный месяц по UTC. Счётчик ключуется началом периода, поэтому сброс это появление новой строки, а не задача по расписанию. Старые строки хранятся 13 месяцев (история) и подчищаются фоновой задачей. | Нет окна гонки на границе периода. |
| Q5 | Место и участники не копятся счётчиком: место это сумма измерений `project_usage` по проектам владельца, участники это число строк `project_members`. Копятся только сборки и токены ИИ (таблица `usage_counters`). | Единый источник правды, нет рассинхрона. |
| Q6 | Мягкий порог один на установку (`quota.warn_percent`, по умолчанию 80). Жёсткий лимит это `hard_limit`. Колонка `quotas.soft_limit` не используется. | Один понятный ползунок в интерфейсе. |
| Q7 | Поведение при исчерпании (`quota.on_exceed`, на установку): `deprioritize` (по умолчанию), `reject`, `warn`. Для сборок `deprioritize` ставит задачу в класс `low` (в конец очереди, работает на свободных раннерах, `JobPriorityClass.low` заложен ранее). Для места, ИИ и участников очереди нет, поэтому `deprioritize` ведёт себя как `reject`. `warn` пропускает, но пишет событие и показывает предупреждение. | Раздел 14.6 дизайна: перед дедлайном студент остаётся с рабочей сборкой. |
| Q8 | Сборка на личном раннере квоту сборок не тратит и не проверяется (D5 личных раннеров). Если задача `personal_first` ушла на общий раннер по таймауту, она не списывается (в учёте остаётся только то, что поставлено на общий маршрут). | Точность до одной сборки не стоит учёта по факту выдачи; ограничение зафиксировано. |
| Q9 | Токены ИИ: `input_tokens + output_tokens` из `TokenUsage`. Кэш-токены Anthropic в сумму не входят. Лимит проверяется перед ходом (по уже накопленному), списывается после; один ход может превысить предел на свою длину (мягкая граница). | Нельзя знать длину ответа до его получения. |
| Q10 | Что считается на сервере: общие (установки) провайдеры. Личный провайдер со своим ключом (`owner_kind=user`, прямой URL) пишется в аудит шлюза, но в квоту токенов не идёт (платит человек). Провайдер через раннер (`runner`) не пишется и не считается вовсе (S7). | Квота защищает общий ресурс. |
| Q11 | Провайдеры организации (`owner_kind=org`) в этап не входят: такого владельца в модели нет. Квоты токенов организации действуют на использование общих провайдеров участниками её проектов. | Отдельный объём работы (CRUD, секреты, интерфейс); вынесено в развилки. |
| Q12 | Админ сбрасывает счётчик владельца за текущий период (`DELETE /api/admin/usage/{kind}/{id}/{resource}`) с записью в аудит. | «Учёт и сброс периода». |
| G1 | Шлюз это декоратор над `IAgentProvider` и `IAIModelLister` (серверный DI). Суммаризатор чата идёт через `IAgentProvider`, поэтому тоже под шлюзом. Локальный режим не меняется. | Один шов, существующие порты, ноль правок в чате. |
| G2 | Отказоустойчивость: ограниченные повторы временных ошибок (только пока в поток ничего не ушло), автомат отказов на провайдера (открывается после N подряд, закрывается через T с одной пробой), переход на другой общий провайдер с той же моделью. | Один упавший провайдер не должен класть чат всей установки. |
| G3 | Аудит: таблица `ai_usage`, строка на вызов (кто, проект, организация, провайдер, модель, токены, исход, длительность). Тел запросов нет (как S5). Отказы по квоте пишутся с исходом `denied`. | Тело промпта содержит исходники, хранить его не нужно. |
| G4 | Белый список моделей: у общего провайдера `models` непуст, значит запрос к модели вне списка отклоняется. | Раздел 15. |
| A1 | Автомасштабирование считает политика (`core/jobs/autoscale.py`), чистая функция без часов и ввода-вывода. Порт `IRunnerOrchestrator` с тремя адаптерами: `off` (только подсказка в админке), `webhook` (HTTP POST с HMAC), `compose` (команда `docker compose up --scale`). Привязки к облаку вендора нет. | Задача этапа. |
| A2 | Политика: минимум, потолок, цель «задач в очереди на слот», порог ожидания старшей задачи, остывание вверх и вниз, окно простоя перед уменьшением. Уменьшение только когда очередь пуста и занято не больше слотов будущего размера. | Не убивать раннер с работой. |
| A3 | Метрики очереди отдаются JSON (`/api/admin/autoscale/metrics`) для внешних скейлеров (KEDA и подобные) независимо от встроенного цикла. | Раздел 14.6: в Kubernetes масштабирует KEDA. |

## 1. Что есть и что меняется

Есть: `jobs.quotas` (одновременность, длительность, переопределения в `quotas`), `QuotaService` с кэшем, предел размера проекта (`ProjectQuotaService`, 413 `project_quota_exceeded`), измерение места в `project_usage`, личные ИИ-провайдеры и ретрансляция, общие провайдеры (`owner_kind=instance`), раннеры и очередь с классами приоритета.

Ошибка (исправляется в первом срезе): `duration_cap` сравнивал `owner_id` пользователя строкой с `str(user_id)`. Переопределение, сохранённое в другом написании UUID (без дефисов, верхний регистр), не находилось, и персональный предел длительности молча не применялся. Теперь ключ пользователя нормализуется через `UUID`, как в `overrides_to_queue_quota`.

## 2. Квоты

### 2.1 Домен (`core/quotas`)

- `QuotaKind`: `storage`, `builds`, `ai_tokens_day`, `ai_tokens_month`, `members`. Описание вида: период (`none`/`day`/`month`), единица, считаем ли счётчиком.
- `QuotaResource` (в `core/jobs/quotas.py`) расширен значениями `storage.bytes_user|org`, `builds.month_user|org`, `ai.tokens_day_user|org`, `ai.tokens_month_user|org`, `members.project_user|org`.
- `QuotaPolicy` (настройки установки): значения по умолчанию на вид (на пользователя и на организацию), `warn_percent`, `on_exceed`. Хранятся в `instance_settings` ключами `quota.<kind>.user`, `quota.<kind>.org`, `quota.warn_percent`, `quota.on_exceed`.
- `resolve_limit(kind, subject, policy, overrides)`: возвращает `ResolvedLimit(hard, source)`, источник `user`, `org`, `installation` или `None` (без лимита).
- `period_of(kind, now)`: границы периода, `reset_at`.
- `QuotaCheck`: `allowed`, `warn`, `exceeded`, `used`, `limit`, `percent`.
- Исключение `QuotaExceededError(kind, scope, used, limit, resets_at)`. HTTP: 429, код `quota_exceeded`, в теле `resource`, `scope`, `used`, `limit`, `resets_at`. Место сохраняет 413 `project_quota_exceeded` для лимита проекта и 413 `owner_storage_exceeded` для лимита владельца.

### 2.2 Хранилище

Миграция `s6_01_quotas_gateway`:

- `quotas.hard_limit` и `soft_limit` становятся `BigInteger` (байты и токены не влезают в 32 бита).
- `usage_counters(owner_kind, owner_id, resource, period_start, used, updated_at)`, PK `(owner_kind, owner_id, resource, period_start)`.
- `ai_usage(id, at, user_id, org_id, project_id, provider_id, provider_owner, model, input_tokens, output_tokens, outcome, error_code, duration_ms)`; индексы по `at`, `(user_id, at)`.

Списание: `INSERT ... ON CONFLICT DO UPDATE SET used = used + :n` (атомарно). Проверка и списание не в одной транзакции (мягкая граница, Q9).

### 2.3 Применение

- **Сборки** (`QueueJobDispatcher._enqueue_routed`): перед постановкой общей задачи `compile` спрашивает `IQuotaGate.check_build(user, org)`. `deprioritize` поднимает `priority_class` до `low`; `reject` бросает `QuotaExceededError`; после постановки `charge`.
- **Место**: `ProjectQuotaService.check_write` дополнительно спрашивает `IOwnerStorageGate` (сумма измерений владельца + прирост против лимита владельца).
- **Участники**: `IMemberQuotaGate.ensure_slot(project_id)` в местах, добавляющих нового участника (добавление владельцем, принятие приглашения, одобрение запроса доступа). Повышение роли существующего участника слот не занимает.
- **ИИ-токены**: шлюз (раздел 3).
- **Сервис использования** (`UsageService`) собирает строки для интерфейса: `UsageLine(kind, used, limit, soft_percent, state, source, resets_at)`.

### 2.4 API

- `GET /api/v1/usage` — строки текущего пользователя и его организаций.
- `GET /api/v1/orgs/{slug}/usage` — строки организации (любой участник).
- `GET|PUT /api/admin/quotas` — умолчания установки (расширено), `GET /api/admin/quotas/overrides`, `PUT|DELETE /api/admin/quotas/overrides/{owner_kind}/{owner_id}/{resource}`.
- `GET /api/admin/usage?owner_kind=&owner_id=` — использование владельца; `GET /api/admin/usage/summary` — итоги установки за период (сборки, токены, место) и верх по потреблению; `DELETE /api/admin/usage/{kind}/{id}/{resource}` — сброс.

Все изменения админа пишутся в аудит (`settings.quotas_update`, `quota.override_set`, `quota.override_delete`, `usage.reset`).

### 2.5 Интерфейс

- Админка, «Квоты»: умолчания по всем видам, поведение при исчерпании, порог предупреждения; таблица переопределений с добавлением, правкой и снятием; поиск владельца; просмотр использования и сброс счётчика.
- Аккаунт, раздел «Использование»: индикаторы (полоса, состояние ок/предупреждение/исчерпано, дата сброса) по пользователю и организациям.
- Страница организации: тот же индикатор по организации.
- Сообщения об отказе: сборка, загрузка файла, добавление участника и чат показывают понятный текст с названием ресурса, цифрами и датой сброса (ru и en).

## 3. ИИ-шлюз

`use_cases/ai_gateway`: `AiGateway` реализует `IAgentProvider` и `IAIModelLister`, оборачивая SDK-реализации.

Поток `run_turn`:

1. Тип провайдера `runner`: сразу во внутренний вызов, без учёта (S7).
2. Белый список моделей общего провайдера (G4).
3. Проверка токеновых квот пользователя и организации проекта (`ai_tokens_day`, `ai_tokens_month`); отказ пишется в `ai_usage` как `denied`.
4. Выбор: автомат отказов выбранного провайдера открыт, значит ищется другой общий провайдер с этой моделью (G2).
5. Вызов с повторами временных ошибок (`APIConnectionError`, таймауты, 429, 5xx), пока в `sink` ничего не ушло; пауза с нарастанием и джиттером.
6. Успех: списание токенов (только общий провайдер, Q10) и строка `ai_usage`. Сбой: строка с исходом `error` и кодом, автомат отказов учитывает сбой.

Список моделей идёт тем же путём без токенов (повторы, автомат, аудит).

Параметры (env, `jobs`-подобная секция `ai_gateway`): число повторов, пауза, порог и время автомата. Состояние автомата в памяти процесса (одна реплика api, как `JobWakeup`).

Админка: список общих провайдеров получает счётчики последних суток (вызовы, токены, ошибки, состояние автомата) через `GET /api/admin/ai-gateway`.

## 4. Автомасштабирование

### 4.1 Метрики

`QueueMetrics`: `queued` (общий маршрут), `queued_oldest_wait_s`, `running`, `runners_online`, `slots_total`, `slots_busy`. Читает `IQueueMetricsReader` (SQL по `jobs` и `runners`). Личные раннеры и личный маршрут не считаются: они не расширяют общий пул.

### 4.2 Политика (`AutoscalePolicy`)

`min_runners`, `max_runners`, `target_queue_per_slot` (по умолчанию 2), `scale_up_wait_s` (30), `cooldown_up_s` (60), `cooldown_down_s` (300), `idle_before_down_s` (300), `step_up` (2), `step_down` (1).

`decide(policy, metrics, state, now)` возвращает `ScaleDecision(current, desired, action, reason)`:

- ниже минимума поднять до минимума (без остывания);
- очередь есть и (глубина на слот выше цели или старшая ждёт дольше порога) и остывание вверх прошло: вверх на `step_up`, не выше потолка;
- очереди нет, простой дольше окна, остывание вниз прошло, занято не больше слотов будущего размера: вниз на `step_down`, не ниже минимума;
- выше потолка опустить до потолка.

### 4.3 Оркестратор

`IRunnerOrchestrator`: `current()` (число или `None`) и `scale_to(n)`. Адаптеры в `infra/runner_scaling`:

- `off`: ничего не вызывает, решение показывается в админке как подсказка.
- `webhook`: `POST` JSON `{event, desired, current, reason, metrics, at}` с заголовком `X-Autoscale-Signature: sha256=<hmac>` (секрет в env `HSE_AUTOSCALE_WEBHOOK_SECRET`), таймаут, повтор не делается (следующий цикл повторит решение).
- `compose`: `docker compose [-p P] [-f F] up -d --no-recreate --scale <service>=N <service>` без shell (argv), с таймаутом.

Цикл (`PeriodicTask`, под лидером) раз в `interval_s`: метрики, решение, при смене числа вызов оркестратора, запись состояния (последнее решение, остывания) и аудит смены. Состояние остывания хранится в `instance_settings` (`autoscale.last_up_at`, `autoscale.last_down_at`), чтобы не терять его при рестарте.

Админка, «Раннеры»: карточка автомасштабирования (режим, границы, метрики сейчас, последнее решение, оставшееся остывание).

API: `GET|PUT /api/admin/autoscale`, `GET /api/admin/autoscale/metrics`, `POST /api/admin/autoscale/evaluate` (сухой расчёт без вызова).

## 5. Порядок срезов

1. Исправление `duration_cap` и тест.
2. Домен квот (`core/quotas`), чистые тесты.
3. Миграция и репозитории.
4. Сервис квот, применение (сборки, место, участники), ошибки HTTP.
5. API квот, использование, переопределения, сброс.
6. Шлюз ИИ: ядро, повторы, автомат, аудит, учёт.
7. Автомасштабирование: политика, метрики, оркестраторы, цикл, API.
8. Интерфейс: админка, аккаунт, организация, тексты ошибок.
9. Живая проверка на отдельном стеке, заметки к релизу.

## 6. Развилки для владельца продукта

- Провайдеры организации (Q11) не сделаны.
- Квота сборок не учитывает откат личного раннера на общий (Q8).
- Токены считаются без кэш-токенов Anthropic (Q9).
- Поведение при исчерпании одно на установку, не на ресурс.
- Уменьшение числа раннеров в compose выбирает контейнер сам; корректное завершение держится на SIGTERM раннера (`/offline`), задача прерванного раннера вернётся в очередь по heartbeat.
