# Жизненный цикл данных: реестр самороста и политики хранения

Цель владельца продукта: установка живёт годами без разработчика и девопса. Всё, что растёт само, имеет умолчание по сроку, настройку в админке («Хранение данных», `/admin/data`) и фоновую очистку. Реестр политик один: `services/api/hse_doc_studio/core/lifecycle/policies.py`.

## 1. Аудит: что растёт само

Составлен по коду и схеме БД ветки `feat/admin-design` (миграции до `s5_01_review`). Скорость роста дана порядком величины для установки на сотни людей; «было» означает состояние до этой ветки.

### Объектное хранилище и диск

| Источник | Было | Стало |
|---|---|---|
| выходы задач в S3 (`artifacts/…/jobs`, `announce/…`) | `job_retention` убирает выходы без владельца | без изменений |

| временные каталоги (`hse-studio-push-hooks-*`) | один каталог на процесс в `/tmp`, внутри контейнера | без изменений: исчезает с контейнером |

### Логи и служебное

| Источник | Было | Стало |
|---|---|---|
| логи контейнеров (`json-file`) | **без лимитов** в `deploy/server`, `deploy/all-in-one` | `max-size=10m`, `max-file=5` на каждый контейнер, меняется `LOG_MAX_SIZE`/`LOG_MAX_FILE` |
| логи процесса api | только stdout, отдельных файлов нет | ограничены ротацией контейнера |
| логи nginx/прокси | прокси в поставку не входит | зона оператора; рекомендация в документации |
| WAL, autovacuum, раздувание Postgres | умолчания Postgres | журналы только добавляются и чистятся отбрасыванием партиций, поэтому раздувания не дают; следить за размером базы (метрика, порог) |
| метрики Prometheus | в памяти процесса, метки по шаблону маршрута | рост ограничен |
| rate-limit и egress | в памяти процесса | рост ограничен |
| heartbeat раннеров | обновление строки на месте (`runners`, `job_runner_polls`) | роста нет |

## 2. Дизайн

**Реестр.** `LifecyclePolicy`: ключ, группа, стратегия, границы срока (по умолчанию, минимум, максимум), таблицы, признаки `run_now` и `protected`. Стратегии: `partition_drop`, `delete_batches`, `file_sweep` (выполняет движок), `own_task` (своя периодическая задача, итог читается из раннера фоновых задач), `on_write`, `infra`.

**Срок.** Правка админа в границах реестра, иначе умолчание окружения (для аудита, ИИ-журнала и задач это прежние `*_RETENTION_DAYS`, зажатые в границы), иначе умолчание реестра. Значение вне границ игнорируется. `0` в окружении значит «хранить без срока» (прежнее поведение `audit_retention_days=0`); админ без правки получает это же, но может задать срок. Нижняя граница аудита 90 дней, снять срок из интерфейса нельзя. Ключи настроек: `retention.<ключ>_days` в `instance_settings`.

**Движок.** `use_cases/lifecycle/engine.py`. Периодическая задача `data_lifecycle` под лидерским замком (`BackgroundTaskRunner`), раз в час, на старте тоже. Каждый источник чистится независимо: сбой одного записывается и не мешает остальным. Нагрузка ограничена пачкой (`batch_size`, 2000), паузой между пачками (50 мс) и бюджетом времени на источник (120 с); недоделанное идёт на следующем тике. Всё идемпотентно: повторное и параллельное удаление ничего не находит. Статистика последнего прогона в `lifecycle_runs` (время, длительность, удалено, ошибка, всего).

**«Освободить место».** Все ручные источники движка одним прогоном на сервере (`use_cases/lifecycle/sweep.py`, таблица `lifecycle_sweeps`, `/api/admin/data-lifecycle/sweep*`): предпросмотр считает записи старше срока с потолком 100 000 (`count_expired` источника), каждый шаг это `run_one`. Подробности в `storage-cleanup.md`, 5.4 и 9.2.

**Партиционирование.** `audit_log` и `ai_usage` разрезаны `RANGE (at)` по месяцам (UTC). Составляющие: `<таблица>_legacy` (бывшая таблица, диапазон `MINVALUE..граница`), `<таблица>_pYYYYMM` и `<таблица>_default` (страховка от записи с дикой датой). Первичный ключ `(id, at)` (требование Postgres); `id` по-прежнему уникален за счёт последовательности. Права роли приложения SELECT/INSERT не меняются: создание и отбрасывание партиций делают функции `SECURITY DEFINER` `lifecycle_ensure_partitions` и `lifecycle_drop_partitions_before`, открытые только для `audit_log` и `ai_usage`. Построчный DELETE для аудита остаётся только внутри `audit_log_purge_batch`; триггеры «только дозапись» действуют на каждой партиции, `DROP` партиции не DELETE и триггеров не вызывает. Будущие партиции создаются на старте любого экземпляра и на каждом прогоне (на 3 месяца вперёд).

**Миграция без простоя** (`lc_02_partition_logs`). Строки не копируются: старая таблица переименовывается в `_legacy` и подключается как партиция (`ATTACH PARTITION`). Это метаданные плюс две проходы по таблице: сборка уникального индекса `(id, at)` и проверка диапазона при подключении. Пока они идут, вставки ждут (около секунды на миллион строк), чтение идёт. Для очень больших журналов оператор заранее строит индекс без блокировки: `CREATE UNIQUE INDEX CONCURRENTLY audit_log_idat_uq ON audit_log (id, at)` (то же для `ai_usage`); миграция его увидит. Граница legacy это следующий месяц (не раньше месяца самой поздней строки): до неё новые записи ложатся в legacy, строки старше срока внутри legacy стираются пачками, а сама партиция отбрасывается, когда вся вышла за срок. Откат (`downgrade`) копирует строки из партиций в обычную таблицу, возвращает последовательность, индексы и триггеры; долго на больших таблицах, зато без потерь (тест на строках).

**Не-Postgres.** Серверный режим работает только на Postgres (SQLite в нём нет), поэтому запасной путь не нужен: партиции есть везде, где они оправданы, а таблицы без партиций чистятся `DELETE ... LIMIT` пачками. Локальный режим данных этого рода не копит.

**Контроль места.** `StorageGuard` (задача `storage_guard`, раз в 5 минут) меряет тома данных, проектов и объектов (`shutil.disk_usage`, одинаковые тома склеиваются) и размер базы (`pg_database_size`; ёмкость базы api не видит, поэтому доля считается только при заданном `HSE_STUDIO__LIFECYCLE__DB_SIZE_LIMIT_BYTES`). Пороги по умолчанию 80% и 90%, меняются в админке (50..95 и 60..99, критический строго выше). Предупреждение приходит каждому действующему админу во «Входящие» (вид `system_alert`, ключ дедупликации с датой: раз в сутки поднимается заново, пока проблема есть). При критическом уровне включается безопасный режим: `StorageSafeModeMiddleware` отвечает `507 storage_critical` на POST/PUT/PATCH с телом больше 1 МБ или без длины, кроме `/api/admin`, `/api/runner`, входа, `/health`, `/metrics`; мелкие правки идут, админ может чистить. Режим снимается сам, когда уровень падает.

**Метрики `/metrics`.** `hse_lifecycle_source_bytes|rows{source}`, `hse_lifecycle_removed_total`, `hse_lifecycle_partitions_dropped_total`, `hse_lifecycle_errors_total`, `hse_lifecycle_last_run_timestamp_seconds`, `hse_lifecycle_sweeps_total{status}` (прогоны «Освободить место», `storage-cleanup.md`), `hse_storage_used_bytes|total_bytes|used_ratio{volume}`, `hse_storage_safe_mode`.

**Что настраивается и что фиксировано.**

| Настраивается админом | Фиксировано |
|---|---|
| сроки `audit_log`, `ai_usage`, `jobs`, `notifications`, `mail_log`, `collab_requests`, `share_links`, `collab_state` | гостевые сессии (7 суток), сессии и токены по истечению, записи сборок (50), PDF-версии, чаты, блобы, сироты, удалённые проекты (env) |
| пороги диска 80/90 | ротация логов контейнеров (compose, env) |
| «очистить сейчас» для всех источников движка, кроме аудита | аудит вручную не чистится |

## 3. Развилки и решения по умолчанию

- Срок из env задаёт умолчание, правка админа его перекрывает (прежнее правило «env побеждает» невозможно: у `audit_retention_days` есть умолчание).
- Аудит нельзя хранить меньше 90 дней и нельзя выключить из интерфейса; выключить может только оператор через `AUDIT_RETENTION_DAYS=0`.
- Источники с собственной задачей (`auth_cleanup`, `project_purge`, `blob_gc`, `orphan_gc`, `quota_housekeeping`) не переписаны: реестр показывает их размер и итог.
- Таблицы `compile_records`, `chat_*`, `project_artifacts` ограничены числом записей, а не временем: срок по времени не вводили.
- Уведомление `system_alert` общее для системных сообщений (его можно использовать другим срезам).

## 4. Проверка на живом стенде

Стенд `scripts/dev/server-stack/stack.sh` (проект `hse-lifecycle`, порт 17333, образ с тегом `lifecycle`), данные засеяны SQL: 320 тыс. строк аудита (возраст до 700 дней, часть вперёд на 80 дней), 100 тыс. строк журнала ИИ, 200 уведомлений, 50 просроченных гостевых сессий.

- Миграция на старте создала `audit_log_legacy`, `audit_log_p202612..p202703` и `audit_log_default`.
- «Очистить сейчас» через `POST /api/admin/data-lifecycle/{key}/run`: `ai_usage` стёр 77 564 строки за 3,5 с, `notifications` 111, `guest_sessions` 44; аудит отвечает 403.
- Плановая задача при старте стёрла из аудита 143 302 строки старше 365 дней пачками за 13 с и записала событие `audit.purged`.
- Отбрасывание партиций: прогон с границей на 62 дня вперёд убрал `audit_log_legacy` и `audit_log_p202612`: источник уменьшился с 99,5 МБ до 1,8 МБ мгновенным `DROP`, без построчного удаления.
- Срок уведомлений 120 дней задан через `PUT .../retention/notifications`, слишком малый срок аудита (30) отвергнут `422 input_invalid`.
- Пороги 50/60 при занятом томе 62%: уровень `critical`, безопасный режим включён; загрузка 3 МБ в `/projects/import` получила `507 storage_critical`, мелкий `PATCH /account` прошёл `200`; админу пришло `system_alert`; пороги возвращены 80/90.
- `/metrics` отдаёт `hse_lifecycle_*`, `hse_storage_used_ratio{volume="data+projects"} 0.6206`, `hse_storage_safe_mode`.
- Ротация логов: у всех контейнеров стенда `json-file`, `max-size=10m`, `max-file=5`; контрольный контейнер с `max-size=100k`, `max-file=3` написал 2 МБ и сохранил около 95 КБ.
