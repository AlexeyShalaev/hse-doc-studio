# Этап 5: ревью-комментарии и совместная правка в реальном времени

Продолжает `collaboration.md` (разделы 7, 14.5, 16). Основа: серверный режим с ролями, ссылками, приглашениями,
сервером как git-remote и автосинком (`local-sync.md`). Только серверный режим: у локальной Студии один человек.

## 1. Решения

| Развилка | Решение | Почему |
|---|---|---|
| Что комментируем | Фрагмент текста исходника (`.tex`, `.md`, любой текстовый файл). Из превью PDF тред тоже по возможности привязывается к исходнику, иначе к месту в PDF (раздел 2.4) | Тред живёт в исходнике: его видят и редактор, и превью |
| Привязка | Цитата с контекстом (prefix, suffix) и подсказкой смещений, как TextQuoteSelector. Сервер её не трактует, разрешает клиент по живому тексту | Переживает любые правки, в том числе пришедшие из git и от агента; не зависит от Yjs, поэтому работает и без совместной сессии |
| Если цитата правится | 1) цитата целиком; 2) цитата рядом с подсказкой; 3) по контексту: что осталось между prefix и suffix; 4) не найдено: тред «оторван», показывается с последней цитатой | Правка слова внутри комментируемой фразы не обрывает тред |
| Кто комментирует | Действие `COMMENT`: рецензент, редактор, владелец; гость по ссылке с такой ролью (имя «Гость: …») | Матрица 7.1 |
| Кто читает треды | Тот, кто читает исходники (`SOURCES_READ`) | Цитата это кусок исходника |
| Кто закрывает/открывает | Автор треда или тот, кто вправе править файл | Рецензент закрывает свои замечания, редактор разбирает все |
| Кто правит/удаляет | Править комментарий только автор. Удалить: автор или владелец. Корневой комментарий уносит тред; автор не удаляет тред, где ответили другие | Нельзя стирать чужой разговор |
| Упоминания | `@имя` из людей проекта (прямые участники и владелец); сервер отбрасывает тех, кто не видит исходники, и гостей. Группы не раскрываются | Упоминание не подтверждает постороннему, что человек в проекте |
| Уведомления | Новые виды «Входящих»: `review_thread` (владельцу и редакторам), `review_reply` (участникам треда), `review_mention`, `review_resolved` (автору треда). Повторы в одном треде схлопываются ключом | Письма не шлём: MAILED_KINDS не меняется |
| Совместная правка | Yjs, один документ на файл, на сервере `pycrdt` внутри api, клиент `y-codemirror.next` | Отдельный Node (Hocuspocus) удвоил бы сервис; pycrdt реализует тот же протокол |
| Источник истины | Файл проекта. Комната отдаёт текст на диск через общий путь сохранения (замок папки, квота, правочный коммит) | git, сборка, агент и синхронизация видят обычный файл |
| Входящий push при открытой сессии | Превращается в операции над `Y.Text` (трёхстороннее слияние), а не блокируется | Решение «или блокировать» из collaboration.md отвергнуто: блокировка push ломает автосинк |
| Читатель | Читает живой текст и видит курсоры, не пишет: обновления от него отбрасываются сервером | Защита на сервере, а не только в интерфейсе |

## 2. Ревью-комментарии

### 2.1 Модель

`review_threads` (id, project_id, path, anchor jsonb, status open|resolved, автор, время, кто закрыл) и
`review_comments` (id, thread_id, автор, имя на момент события, текст до 4000 знаков, упоминания, правка).
Автор это id человека или гостевой сессии (`gs_…`), поэтому без внешнего ключа. Предел 500 тредов на файл.

### 2.2 API (`/api/v1/projects/{id}/review/…`)

| Метод и путь | Действие |
|---|---|
| `GET threads?path=&status=` | список с комментариями |
| `POST threads` | новый тред: путь, цитата с контекстом, текст, упоминания |
| `POST threads/{id}/comments` | ответ |
| `PUT threads/{id}/status` | `open` или `resolved` |
| `PATCH comments/{id}` / `DELETE comments/{id}` | править / удалить |
| `GET mentions?q=` | люди для автодополнения `@` |

Ошибки: `empty_body`, `body_too_long`, `empty_quote`, `quote_too_long` (422); `anchor_stale` (цитаты в файле уже
нет), `too_many_threads`, `thread_has_replies` (409). Маршруты занесены в `ROUTE_ACTIONS`; путь файла проверяет сценарий.

### 2.3 Клиент

Панель «Комментарии» в редакторе исходников, подсветка фрагментов в CodeMirror, кнопка «Комментировать» на
выделении (и Ctrl/Cmd+Shift+M), ответы, «Решить/Открыть», фильтр «Открытые/Все». Ссылка из «Входящих» ведёт к файлу и треду
(`?file=…&thread=…`). В сессии совместной правки панель обновляется событием `review` от сервера, без неё опросом.

### 2.4 Комментарии из превью PDF

Научрук и рецензенты читают PDF, а не LaTeX. Комментарий оставляется прямо из превью: выделить текст, нажать
«Комментировать».

| Развилка | Решение | Почему |
|---|---|---|
| Где кнопка | В панели выделения превью рядом со «Спросить ИИ», «В исходнике», «Копировать». Видна тем, кому можно `COMMENT` | Тот же жест, что у остальных действий над выделением |
| К чему привязан тред | Если место нашлось в исходнике, это обычный тред с цитатой из исходника (`kind: "text"`), он сразу виден в редакторе. Иначе тред привязан к PDF (`kind: "pdf"`) | Исходниковый тред переживает пересборку и правки, PDF-якорь нужен только как запасной путь |
| Как ищется исходник | Сервер: обратный SyncTeX по центру первого и последнего прямоугольника выделения даёт файл и строку; в окне ±40 строк ищется выделенный текст. Сравнение по «видимому» тексту: из LaTeX убраны комментарии, имена команд, аргументы `\cite`, `\ref`, `\label` и подобных, имена окружений и спецификации таблиц; обе стороны разложены NFKD без диакритики (лигатуры, `ё` и `е`), без регистра, остаются только буквы и цифры (переносы, пробелы, кавычки и тире не мешают). Текст сносок ищется отдельно от тела: в теле от сноски остался только знак. Номер раздела и «Таблица 1.1 –» в начале выделения при втором заходе отбрасываются | Так совпадают `иссле-\nдование` и `исследование`, `ﬁ` и `fi`, `\textbf{важно}` и «важно», `[3]` и `\cite{knuth}` |
| Когда находка надёжна | Точное совпадение по буквам и цифрам не короче 4 знаков, ближайшее к строке SyncTeX; или нечёткое (доля совпадения от 0,85, `difflib` по затравкам) при длине от 12 знаков; вне окна только точное и единственное в файле. Иначе PDF-якорь. На тестах: случайные выделения из настоящей ВКР (105 страниц, XeLaTeX) находятся в 97% случаев, из документов шаблонов Студии (тело текста) в 94%, ни одного не на том месте; промахи это текст из макросов (титул, рамка ГОСТ, `\ProjectName`) | Лучше честный PDF-якорь, чем тред не на том месте |
| Документ без исходника | Загруженный PDF, офисный документ или сборка без SyncTeX: сразу PDF-якорь | Больше не к чему привязать |
| Путь PDF-треда | `path` это путь PDF, который показывает превью (выход сборки или PDF-предпросмотр офисного файла) | Лимит тредов на файл и фильтр по пути работают как раньше |
| Метки в превью | На поле страницы значок у каждого треда документа. Исходниковый тред: цитата ищется в текущем тексте файла (как в редакторе), строка идёт в прямой SyncTeX, клиент уточняет место поиском видимого текста цитаты на этой странице. PDF-тред: по `rects`, если PDF тот же (`build_sha`), иначе поиск `text` на той же странице и соседних (±2) | Метка там, где фрагмент сейчас, а не где был |
| PDF пересобран, места нет | Тред остаётся в списке с пометкой «Место изменилось», метки нет | Не теряем замечание |
| Какие треды видит превью | PDF-треды этого документа и исходниковые треды файлов, из которых он собран (входные файлы SyncTeX) | Комментарии к другим документам не мешают |
| Права | Как у тредов в редакторе: читает тот, кто читает исходники (`SOURCES_READ`, в том числе PDF-треды); пишет роль с `COMMENT` (рецензент, редактор, владелец, гость по ссылке с такой ролью); закрывает автор или тот, кто правит файл треда | Одна политика для всех тредов |
| Телефон | Панель выделения слушает `selectionchange`, а не только отпускание мыши: на таче выделение делается долгим нажатием и ручками, `mouseup` не приходит. На таче панель прижата к низу просмотра во всю ширину: системное меню выделения встаёт над текстом, а четыре кнопки не уходят за край узкого экрана. Боковая панель превью на телефоне это шторка снизу (выбранный фрагмент прокручивается к верху и виден над ней); в редакторе панель по-прежнему накрывает текст | Работает без своей «долгой кнопки»: долгое нажатие уже выделяет слово |
| «Входящие» | Упоминания и уведомления как у обычных тредов. В уведомлении PDF-треда есть `doc_id`, ссылка ведёт в превью документа к треду: `/projects/{id}/documents/{doc}?thread=…` | Человек попадает туда, где оставлен комментарий |
| MCP | `list_review_threads` отдаёт `kind`, у PDF-треда `doc_id`, `page`, `text` (он же `quote`). `create_review_thread` остаётся по исходнику | У агента есть исходники и текст PDF без координат: цитата из исходника точнее, тред сразу виден и в редакторе, и в превью через SyncTeX |

#### Контракт

Якорь треда теперь различается полем `kind`:

- `{kind: "text", quote, prefix, suffix, start, end}`: прежний, `kind` в запросе можно не передавать;
- `{kind: "pdf", doc_id, page, rects: [{x, y, width, height}], text, build_sha}`: координаты в пунктах PDF от левого
  верхнего угла страницы, до 64 прямоугольников; `text` выделенный текст до 2000 знаков; `build_sha` sha256 PDF на
  момент создания (ставит сервер).

| Метод и путь | Действие |
|---|---|
| `POST review/pdf-threads` | тред из превью: `{doc_id, page, rects, text, body, mentions}`. Ответ `ThreadModel` (якорь `text` или `pdf`) |
| `GET review/documents/{doc_id}` | треды документа и места на текущем PDF: `{build_sha, items: [{thread, place}]}`, `place` это `{page, rects, text, exact}` или `null` (место не найдено) |

`exact: true` значит «прямоугольники точные» (PDF-тред на том же PDF); иначе клиент уточняет место поиском `text`.
Права маршрутов: `COMMENT` и `SOURCES_READ`, документ и файлы проверяет сценарий.

Ошибки: `empty_body`, `body_too_long`, `empty_quote` (пустой текст), `quote_too_long`, `bad_rects` (нет
прямоугольников, больше 64, страница меньше 1) (422); `pdf_missing` (у документа нет собранного PDF),
`too_many_threads` (409); документа нет (404).

#### Интерфейс (RU)

- Кнопка в панели выделения: «Комментировать».
- Кнопка панели в инструментах превью: «Комментарии» со счётчиком открытых.
- Новый тред: «Новый комментарий», цитата выделения, поле «Комментарий. @ чтобы упомянуть», «Отправить», «Отмена».
- После создания: «Комментарий привязан к исходнику: {{file}}» или «Комментарий привязан к месту в PDF: в
  исходнике это место не нашлось».
- Метка на поле: подсказка «Комментарий: {{name}}», у нескольких «Комментарии: {{count}}».
- Пометки в списке: «Место изменилось: PDF пересобран», «Место в PDF не найдено», у PDF-треда «К месту в PDF»,
  у исходникового «{{file}}», кнопка «Открыть в исходнике».
- Ошибки: `pdf_missing` «Сначала соберите документ», `bad_rects` «Выделите текст ещё раз».

#### План

1. Бэкенд: PDF-якорь в сущности и хранилище (jsonb, без миграции), поиск цитаты по SyncTeX (`core/review/pdf_match.py`),
   `POST review/pdf-threads`, `GET review/documents/{doc_id}`, `doc_id` в уведомлении, MCP `list`, эталоны контракта.
2. Фронт: схема якоря, кнопка в панели выделения (и на таче), создание, метки на полях, подсветка, панель
   «Комментарии» в превью (общий компонент с редактором), ссылка из «Входящих», демо.
3. SyncTeX со сборки на раннере: раннер выгружает `<stem>.synctex.gz` рядом с PDF, api кладёт его в
   `.build/<doc_id>/`, где его ищет `SyncTexUC` (раньше на сервере с раннерами SyncTeX не было, и «В исходнике»
   тоже не работал). e2e на стенде server-lite с раннером поддельного TeX: сборка печатает строки исходника на
   латинице и кладёт SyncTeX к ним (`e2e/tests/pdf-comments.spec.ts`, `make e2e-pdf-comments`). Справка.

## 3. Совместная правка

### 3.1 Транспорт

`wss://…/api/collab/v1/projects/{id}/room?path=…`: вне `/api/v1`, потому что гард маршрутов рассчитан на HTTP.
Сокет сам проверяет Origin (чужая страница не открывает его с cookie пользователя), разбирает актора (cookie,
гостевая cookie, токен) и право на файл через те же `IProjectAccessChecker` и политику. Кадры двоичные:
0 синхронизация, 1 присутствие (стандарт y-websocket); свои 9 «сбросить на диск» (ответ 10), 11 событие сервера.

Коды закрытия: 4401 войти заново, 4403 нет права, 4404 нет файла, 4415 не текст или выключено, 4429 лимит,
1009 слишком большое, 1013 клиент отстал.

### 3.2 Комната

Один `Y.Doc` на `(проект, путь)`. Открывается из файла; родословная документа хранится в
`<data_dir>/collab/<проект>/<хеш пути>.ystate` вместе с эпохой. Благодаря этому оффлайн-правки клиента после
закрытия комнаты или перезапуска сервера сливаются без дублирования текста. Если файл рядом изменился, разница
накладывается операциями. Состояние всегда вторично: потеряно или раздуто, комната собирается из файла заново, а
клиент по смене эпохи перезагружает редактор (его текст копируется в буфер обмена).

Запись на диск: через 0,8 с после правки, не реже чем раз в 5 с при непрерывном вводе, при закрытии комнаты и по
запросу клиента (кадр 9: перед сборкой и синхронизацией ждёт подтверждения).

### 3.3 Согласование с git, автосинком и остальными записями

- Перед любой операцией над папкой проекта (синхронизация, снимок, восстановление, приём push, сборка, правка
  шаблона) замок папки сначала сбрасывает на диск несохранённый текст открытых комнат (`CollabAwareFolderLocks`).
  Операция видит свежий текст, а не тот, что был 800 мс назад.
- После операции или любой чужой записи (git, агент, VS Code) комната замечает смену версии файла (сверка раз в
  секунду и перед каждой своей записью). Если за комнатой нет несохранённого, чужой текст накладывается как
  минимальные правки, курсоры остаются на местах. Если есть, делается трёхстороннее слияние по строкам: база
  (последняя записанная версия), мой текст комнаты, версия на диске. При споре за одну строку побеждает комната, а
  чужая версия предварительно фиксируется правочным коммитом, чтобы не пропасть из истории.
- Файл удалён или стал нетекстовым: участникам приходит событие, комната закрывается, состояние стирается.

### 3.4 Права

- Вход: `FILES_READ` на путь. Запись: `FILES_WRITE` на путь (в командном проекте автор пишет в своей папке) и проект
  не заперт (`423`-режимы). Иначе подключение read-only: участник видит текст и курсоры, обновления от него
  отбрасываются, о чём ему один раз сообщается.
- Права пересматриваются раз в 20 с: отзыв закрывает сокет (4403), смена роли переключает запись и чтение событием `role`.
- Присутствие: сервер сам подставляет имя и цвет по аккаунту, из состояния клиента оставляет только курсор.

### 3.5 Потеря связи

Клиент хранит локальный `Y.Doc` и продолжает принимать ввод; индикатор «Нет связи, правки сохранены локально».
При возврате сессия синхронизируется заново и правки сливаются как CRDT. Автосохранение через `PUT` и черновик в `localStorage` в сессии
отключены: набранное хранит локальный `Y.Doc`, запись делает комната. Переподключение с
нарастающей паузой до 15 с; коды 4401/4403/4404/4415 не повторяются, а объясняются. Если эпоха сервера изменилась,
несохранённый текст копируется в буфер обмена, а редактор открывается заново на новом документе.

### 3.6 Пределы нагрузки (`HSE_STUDIO__COLLAB__*`)

| Предел | По умолчанию |
|---|---|
| участников в комнате | 16 |
| открытых файлов на проект / на реплику | 8 / 200 |
| подключений одного человека | 8 |
| сообщение от клиента | 1 МиБ |
| размер текста комнаты | 2 МиБ |
| обновлений курсора в секунду | 30 на клиента, лишнее отбрасывается |
| очередь клиента | 512 кадров, отставший отключается (1013) и синхронизируется заново |
| простаивающая комната | 20 с после выхода последнего |

Документ закреплён за репликой: при нескольких воркерах или репликах без закрепления по `(проект, путь)` на одном
файле могут появиться две комнаты. Они не портят данные (обе пишут через диск и сливаются трёхсторонне), но
правки в них видны друг другу с задержкой в секунду и курсоры не общие. Для публикации с несколькими репликами
нужен sticky-роутинг по хешу пути; в этой ветке не реализован.
