# План подписей: смешанные подписи на одном PDF и подписание комплекта

Статус: принято, внедряется тремя PR (раздел 12).

## 1. Задача

Документ подписывают несколько участников проекта: авторы, руководитель, консультант, академический руководитель.
У каждого свой слот и свой способ:

- картинка (PNG);
- встроенная ЭП PAdES, видимая или нет;
- открепленная ЭП: OpenPGP `.asc` или CMS/CAdES `.sig`/`.p7s` (в том числе ГОСТ из КриптоПро), на странице плашка
  «Подписано с помощью открепленной электронной подписи».

На одном PDF возможна любая смесь, подписывают в любом порядке и в разное время. До этого изменения способы жили в
двух механизмах: выгрузка подписанного PDF (`get_signed_doc_pdf`, PAdES и CAdES на лету при скачивании) и фиксация с
приложенными подписями (`freeze_pdf`, «Подписать в Студии»). Счётчик точки сдачи считал подпись по размещению и PNG,
поэтому открепленная ЭП без файла подписи давала «0 из 3» без объяснения.

## 2. Инварианты

1. Каждая криптоподпись покрывает ровно те байты, которые подписант видел и подтвердил.
2. Новая подпись, любым способом, не делает недействительными уже поставленные.
3. По итоговому комплекту любой проверит каждую подпись стандартными средствами (gpg, КриптоАРМ, Adobe, pyHanko) без
   Студии, и понятно, к какому файлу относится каждая открепленная подпись.
4. Картинка не выдаётся за ЭП: в интерфейсе, в счётчике и в комплекте видно, какая подпись криптографическая, а какая
   графическая.

## 3. Модель

Состояние подписей (`.hse-studio/signatures.json`, `SignaturesState`) хранит то, что сделано. План подписей
(`core/signatures/plan.py`) вычисляется из состояния и проекта и отвечает на вопрос «кто, каким способом и чего не
хватает». Один и тот же расчёт кормит счётчик точки сдачи, «Подписать комплект», сборку комплекта и MCP.

### 3.1 Слот плана

| Поле | Откуда |
|---|---|
| документ, слот | пункт профиля сдачи (`items[].signatures`) или включённое размещение |
| подписант | персона проекта (3.2) и имя из карточки проекта |
| способ | `image`, `detached`, `pades`; выводится из `sign_mode` слота |
| видимая метка | `png`, `plate` (плашка открепленной ЭП) или `none` |
| статус | `pending` (ждёт), `signed` (подписано), `invalid` (недействительно), `stale` (устарело) |
| причина и подсказка | код (`no_signature_file`, `rebuilt`, ...) и текст на языке интерфейса |
| проверка | формат, вердикт, подписант и отпечаток из самой подписи, заметки (`chain_untrusted_root`, ...) |
| разрешённые способы | ограничение профиля сдачи (3.3) |

Соответствие режимов: `image` это картинка; `image_crypto` и `crypto_invisible` это PAdES (с картинкой или без);
`detached_text` и устаревший `detached` это открепленная ЭП (с плашкой или с картинкой). Новых значений `sign_mode`
нет, поэтому данные не переписываются (раздел 10).

### 3.2 Персона слота

| Слот | Персона |
|---|---|
| `<слот>--<слаг>` (командный, по автору) | слаг автора |
| `supervisor`, `co_supervisor`, `academic_supervisor` | та же роль руководителя |
| остальные (`author` в solo) | `author`, владелец solo-проекта |

Персона участника берётся из приглашения (`persona` в членстве проекта). Владелец solo-проекта получает персону
`author`. Локально человек один: его персоны это авторы проекта (в команде слаги авторов, чей комплект ведёт
проект) плюс персоны тех слотов, где на плашке указан его собственный ключ из Студии (руководитель в своей локальной
Студии).

### 3.3 Ограничение способов профилем

Пункт профиля может ограничить способы по слоту каталога:

```yaml
- doc_id: topic_application
  signatures: [author, supervisor]
  methods: { author: [image, detached], supervisor: [image, detached] }
```

Слот без записи принимает любой способ. Неизвестный способ это ошибка пака при загрузке. Способ, который точка не
принимает, в плане этой точки даёт `pending/method_not_allowed`.

### 3.4 Статусы

Картинка: `signed`, если размещение включено и PNG на месте. Если документ сдаётся из зафиксированного файла (на нём
есть криптослот) и видимый слой изменился после фиксации, картинка в сдаваемом файле старая: `stale/marks_changed`.

Криптоподпись (открепленная и PAdES), по порядку проверок:

| Условие | Статус, причина |
|---|---|
| способ не принимает точка | `pending/method_not_allowed` |
| нет размещения при видимой метке | `pending/placement_off` |
| нет PNG при метке-картинке | `pending/no_image` |
| документ не собран | `pending/not_built` |
| PDF не зафиксирован | `pending/not_frozen` |
| документ пересобран после фиксации | `stale/rebuilt` (есть подпись) или `pending/rebuilt` |
| видимый слой изменился после фиксации | `stale/marks_changed` или `pending/marks_changed` |
| нет файла открепленной подписи | `pending/no_signature_file` |
| нет встроенной подписи | `pending/no_embedded` |
| подпись к другой фиксации | `stale/other_pdf` |
| вердикт `invalid` | `invalid/invalid_signature` |
| вердикт `unknown_key` (нет открытого ключа) | `pending/unknown_key` |
| иначе (`valid` или `unverified`) | `signed` |

`unknown_key` не считается подписью: комплект без открытого ключа подписанта нельзя проверить вне Студии (инвариант
3). Счётчик точки: «подписано k из n», где n это пары «документ, слот» профиля после тех же гейтов, что у сборки
пакета (NDA, вид проекта, автор команды).

## 4. Порядок слоёв

```text
L0  собранный PDF (source_sha256)
L1  видимый слой: все картинки, плашки открепленных ЭП и картинки видимых PAdES одним проходом
    = зафиксированный PDF B (sha256)                  .hse-studio/frozen/<doc>.pdf
L2  открепленные подписи, каждая независимо над B     .hse-studio/detached/<doc>/<slot>.<asc|sig|p7s>
L3  PAdES: B ‖ Δ1 ‖ Δ2 ‖ ... инкрементальные обновления = итоговый F
                                                      .hse-studio/frozen/<doc>.signed.pdf
```

- Всё видимое ставится до фиксации. Картинка PAdES-слота уже стоит в B, а поле подписи PAdES невидимое: внешний вид
  не требует перерисовки страницы после подписи, и B остаётся префиксом F.
- Данные плашки (владелец, сертификат, срок) собираются заранее: из ключа подписанта в Студии (ключ по умолчанию,
  раздел 7), из загруженного сертификата или вручную.
- Открепленная подпись всегда над B, в любом порядке относительно PAdES: B не меняется, когда дописывается F.
- PAdES i покрывает `B ‖ Δ1 ‖ ... ‖ Δi`. Подписи утверждающие (approval), без сертифицирующей подписи и DocMDP: по
  правилам PAdES и диф-политике pyHanko и Adobe следующее обновление, которое только добавляет поле подписи и саму
  подпись, разрешено, и прежние подписи остаются действительными.
- Перед каждым PAdES Студия сверяет: текущий F совпадает с записанным `signed_sha256`, его начало длиной `size`
  совпадает с B. Иначе отказ «файл изменился», ничего не дописывается.
- После каждого PAdES Студия заново проверяет все подписи F и записывает вердикты.

Почему держатся инварианты:

1. Открепленная подпись делается над B, который человек открывает по ссылке «Зафиксированный PDF»; PAdES над текущим
   F. «Подписать комплект» принимает от клиента отпечатки того, что показано (раздел 7.2), и отказывает, если байты
   изменились между показом и подписью.
2. Новая открепленная не трогает B, новая PAdES только дописывает F. Единственное, что меняет B, это повторная
   фиксация (новая сборка, новая картинка или плашка). Она сбрасывает подписи старой версии, и это происходит только
   по явному подтверждению со списком сбрасываемых подписей; автоматической перефиксации нет.
3. Комплект кладёт B и F (если различаются), подписи с именами документа и подписанта, открытые ключи и
   «КАК_ПРОВЕРИТЬ.txt» с командами (раздел 8).
4. У каждого слота плана есть способ и признак `crypto`; счётчик и комплект подписывают графическую подпись как
   «картинка».

## 5. Права

- Политика `SIGN` (`core/access/policy.py`): слот `<слот>--<слаг>` подписывает привязанный к автору `<слаг>` (как
  было); слот руководителя (`supervisor`, ...) теперь ещё и участник с этой персоной; остальные слоты владелец.
  Владелец сохраняет право управлять слотами (загрузить картинку, приложить готовую подпись, полученную от
  руководителя): это не подпись своим ключом.
- Подпись ключом из Студии (одиночная «Подписать в Студии», PAdES, «Подписать комплект», MCP) дополнительно требует,
  чтобы персона слота была персоной актора (3.2). Подписать чужой слот своим ключом нельзя ни владельцу, ни локально.
  Единственное послабление локально: явная одиночная подпись слота, на плашке которого подписант не указан (персону
  локальному человеку не назначить, а он сам выбирает слот и ключ). «Подписать комплект» локально берёт только слоты
  авторов и слоты с его ключом на плашке.
- Если на плашке указан ожидаемый подписант (`signer_id`), ключ должен с ним совпасть. Иначе отказ «на плашке
  другой подписант», чтобы не было «подписал не тот, кто на плашке».
- «Ждут вашей подписи: N» это число слотов актора по всем точкам проекта, у которых статус не `signed`.

## 6. Запрещённые комбинации

Проверяются при настройке слота (`PATCH /signatures/slots/{slot}/config`), ответ 400 с объяснением:

| Комбинация | Почему |
|---|---|
| PAdES с ключом OpenPGP | встроенная подпись PDF строится только на сертификате X.509 (PKCS#12); OpenPGP подходит для открепленной `.asc` |
| способ, который не принимает ни одна точка, требующая слот | такой подписью нечего сдавать |

Способ, разрешённый хотя бы одной точкой, не запрещается: слот один на все точки проекта, а точки идут в разное время
(заявка в ноябре, защита в июне). На точке, которая его не принимает, план показывает `method_not_allowed`.

Правило порядка, а не комбинации: картинку или плашку нельзя добавить к уже подписанному документу без перефиксации.
Это не запрещается при настройке (картинку загружают для всех документов сразу), а показывается статусом
`marks_changed` и предупреждением перед перефиксацией.

Не входит в модель и не меняется: подписи не-PDF документов (docx, pptx без конвертации) и сертифицирующие подписи
PDF.

## 7. Подписать комплект

### 7.1 Ключ по умолчанию

В профиле пользователя выбирается ключ подписи по умолчанию. Если ключ один, он выбирается сам. Плашка открепленной
ЭП, у которой подписант не задан, при фиксации берёт данные из этого ключа. Пароль ключа Студия не хранит.

### 7.2 Два шага

1. `POST /projects/{id}/signature-plan/sign-preview` (`profile_id`, `author`, `identity_id`): что будет сделано по
   каждому документу профиля: нужна ли фиксация, чьи подписи она сбросит, какие слоты актора и каким способом будут
   подписаны, каким ключом, нужен ли пароль, что мешает (нет картинки, ключ не подходит к способу, нет права
   фиксировать). В ответе отпечаток каждого документа: `sha256` зафиксированного или итогового PDF, а для
   незафиксированного пара «хэш сборки, отпечаток видимого слоя».
2. `POST /projects/{id}/signature-plan/sign` с теми же параметрами, паролем, `confirm_reset` и отпечатками из шага 1.
   Сервер пересчитывает предпросмотр. Если отпечаток не совпал: 409 «документ изменился, посмотрите заново». Если
   фиксация сбросит чужие подписи, а `confirm_reset` не передан: 409 со списком. Иначе по каждому документу: фиксация
   (если нужна), затем подпись всех слотов актора его способом. Пароль спрашивается один раз на всё действие.

Нельзя: подписывать после пересборки без нового явного действия человека (отпечатки шага 1 больше не совпадут),
подписывать чужой слот, хранить пароль.

## 8. Комплект для LMS

Документ, на котором есть криптоподпись, сдаётся из зафиксированных байтов. Имена:

| Файл | Что это |
|---|---|
| `<Документ>.pdf` | итоговый PDF: F, если есть PAdES, иначе B |
| `<Документ>.для-открепленных-подписей.pdf` | B, только если есть и PAdES, и открепленные; его байты совпадают с началом `<Документ>.pdf` |
| `<PDF без .pdf>.<Подписант>.openpgp.asc` | открепленная OpenPGP к PDF с тем же началом имени |
| `<PDF без .pdf>.<Подписант>.cades.p7s` (`.sig`) | открепленная CMS/CAdES |
| `public-key.<Подписант>.asc` | открытый ключ OpenPGP подписанта |
| `КАК_ПРОВЕРИТЬ.txt` | по каждому документу: файлы, SHA-256, подписи с видом (графическая, открепленная, встроенная), команды |

Команды в `КАК_ПРОВЕРИТЬ.txt`: `gpg --import public-key.*.asc` и `gpg --verify <подпись> <PDF>`; `openssl cms -verify
... -content <PDF>` и КриптоАРМ или Госуслуги для ГОСТ; `pyhanko sign validate --pretty-print <PDF>` или панель
подписей Adobe для PAdES; для пары B и F команда, которая показывает, что B это начало F.

## 9. MCP

- `get_signature_plan(project_id, profile_id?, doc_id?, author?)`: план и статусы, право `OUTPUT_READ`.
- `sign_submission(project_id, profile_id, author?, confirm_reset?)`: то же, что 7.2, от имени владельца токена его
  ключом по умолчанию. Тул опасный: в настройках MCP он выключен, пока его не включат поимённо. В облаке токену нужно
  отдельное право `sign`, право `mcp` его не включает. Если ключ защищён паролем, тул отвечает «ключ защищён паролем,
  подпишите в интерфейсе» и пароль не принимает. Отпечатки берутся из того же вызова: агент подписывает то, что
  видел план, а пересборка между вызовами даёт отказ.
- Пароли и закрытые ключи никогда не попадают в ответы тулов, журнал MCP (там только имена аргументов) и аудит.

## 10. Миграция существующих данных

- `signatures.json` не переписывается. Новые поля необязательны: `embedded` (PAdES по документу и слоту),
  `frozen[doc].signed_path`, `signed_sha256`, `signed_size`. Старый файл читается как «PAdES нет».
- Старая Студия сохраняет незнакомые поля (`preserve_unknown`), git-слияние держит `embedded` и `signed_path` в
  группе подписей документа вместе с `frozen` и `detached`.
- Зафиксированные PDF и приложенные открепленные подписи считаются как раньше; их статус теперь виден в счётчике.
- Режим `detached` (картинка плюс CAdES при скачивании) становится открепленной ЭП с картинкой вместо плашки:
  подпись делается над зафиксированным PDF и хранится как остальные открепленные.
- Выгрузка `/pdf/signed` остаётся предпросмотром для печати: PAdES и CAdES на лету в ней не считаются подписями
  плана и в комплект не попадают.
- Поведение сдачи меняется: слот `image_crypto` раньше проходил по одной картинке, теперь требует встроенной
  подписи; открепленная подпись с вердиктом `unknown_key` раньше проходила, теперь требует открытого ключа.

## 11. Аудит

События (сервер: журнал аудита; локально: строка лога): `signature.freeze`, `signature.unfreeze`,
`signature.attach`, `signature.sign` (одиночная и PAdES), `signature.delete`, `signature.submission_sign` (итог по
комплекту), `signature.default_key`. В деталях проект, документ, слот, способ, формат и вердикт; без паролей,
ключей и содержимого файлов.

## 12. Этапы

- PR A: этот документ, модель плана, `GET /projects/{id}/signature-plan`, счётчик точки сдачи по плану, запрещённые
  комбинации при настройке слота, `methods` в профиле сдачи, поля `embedded` и `signed_*`.
- PR B: права на слоты и «Ждут вашей подписи», ключ по умолчанию, PAdES над зафиксированным PDF, «Подписать
  комплект», аудит.
- PR C: комплект для LMS по разделу 8, сдача по плану, MCP `get_signature_plan` и `sign_submission`, право токена
  `sign`.

## 13. Открытые вопросы

- Запрет способа, который не принимает ни одна точка, может мешать паку, где ограничения появятся позже. Сейчас ни
  один пак `methods` не задаёт; для hse-cs-sse «картинка или открепленная ЭП» добавляется в следующей версии пака.
- Персона «автор» владельца командного проекта без привязки к слагу не выводится: такой владелец подписывает слоты
  авторов только после привязки к себе.
- Проверка цепочки PAdES использует доверенные корни Студии; списки отзыва и OCSP не запрашиваются, как и для CMS.
