# Очистка места из админки: диски раннеров и «Освободить место»

Статус: принято 11.11.2026, внедряется срезами раздела 12. Решение владельца продукта: в облачной админке, как в
локальной Студии, можно чистить старые образы и кэши; детали ниже приняты по умолчанию, неочевидные помечены
**Развилка**.

Основа: `docs/design/data-lifecycle.md` (реестр самороста, «Хранение данных», движок очистки),
`docs/design/k8s-runner.md` (раннер в Kubernetes, PodSecurity restricted), `docs/design/runner-install.md`
(установка и обновление раннеров из админки), протокол раннера `core/jobs/wire.py` и `contracts/runner/openapi.yaml`.

Документ не входит в сайт документации, это рабочий дизайн для разработки.

## 1. Задача

В локальной Студии есть Настройки, раздел «Диск»: сколько места занимают образы TeX Live, LanguageTool, Gotenberg,
сама программа, кэш сборки Docker, и кнопки «Удалить старые версии», «Очистить кэш сборки», «Удалить висячие
образы», «Очистить всё». В облаке ничего похожего нет: api к Docker не ходит, а образы копятся на машинах раннеров.
Типичный случай: сервер из `deploy/server`, общий раннер на том же хосте, апдейтер каждый выпуск качает новый образ
Студии на 1..2 ГБ, через полгода на диске десяток старых версий, и админ узнаёт об этом по предупреждению «Место
заканчивается» без кнопки, которая бы помогла.

Цели:

1. **Диск раннера.** Админ в меню строки раннера открывает «Диск»: разбивка занятого места по тем же категориям,
   что в локальной Студии, плюс кэш файлов и рабочие копии раннера; запускает очистку, видит ход и итог
   «Освобождено N». Раннер чистит тем же кодом, что локальная Студия. Текущая и предыдущая версии и тома не
   трогаются.
2. **Раннер в Kubernetes.** Только кэш файлов и рабочие копии: размер и «Очистить кэш раннера». Образы на узлах
   кластера не трогаем и честно пишем, что их чистит Kubernetes.
3. **Хранилище.** Кнопка «Освободить место»: все очистки из «Хранения данных» одним действием, с подтверждением, что
   именно удалится по текущим срокам, и итогом. Рядом ссылки на «Хранение данных» и на диски раннеров.
4. **Личные раннеры.** Владелец видит «Диск» своего раннера в «Мои раннеры» и чистит его сам.
5. Права, аудит каждой очистки, тексты RU и EN, галерея состояний, пользовательская документация и e2e.

Не цели:

- Чистить образы на узлах Kubernetes (`crictl rmi`, DaemonSet с доступом к containerd): это привилегированный доступ
  к узлу, которого у Студии нет и не будет (раздел 7).
- Удалять тома Docker (кэш TeX Live, модели Ollama) и чужие образы и контейнеры хоста (Postgres, MinIO, прочие
  проекты). Правило локального «Диска» сохраняется: всё вне категорий Студии невидимо и неприкосновенно.
- Автоматическая очистка раннера по порогу места. Это следующий шаг поверх того же кода (раздел 13).
- Очистка объектного хранилища и сирот вне сроков: это фоновые задачи `blob_gc`, `orphan_gc`, `project_purge`
  (раздел 13).
- MCP-тулы для очистки (раздел 8.4).

## 2. Что есть сейчас

### 2.1 Локальная Студия: «Диск»

| Часть | Где | Что делает |
|---|---|---|
| Замер и очистка Docker | `infra/docker/system_manager.py` (`DockerSystemManager`) | `docker system df -v`, классификация образов по категориям (`compile`, `languagetool`, `office`, `ai`, `app`, `dangling`, `other`), `builder prune`, `image prune`, `image rm` без `--force`, удаление остановленных контейнеров с меткой `com.hse-studio.managed` |
| Задача очистки | `infra/docker/cleanup_jobs.py` (`DockerCleanupJobManager`) | одна очистка за раз, план по шагам, ход по шагам, отмена между шагами |
| Правила | `use_cases/system/get_docker_disk_usage.py`, `old_versions.py`, `cleanup_docker.py` | `ours_only` (чужое не показывается), защищённые образы (активный образ категории, текущая версия Студии, `latest`), «старые версии» (ниже текущей, не заняты, предыдущая для отката сохраняется), план только из того, что разрешает свежий замер |
| API | `api/routers/v1/docker_system.py` | `GET /system/docker-usage`, `POST/GET /system/docker-cleanup`, `.../cancel`; только локальный режим |
| Интерфейс | `widgets/settings/sections/disk/*`, локаль `settings.json` (`disk.*`) | полоса по категориям, «Старые версии», списки образов, контейнеров и томов, ход очистки |

Правила зависят от настроек api (`settings.compile.allowed_repos`, `settings.image_base`, `ISettingsRepository` с
выбранными образами), поэтому в процессе раннера их сейчас не собрать.

### 2.2 Облачная админка

- «Хранилище» (`/admin/storage`, `features/admin-ops/ui/Storage*.tsx`, `admin/storage.json`, `GET /api/admin/storage`):
  число проектов и объектов, том проектов, владельцы. Только статистика, действий нет.
- «Хранение данных» (`/admin/data`, `DataLifecycleView.tsx`, `admin/data.json`, `/api/admin/data-lifecycle`): сроки,
  размеры источников, «Очистить сейчас» по одному источнику (`POST /{key}/run`, синхронно, аудит
  `lifecycle.run_now`), пороги места и безопасный режим. Вручную чистятся источники движка (`partition_drop`,
  `delete_batches`, `file_sweep`) с `run_now`: `ai_usage`, `jobs`, `notifications`, `collab_requests`,
  `share_links`, `guest_sessions`, `collab_state`. Журнал аудита вручную не чистится.
- «Раннеры» и «Личные раннеры» (`RunnersView.tsx`, `PersonalRunnersView.tsx`): меню строки (пауза, «Как
  развёрнут», «Обновить» у установленных из админки, смена токена, отзыв). Админ не может сменить токен личного
  раннера (`RunnerRegistry.rotate_token`), но может поставить его на паузу и отозвать.

### 2.3 Где лежат образы и кэши

| Где | Что копится | Кто чистит сейчас |
|---|---|---|
| хост общего раннера с Docker (`deploy/server`, установка из админки «Docker рядом» и по SSH, `install.sh`) | образы Студии старых версий (апдейтер, обновление раннера), старые теги TeX Live и сервисов, висячие слои, кэш сборки Docker | никто |
| `data_dir` раннера (`HSE_RUNNER__DATA_DIR`) | кэш файлов `blobs/` (предел `cache_max_bytes`, 2 ГиБ, LRU), рабочие копии `workspaces/` (предел `workspaces_max_bytes`, 20 ГиБ, LRU) | сам раннер по пределам (`BlobCache.evict`, `RunnerWorkspaces.evict`) |
| узел Kubernetes (раннер с `executor=kubernetes`) | образ TeX Live в containerd узла | сборщик мусора образов kubelet (`imageGCHighThresholdPercent`) |
| PVC данных раннера в Kubernetes | `blobs/`, `workspaces/` | раннер по пределам |
| машина владельца личного раннера (CLI) | как у общего раннера | никто |
| компьютер с локальной Студией, подключённой раннером (`host_kind=desktop`) | Docker локальной Студии | сам человек: Настройки, «Диск» |

### 2.4 Канала команд раннеру нет

Протокол раннера только тянущий: раннер держит долгий опрос `POST /poll` и получает конверт задачи. Опрос открыт,
только пока есть свободный слот (`PollRequest.free_slots + free_ai_slots >= 1`); раннер, занятый сборками, или
локальная Студия с закрытым шлюзом не опрашивает вовсе. Обратная связь к раннеру есть только в ответе пульса задачи
(`HeartbeatResponse.cancel`). Возможности согласуются в `/announce` (`FEATURE_*`, пересечение объявленных раннером и
известных серверу); отчёт `/deployment` шлётся раз в час после согласования `deployment_info`. На этом образце и
строится новое (раздел 6).

## 3. Решения

| № | Решение | Почему |
|---|---|---|
| S1 | Раннер сам меряет и сам чистит; сервер передаёт только **цели** очистки (`old_versions`, `build_cache` и т. д.), никогда ссылки на образы. План раннер строит по свежему замеру своими правилами. | Сервер (или тот, кто его взломал) не может назвать произвольный образ: худшее, что он может, это удалить неиспользуемые образы Студии и кэш, которые и так скачаются заново. Устаревший экран не расширит удаление, как и в локальной Студии (`_plan_refs`). |
| S2 | Код правил один: из `use_cases/system` выносится `DockerDiskPlanner`, не зависящий от настроек api; локальная Студия и раннер собирают его каждый из своей конфигурации. Живёт он в `core/docker_disk`, а не в `use_cases`: процесс раннера `use_cases` не импортирует (`test_runner_isolation`). `DockerCleanupJobManager` получает подключаемые виды шагов, раннер добавляет шаги своего кэша. | Требование «тем же кодом»; две копии правил разъедутся на первом же новом исключении. |
| S3 | Новый канал команд: отдельный долгий опрос `POST /control/poll`, возможности `control` и `disk`. | Канала нет, а `/poll` не годится: занятый раннер его не открывает (2.4). Отвергнутые варианты в 6.6. |
| S4 | Команды и последний отчёт о диске живут в Postgres (`runner_commands`, `runners.disk`), а не в памяти api. | Опрос раннера и запрос админа могут прийти на разные реплики api. |
| S5 | Отчёт о диске раннер шлёт сам: после `/announce`, раз в 6 часов, после каждой очистки и по команде «Обновить» (`disk.measure`). | `docker system df -v` идёт до 90 с, обход рабочих копий тоже не бесплатен: мерить на каждый показ экрана нельзя. |
| S6 | Kubernetes-раннер (`executor=kubernetes`) отдаёт только кэш файлов, рабочие копии и том данных; Docker-часть `null` с причиной `kubernetes`. Цель `runner_cache` у него единственная. | Образы узла чистит kubelet; Студии нужен был бы доступ к узлу, а namespace раннера restricted. |
| S7 | Локальная Студия как раннер (`host_kind=desktop`) отдаёт только кэш раннера; Docker-часть `null` с причиной `managed_locally`, на экране ссылка на Настройки, «Диск». | Docker этого компьютера уже управляется в самой Студии, а человек сидит за ним. Две кнопки для одного Docker путают. |
| S8 | **Развилка.** Личный раннер: смотреть и чистить может владелец и админ установки. Удалить предыдущую версию (откат) может только владелец. Очистка админом личного раннера приходит владельцу во «Входящие». | Админ уже может поставить личный раннер на паузу и отозвать его, очистка слабее отзыва; но это чужая машина, поэтому необратимое для владельца (откат) только у него, и он узнаёт обо всём, что сделали без него. Вариант «админ только смотрит» в разделе 13. |
| S9 | Кэш раннера чистится без остановки сборок: блобы, тронутые за последние 10 минут, и рабочие копии под замком задачи пропускаются. | Сборка, которая прямо сейчас копирует блоб в рабочую папку, не должна падать из-за очистки. |
| S10 | «Освободить место» это прогон всех ручных источников движка подряд на сервере (`lifecycle_sweeps`), а не цикл запросов из браузера. Подтверждение показывает срок и число записей по каждому источнику (счёт с потолком). | Прогон до 7 источников по 120 с бюджета не помещается в один HTTP-запрос и не должен обрываться закрытой вкладкой. Счёт с потолком (`LIMIT 100001`) дешёвый даже на миллионах строк. |
| S11 | Итог «Освободить место» показывает отдельно «удалено записей» и «освобождено на диске». Освобождённым считается уменьшение размера источника по его замеру. | DELETE в Postgres освобождает место внутри базы, а не на диске; честно отличается от отбрасывания партиции и стирания файлов. |
| S12 | В «Освободить место» не входят фоновые уборки (`blob_gc`, `orphan_gc`, `project_purge`, `auth_cleanup`) и очистка раннеров. На экране это сказано, раннеры даны ссылкой. | У фоновых задач свои сроки и лидерский замок, запуск вне расписания требует изменения `BackgroundTaskRunner`. Раннеры чистятся осознанно по одному: это чужие машины и, возможно, чужие сборки. |
| S13 | Новые таблицы растут, поэтому сразу попадают в реестр `core/lifecycle/policies.py`: `runner_commands` и `lifecycle_sweeps` со стратегией `on_write` (последние 20 на раннер и 20 прогонов). | Правило `data-lifecycle.md`: всё, что растёт само, ограничено и видно в «Хранении данных». |
| S14 | Без MCP. | Раздел 8.4. |

## 4. Как это выглядит

### 4.1 Раннеры: «Диск»

В меню строки раннера («Раннеры» и «Личные раннеры» админки) новый пункт **«Диск»** рядом с «Как развёрнут».
Открывается диалог того же размера, что «Как развёрнут».

Шапка: «Диск раннера «{name}»», строка «Замер от {когда}», кнопка «Обновить». Затем полоса занятого места по
категориям (та же, что в локальном «Диске»: цвета `--chart-N`, порядок категорий постоянный) с легендой и итогом
«Занято {size}, можно освободить {size}». Под полосой строка тома данных раннера: «Том данных раннера: свободно
{free} из {total}».

Ниже блоки с действиями, каждый со своей кнопкой и размером:

| Блок | Что показывает | Кнопка | Цель |
|---|---|---|---|
| Старые версии | образы прежних версий Студии и устаревшие теги сервисов; строка «Текущая версия: 0.21.0», «Для отката: …, сохраняется» | «Удалить старые версии» | `old_versions` |
| Неиспользуемые образы | образы Студии, которые не нужны раннеру и ни одним контейнером не заняты (до 100 строк) | «Удалить неиспользуемые» | `unused_images` |
| Кэш сборки Docker | размер и сколько из него можно освободить | «Очистить кэш сборки» | `build_cache` |
| Висячие образы | число и размер | «Удалить висячие образы» | `dangling_images` |
| Остановленные контейнеры Студии | число и размер | входит только в «Очистить всё» | `stopped_containers` |
| Кэш раннера | кэш файлов (размер, число, предел), рабочие копии (размер, число, предел, «занято сборками: N») | «Очистить кэш раннера» | `runner_cache` |
| Тома | имя и размер, без кнопок; подпись, почему не удаляются | | |

Внизу главная кнопка «Очистить всё»: все цели, кроме отката. Каждая кнопка спрашивает подтверждение со списком того,
что удалится, и размерами из последнего замера. В подтверждении «Удалить старые версии» флажок «Удалить и
предыдущую версию ({ref}, {size})» с предупреждением; у личного раннера в админке флажка нет (S8).

После подтверждения на месте кнопок полоса хода: «Ждём раннер» (команда ещё не забрана), затем «Идёт очистка: шаг
{n} из {total}, освобождено {size}» со списком шагов (`pending`, `running`, `done`, `error`, `skipped`) и кнопкой
«Остановить после текущего шага». Итог: «Освобождено {size}» (или «Освобождать было нечего»), при ошибках «Очистка
завершилась с ошибками» и шаги с причиной. После итога раннер сам присылает новый замер, полоса обновляется.

Уточнено в W3 (`entities/runner/ui`): подтверждение открывается не вторым окном, а на месте блоков внутри того же
диалога (окно поверх окна на телефоне неудобно), с кнопками «Отмена» и «Очистить» или «Удалить» и строкой
«Освободится около {size}». Флажок отката решает `can_include_rollback` вида, а не сама панель. Команду, которую
раннер ещё не забрал, можно отменить кнопкой «Отменить» (переход `queued` в `cancelled`). Итог закрытой команды
скрывается крестиком до следующей очистки. Шаг, оставшийся `running` у закрытой команды (`lost`), помечен
предупреждением, а не крутилкой.

Особые состояния диалога:

| Состояние | Что видно |
|---|---|
| раннер без возможности `disk` (старая версия) | заглушка «Обновите раннер, чтобы видеть диск», версия раннера; у установленного из админки кнопка «Обновить» (тот же `onUpgrade`, что в «Как развёрнут») |
| `executor=kubernetes` | только «Кэш раннера» и том данных; плашка про образы узлов (4.4) |
| `host_kind=desktop` | только «Кэш раннера»; плашка «Образы на этом компьютере чистятся в самой Студии» |
| Docker недоступен (`docker.available=false`) | Docker-блоки заменены строкой «Раннер не достучался до Docker»; «Кэш раннера» работает |
| раннер не на связи | последний замер с пометкой «Раннер не на связи с {когда}», кнопки очистки и «Обновить» выключены с подсказкой |
| замера ещё нет | «Раннер ещё не прислал замер», кнопка «Обновить» |
| замер старше суток | пометка «Замер устарел» рядом со временем |
| отозванный раннер | пункта «Диск» в меню нет |
| личный раннер у админа | плашка «Это личный раннер {owner}. Владелец получит уведомление об очистке, предыдущую версию может удалить только он.» |

### 4.2 Мои раннеры

В карточке своего раннера (`features/my-runners`) кнопка «Диск» открывает тот же диалог (общий компонент из
`entities/runner`, раздел 12). Отличия от админки: нет плашки владельца, флажок отката есть.

Уточнено в W5: «Диск» это пункт меню «⋯» строки раннера (как в админке), между «Приостановить» и «Сменить токен»,
у любого неотозванного раннера, в том числе на паузе и не на связи; старую версию окно встречает заглушкой
«Обновите раннер». Открытое окно живёт в адресе: `/settings/runners?disk={id}` (как `?user=` у карточки
пользователя в админке), закрытие убирает параметр. Ссылка на отозванный или чужой раннер окна не открывает.
Уведомление `runner_disk_cleaned` ведёт на `/settings/runners?disk={ref_id}` (`myRunnerDiskPath` в
`entities/runner`; поля payload в 8.2).

### 4.3 Хранилище: «Освободить место»

## 5. Модель данных

### 5.1 Отчёт о диске раннера

`core/jobs/disk.py`, замороженные датаклассы, кодируются `codec.encode` как остальной протокол:

```text
RunnerDiskReport
  measured_at                       время замера на раннере (UTC)
  targets: [DiskTarget]             цели, которые этот раннер умеет выполнять сейчас
  docker: DockerDisk | null         null у kubernetes и desktop (причина в docker_reason)
  docker_reason: kubernetes | managed_locally | null
  cache: RunnerCacheDisk
  volume: {total_bytes, free_bytes} | null       том data_dir (shutil.disk_usage); null, если не прочитать

DockerDisk
  available                         false: docker не ответил; числа 0, списки пусты, old_versions без пунктов
                                    и с версией раннера (структура та же, не null)
  categories: [{key, bytes}]        key: compile | languagetool | office | ai | app | cache | runtime
  total_bytes, cleanable_bytes      cleanable_bytes: ровно то, что освободит «Очистить всё», без отката (9.3)
  build_cache: {bytes, reclaimable_bytes, count}
  dangling: {bytes, count}
  stopped_containers: {bytes, count}
  unused_images: [{ref, category, size_bytes}]   до 100, `unused_truncated` при обрезке; без пунктов
                                    old_versions и отката (5.2); category из compile | languagetool |
                                    office | ai | app
  unused_truncated
  old_versions: {current_version, rollback: OldItem | null, items: [OldItem], reclaimable_bytes, rollback_bytes}
                                    items до 100, как `OldVersions` локального «Диска»
  volumes: [{name, size_bytes}]     только тома Студии (кэш TeX, модели)

OldItem: {kind: studio_image | service_image | container, ref, version, size_bytes}

RunnerCacheDisk
  blobs: {bytes, count, limit_bytes}
  workspaces: {bytes, count, limit_bytes, busy}  busy: сколько папок сейчас под замком задачи

DiskTarget: old_versions | unused_images | build_cache | dangling_images | stopped_containers | runner_cache
```

Чего в отчёте нет: путей (`data_dir`, корень Docker), имён рабочих папок (это id проектов), чужих образов и
контейнеров, переменных окружения. Отчёт ограничен 64 КБ, сервер отвергает больший (`413`) и лишние поля
(`extra=forbid`). Это данные, присланные раннером: сервер их проверяет схемой и показывает как текст.

Уточнено в B1 (`core/jobs/disk.py`, `RunnerDiskReportBody`): `docker` пуст ровно тогда, когда задан
`docker_reason`; цели, кроме `runner_cache`, допустимы только при `docker.available=true`; цели без повторов.
Ссылка образа до 384 символов, версия до 64, томов до 32, размеры и счётчики неотрицательные. Сто строк с
предельно длинными ссылками в 64 КБ не помещаются, поэтому раннер (B3) после обрезки до 100 проверяет размер
закодированного отчёта и при необходимости укорачивает списки дальше (`unused_truncated`, итоги по-прежнему по всем);
сто строк обычной длины помещаются с запасом (контрактный тест).

### 5.2 Цели и правила

| Цель | Что делает раннер | Правило безопасности |
|---|---|---|
| `old_versions` | `image rm` каждого образа и `rm` контейнера из `old_versions.items`; с `include_rollback` и образ отката | как в локальном «Диске»: версия ниже текущей, не занята, не защищена; откат только по флагу |
| `unused_images` | `image rm` каждого неиспользуемого образа категорий Студии | не `other`, не `dangling`, не защищён (активный образ категории у раннера, его собственный образ, `latest`), не занят, не входит в `old_versions` (ни пунктом, ни откатом): иначе эта цель снимала бы откат в обход `include_rollback` и S8 |
| `build_cache` | `builder prune -f` | как локально |
| `dangling_images` | `image prune -f` | как локально |
| `stopped_containers` | `rm` остановленных контейнеров с меткой `com.hse-studio.managed` | метка проверяется в момент удаления |
| `runner_cache` | два шага: блобы и рабочие копии | блобы с `mtime` моложе 10 минут и рабочие папки под замком проекта пропускаются; папка выгрузки выходов не трогается |

Защищённые образы раннера: его `tex_image`, образ Студии его версии (`image_base:__version__`) и `image_base:latest`
(`studio_protected_refs`). Текущая версия для «старых версий» это версия раннера. Категории строит общая функция из
умолчаний allowlist конфигурации (`compile`, `languagetool`, `office`, `ai`) и репозитория `tex_image` раннера
(`default_docker_categories(tex_image=...)` в `core/docker_disk/categories.py`; умолчания сверены с настройками api
тестом, потому что раннер `api/config` не импортирует).

План строится на раннере по свежему замеру в момент начала (S1). Цель, которой нет в `targets` отчёта, сервер
отвергает до отправки команды (`disk_target_unavailable`), раннер тоже пропускает её с ошибкой шага.

### 5.3 Команда раннеру

```text
RunnerCommand
  id (uuid), runner_id, kind: disk.measure | disk.cleanup,
  payload: {targets: [DiskTarget], include_rollback} (у disk.cleanup) | {} (у disk.measure),
  state: queued | delivered | running | cancelling | done | cancelled | error | expired | lost,
  progress: CommandProgress | null,
  created_by (user id), created_at, delivered_at, updated_at, finished_at

CommandProgress
  steps: [{kind, ref, status: pending | running | done | error | skipped, freed_bytes, error}]
  freed_bytes, error
```

`kind` шага: `build_cache`, `dangling_images`, `image`, `container`, `runner_blobs`, `runner_workspaces` (первые
четыре это `StepKind` локального `cleanup_jobs`). `ref` у образа это `repo:tag` или id висячего слоя, у контейнера
имя, у остальных `null`. Ошибка шага это одна строка до 300 символов (последняя строка stderr Docker, как
`_short_err`).

Переходы:

| Из | В | Когда |
|---|---|---|
| (нет) | `queued` | админ или владелец запустил; у `disk.measure` повторный запрос возвращает уже стоящую в очереди |
| `queued` | `delivered` | раннер забрал команду в `/control/poll` |
| `queued` | `expired` | не забрана за 10 минут |
| `delivered`, `running` | `running` | первый отчёт о ходе |
| `delivered`, `running` | `cancelling` | «Остановить после текущего шага»; раннер узнаёт в ответе на следующий отчёт о ходе |
| `queued` | `cancelled` | остановка до того, как раннер её забрал |
| `delivered`, `running`, `cancelling` | `done`, `cancelled`, `error` | итоговый отчёт раннера |
| `delivered`, `running`, `cancelling` | `lost` | нет отчёта о ходе 3 минуты, раннер отозван или прислал `/offline` |

Из `delivered` сразу в итог (уточнено в B1): `disk.measure` хода не шлёт, раннер присылает свежий `/disk` и
закрывает команду итогом `done` с пустым списком шагов; так же закрывается очистка, которой нечего делать. Таблица
переходов это `COMMAND_TRANSITIONS` в `core/jobs/disk.py`. В ходе раннер может прислать только `running`, `done`,
`cancelled`, `error`.

Одновременно у раннера не больше одной незавершённой `disk.cleanup` (частичный уникальный индекс), повторный запуск
даёт `409 runner_disk_busy`. `disk.measure` при идущей очистке не нужна: раннер присылает замер сам после итога.
Просрочку и потерю ставит периодическая задача `runner_commands_reaper` (раз в минуту, под лидерским замком) и
проверка при чтении.

### 5.4 Прогон «Освободить место»

```text
LifecycleSweep
  id, status: running | cancelling | done | cancelled | error | interrupted,
  started_by (id пользователя или null), started_at, updated_at, finished_at,
  steps: [{key, status: pending | running | done | error | skipped, removed, partitions_dropped, more,
           bytes_before, bytes_after, error}],
  removed_total, freed_bytes
```

Источники берутся из реестра: стратегия движка и `run_now` (сейчас семь, раздел 2.2), в порядке реестра. Каждый
шаг это `LifecycleEngine.run_one(key)` (тот же прогон, что по кнопке источника и по расписанию, с тем же бюджетом и
замком источника). `bytes_before` и `bytes_after` из `source.measure()` до и после; `freed_bytes` это сумма
положительных разностей. `more=true` значит, что бюджет кончился раньше, остальное уйдёт на плановом тике; в итоге
это сказано строкой «часть записей удалится при следующей плановой очистке».

Прогон идёт задачей asyncio в реплике, принявшей запрос, и после каждого шага обновляет строку (`updated_at`).
Одновременно один прогон (частичный уникальный индекс по `status in (running, cancelling)`), второй запуск даёт
`409 lifecycle_sweep_busy`. Строка `running` без обновления дольше 5 минут при чтении и в задаче
`data_lifecycle` становится `interrupted`.

Предпросмотр: для каждого источника `source.count_expired(cutoff, cap=100_000)`. Для `partition_drop` и
`delete_batches` это `SELECT count(*) FROM (SELECT 1 FROM <таблица> WHERE <время> < :cutoff LIMIT :cap + 1)`, с
`statement_timeout` 3 с на запрос (по таймауту `count=null`, на экране «не удалось посчитать»); для `file_sweep`
число файлов старше срока с тем же потолком. Метод добавляется в порт источника движка (`core/lifecycle/ports.py`)
с реализацией по умолчанию `null`.

Уточнение при внедрении (B7): сигнатура `count_expired(now, cutoff, cap) -> ExpiredCount(count, cutoff)`, источник
сам возвращает границу, по которой считал (у гостевых сессий она своя, 7 суток после истечения). Порт это
`Protocol`, поэтому «реализация по умолчанию» означает, что каждый источник реализует метод, а `TableMeasure` (без
своей очистки) отвечает `count=null`. У `jobs` считаются только строки задач: выходы без владельца в хранилище идут по
своему порогу. Счёт идёт через `LifecycleEngine.count_expired(key, cap)`, граница та же, что у `run_one`.
`removed_total` и `freed_bytes` не хранятся отдельными колонками, а считаются из шагов. Закрытый прогон
(`interrupted`, остановка api) переводит шаг `running` в `error` с причиной `interrupted`, а `pending` в `skipped`.

### 5.5 Где хранится

Миграция `dk_01_runner_disk`:

- `runners.disk` (JSONB, последний `RunnerDiskReport`), `runners.disk_at` (время приёма). Как `deployment` и
  `deployment_at`: строка обновляется на месте, роста нет.
- `runner_commands`: поля 5.3, `progress` JSONB, индекс `(runner_id, created_at desc)`, частичный уникальный индекс
  `(runner_id) WHERE kind = 'disk.cleanup' AND state IN ('queued','delivered','running','cancelling')`, каскад при
  удалении раннера. Предел: при вставке удаляются завершённые сверх 20 последних этого раннера.

Миграция `dk_02_lifecycle_sweeps`: таблица `lifecycle_sweeps` по 5.4, шаги JSONB, частичный уникальный индекс на
незавершённый, предел 20 последних при вставке.

Порядок миграций (B7 и B5 идут параллельно): цепочка alembic обязана иметь один head
(`test__migrations__chain__has_single_head`, `head_revision()` при старте). `dk_02_lifecycle_sweeps` ведётся от
`sr_10_new_version_kind`. Срез, который сливается вторым, переставляет свой `down_revision` на ревизию первого:
если B7 уже в `master`, `dk_01_runner_disk` ставит `down_revision = "dk_02_lifecycle_sweeps"`. Номера в именах не
задают порядок, порядок задаёт только `down_revision`.

`notifications.kind` ограничен перечнем в базе, поэтому `dk_01` добавляет в него `runner_disk_cleaned` тем же
приёмом, что `sr_08_notification_kinds`.

Реестр `policies.py`: `runner_commands` (`Group.database`, `Strategy.on_write`), `lifecycle_sweeps`
(`Group.database`, `Strategy.on_write`); подписи в `admin/data.json` (`fixed`: «20 на раннер», «20 прогонов»).

## 6. Протокол раннера

### 6.1 Возможности

Две новые возможности в `SERVER_FEATURES` и в `/announce` раннера:

- `control`: канал команд (6.2). Раннер объявляет её всегда, когда в нём есть хотя бы одна команда.
- `disk`: команды `disk.measure`, `disk.cleanup` и отчёт `/disk`. Объявляет любой раннер новой версии, включая
  Kubernetes и локальную Студию: что из диска у него есть, говорит сам отчёт (`targets`, `docker_reason`).

Команду вида `disk.*` сервер ставит только раннеру, у которого в согласованных `features` есть и `control`, и
`disk`. Список команд расширяемый: будущий вид объявляет свою возможность, а канал остаётся тем же.

Константы `FEATURE_CONTROL` и `FEATURE_DISK` появляются в `wire.py` в B1, а в `SERVER_FEATURES` попадают в B5
вместе с адресами `/control/*` и `/disk`: сервер без этих адресов возможности не согласует, и новый раннер не
откроет канал, которому некому ответить.

### 6.2 Канал команд

Под `/api/runner/v1`, авторизация как у остального протокола (Bearer токен раннера, `X-Runner-Id`). Токен задачи не
нужен: команда принадлежит раннеру, а не задаче.

| Метод и путь | Тело | Ответ | Что |
|---|---|---|---|
| `POST /control/poll` | `{wait_s}` (0..25) | `{command: RunnerCommandEnvelope \| null}` | долгий опрос команд: ответ сразу, как появилась команда для этого раннера, иначе `null` через `wait_s`; забранная команда становится `delivered` |
| `POST /control/{id}/progress` | `{state: running \| done \| cancelled \| error, progress: CommandProgress}` | `{cancel: bool}` | ход и итог; `cancel=true` доставляет остановку; итоговое состояние закрывает команду, повтор итога безвреден |
| `POST /disk` | `RunnerDiskReport` | `204` | последний замер; принимается только после согласования `disk` |

```text
RunnerCommandEnvelope: {id, kind, payload, issued_at}
```

Опрос команд устроен как `/poll` задач: проверка таблицы по `(runner_id, state='queued')`, ожидание пробуждения или
интервала (2 с), `touch` раннера не делает (живость меряет опрос задач), закрывается при уходе клиента, обслуживании
и остановке api (`_poll_gone`). Пробуждение внутри реплики, принявшей команду, мгновенное; на другой реплике не
позже интервала.

Коды ошибок протокола (`RunnerErrorCode`, `contracts/runner/error_codes.json`):

| Код | HTTP | Когда |
|---|---|---|
| `command_not_found` | 404 | чужая или удалённая команда |
| `command_finished` | 409 | ход по уже закрытой (`expired`, `lost`, итог): раннер бросает выполнение после текущего шага |
| `feature_not_negotiated` | 409 | `/control/*` или `/disk` без согласованной возможности |
| `disk_report_too_large` | 413 | отчёт больше 64 КБ |

Уточнено в B5 (`use_cases/jobs/runner_control.py`, `RunnerControlService`):

- Ход по команде, которую раннер ещё не забрал (`queued`), даёт `404 command_not_found`, как чужая. Повтор того же
  итога отвечает `{cancel: false}`; другой итог и любой ход после `expired` или `lost` дают `409 command_finished`.
  Пока команда `cancelling`, ход `running` её не сдвигает, ответ `{cancel: true}`.
- `lost` ставится не только по тишине 3 минуты, но и раннеру, который отозван или прислал `/offline` позже последнего
  хода команды (`runners.offline_at >= runner_commands.updated_at`). Проверка при чтении идёт по одному раннеру
  (`get`, `recent`, `enqueue`), `runner_commands_reaper` раз в минуту по всем.
- Опрос выдаёт команду вида, возможность которого раннер согласовал сейчас: раннер, откатившийся на версию без
  `disk`, команду не получает, и она истекает. Пауза раннера команды не держит.
- `enqueue` прав не проверяет (это B6), но держит правила постановки: без `control` и `disk` это
  `RunnerCommandUnsupportedError` (`409 runner_disk_unsupported` в B6), вторая очистка и `disk.measure` поверх идущей
  очистки `RunnerCommandBusyError` (`409 runner_disk_busy`), повторный `disk.measure` возвращает стоящий.
- Закрытие команды любым путём (итог раннера, остановка до доставки, просрочка, потеря) сообщается наблюдателям
  `IRunnerCommandObserver.command_finished` ровно один раз: переход условный, его делает одна реплика. Сюда B6
  подключает аудит `runner.disk_cleaned` и уведомление.
- `/disk` хранится и у личного раннера (в отличие от `/deployment`): его диск видит владелец. `runners.disk`
  читается отложенно, строку раннера протокол читает на каждом запросе. `runner_commands.created_by` без внешнего
  ключа, как `runners.created_by`. Вид уведомления `runner_disk_cleaned` в `dk_01` заведён на бэкенде целиком
  (перечисление, форма API, проверка в базе); отправка в B6, «Входящие» в W5.

### 6.3 Исполнение на раннере

`RunnerControlLoop` (`infra/runner/control.py`) запускается `RunnerLoop` после удачного `/announce`, если
согласованы `control` и `disk`, и живёт отдельной задачей asyncio рядом с опросом задач: слоты сборок его не
касаются. При `request_stop` опрос команд прекращается, идущая очистка доходит до конца текущего шага и шлёт итог
`cancelled`.

`RunnerDiskService` (`infra/runner/disk.py`) это всё про диск на раннере:

- `measure()`: Docker-часть через `DockerDiskPlanner` (2.1, S2), если `executor=docker`, `host_kind=cli` и
  `docker` отвечает; кэш из `BlobCache.usage()` и `RunnerWorkspaces.usage()`; том `shutil.disk_usage(data_dir)`.
- `cleanup(targets, include_rollback)`: свежий замер, план через `DockerDiskPlanner.plan(...)` (бывший
  `StartDockerCleanupUC.execute` без DI) плюс шаги `runner_blobs` и `runner_workspaces`, запуск в
  `DockerCleanupJobManager` с наблюдателем хода.
- `BlobCache.clear(min_idle_s=600)` и `RunnerWorkspaces.clear()`: те же обходы, что `evict`, с пределом 0 и
  правилами S9; возвращают освобождённые байты.

Общий код (срез B2): `DockerDiskPlanner(probe, protected_refs=..., current_version=..., image_base=...)` с
`measure()` (замер `DockerDiskSnapshot`: только своё, откат защищён, `cleanable_bytes`, `old_versions`) и
`plan(CleanupPlanRequest(targets, include_rollback=...))`; цели не из Docker (`runner_cache`) планировщик пропускает,
Docker недоступен даёт `DockerUnavailableError`. Полоса категорий отчёта считается `category_breakdown(usage)` так же,
как во фронтенде. Шаги кэша подключаются в `DockerCleanupJobManager(manager, extra_steps={"runner_blobs": ...})`
(подменить шаги Docker нельзя), ход принимает `start(steps, observer=...)`: наблюдатель вызывается на каждой смене
статуса шага и после итога, его сбой очистку не останавливает. Исключение подключённого шага становится ошибкой шага
с именем типа исключения (без путей).

Уточнено в B3 (`infra/runner/disk.py`):

- `image_base` раннера это новая настройка `HSE_RUNNER__IMAGE_BASE` с умолчанием `DEFAULT_IMAGE_BASE`
  (`core/docker_disk/categories.py`, совпадает с `image_base` api и `IMAGE` локальной Студии, сверяет тест). Своего
  образа раннер не знает, а ставится из того же реестра, что сервер. Раннер форка с другим реестром без настройки
  не видит образов Студии (они `other`) и ничего из них не удаляет. Тома Студии у раннера: `tex_cache_volume` и
  умолчания томов LanguageTool и Ollama (`DEFAULT_SERVICE_VOLUMES`, тоже сверены с api).
- Причина без Docker выбирается так: `executor=kubernetes` даёт `kubernetes`, иначе `host_kind=desktop` даёт
  `managed_locally`. `targets` при доступном Docker все шесть, иначе только `runner_cache`.
- `usage` и `clear` у кэша и рабочих копий асинхронные, а не обходы `evict` с пределом 0: обход идёт в потоке, а
  блоб удаляется в цикле событий без `await` между проверкой и удалением (замок `ensure` свободен, `mtime`
  перечитан и старше `BLOB_MIN_IDLE_S`). Рабочая папка удаляется под замком своего проекта: задача этого проекта,
  пришедшая во время удаления, ждёт и собирает папку заново из кэша.
- Отчёт: списки по убыванию размера, томов до 32 крупнейших; строка, не влезающая в контракт (пустое имя,
  ссылка длиннее 384), в списки не попадает, а в итогах учтена. Обрезка режет оба списка вместе: 100, затем на
  четверть, пока `json.dumps(encode(report))` больше 64 КБ. `unused_truncated` говорит только про неиспользуемые;
  обрезку старых версий видно по `reclaimable_bytes` больше суммы строк.
- Очистка: Docker-цель, которую раннер выполнить не может (Kubernetes, локальная Студия, Docker не ответил на
  замер), не планируется, причина одной строкой в `CommandProgress.error`, остальные цели выполняются, итог `error`.
  Пустой план закрывается `done` без шагов. Ошибка шага сводится к одной строке до 300 символов.
- API для канала (B4): `measure() -> RunnerDiskReport`; `cleanup(payload, observer) -> DiskCleanupRun` запускает
  очистку в фоне и возвращается сразу (`DiskCleanupBusyError`, если идёт другая); `run.state`, `run.progress`,
  `run.cancel()` (до начала шагов тоже: тогда все шаги `skipped`), `await run.wait()` возвращает итог после того,
  как наблюдатель `(state, progress)` получил его, ровно один раз. Наблюдатель зовётся на каждой смене статуса шага
  с `running` и неизменяемым `CommandProgress`, его сбой очистку не останавливает. Контейнер раннера уже отдаёт
  `RunnerDiskService` (`build_runner_disk_service`), B4 только подключает его к `RunnerControlLoop`.

Ход шлётся не чаще раза в секунду и всегда на смене статуса шага; сбой доставки хода не останавливает очистку
(повтор на следующем), итог повторяется до 10 раз с паузой, как `complete` задачи. После итога раннер сразу шлёт
новый `/disk`. Отчёт раз в 6 часов и после `/announce` идёт тем же путём, что `/deployment` (`_report_*_if_due`).

Локальная Студия как раннер (`infra/remote_runner`) получает тот же `RunnerControlLoop` и `RunnerDiskService` с
`host_kind=desktop`: Docker-часть `null`, цель только `runner_cache`.

Уточнено в B4 (`infra/runner/control.py`, `RunnerControlLoop`):

- Канал открывается, только если согласованы обе возможности, `control` и `disk`; без `control` раннер не шлёт и
  `/disk`. Со старым сервером цикл не стартует и в журнал ничего не пишет. Ответ `404`, `405` или
  `feature_not_negotiated` на опрос команд закрывает канал до следующего `/announce` (повторный `/announce` открывает
  его снова). Подключение одно на оба процесса: контейнер раннера (`RunnerProvider.get_control`) отдаёт цикл и
  консольному раннеру, и сессии локальной Студии.
- Отчёт о диске идёт не через `_report_*_if_due` опроса задач, как `/deployment`, а своей задачей канала: опрос
  задач стоит, пока слоты заняты или шлюз Студии закрыт. Отчёт шлётся при открытии канала (то есть после
  `/announce`), по повторному `/announce`, раз в 6 часов (`DISK_REPORT_EVERY_S`), после итога каждой очистки и по
  `disk.measure`; неудачный повторяется через 5 минут. Замеры идут по одному.
- Ход очистки повторяется раз в минуту, пока шаг идёт дольше (до первого шага это пустой `running`): иначе замер
  Docker перед планом (до 90 с) и долгий `builder prune` упираются в `lost` через 3 минуты тишины.
- Остановка раннера: опрос команд снимается сразу, идущая очистка получает `cancel()`, итог `cancelled` уходит
  раньше `/offline` (по `/offline` сервер считает идущую команду потерянной, B5). Шаг ждут до 30 с, затем снимают
  принудительно и всё равно шлют `cancelled`.
- Ответ `command_finished` или `command_not_found` на ход останавливает очистку после текущего шага, дальше ход и
  итог по этой команде не шлются. Очистка при уже идущей закрывается `error` со строкой «another disk cleanup is
  already running on this runner». Повторная доставка того же id (раннер помнит последние 64) не запускает команду
  второй раз: идущая продолжается, по завершённой повторяется итог. Команда, которую раннер не может разобрать
  (неизвестный вид), закрывается `error` по своему id, если он читается.
- Пустой ответ опроса быстрее секунды (`HSE_RUNNER__POLL_WAIT_S=0`) ждёт остаток секунды. В сессии локальной
  Студии опрос команд не считается признаком связи: «в сети» по-прежнему говорит только опрос задач.

### 6.4 Совместимость

| Сервер | Раннер | Что происходит |
|---|---|---|
| новый | старый (нет `disk` в `features`) | `GET .../disk` отвечает `supported=false`, `reason=outdated`; экран «Обновите раннер, чтобы видеть диск»; команды не ставятся (`409 runner_disk_unsupported`) |
| старый | новый | `/announce` возвращает пересечение без `control` и `disk`: раннер не открывает канал и не шлёт `/disk`, работает как раньше |
| старый (до `/announce`) | новый | `/announce` отвечает 404, раннер на протоколе 1.0, как сейчас |
| новый | новый, Kubernetes | отчёт без Docker-части, цель `runner_cache` |
| новый | новый, локальная Студия | отчёт без Docker-части с причиной `managed_locally` |

Минимальная версия раннера для диска это первая версия со срезом B4; экран берёт её из ответа (`min_version`), а не
из кода фронтенда.

### 6.5 Порядок изменения контракта

Как требует `wire.py`: сначала `contracts/runner/openapi.yaml` и `error_codes.json` с фикстурами, затем модель
`wire.py` и `disk.py`, затем pydantic-схемы; контрактный тест сверяет все три.

### 6.6 Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| команда в ответе `/poll` задач | раннер без свободного слота `/poll` не открывает: занятый длинной очередью раннер получит команду через десятки минут, локальная Студия с закрытым шлюзом никогда |
| команда в ответе `/poll` и пульса задачи | два пути доставки, раннер без задач и без слотов (закрытый шлюз) всё равно глух; сложнее рассуждать о повторах |
| очистка как задача очереди (`JobKind.runner_disk`) с привязкой к раннеру | очередь не умеет адресовать конкретный раннер, задача прошла бы квоты, справедливую очередь и теги; заняла бы слот сборки; повторы аренды для очистки вредны |
| сервер присылает список образов к удалению | нарушает S1: расширяет то, что может удалить взломанный или устаревший сервер |
| раннер поднимает свой HTTP-порт для команд | раннеры стоят за NAT и не принимают входящих (весь протокол тянущий) |
| в Kubernetes чистить образы узла DaemonSet-ом с `hostPath` на сокет containerd | привилегированный под на каждом узле против PodSecurity restricted; kubelet и так делает это сам |

## 7. Права и безопасность

| Действие | Админ установки, общий раннер | Админ установки, чужой личный | Владелец личного | Остальные |
|---|---|---|---|---|
| видеть «Диск», обновить замер | да | да | да | нет (404) |
| очистка любой цели, кроме отката | да | да, владельцу уведомление | да | нет |
| удалить и предыдущую версию (`include_rollback`) | да | нет (`403 forbidden`) | да | нет |
| остановить идущую очистку | да | да | да | нет |
| «Освободить место» в «Хранилище» | да | | | нет |

- Админские адреса под `admin_guard`: только сессия, без PAT, как вся админка. Владелец ходит в
  `/api/v1/account/runners/{id}/disk*` с теми же правилами, что остальные адреса «Мои раннеры»
  (`RunnerRegistry.my_runner`: чужой раннер это 404).
- В `RunnerRegistry` добавляется `require_disk_access(actor, runner, *, rollback)`: админ установки или владелец
  `owner_kind=user`; откат только владельцу, если раннер личный.
- Раннер отозван: 404. Раннер на паузе: диск доступен (пауза про задачи, а не про обслуживание).
- Сервер не может удалить на раннере ничего, кроме неиспользуемых образов Студии, её остановленных контейнеров, кэша
  сборки и кэша раннера (S1). Тома, чужие образы и контейнеры недостижимы ни из одного плана.
- В Kubernetes у раннера нет прав сверх нынешней Role (`pods`, `pods/log`, `pods/exec` в своём namespace): диск
  раннера читается из его PVC, узел не трогается.
- Отчёт раннера не содержит путей и id проектов (5.1), поэтому админ, глядя на чужой личный раннер, не узнаёт, над
  какими проектами там работали.

## 8. Аудит, уведомления, метрики, MCP

### 8.1 Аудит

| Событие | Когда | Актор | `target` | `details` |
|---|---|---|---|---|
| `runner.disk_cleanup` | команда очистки поставлена | кто запустил | id раннера | `targets`, `include_rollback`, `owner_kind`, `owner_id`, `command_id` |
| `runner.disk_cleanup_cancel` | остановка | кто остановил | id раннера | `command_id` |
| `runner.disk_cleaned` | итог очистки (`done`, `cancelled`, `error`, `lost`, `expired`) | кто запустил | id раннера | `command_id`, `state`, `freed_bytes`, `errors` (число), `steps` (число) |
| `lifecycle.sweep` | прогон запущен | админ | `all` | `sweep_id`, `sources` |
| `lifecycle.sweep_cancel` | остановка прогона | кто остановил | `all` | `sweep_id` |
| `lifecycle.swept` | итог прогона (`done`, `cancelled`, `error`, `interrupted`) | кто запустил | `all` | `sweep_id`, `status`, `removed`, `freed_bytes`, `errors` |

Уточнение при внедрении (B7): поле `keys` в `details` переименовано в `sources`: журнал вычёркивает значения под
ключами, в имени которых есть `key`, `token`, `secret` и подобное (`core/identity/redaction.py`), поэтому `keys`
приходил бы как `[redacted]`. То же правило касается полей B6. Событие остановки прогона добавлено по образцу
`runner.disk_cleanup_cancel`: тест покрытия аудита требует события у каждой изменяющей ручки админки.

`disk.measure` в аудит не пишется: это чтение. Подписи всех новых действий в `admin/audit.json` ru и en в том же
срезе, что пишет событие: тест `auditActions.test.ts` сверяет коды домена `runner` в коде бэкенда с подписями.

### 8.2 Уведомления

`runner_disk_cleaned` владельцу личного раннера, только если очистку запустил не он; только «Входящие», без письма.
Payload: `runner_id`, `runner_name`, `freed_bytes`, `state`. Переход ведёт в «Мои раннеры» с открытым «Диском».

Уточнено в B6: форма уведомления общая (`NotificationPayload`), поэтому поля легли так: `ref_id` id раннера,
`excerpt` имя раннера, `actor_name` кто чистил, `outcome` итог (`done`, `cancelled`, `error`, `lost`), новое поле
`freed_bytes` (число, у остальных видов `null`; в API `NotificationPayloadModel.freed_bytes`, в эталонах
`Notification*` явным `null`). Уведомление уходит только по итогу команды, которую раннер успел забрать
(`delivered_at` есть): просроченная или остановленная до доставки очистка ничего не удалила. Ключ повтора
`runner_disk_cleaned:<id команды>`. Вид во фронтенде завёл W5; там же `freed_bytes` в zod-схеме стало обязательным
(у прочих видов `null`, как в эталонах) и появился эталон `Notification/runner_disk_cleaned.json`.

### 8.3 Метрики

`/metrics`: `hse_runner_disk_cleanable_bytes{scope="shared"|"personal"}` (сумма по последним отчётам),
`hse_runner_disk_cleanups_total{state}`, `hse_lifecycle_sweeps_total{status}`. Метки по раннеру не вводим: число
раннеров не ограничено.

Уточнено в B6: `hse_runner_disk_cleanable_bytes` пересчитывает `runner_commands_reaper` (раз в минуту, у лидера) по
проекции замеров неотозванных раннеров с `disk`; до первого пересчёта семейства нет. `hse_runner_disk_cleanups_total`
считает наблюдатель итога в процессе, где команда закрылась (ровно один раз на команду), только `disk.cleanup`.
В аудите `runner.disk_cleaned` поле `errors` это число шагов с ошибкой плюс один, если у хода есть общая причина.

### 8.4 MCP

Не нужен. Админские тулы MCP только читают (`admin_runner_summary` и соседи, `mcp.md`, M7), а удаление образов на
чужих машинах это ровно то, что не стоит отдавать агенту: польза мала (админ делает это раз в месяц одной кнопкой),
риск в том, что модель по ошибке снимет откат. Если понадобится, сводка диска добавляется в `admin_runner_summary`
полями только для чтения отдельным решением.

### 9.1 Админка и «Мои раннеры»

|---|---|---|---|
| `GET /api/admin/runners/{id}/disk` | админ | диск раннера | `RunnerDiskView` |

Списки раннеров (`RunnerInfo` админки, `MyRunner`) получают поле `disk: {supported, cleanable_bytes, measured_at} |
null`: по нему меню решает, показывать ли пункт как обычный или с пометкой «обновите».

```text
RunnerDiskView
  runner_id, supported, reason: outdated | null    (отозванный раннер: 404, раздел 7),
  min_version (с какой версии раннер сообщает диск),
  online (раннер на связи сейчас), last_seen_at,
  report: RunnerDiskReport | null, received_at, stale (замер старше суток),
  command: RunnerDiskCommand | null    (незавершённая очистка или последняя завершённая за 24 часа),
  measuring: bool                      (стоит или идёт disk.measure),
  can_clean (поддержан, на связи, замер есть, очистка не идёт),
  can_include_rollback (права раздела 7 и `old_versions` в targets отчёта),
  personal_owner: {id, name} | null    (только в админке и только у личного раннера)

  id, kind, state, targets, include_rollback, created_at, finished_at,
  created_by: {id, name} | null, progress: CommandProgress | null
  у disk.measure: targets [], include_rollback false

RunnerDiskCleanupRequest
  targets: [DiskTarget] (1..6, без повторов), include_rollback: bool

RunnerDiskSummary
  reporting (сколько неотозванных общих раннеров прислали отчёт), outdated (сколько не умеют),
  min_version, cleanable_bytes (сумма по общим),
  top: [{runner_id, name, cleanable_bytes, measured_at}] (до 3 общих по убыванию)
```

`created_by` в `RunnerDiskCommand` B6 отдаёт именно объектом `{id, name}` (имя берётся соединением с
пользователями), а `null`, если человека уже нет. Это отличается от
`started_by` прогона «Освободить место» (9.2, только id): диалог «Диск» показывает, кто запустил очистку, а
плашка прогона имени не показывает.

Коды ошибок (тело `{code, detail}`, как `IdentityError`):

| Код | HTTP | Когда |
|---|---|---|
| `not_found` | 404 | нет раннера, отозван, чужой личный для владельца |
| `forbidden` | 403 | откат чужого личного раннера админом (не админ и не владелец получают 404, раздел 7) |
| `runner_disk_unsupported` | 409 | раннер не согласовал `control` и `disk` |
| `runner_offline` | 409 | раннер не на связи (тот же критерий, что статус `offline` в списке) |
| `runner_disk_busy` | 409 | у раннера уже идёт очистка |
| `disk_target_unavailable` | 409 | цели нет в `targets` последнего отчёта (Kubernetes, Docker недоступен) |
| `input_invalid` | 422 | пустой или повторяющийся список целей; `include_rollback` без цели `old_versions` |
| `command_finished` | 409 | остановка уже закрытой команды |

Уточнено в B6 (`use_cases/jobs/runner_disk.py`, `RunnerDiskUC`, `RunnerDiskObserver`):

- Права. `RunnerRegistry.require_disk_access(actor, runner, *, rollback)`: владелец личного раннера может всё (админ
  на своём личном раннере тоже владелец, откат ему доступен); админ установки может всё, кроме отката чужого личного
  (`403 forbidden`); остальным и отозванному раннеру 404. Админские адреса не админу отвечают 404 ещё в
  `admin_guard`, «Мои раннеры» находят раннер через `RunnerRegistry.my_runner` (чужой это 404).
- Порядок проверок очистки: 404, `input_invalid` (пустой список, повторы, неизвестная цель, откат без
  `old_versions`; проверяется в сценарии до сборки `DiskCleanupPayload`, поэтому тело с кодом, а pydantic проверяет
  только виды целей и не больше шести), 403 отката, `runner_disk_unsupported`, `runner_offline`, `runner_disk_busy`,
  `disk_target_unavailable`. «Обновить» проверяет поддержку и связь, при идущей очистке `runner_disk_busy`.
- `online`: статус раннера без учёта паузы (пауза про задачи) равен `online` или `stale`; `offline`, отозванный и
  личный при выключенных личных раннерах не на связи.
- `report` у неподдержанного раннера (откатился на версию без `disk`) `null`, даже если старый замер в базе есть.
  `command` это незавершённая очистка или последняя завершённая с `finished_at` не старше суток; `disk.measure` в
  `command` не попадает, его видно по `measuring`.
- Остановка принимает только `disk.cleanup`: id замера, чужой и неизвестный id дают `404 not_found`. Коды протокола
  раннера наружу не уходят: `command_not_found` становится `not_found`, `command_finished` остаётся собой.
- Списки и сводка читают не отчёты целиком, а проекцию `IRunnerDiskStore.list_disk_briefs` (правило 9.3 считается в
  SQL в `bigint`), через `RunnerControlService.disk_briefs`. В сводке `reporting` это неотозванные общие раннеры с
  `disk` и замером, `outdated` неотозванные общие без `disk`, в `top` только раннеры с `cleanable_bytes > 0`.
- `min_version` это `DISK_MIN_RUNNER_VERSION` в `core/jobs/disk.py` (0.22.0, первая версия со срезом B4).

### 9.3 Общие правила

Схемы строгие (`extra=forbid`, `z.strictObject`), все поля приходят явно, пустое значение `null`, время ISO 8601 UTC,
размеры в байтах целыми. Фронтенд опрашивает `GET .../disk` раз в 2 с, пока команда не закрыта, иначе раз в 30 с
при открытом диалоге; `GET .../sweep` раз в 2 с, пока прогон идёт.

`cleanable_bytes` сводки, поля `disk` в списках и строки «можно освободить» считаются одним правилом:
`docker.cleanable_bytes` (если Docker ответил) плюс кэш файлов и рабочие копии раннера целиком. `disk.measure`
во время идущей очистки даёт `409 runner_disk_busy`: раннер сам пришлёт замер после итога.

## 10. Тесты

Бэкенд:

- `DockerDiskPlanner` на фейковом `run_docker`: те же сценарии, что сейчас у локального «Диска» (защита активного

  не отвечает; отчёт меньше 64 КБ при 1000 образах (обрезка).
- `RunnerControlLoop` на `httpx.MockTransport`: забор команды, ход, остановка по `cancel`, итог с повторами,

  сервиса с общей базой, `/disk` отвергает лишние поля и большой отчёт, `feature_not_negotiated`.
- Права таблицей раздела 7 (админ, владелец, чужой, откат), аудит каждого события, уведомление только при чужом
  запуске.
- «Освободить место»: предпросмотр с потолком и таймаутом, прогон по всем источникам с ошибкой одного (остальные
  идут), остановка, `interrupted` по устаревшему `updated_at`, `lifecycle_sweep_busy`, `freed_bytes` из разностей.
- Контрактный тест протокола раннера (openapi, `wire.py`, pydantic) и сверка `error_codes.json`.

## 13. Открытые вопросы

- Сделать ли админа установки только зрителем диска чужого личного раннера (S8). Сейчас он может чистить, кроме
  отката, а владелец узнаёт из «Входящих».
- Автоочистка раннера по порогу: раннер сам чистит кэш сборки и висячие образы, когда на томе Docker меньше 10%
  свободного. Тот же `RunnerDiskService`, но решение о пороге и о том, кто его настраивает (админка или
  `HSE_RUNNER__*`), отдельно.
- Апдейтер сервера после удачного обновления сам удаляет версии старше предыдущей: тогда «Старые версии» на хосте
  сервера почти всегда пусты.
- Запуск фоновых уборок (`blob_gc`, `orphan_gc`, `project_purge`) из «Освободить место»: нужен `run_now(name)` у
  `BackgroundTaskRunner` под лидерским замком.
- Kubernetes: показывать занятое образами на узле только для чтения (kubelet `stats/summary`) требует права
  `nodes/proxy`, которого у Студии нет; без него остаётся текст.
- Одной кнопкой чистить все общие раннеры сразу (сейчас по одному, S12).
