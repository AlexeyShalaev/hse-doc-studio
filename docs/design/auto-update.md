# Автообновление серверной установки

Как установка в режиме `server` узнаёт о новых релизах, ставит их без девопса и возвращается назад, если версия не поднялась. Опирается на `docs/design/backups.md` (полный бэкап перед обновлением), на защиту `db-ahead` в `infra/db/migrator.py` и на `docs/ru/deploy/operations.md` (ручной порядок обновления, который эта подсистема автоматизирует).

Решения ниже приняты по умолчанию; неочевидные помечены **Развилка**. Для одиночной установки в одном контейнере (all-in-one, личная Студия) остаётся прежний механизм `infra/update/updater.py`: он не затронут.

## 1. Что было и чего не хватало

- `ensure_db_current`/`migrate_if_needed`: api под advisory-локом доводит схему до head при старте (`HSE_STUDIO__DB__AUTO_MIGRATE`, в Helm этим занят Job). Образ старше схемы не стартует (`DbAheadError`): откатить образ без отката базы нельзя.
- Обновление compose-установки руками: `docker compose pull && up -d`, без бэкапа, без проверки здоровья, без отката.
- Одиночный self-updater (`infra/update/updater.py`) пересоздаёт один контейнер и откатывает его по healthcheck. Он не знает про Postgres, миграции и несколько сервисов.
- Бэкапы (`feat/backups`) есть, но с обновлением не связаны.
- Самодиагностики установки в master нет, поэтому здоровье проверяется пробой (раздел 6).

## 2. Архитектура: кто что делает

```
 админка / планировщик                 сервис updater                   docker host
 ┌────────────────────┐   poll (HTTP)  ┌───────────────────┐  docker.sock  ┌──────────┐
 │ api: UpdateService │◄───────────────│ server_updater    │──────────────►│ postgres │
 │  решения, учёт,    │   events       │  снимок, образ,   │               │ api      │
 │  аудит, уведомления│◄───────────────│  миграции, откат  │               │ runner   │
 └────────────────────┘                └───────────────────┘               └──────────┘
```

**api только решает и ведёт учёт.** У него нет доступа к docker и не будет. Он:

- спрашивает фид релизов (GitHub Releases, `infra/update/feed.py`) и хранит список в `instance_settings`;
- по политике решает: молчать, сообщить или завести запуск (`core/server_update/decision.py`, чистая функция);
- ведёт журнал запусков (`update_runs`, миграция `up_01_server_updates`), аудит, уведомления, метрики;
- запускает полный бэкап перед обновлением и ждёт его результата.

**Исполняет отдельный сервис `updater`** (тот же образ приложения, `python -m hse_doc_studio.infra.update.server_updater`, только стандартная библиотека и docker CLI). Он сам приходит за работой: `POST /api/updater/v1/poll` раз в 15 секунд, во время запуска каждые 30 секунд сердцебиением. Результат шлёт событиями `POST /api/updater/v1/runs/{id}/events`.

**Развилка (почему не внутри api).** Обновляемый процесс не может надёжно заменить сам себя: на середине пересоздания он умирает вместе с состоянием запуска. Исполнитель обязан пережить гибель api и Postgres, поэтому он отдельный контейнер со своим журналом на диске (`updater-data`). Это же причина, по которой откат с восстановлением базы возможен: восстановить базу, из которой живёт api, изнутри api нельзя.

**Развилка (поллинг, а не команда от api).** Апдейтер ходит к api, а не наоборот. Апдейтеру не нужен входящий порт, а у api нет канала, по которому можно приказать что-то хосту: даже взломанный api не получает возможности запустить произвольную команду на хосте, он может лишь завести запись «обновить на версию X» (версия проверяется апдейтером по формату и по дайджесту). Секрет протокола `UPDATER_TOKEN` (Bearer, сравнение за постоянное время, перебор режется по IP, без токена протокол закрыт).

### Опасность docker.sock

Сокет docker равен root на хосте. У апдейтера он есть (иначе нечем пересоздавать контейнеры), как уже есть у раннера. Меры:

- профиль compose `updater` включается отдельно и сознательно; без `UPDATER_TOKEN` исполнитель выключен, Студия только сообщает о версиях;
- апдейтер не публикует портов, принимает работу лишь от api по общему секрету, версия цели проверяется регуляркой `\d+.\d+.\d+` и дайджестом;
- образ берётся из того же репозитория, что у работающего api (`plan.target_ref`): подменить репозиторий через api нельзя;
- пересоздание отказывается работать с контейнерами, у которых есть опции, которые оно не переносит (`privileged`, `cap_add`, `devices`, `tmpfs` и т. п.): список в `plan.unsupported_options`; запуск отменяется до любых изменений, оператор обновляет руками;
- опорные данные (DSN, ключи) апдейтер получает из окружения контейнера api через временный `--env-file` с правами 0600 и удаляет его по окончании, в командной строке секретов нет.

Более узкую альтернативу (прокси к сокету с белым списком вызовов, rootless docker) оператор может поставить сам: апдейтер ходит к docker только через CLI и `DOCKER_HOST`.

**Развилка (Helm).** В Kubernetes api сам не обновляется и апдейтера нет: `server_update.executor = none` (умолчание). Проверка релизов, уведомления и страница работают, а ставит версию оператор командой `helm upgrade … --atomic --wait`: откат при неуспехе делает Helm, миграции идут pre-upgrade Job’ом с `activeDeadlineSeconds`. Страница показывает готовую команду. Исполнитель на Kubernetes API (ServiceAccount с правом патчить один Deployment) не делаем: Helm и GitOps (Argo CD, Flux) решают эту задачу лучше и уже у оператора есть.

## 3. Проверка релизов

- Канал `stable`: фид GitHub Releases без черновиков и предрелизов (`prerelease` отфильтрован). Других каналов не публикуем; ключ `update.channel` оставлен под будущее, API принимает только `stable`.
- Источник: `HSE_STUDIO__UPDATE_FEED_URL` (по умолчанию официальные релизы), тот же, что у кнопки «проверить» в личной Студии; зеркало или форк задаются им же, `off` выключает сеть.
- Период проверки 6 часов, после неудачи повтор через 30 минут; результат (список релизов с заметками и ссылкой на `image-digest.json`) хранится в базе, поэтому переживает рестарт и офлайн.
- Подпись и дайджест (раздел 7).

## 4. Политика и окно

Настройки в `instance_settings` (`update.*`), правятся в админке и пишутся в аудит:

| Ключ | Значения | Умолчание |
|---|---|---|
| `policy` | `off` (не проверять), `notify` (сообщать), `auto` (ставить в окно) | `notify` |
| `max_bump` | `patch`, `minor`: самый крупный шаг без человека | `minor` |
| `window_days`, `window_start_min`, `window_minutes` | дни недели (0 = понедельник), начало в минутах от полуночи UTC, длительность 15..1440 | каждый день, 02:00, 180 минут |
| `backup_first` | ждать успешного полного бэкапа | да |
| `verify` | `digest`, `cosign`, `none` | `digest` |
| `notify_admins` | уведомления во «Входящие» | да |

**Развилка (умолчание `notify`).** Установка не обновляется сама, пока администратор не включил `auto`: поведение после апгрейда не меняется молча.

**Развилка (мажорные версии).** Шаг `major` политика не ставит никогда, только сообщает; ставится вручную кнопкой. Внутри разрешённого шага берётся самая новая версия (при 0.3.1 и релизах 0.3.5, 0.4.0, 1.0.0 цель 0.4.0 при `minor` и 0.3.5 при `patch`).

Решение планировщика (`decide`), от дешёвых проверок к зависящим от окружения: политика выключена; нет релиза новее; `notify` (одно уведомление на версию); шаг слишком крупный; исполнитель выключен; запуск уже идёт; версия уже откатывалась или падала (повтор каждый тик бессмыслен, ждём следующий релиз); апдейтер молчит; вне окна; иначе старт. Окно может переходить через полночь, день недели относится к началу окна.

## 5. Порядок обновления

```
api:      запрос (авто или кнопка) -> [полный бэкап] -> queued
updater:  preflight -> snapshot -> pull -> verify -> stop -> migrate -> restart -> health -> finish
                                                     └ любой сбой отсюда и ниже: rollback [-> restore] -> health
```

1. **Запрос.** Запись `update_runs` создаётся с уникальным частичным индексом «не больше одного активного запуска». Если `backup_first` и есть назначение бэкапов, статус `waiting_backup`: api запускает обычный полный бэкап (`BackupService`), планировщик ждёт его итога. Бэкап не удался: запуск `cancelled`, админы получают уведомление, ничего не тронуто. Назначения нет: предупреждение в журнале запуска и баннер на странице, обновление идёт со снимком базы. Другой бэкап уже идёт: ждём до 2 часов.
2. **Preflight.** Находит контейнеры сервисов по меткам compose, проверяет поддерживаемые опции и свободное место под снимок.
3. **Snapshot.** Одноразовый контейнер текущего образа в сети api с его окружением: `hse-doc-studio db current` (ревизия «до») и `hse-doc-studio db snapshot --out …` (`pg_dump -Fc` клиентом версии сервера, с контрольной суммой) в том `updater-data`. Предыдущий образ закрепляется локальным тегом `<репозиторий>:rollback-prev`, чтобы чистка образов его не убрала. Это обязательный снимок базы: он есть независимо от того, настроен ли внешний бэкап.
4. **Pull + verify.** `docker pull <репозиторий>:<версия>`; проверка по выбранному режиму (раздел 7). Отказ: запуск `cancelled`, система не тронута.
5. **Stop.** Раннер, затем api. С этой точки отказ ведёт в откат. Простой от остановки до healthy обычно 1–3 минуты; в личной установке это уместно, для кафедры окно ночью.
6. **Migrate.** Одноразовый контейнер новой версии `db upgrade` при остановленных api и раннере: никто не пишет в базу во время миграции, и api не стартует на полу-схеме. Затем `db current` (ревизия «после»).
7. **Restart.** Контейнеры пересоздаются `docker run` из `docker inspect` старых: порты, тома, окружение, сети **с алиасами** (имя сервиса в сети compose), метки compose, healthcheck, ротация логов, группы. Порядок: api, раннер.
8. **Health.** Контейнеры работают (у раннера и апдейтера проверка образа `curl :8000` отключена в compose: у них нет HTTP, и «unhealthy» навсегда откатывало бы каждое обновление), не перезапускаются по кругу (`RestartCount` не растёт), healthcheck api `healthy`, и `GET /health/ready` отвечает 200 непрерывно 20 секунд; всё в пределах 5 минут. Самодиагностики установки в master нет, поэтому проба простая; когда она появится, достаточно заменить проверку в `Engine._healthy_once`.
9. **Finish.** Событие `succeeded` с ревизиями; в `.env` установки `TAG=<версия>` (если файл доступен на запись), чтобы ручной `compose up` не вернул старое; из снимков остаются два последних.

### Откат

Автоматический, при любом сбое после остановки (миграция, запуск, здоровье, непредвиденная ошибка, смерть самого апдейтера):

1. Остановить и удалить новые контейнеры.
2. Если миграции начинались, узнать ревизию базы новым образом. **Ревизия изменилась** (миграции прошли): старый образ не запустится на схеме новее себя (`DbAheadError`), поэтому база восстанавливается из снимка (`db restore-snapshot`: схема `public` пересоздаётся и дамп разворачивается через `psql --single-transaction`, всё или ничего; `pg_restore --clean` на партиционированных таблицах падает) старым образом. Так как api был остановлен всё время между снимком и миграцией, данные не теряются. Журнал `update_runs` лежит в той же базе: при восстановлении его строки сохраняются и возвращаются поверх снимка, иначе откат стёр бы запись самого себя и предыдущего обновления. События для неизвестного api запуска (404) апдейтер отбрасывает. **Ревизия не изменилась** (патч без миграций): база не трогается, пишущий api мог принять данные, их терять незачем.
3. Пересоздать контейнеры из прежних образов: по имени, если тег всё ещё указывает на тот же образ, иначе по **идентификатору** (тег мог двинуться; контейнер из идентификатора теряет имя образа, поэтому имя восстанавливается по тегам образа при следующем запуске) и дождаться здоровья.
4. Итог `rolled_back` (с признаком `db_restored`) или `failed`, если восстановление или возврат не удались: в сообщении точное место снимка и команда `docker compose up -d`.

**Развилка (потеря данных при откате после здорового старта).** Если новая версия поднялась, проработала и сломалась позже, автоматического отката нет: откат по кнопке (см. ниже) с явным подтверждением потери данных. Автоматически откатываем только то, что не прошло проверку здоровья в самом обновлении.

**Устойчивость к падению апдейтера.** Каждый шаг пишется в журнал на диске до исполнения. При старте апдейтер читает журнал: запуск, дошедший до остановки, откатывается по той же процедуре; не дошедший, закрывается как отменённый. События, не доставленные в api (он гасится на время обновления), лежат в очереди журнала и уходят по порядку после возвращения.

### «Откатить» по кнопке

Доступна, пока текущая версия равна цели последнего успешного обновления и у апдейтера есть закреплённые прежние образы. Если обновление меняло ревизию базы, откат восстановит снимок, снятый перед обновлением, и **всё записанное после обновления будет потеряно**: кнопка требует явного подтверждения (`restore_db`), без него API отвечает 422. Если схема не менялась, откат возвращает образы и данные не трогает. Перед откатом с потерей данных, как и перед обновлением, идёт полный бэкап. Если откат не поднялся, апдейтер возвращает образы, что стояли до него, и сообщает `failed`.

## 6. Журнал, аудит, уведомления, метрики

- **Журнал** `update_runs`: вид (обновление/откат), инициатор (авто/ручной), статусы `waiting_backup`, `queued`, `running`, `succeeded`, `rolled_back`, `failed`, `cancelled`, фаза, версии и ревизии «до/после», ссылка на запуск бэкапа, события (до 300, с `seq` для идемпотентной доставки «хотя бы раз»), код и текст ошибки.
- **Потерянные запуски** (уборка планировщика): `queued` без апдейтера дольше 10 минут отменяется (`updater_offline`); `running`, от которого апдейтер молчит больше 15 минут, становится `failed` (`updater_lost`). Пока апдейтер шлёт сердцебиение, длинный `pull` не считается потерей.
- **Аудит**: `update.check`, `update.settings_update`, `update.run_request` (с `trigger`), `update.rollback_request`, `update.run_cancel`, `update.run_finish` (исход, версии, ревизии, `db_restored`, длительность).
- **Уведомления**: `system_alert` с кодом в `outcome` (`update_available`, `update_succeeded`, `update_rolled_back`, `update_failed`, `update_cancelled`), версия в `path`, причина в `excerpt`; получают активные администраторы, переход ведёт на страницу «Обновления». Новой миграции для вида не нужно.
- **Метрики** (`/metrics`, из снимка планировщика): `hse_update_available`, `hse_update_updater_up`, `hse_update_executor_enabled`, `hse_update_run_active`, `hse_update_last_check_timestamp_seconds`, `hse_update_policy{policy}`, `hse_update_runs_total{result}`, `hse_update_last_run_timestamp_seconds`, `hse_update_last_run_success`, `hse_update_last_run_duration_seconds`. Алерты: `hse_update_updater_up == 0` при `hse_update_executor_enabled == 1`; `hse_update_last_run_success == 0`.

## 7. Подпись и дайджест образов

`publish.yml` после публикации образа:

1. подписывает образ по дайджесту `cosign sign --yes` (keyless, OIDC GitHub, подпись рядом с образом в реестре);
2. прикладывает к релизу GitHub файл `image-digest.json` (`{image, version, digest}`, `digest` это дайджест индекса мультиархитектурного образа).

Апдейтер после `docker pull`:

- `verify = digest` (умолчание): дайджест из `RepoDigests` скачанного образа должен совпасть с дайджестом из файла релиза (файл берётся только по https, до 64 КБ, версия в файле должна совпасть с целевой). Нет файла или дайджеста: запуск отменяется (`digest_missing`), оператор может сознательно выбрать `none`;
- `verify = cosign`: дополнительно `cosign verify` в контейнере `ghcr.io/sigstore/cosign/cosign` с привязкой к workflow `publish.yml` этого репозитория на теге релиза (`--certificate-identity-regexp`, `--certificate-oidc-issuer https://token.actions.githubusercontent.com`);
- `verify = none`: для закрытых зеркал и форков, в журнале предупреждение.

**Развилка.** Дайджест из релиза защищает от подмены образа в реестре, но не от взлома самого репозитория GitHub: от него защищает подпись cosign с привязкой к workflow. Релизы, вышедшие до этой подсистемы, дайджеста не имеют: с ними `digest` не пройдёт, для них нужна ручная установка или `none`.

## 8. Страница админки «Обновления»

Раздел `/admin/updates`: установленная и доступная версии с заметками, время проверки, состояние апдейтера, ближайшее окно; кнопки «Проверить сейчас», «Обновить сейчас» (подтверждение с предупреждением о простое), «Откатить на X» (подтверждение; при смене схемы с предупреждением о потере данных); политика, предел шага, дни и время окна (UTC), бэкап, проверка образа, уведомления; история с исходом и ходом запуска (события по фазам). Баннеры: идёт запуск (с «Отменить», пока апдейтер не начал), последний запуск откатился или упал, апдейтер не отвечает, исполнитель не подключён (Helm: готовая команда), нет назначения бэкапов, фид не ответил. Во время обновления api гаснет: опросы статуса не повторяются при ошибке, страница восстанавливается сама.
