# Автообновление серверной установки

Как установка в режиме `server` узнаёт о новых релизах, ставит их без девопса и возвращается назад, если версия не поднялась. Опирается на `docs/design/backups.md` (полный бэкап перед обновлением), на защиту `db-ahead` в `infra/db/migrator.py` и на `docs/ru/deploy/operations.md` (ручной порядок обновления, который эта подсистема автоматизирует).

Решения ниже приняты по умолчанию; неочевидные помечены **Развилка**. Для одиночной установки в одном контейнере (all-in-one, личная Студия) остаётся прежний механизм `infra/update/updater.py`: он не затронут. Исполнителей два: `compose` (разделы 2 и 5) и `kubernetes` (раздел 5а, решение владельца продукта от 03.11.2026).

## 1. Что было и чего не хватало

- `ensure_db_current`/`migrate_if_needed`: api под advisory-локом доводит схему до head при старте (`HSE_STUDIO__DB__AUTO_MIGRATE`, в Helm этим занят Job). Образ старше схемы не стартует (`DbAheadError`): откатить образ без отката базы нельзя.
- Обновление compose-установки руками: `docker compose pull && up -d`, без бэкапа, без проверки здоровья, без отката.
- Одиночный self-updater (`infra/update/updater.py`) пересоздаёт один контейнер и откатывает его по healthcheck. Он не знает про Postgres, миграции и несколько сервисов.
- Бэкапы (`feat/backups`) есть, но с обновлением не связаны.
- Самодиагностики установки в master нет, поэтому здоровье проверяется пробой (раздел 6).

## 2. Архитектура: кто что делает

```
 админка / планировщик                 сервис updater                   docker host
 ┌────────────────────┐   poll (HTTP)  ┌───────────────────┐  docker.sock  ┌──────────┐
 │ api: UpdateService │◄───────────────│ server_updater    │──────────────►│ postgres │
 │  решения, учёт,    │   events       │  снимок, образ,   │               │ api      │
 │  аудит, уведомления│◄───────────────│  миграции, откат  │               │ runner   │
 └────────────────────┘                └───────────────────┘               └──────────┘
```

**api только решает и ведёт учёт.** У него нет доступа к docker и не будет. Он:

- спрашивает фид релизов (GitHub Releases, `infra/update/feed.py`) и хранит список в `instance_settings`;
- по политике решает: молчать, сообщить или завести запуск (`core/server_update/decision.py`, чистая функция);
- ведёт журнал запусков (`update_runs`, миграция `up_01_server_updates`), аудит, уведомления, метрики;
- запускает полный бэкап перед обновлением и ждёт его результата.

**Исполняет отдельный сервис `updater`** (тот же образ приложения, `python -m hse_doc_studio.infra.update.server_updater`, только стандартная библиотека и docker CLI). Он сам приходит за работой: `POST /api/updater/v1/poll` раз в 15 секунд, во время запуска каждые 30 секунд сердцебиением. Результат шлёт событиями `POST /api/updater/v1/runs/{id}/events`.

**Развилка (почему не внутри api).** Обновляемый процесс не может надёжно заменить сам себя: на середине пересоздания он умирает вместе с состоянием запуска. Исполнитель обязан пережить гибель api и Postgres, поэтому он отдельный контейнер со своим журналом на диске (`updater-data`). Это же причина, по которой откат с восстановлением базы возможен: восстановить базу, из которой живёт api, изнутри api нельзя.

**Развилка (поллинг, а не команда от api).** Апдейтер ходит к api, а не наоборот. Апдейтеру не нужен входящий порт, а у api нет канала, по которому можно приказать что-то хосту: даже взломанный api не получает возможности запустить произвольную команду на хосте, он может лишь завести запись «обновить на версию X» (версия проверяется апдейтером по формату и по дайджесту). Секрет протокола `UPDATER_TOKEN` (Bearer, сравнение за постоянное время, перебор режется по IP, без токена протокол закрыт).

### Опасность docker.sock

Сокет docker равен root на хосте. У апдейтера он есть (иначе нечем пересоздавать контейнеры), как уже есть у раннера. Меры:

- профиль compose `updater` включается отдельно и сознательно; без `UPDATER_TOKEN` исполнитель выключен, Студия только сообщает о версиях;
- апдейтер не публикует портов, принимает работу лишь от api по общему секрету, версия цели проверяется регуляркой `\d+.\d+.\d+` и дайджестом;
- образ берётся из того же репозитория, что у работающего api (`plan.target_ref`): подменить репозиторий через api нельзя;
- пересоздание отказывается работать с контейнерами, у которых есть опции, которые оно не переносит (`privileged`, `cap_add`, `devices`, `tmpfs` и т. п.): список в `plan.unsupported_options`; запуск отменяется до любых изменений, оператор обновляет руками;
- опорные данные (DSN, ключи) апдейтер получает из окружения контейнера api через временный `--env-file` с правами 0600 и удаляет его по окончании, в командной строке секретов нет.

Более узкую альтернативу (прокси к сокету с белым списком вызовов, rootless docker) оператор может поставить сам: апдейтер ходит к docker только через CLI и `DOCKER_HOST`.

**Развилка (Helm и исполнитель kubernetes).** Первая редакция этого раздела отвергала исполнитель на Kubernetes API: ставит версию оператор командой `helm upgrade … --atomic --wait`, откат при неуспехе делает Helm, а Helm и GitOps (Argo CD, Flux) решают задачу лучше. **Пересмотрено 03.11.2026 (решение владельца продукта).** Довод «лучше решают» верен для команд с GitOps, но у остальных установок кнопки «Обновить сейчас» и «Откатить» в Kubernetes оставались мёртвыми, а страница показывала команду, которую некому выполнять ночью в окне обслуживания. Поэтому добавлен второй исполнитель `kubernetes` (раздел 5а):

- он включается флагом чарта `updater.enabled` (по умолчанию выключено) и ничего не меняет для тех, у кого `executor = none`: Helm и GitOps остаются поддерживаемым путём, страница по-прежнему показывает готовую команду `helm upgrade` для установок с выключенным исполнителем;
- архитектура та же, что у compose: api решает и ведёт учёт и прав в кластере не получает, исполняет отдельный под `updater` со своим ServiceAccount и Role строго на свой namespace (раздел 5а.3);
- исполнитель опирается на Deployment и Job, а не на запись релиза Helm, поэтому работает и у установок без Helm-записи (манифесты руками, Kustomize, Argo CD).

Цена решения названа в разделе 5а: снимка базы и отката схемы в первой версии нет, и это определяет, когда откат образа вообще безопасен.

## 3. Проверка релизов

- Канал `stable`: фид GitHub Releases без черновиков и предрелизов (`prerelease` отфильтрован). Других каналов не публикуем; ключ `update.channel` оставлен под будущее, API принимает только `stable`.
- Источник: `HSE_STUDIO__UPDATE_FEED_URL` (по умолчанию официальные релизы), тот же, что у кнопки «проверить» в личной Студии; зеркало или форк задаются им же, `off` выключает сеть.
- Период проверки 6 часов, после неудачи повтор через 30 минут; результат (список релизов с заметками и ссылкой на `image-digest.json`) хранится в базе, поэтому переживает рестарт и офлайн.
- Подпись и дайджест (раздел 7).

## 4. Политика и окно

Настройки в `instance_settings` (`update.*`), правятся в админке и пишутся в аудит:

| Ключ | Значения | Умолчание |
|---|---|---|
| `policy` | `off` (не проверять), `notify` (сообщать), `auto` (ставить в окно) | `notify` |
| `max_bump` | `patch`, `minor`: самый крупный шаг без человека | `minor` |
| `window_days`, `window_start_min`, `window_minutes` | дни недели (0 = понедельник), начало в минутах от полуночи UTC, длительность 15..1440 | каждый день, 02:00, 180 минут |
| `backup_first` | ждать успешного полного бэкапа | да |
| `verify` | `digest`, `cosign`, `none` | `digest` |
| `notify_admins` | уведомления во «Входящие» | да |

**Развилка (умолчание `notify`).** Установка не обновляется сама, пока администратор не включил `auto`: поведение после апгрейда не меняется молча.

**Развилка (мажорные версии).** Шаг `major` политика не ставит никогда, только сообщает; ставится вручную кнопкой. Внутри разрешённого шага берётся самая новая версия (при 0.3.1 и релизах 0.3.5, 0.4.0, 1.0.0 цель 0.4.0 при `minor` и 0.3.5 при `patch`).

Решение планировщика (`decide`), от дешёвых проверок к зависящим от окружения: политика выключена; нет релиза новее; `notify` (одно уведомление на версию); шаг слишком крупный; исполнитель выключен; запуск уже идёт; версия уже откатывалась или падала (повтор каждый тик бессмыслен, ждём следующий релиз); апдейтер молчит; вне окна; иначе старт. Окно может переходить через полночь, день недели относится к началу окна.

## 5. Порядок обновления

```
api:      запрос (авто или кнопка) -> [полный бэкап] -> queued
updater:  preflight -> snapshot -> pull -> verify -> stop -> migrate -> restart -> health -> finish
                                                     └ любой сбой отсюда и ниже: rollback [-> restore] -> health
```

1. **Запрос.** Запись `update_runs` создаётся с уникальным частичным индексом «не больше одного активного запуска». Если `backup_first` и есть назначение бэкапов, статус `waiting_backup`: api запускает обычный полный бэкап (`BackupService`), планировщик ждёт его итога. Бэкап не удался: запуск `cancelled`, админы получают уведомление, ничего не тронуто. Назначения нет: предупреждение в журнале запуска и баннер на странице, обновление идёт со снимком базы. Другой бэкап уже идёт: ждём до 2 часов.
2. **Preflight.** Находит контейнеры сервисов по меткам compose, проверяет поддерживаемые опции и свободное место под снимок.
3. **Snapshot.** Одноразовый контейнер текущего образа в сети api с его окружением: `hse-doc-studio db current` (ревизия «до») и `hse-doc-studio db snapshot --out …` (`pg_dump -Fc` клиентом версии сервера, с контрольной суммой) в том `updater-data`. Предыдущий образ закрепляется локальным тегом `<репозиторий>:rollback-prev`, чтобы чистка образов его не убрала. Это обязательный снимок базы: он есть независимо от того, настроен ли внешний бэкап.
4. **Pull + verify.** `docker pull <репозиторий>:<версия>`; проверка по выбранному режиму (раздел 7). Отказ: запуск `cancelled`, система не тронута.
5. **Stop.** Раннер, затем api. С этой точки отказ ведёт в откат. Простой от остановки до healthy обычно 1–3 минуты; в личной установке это уместно, для кафедры окно ночью.
6. **Migrate.** Одноразовый контейнер новой версии `db upgrade` при остановленных api и раннере: никто не пишет в базу во время миграции, и api не стартует на полу-схеме. Затем `db current` (ревизия «после»).
7. **Restart.** Контейнеры пересоздаются `docker run` из `docker inspect` старых: порты, тома, окружение, сети **с алиасами** (имя сервиса в сети compose), метки compose, healthcheck, ротация логов, группы. Порядок: api, раннер.
8. **Health.** Контейнеры работают (у раннера и апдейтера проверка образа `curl :8000` отключена в compose: у них нет HTTP, и «unhealthy» навсегда откатывало бы каждое обновление), не перезапускаются по кругу (`RestartCount` не растёт), healthcheck api `healthy`, и `GET /health/ready` отвечает 200 непрерывно 20 секунд; всё в пределах 5 минут. Самодиагностики установки в master нет, поэтому проба простая; когда она появится, достаточно заменить проверку в `Engine._healthy_once`.
9. **Finish.** Событие `succeeded` с ревизиями; в `.env` установки `TAG=<версия>` (если файл доступен на запись), чтобы ручной `compose up` не вернул старое; из снимков остаются два последних.

### Откат

Автоматический, при любом сбое после остановки (миграция, запуск, здоровье, непредвиденная ошибка, смерть самого апдейтера):

1. Остановить и удалить новые контейнеры.
2. Если миграции начинались, узнать ревизию базы новым образом. **Ревизия изменилась** (миграции прошли): старый образ не запустится на схеме новее себя (`DbAheadError`), поэтому база восстанавливается из снимка (`db restore-snapshot`: схема `public` пересоздаётся и дамп разворачивается через `psql --single-transaction`, всё или ничего; `pg_restore --clean` на партиционированных таблицах падает) старым образом. Так как api был остановлен всё время между снимком и миграцией, данные не теряются. Журнал `update_runs` лежит в той же базе: при восстановлении его строки сохраняются и возвращаются поверх снимка, иначе откат стёр бы запись самого себя и предыдущего обновления. События для неизвестного api запуска (404) апдейтер отбрасывает. **Ревизия не изменилась** (патч без миграций): база не трогается, пишущий api мог принять данные, их терять незачем.
3. Пересоздать контейнеры из прежних образов: по имени, если тег всё ещё указывает на тот же образ, иначе по **идентификатору** (тег мог двинуться; контейнер из идентификатора теряет имя образа, поэтому имя восстанавливается по тегам образа при следующем запуске) и дождаться здоровья.
4. Итог `rolled_back` (с признаком `db_restored`) или `failed`, если восстановление или возврат не удались: в сообщении точное место снимка и команда `docker compose up -d`.

**Развилка (потеря данных при откате после здорового старта).** Если новая версия поднялась, проработала и сломалась позже, автоматического отката нет: откат по кнопке (см. ниже) с явным подтверждением потери данных. Автоматически откатываем только то, что не прошло проверку здоровья в самом обновлении.

**Устойчивость к падению апдейтера.** Каждый шаг пишется в журнал на диске до исполнения. При старте апдейтер читает журнал: запуск, дошедший до остановки, откатывается по той же процедуре; не дошедший, закрывается как отменённый. События, не доставленные в api (он гасится на время обновления), лежат в очереди журнала и уходят по порядку после возвращения.

### «Откатить» по кнопке

Доступна, пока текущая версия равна цели последнего успешного обновления и у апдейтера есть закреплённые прежние образы. Если обновление меняло ревизию базы, откат восстановит снимок, снятый перед обновлением, и **всё записанное после обновления будет потеряно**: кнопка требует явного подтверждения (`restore_db`), без него API отвечает 422. Если схема не менялась, откат возвращает образы и данные не трогает. Перед откатом с потерей данных, как и перед обновлением, идёт полный бэкап. Если откат не поднялся, апдейтер возвращает образы, что стояли до него, и сообщает `failed`.

## 5а. Исполнитель kubernetes

Тот же протокол с api (`/api/updater/v1`, опрос раз в 15 секунд, события по `seq`), то же журналирование, аудит, уведомления и метрики `hse_update_*`: всё это живёт в api и от исполнителя не зависит. Отличается то, что делает апдейтер.

### 5а.1. Что делает исполнитель

```
api:      запрос (авто или кнопка) -> [полный бэкап | подтверждение риска] -> queued
updater:  preflight -> verify -> precheck(Job) -> stop -> migrate(Job) -> restart -> health -> finish
                                                  └ сбой отсюда и ниже: откат образа, если схема не менялась; иначе «Нужны руки»
```

1. **Preflight.** Читает Deployment api (имя и контейнер из `HSE_UPDATER__KUBE__DEPLOYMENT` и `__CONTAINER`), запоминает образ и число реплик, убирает Job’ы прошлых запусков (метка `app.kubernetes.io/managed-by=hse-doc-studio-updater`).
2. **Verify** (раздел 7): дайджест из `image-digest.json`; `cosign` при выборе «Дайджест и подпись». Отказ: запуск `cancelled`, кластер не тронут.
3. **Precheck.** Job `hse-doc-studio db current` на **новом** образе, собранный из шаблона пода api (то же окружение и Secret, тот же `securityContext`, pull-секреты, узлы; тома и токен ServiceAccount не переносятся). Это проверка, что образ тянется и стартует, что база читается, и ревизия «до». Отказ (в том числе `ErrImagePull`, `Unschedulable` дольше `pod_start_timeout`): `cancelled`, api не останавливали.
4. **Stop.** `replicas: 0` у Deployment, ожидание, пока подов api нет. С этой точки отказ ведёт в откат или в «Нужны руки».
5. **Migrate.** Job `hse-doc-studio db upgrade` на новом образе (`backoffLimit: 0`, `activeDeadlineSeconds`, TTL 24 часа: лог доступен для диагностики), затем Job `db current` (ревизия «после»). Api остановлен: никто не пишет в базу, и новый api не стартует на полу-схеме.
6. **Restart.** Один патч Deployment: образ контейнера и прежнее число реплик. Образ тянет kubelet.
7. **Health.** Поды нового образа не в `CrashLoopBackOff`, `ImagePullBackOff`, `CreateContainerConfigError`, не перезапускались; Deployment применил последнюю версию спецификации и все реплики готовы; `GET /health/ready` отвечает 200 непрерывно 20 секунд; всё в пределах `HSE_UPDATER__HEALTH_TIMEOUT_S` (300 с).
8. **Finish.** Событие `succeeded` с ревизиями; `last_ok` (прежний и новый образ, ревизии) сохраняется для кнопки «Откатить».

Простой тот же, что у compose: от `replicas: 0` до готовности новой версии, обычно 1–3 минуты плюс время миграций. Обновление без простоя по-прежнему вне объёма (раздел 10).

**Развилка (образ по дайджесту).** Deployment получает образ вида `<репозиторий>:<версия>@sha256:<дайджест из релиза>`. Kubelet тянет ровно тот образ, который апдейтер проверил по `image-digest.json`: у Kubernetes нет места между «проверили» и «запустили», где образ можно подменить тегом (в compose для этого нужны `docker pull` и сверка `RepoDigests`). Режим `none` ставит образ по тегу.

### 5а.2. Состояние запуска

Как у compose: апдейтер пишет журнал на диск до каждого шага (файл `journal.json`, очередь событий для api, который гаснет на время обновления), при старте читает его и доводит незаконченное. **Отличие:** в чарте нет PVC апдейтера (лишний том с классом хранения ради нескольких килобайт), а emptyDir умирает вместе с подом, поэтому запуск (`run`) и последний успешный (`last_ok`) дополнительно копируются в аннотации `hse-doc-studio.io/updater-run` и `hse-doc-studio.io/updater-last-ok` Deployment api (для этого и так нужно право `patch`; JSON-merge-patch, аннотации не входят в шаблон пода и не вызывают раскатку). Новый под при старте берёт запуск из файла, а если файла нет, из аннотаций:

- запуск, не дошедший до остановки api: закрывается как `cancelled` (`updater_restarted`);
- дошедший до остановки: откатывается по той же процедуре, что при сбое (раздел 5а.4);
- уже здоровый, но не закрытый (флаг `healthy`): закрывается как `succeeded`, а не откатывается.

Потеряться может только очередь недоставленных событий (она лишь в файле); итоговое событие запуска апдейтер шлёт после восстановления, а `run_lost_s` в api страхует от вечного `running`.

### 5а.3. Права

Включаются флагом `updater.enabled` (по умолчанию `false`). Чарт создаёт `ServiceAccount`, `Role` и `RoleBinding` **только в namespace релиза**:

| apiGroup | ресурс | глаголы | зачем |
|---|---|---|---|
| `apps` | `deployments`, **только** `resourceNames: [<релиз>-api]` | `get`, `patch` | читать шаблон пода, менять образ и реплики, писать аннотации журнала |
| `batch` | `jobs` | `create`, `get`, `list`, `watch`, `delete` | миграции, `db current`, cosign, уборка прошлых запусков |
| `` | `pods` | `get`, `list` | дожидаться Job и здоровья, находить причину сбоя |
| `` | `pods/log` | `get` | лог Job (ревизия базы, причина сбоя) |

Нет `secrets` и `configmaps` (окружение Job берётся ссылками `secretKeyRef` из шаблона пода, значения апдейтер не читает), нет `create`/`delete` у Deployment (он не создаёт и не удаляет рабочие нагрузки), нет `ClusterRole`, нет других namespace. Под апдейтера проходит Pod Security Standard `restricted` (`runAsNonRoot`, `seccompProfile: RuntimeDefault`, `drop: [ALL]`, корень только для чтения, emptyDir под данные и `/tmp`), одна копия со стратегией `Recreate`. Под Job проходят `restricted` тоже (securityContext копируется из api). NetworkPolicy в чарте только у подов сборки раннера: метка `managed-by` у Job обновления другая, их правила не затрагиваются; свои NetworkPolicy оператора видят метки экземпляра (`app.kubernetes.io/name`, `app.kubernetes.io/instance`) на подах Job, а метку Service (`component: api`) Job не наследует (иначе под миграций получал бы трафик).

**Развилка (почему не права на `deployments/scale` или `replicasets`).** `patch` одного Deployment уже включает `spec.replicas`; подресурс `scale` добавил бы второй путь к тому же без пользы.

Что остаётся риском, а не мерой: токен апдейтера позволяет патчить образ api на любой. Это та же ситуация, что с docker.sock у compose, но уже: образ задаётся только как `<репозиторий api>:<версия, regex \d+.\d+.\d+>[@дайджест]` (репозиторий берётся из самого Deployment, подменить его через api нельзя), а аннотации и реплики ограничены кодом апдейтера.

### 5а.4. Схема базы и откат: что решено и почему

Образ старше схемы не стартует (`DbAheadError`), поэтому откат образа без отката базы возможен, только пока миграции не менялись. Полноценный откат схемы (как снимок `pg_dump` у compose) в Kubernetes требует клиента Postgres нужной версии, места под дамп и тома, которых у чарта нет; делать его в первой версии не стали. Вместо него:

1. **Перед обновлением** (api): если в «Бэкапах» есть назначение по умолчанию и в политике включён полный бэкап, запускается полный бэкап и обновление ждёт его успеха (бэкап не удался: `cancelled`, ничего не тронуто). Иначе обновление **требует явного подтверждения риска**: ручной запрос без `accept_risk` отвечает 422 `risk_not_confirmed`, диалог в админке показывает переключатель «Я понимаю: полного бэкапа не будет и базу откатить нельзя», подтверждение пишется в журнал запуска (событие `warn`) и аудит (`risk_accepted`). Автоустановка без бэкапа **не стартует** (причина `backup_required`, админы получают уведомление один раз): согласия человека у неё нет.
2. **После остановки** (исполнитель) отличить «откат безопасен» от «небезопасен» позволяет ревизия alembic: «до» читается Job’ом на этапе precheck, «после» после `db upgrade`, а если миграция упала или новая версия не поднялась, ревизия читается ещё раз (Job `check`) и сравнивается с «до».
   - **Ревизия не изменилась** (миграций в релизе нет либо `db upgrade` откатил свою транзакцию): образ и реплики возвращаются, ждём здоровья, итог `rolled_back`. Данные цели.
   - **Ревизия изменилась** (или прочитать её не удалось: считаем, что изменилась) и новая версия не поднялась: образ **не откатывается**, старый не стартует на новой схеме, а молчаливый откат оставил бы api в `CrashLoopBackOff` с ложным «откачено». Запуск завершается `failed` с кодом `needs_manual_action` (в интерфейсе «Нужны руки»), Deployment остаётся как есть (новый образ, либо `replicas: 0`, если упали сами миграции), а в ход запуска пишутся три события: что именно в Deployment, команды диагностики (`describe`, `logs`, логи Job) и два пути. Путь A, вперёд: устранить причину (конфигурация, Secret, ресурсы, сломанная миграция), Deployment сам перезапускает под; для полу-применённой миграции `helm upgrade` с целевым `image.tag` (его pre-upgrade Job доведёт схему). Путь Б, назад: восстановить базу из бэкапа, снятого перед обновлением, затем `kubectl set image` на прежний образ и `kubectl scale` на прежнее число реплик (команды с подставленными именами уже в событии).
3. **Кнопка «Откатить»** доступна, только пока последнее обновление не меняло схему (`from_revision == to_revision`, обе известны). Перед откатом Job `db current` на прежнем образе проверяет, что ревизия в базе всё ещё равна «после»: если кто-то уже ушёл дальше, запуск отменяется (`schema_ahead`). Если обновление меняло схему, кнопки нет, страница объясняет почему (`rollback_blocked`), а API отвечает 409 `rollback_unsafe`: восстанавливать базу из бэкапа нужно вручную. Параметр `restore_db` в kubernetes игнорируется.

### 5а.5. Что не затронуто и что нужно знать оператору

- **Дрейф Helm.** Апдейтер патчит образ Deployment мимо Helm. Следующий `helm upgrade` без `--set image.tag=<установленная версия>` (или с `--reuse-values`, если тег не задан) вернёт образ, записанный в values, и откатит версию вслед за чартом. Поэтому после обновления из админки зафиксируйте версию в values (или в GitOps-репозитории): страница «Обновления» показывает версию, а `manual_command` уже содержит `--set image.tag`. Релиз Helm апдейтер не читает и не меняет (`helm.sh/release.v1` остаётся прежним): так он работает и без Helm.
- **Раннер и апдейтер** обновляются вместе с чартом. Меняется только Deployment api; раннер задач (если включён) продолжает работать на своём образе, протокол раннера версионирован. Сам апдейтер обновляется `helm upgrade` (как и в compose, он не входит в обновляемые сервисы).
- **Несколько реплик.** Чарт держит одну реплику api (том RWO); исполнитель возвращает ровно то число реплик, что было до обновления.

## 5б. Откат на выбранную версию и переключатель автоустановки

Решения 07.11.2026 (задача «откат из админки и выключение автообновления»).

**Откат на выбранную версию** это отдельный вид запуска `downgrade` (миграция `dg_01`, расширяет проверку `update_runs.kind`). Исполняет его тот же путь, что обновление вперёд: проверка образа (дайджест и cosign из релиза выбранной версии, `digests_url` берётся из списка релизов), остановка, замена образа, ожидание здоровья, возврат прежнего образа при неудаче. Отличия:

- **Политика схемы: head целевого образа обязан равняться ревизии базы.** Откат меняет только образ, поэтому схема не должна отличаться. Обратную совместимость схемы мы не декларируем, строгое равенство единственное, что можно доказать. Развилка: можно было разрешать откат на версии из «списка совместимых», который ведёт релиз, но у уже вышедших релизов такого списка нет, а ошибиться в сторону потери данных дороже, чем отказать.
- Проверка двухступенчатая. api знает ревизии по истории запусков (`known_revisions`: до запуска база стоит на head версии `from_version`, после успеха на head `to_version`; текущая версия равна head этого образа) и сразу отказывает 409 `schema_incompatible`, если известная ревизия версии отличается. Версию, которой не было на этой установке, проверяет апдейтер по самому образу до остановки сервисов (Job `db current` в kubernetes, одноразовый контейнер в compose; в compose после снимка и pull): head образа не равен ревизии базы, запуск отменяется `schema_incompatible`, ничего не тронуто. Миграции при откате не применяются, `db upgrade` на равных ревизиях ничего не делает.
- Бэкап: те же правила, что у обновления (`backup_first` и назначение), ждём его успеха. Подтверждение риска (`accept_risk`) не нужно: схема не меняется.
- **Совместимость апдейтера.** Апдейтер старой версии сам не умеет проверять head и принял бы `downgrade` за обновление без проверки. Поэтому апдейтер сообщает в `poll` поле `capabilities` (сейчас `downgrade`), api хранит его в `instance_settings` (`update.updater_capabilities`) и отдаёт такой запуск только тому, кто это умеет; иначе 409 `updater_outdated`. Старый апдейтер поля не шлёт, поле необязательное, протокол остаётся `1`.
- После успешного отката автоустановка переводится в `notify` (аудит `update.auto_toggle`, причина `downgrade`), иначе планировщик вернул бы новую версию в ближайшее окно; версия, с которой ушли, при этом попадает в `failed_targets`, как после ручного отката. Вернуться вперёд можно обычным обновлением на выбранную версию.
- Гонки: единственность активного запуска обеспечивает уникальный частичный индекс `uq_update_runs_single_active`, второй запрос (обновление, откат или автозапуск) получает 409 `already_running`. Апдейтер исполняет один запуск за раз.

**Переключатель автоустановки** это политика `auto` <-> `notify` одним вызовом `PUT /api/admin/updates/auto`. Отдельного флага нет: политика уже хранится в `instance_settings`, её читает планировщик, она переживает рестарты. Выключение: автозапуск не создаётся (`decide` отдаёт `notify`), планировщик перед созданием автозапуска перечитывает политику (админ мог выключить, пока тик решал), а автозапуск, созданный раньше и ещё не взятый апдейтером (`waiting_backup` или `queued`), отменяется (`auto_update_disabled`); повторная проверка в `poll` закрывает окно между записью политики и отменой. Запуски, начатые человеком, переключатель не отменяет. Проверка релизов и уведомления не зависят от переключателя (они зависят только от режима «Выключено»). Аудит: `update.auto_toggle`.

## 6. Журнал, аудит, уведомления, метрики

- **Журнал** `update_runs`: вид (обновление/откат), инициатор (авто/ручной), статусы `waiting_backup`, `queued`, `running`, `succeeded`, `rolled_back`, `failed`, `cancelled`, фаза, версии и ревизии «до/после», ссылка на запуск бэкапа, события (до 300, с `seq` для идемпотентной доставки «хотя бы раз»), код и текст ошибки.
- **Потерянные запуски** (уборка планировщика): `queued` без апдейтера дольше 10 минут отменяется (`updater_offline`); `running`, от которого апдейтер молчит больше 15 минут, становится `failed` (`updater_lost`). Пока апдейтер шлёт сердцебиение, длинный `pull` не считается потерей.
- **Аудит**: `update.check`, `update.settings_update`, `update.run_request` (с `trigger`), `update.rollback_request`, `update.run_cancel`, `update.run_finish` (исход, версии, ревизии, `db_restored`, длительность).
- **Уведомления**: `system_alert` с кодом в `outcome` (`update_available`, `update_succeeded`, `update_rolled_back`, `update_failed`, `update_cancelled`), версия в `path`, причина в `excerpt`; получают активные администраторы, переход ведёт на страницу «Обновления». Новой миграции для вида не нужно.
- **Метрики** (`/metrics`, из снимка планировщика): `hse_update_available`, `hse_update_updater_up`, `hse_update_executor_enabled`, `hse_update_run_active`, `hse_update_last_check_timestamp_seconds`, `hse_update_policy{policy}`, `hse_update_runs_total{result}`, `hse_update_last_run_timestamp_seconds`, `hse_update_last_run_success`, `hse_update_last_run_duration_seconds`. Алерты: `hse_update_updater_up == 0` при `hse_update_executor_enabled == 1`; `hse_update_last_run_success == 0`.

## 7. Подпись и дайджест образов

`publish.yml` после публикации образа:

1. подписывает образ по дайджесту `cosign sign --yes` (keyless, OIDC GitHub, подпись рядом с образом в реестре);
2. прикладывает к релизу GitHub файл `image-digest.json` (`{image, version, digest}`, `digest` это дайджест индекса мультиархитектурного образа).

Апдейтер после `docker pull`:

- `verify = digest` (умолчание): дайджест из `RepoDigests` скачанного образа должен совпасть с дайджестом из файла релиза (файл берётся только по https, до 64 КБ, версия в файле должна совпасть с целевой). Нет файла или дайджеста: запуск отменяется (`digest_missing`), оператор может сознательно выбрать `none`;
- `verify = cosign`: дополнительно `cosign verify` в контейнере `ghcr.io/sigstore/cosign/cosign` с привязкой к workflow `publish.yml` этого репозитория на теге релиза (`--certificate-identity-regexp`, `--certificate-oidc-issuer https://token.actions.githubusercontent.com`);
- `verify = none`: для закрытых зеркал и форков, в журнале предупреждение.

**Kubernetes** (раздел 5а). Пулла отдельным шагом нет: образ с дайджестом (`<репо>:<версия>@sha256:…`) тянет kubelet, поэтому режим `digest` означает «в Deployment записан ровно дайджест из файла релиза» (файл тот же и с теми же проверками: https, до 64 КБ, версия совпадает), а несовпадение дайджеста с содержимым реестра kubelet отвергает сам. Режим `cosign` проверяется Job’ом с образом `ghcr.io/sigstore/cosign/cosign` (тот же закреплённый тег и та же привязка к workflow `publish.yml`, `--certificate-identity-regexp`, `--certificate-oidc-issuer`): тяжёлых зависимостей в апдейтере это не добавляет, нужны только исходящий доступ пода из namespace к реестру и Sigstore (Rekor, TUF) и pull-секреты api (копируются в Job). Если egress закрыт, проверка закончится `signature_invalid`, запуск `cancelled`: оператор выбирает `digest` или открывает доступ. `none` ставит образ по тегу, в журнале предупреждение.

**Развилка.** Дайджест из релиза защищает от подмены образа в реестре, но не от взлома самого репозитория GitHub: от него защищает подпись cosign с привязкой к workflow. Релизы, вышедшие до этой подсистемы, дайджеста не имеют: с ними `digest` не пройдёт, для них нужна ручная установка или `none`.

## 8. Страница админки «Обновления»

Раздел `/admin/updates`: установленная и доступная версии с заметками, время проверки, состояние апдейтера, ближайшее окно; кнопки «Проверить сейчас», «Обновить сейчас» (подтверждение с предупреждением о простое), «Откатить на X» (подтверждение; при смене схемы с предупреждением о потере данных); политика, предел шага, дни и время окна (UTC), бэкап, проверка образа, уведомления; история с исходом и ходом запуска (события по фазам). Баннеры: идёт запуск (с «Отменить», пока апдейтер не начал), последний запуск откатился или упал (при `needs_manual_action` отдельный текст «образ не откачен, нужны ручные действия»), апдейтер не отвечает, исполнитель не подключён (Helm: готовая команда, оставлена запасным вариантом для установок с `executor = none`), нет назначения бэкапов, фид не ответил. В Kubernetes с включённым исполнителем «Апдейтер» показывает «работает, версия X», кнопки включены, подтверждение предупреждает о простое и о том, что при смене схемы образ не откатывается; без бэкапа в диалоге обязателен переключатель подтверждения риска, а вместо кнопки «Откатить» после обновления со сменой схемы стоит пояснение. Во время обновления api гаснет: опросы статуса не повторяются при ошибке, страница восстанавливается сама.

## 10. Что не вошло

- Обновление без простоя (blue/green): схема и api одноэкземплярные, миграции нескольких версий не гарантируют обратной совместимости.
- Снимок базы и откат схемы в Kubernetes: защита это полный бэкап или подтверждение риска и откат образа, пока схема не менялась (раздел 5а.4). Следующий шаг, если понадобится: Job со снимком `db snapshot` на том апдейтера и `db restore-snapshot`, как у compose.
- Обновление раннера и самого апдейтера в Kubernetes: меняется только Deployment api (права Role ровно на него), остальное идёт `helm upgrade`.
- Запись об обновлении в релизе Helm: исполнитель kubernetes её не читает и не пишет (дрейф Helm, раздел 5а.5).
- Обновление самого апдейтера и сторонних образов (postgres, minio, onlyoffice): они закреплены тегами в compose и меняются вместе с релизом compose-файла вручную. Апдейтер обновляется командой `docker compose pull updater && docker compose up -d updater`; протокол версионирован (`protocol: 1`), старый апдейтер с новым api совместим.
- Автоматический откат по метрикам после здорового старта (раздел 5).
- Подписанные релизы до этой подсистемы.
