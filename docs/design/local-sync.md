# Локальная Студия и сервер: автосинхронизация и выгрузка PDF

Статус: решения приняты 31.10.2026 (ветка `feat/local-sync`). Основа: `collaboration.md`, раздел 12 («Гибрид: сервер как remote»). Всё, что в списке «вне объёма», остаётся на потом.

## 1. Автосинхронизация

### 1.1 Что делает

Локальная Студия сама держит проект в согласии с сервером, пока проект открыт в окне:

- после паузы в правках отправляет (push) свои изменения;
- сама забирает (pull) чужие, если неотправленных правок нет;
- при конфликте останавливается и показывает существующий экран слияния;
- показывает состояние: «Синхронизировано», «Отправляется», «Конфликт», «Нет сети» (плюс уже существующие «Есть чужие изменения», «Нужен вход», «Ошибка»);
- выключается переключателем для проекта.

### 1.2 Решения

| № | Решение | Почему |
|---|---|---|
| A1 | Оркестрирует веб-клиент локальной Студии (хук `useAutoSync`), а не планировщик бэкенда. Бэкенд хранит настройку и отдаёт её в статусе. | Перед снимком нужно дописать несохранённые правки редакторов (`flushPendingSaves`), а слияние не должно ложиться под открытый редактор; всё это знает только клиент. Правки в Студии вносятся через её окно, закрытое окно правок не порождает. |
| A2 | Настройка `auto_sync` хранится в `hse-sync.json` проекта (`SyncState.auto_sync: bool \| None`). `None` значит «по умолчанию»: включено, если доступ к проекту получен входом на сервер Студии (`origin = device`), иначе выключено. Статус отдаёт `auto_sync: {enabled, explicit}`. | Автоматическая отправка в GitHub или GitLab без согласия человека неожиданна, а вход на сервер Студии и есть согласие на обмен. Явный выбор (вкл или выкл) побеждает умолчание. |
| A3 | Правку определяет сигнал сохранения файла (`noteProjectEdit` в `shared/lib/editActivity`, его вызывают мутации файлов) плюс признак `ahead > 0`. Пауза 20 с после последней правки, не чаще одной автоотправки в 60 с (если нужно лишь забрать чужое, зазор 15 с). | Коммит правки может быть отложен троттлингом VCS (5 с), поэтому `ahead` одного недостаточно; снимок перед синхронизацией всё равно подхватит файлы. |
| A4 | «Забирает, если нет неотправленных правок»: статус `behind` при `ahead = 0` и без правок за сессию запускает синхронизацию (она сводится к fast-forward) без паузы, с задержкой 3 с. Если правки есть, забор идёт тем же циклом после паузы: это обычная синхронизация (выборка, слияние, отправка). | Чужие изменения без своих не могут конфликтовать; со своими слияние уже умеет существующий цикл, а конфликт останавливает автосинк. |
| A5 | Используется существующая синхронизация (`POST /git/sync`, операции, фазы, отмена). Новых серверных операций нет. Запуск помечается как автоматический только на клиенте: итоговые тосты успеха не показываются (состояние видно в индикаторе), ошибки и конфликт показываются. Экран конфликтов сам не открывается (в отличие от ручного запуска). | Автоматика не должна отнимать внимание и уводить со страницы. |
| A6 | Остановки без повторов: `conflicts`, `auth_failed`, `blocked` (чужая ветка, только чтение, нет профиля, недоверенное хранилище), `no_remote`, режим «только чтение». `offline`: ждём события `online` и очередного ответа статуса. Ошибка операции: повтор с задержкой 30 с, потом удвоение до 10 мин, после трёх подряд неудач автосинк останавливается до ручного действия или смены состояния. | Неверный доступ повторами не лечится, а повторы на сломанном сервере только шумят. |
| A7 | Индикатор: существующий элемент синхронизации (`SyncControl`) получает метку «Авто» и подпись состояния; в панели синхронизации и в настройках проекта стоит переключатель. Выключенный автосинк оставляет ручную кнопку как есть. | Один элемент состояния для людей и скринридера. |
| A8 | Обращения вкладок согласуются существующим `sync_busy`: если операция уже идёт (в другой вкладке), клиент присоединяется к ней. | Нет второго замка. |

Вне объёма: автосинк при закрытом окне, автосинк по расписанию на стороне бэкенда, слияние без участия человека при конфликте.

## 2. Выгрузка PDF на сервер

### 2.1 Что делает

После успешной локальной сборки Студия отправляет собранный PDF на сервер как артефакт проекта. Артефакт видят те, кто видит результат проекта (читатель и выше, по ссылке тоже), на сайте он открывается в просмотрщике и скачивается.

### 2.2 Решения

| № | Решение | Почему |
|---|---|---|
| P1 | Таблица `project_artifacts` (id, project_id, kind=`pdf`, doc_id, file_name, size, sha256, object_key, pages, source_commit, built_at, uploaded_at, uploaded_by, uploaded_by_name, client_name), байты в объектном хранилище по ключу `artifacts/<project_id>/uploads/<doc_id>/<artifact_id>.pdf`. Миграция `ls_01_project_artifacts`. | Префикс `artifacts/<project_id>/` уже входит в измерение занятого места проекта и в сборку мусора сирот, поэтому квоты и очистка при удалении проекта работают без правок. PDF не попадает в git и не мешает слиянию. |
| P2 | Загрузка: `PUT /git/-/projects/{project_id}/documents/{doc_id}/pdf`, тело `application/pdf`, заголовок `X-Content-SHA256`. Подлинность: токен доступа с `git:write` (тот же токен, что у входа по коду устройства), cookie не читаются. Отдельного scope не вводим. | Токен из device flow уже выдан и отзывается в одном месте; `git:write` значит «может менять проект». API `/api/v1` git-токену закрыт (S21), поэтому загрузка живёт рядом с остальными `/git/-/*`. |
| P3 | Право на загрузку: действие `BUILD_RUN` (редактор и владелец) с областью документа (автор командного проекта грузит только свой документ). Чтение: `OUTPUT_READ` (список и файл в `/api/v1`), как у PDF сборки. | Выгрузка это публикация результата сборки; читатель сборку не запускает и PDF не заливает. |
| P4 | Пределы: размер `artifacts.max_pdf_bytes` (по умолчанию 100 МиБ, отказ 413 по `Content-Length` и по факту чтения), тело должно начинаться с `%PDF-`, `doc_id` из проекта, хранится не больше 5 последних PDF на документ (старые стираются после успешной записи), частота по общему лимиту `GIT_HTTP` человека, суммарный размер входит в квоту проекта (измерение `artifacts/<id>/`). Тот же sha256 подряд для документа не создаёт новую запись (ответ 200 с прежней). | Защита диска и повторов. |
| P5 | Аудит: `artifact.pdf_uploaded` (проект, документ, размер, sha256, имя токена-устройства), `artifact.pdf_rejected` не пишется (отказы видны в журнале запросов), `artifact.deleted` при удалении. Скачивания в аудит не пишутся (просмотр PDF частый). | Видно, кто и когда выложил файл, без шума. |
| P6 | Удаление артефакта вручную: `DELETE /api/v1/projects/{id}/artifacts/{artifact_id}` по праву записи файлов (`FILES_WRITE`). | Ошибочную выгрузку (например, в NDA-проект) можно убрать. |
| P7 | Локальная сторона: порт `IStudioServerClient.upload_pdf`, сценарий `PublishPdfUC`, срабатывает после успешной сборки (хук `CompileJobHooks`) в фоне и вручную (`POST /projects/{id}/git/pdf`). Включено по умолчанию, если проект подключён к серверу Студии (вход по коду устройства); права токена заранее не проверяются, нехватка `git:write` приходит отказом `pdf_scope_missing` и подсказкой «войдите заново»; отключается настройкой проекта `pdf_upload`. Результат последней выгрузки (документ, время, статус, код ошибки) лежит в `hse-sync.json` и виден в статусе. Сбой выгрузки сборку не ломает. | Выгрузка вторична по отношению к сборке. |
| P8 | Сайт: на странице обзора проекта карточка «PDF из локальной Студии» (документ, время, размер, кто выгрузил, открыть в просмотрщике, скачать, удалить). | PDF виден там же, где читатель смотрит результат. |

Вне объёма: удалённая сборка без Docker, CI-токен проекта (отдельная спецификация), подписанные PDF как отдельные артефакты, версии одного PDF для нескольких документов за раз.
