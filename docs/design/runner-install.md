# Установка раннеров из админки

Статус: дизайн, 06.11.2026. Решения, помеченные **Развилка**, приняты по умолчанию и ждут подтверждения владельца продукта. Основа: `k8s-runner.md` (исполнитель kubernetes), раздел «Подключение раннера» в `docs/ru/deploy/runners.md`, личные раннеры.

## 1. Задача

Сегодня админ выпускает токен регистрации, видит секрет и строку `HSE_RUNNER__API_URL=… hse-doc-studio runner`, а дальше всё руками. Нужно три способа поставить раннер из страницы «Раннеры»:

1. **На этой же машине** (Docker рядом или Deployment в том же кластере).
2. **По SSH** на другую машину, с ходом установки в реальном времени.
3. **Копируемая команда** (docker run и curl-скрипт), которая показывается вместе с токеном.

Порядок работы: п.3, затем п.1, затем п.2. Каждый срез отдельный PR в master.

## 2. Общие принципы

- Все новые маршруты в `/api/admin` (область `instance_admin`, чужому 404), записи в `ROUTE_SCOPES`, проверка прав на каждом эндпоинте.
- Секреты (токен регистрации, пароль и ключ SSH, passphrase) не попадают в логи, аудит, телеметрию, ответы API (кроме разового показа токена, как сейчас). Ответы с секретами идут с `Cache-Control: no-store`.
- Токен для установленного раннера создаёт сама Студия (одноразовый, срок час, одно использование) и передаёт его раннеру в окружении установки; в журнал и ответ он не уходит.
- Строки интерфейса в ru и en, мобильная адаптация и крупный текст через существующие компоненты и токены размеров.
- Образ раннера один и тот же: `settings.image_base:<версия>`, команда `hse-doc-studio runner`. Отдельного бинарника для хоста нет (пакета на PyPI нет), поэтому «служба» на хосте это systemd-юнит или launchd-задание, которое держит контейнер раннера. **Развилка:** для хоста без Docker скрипт честно сообщает, что нужен Docker, и показывает ссылку на установку; нативный режим без контейнера не делаем.

## 3. Срез 1: копируемая команда (п.3)

### 3.1 Ответ API

`POST /api/admin/runner-tokens` и `POST /api/admin/runners/{id}/rotate-token` дополнительно возвращают `docker_command` и `script_command`. Поле `command` остаётся (совместимость).

- `docker_command`: одна строка `docker run -d --name hse-runner --restart unless-stopped … -e HSE_RUNNER__API_URL=<public_url> -e HSE_RUNNER__TOKEN=<секрет> <образ> hse-doc-studio runner`. Для ротации вместо `HSE_RUNNER__TOKEN` стоит `HSE_RUNNER__RUNNER_TOKEN`, как в `runner_token_command`.
- `script_command`: `curl -fsSL <public_url>/api/runner/v1/install.sh | sudo HSE_RUNNER__API_URL=… HSE_RUNNER__TOKEN=… sh -s -- install`.
- Адрес берётся из `settings.auth.public_url`, иначе из запроса админа (как `studio_base_url`).

### 3.2 Скрипт установки

`GET /api/runner/v1/install.sh`, без входа, без секретов в самом скрипте: токен передаётся окружением команды. Скрипт одинаков для всех, поэтому его можно сначала скачать и прочитать (`curl … -o install.sh; less install.sh; sh install.sh install`).

Что делает `install`:

1. Определяет ОС (`Linux`, `Darwin`) и проверяет, что запущен Docker; нет Docker, выходит с понятным текстом и ссылкой.
2. Перед действиями печатает план: что будет создано (юнит или plist, путь, образ, адрес Студии, каталог данных).
3. Linux с systemd: пишет `/etc/systemd/system/hse-runner.service` (`ExecStart` с `docker run --rm --name hse-runner …`, `Restart=always`), токен кладёт в `/etc/hse-runner/env` с правами 0600, `systemctl daemon-reload`, `enable --now`.
4. macOS: пишет `~/Library/LaunchAgents/ru.hse-doc-studio.runner.plist` (или `/Library/LaunchDaemons` под sudo) с `RunAtLoad` и `KeepAlive`, токен в файле окружения 0600, `launchctl bootstrap`.
5. Идемпотентность: повторный запуск перезаписывает юнит тем же содержимым, перезапускает службу, не плодит дубликатов; сохранённый `identity.json` в каталоге данных не трогается, поэтому токен регистрации нужен только первый раз.
6. `uninstall`: останавливает и отключает службу, удаляет юнит и файл окружения; каталог данных и контейнер удаляются только с флагом `--purge`. `status` печатает состояние.

Режим `HSE_RUNNER_DRY_RUN=1` печатает действия, ничего не меняя. Токен в плане и сообщениях маскируется.

### 3.3 Интерфейс

В окне «токен создан» и «токен раннера после ротации» две вкладки: «Docker» и «Скрипт (служба)». Над командой текст, что выполнится; кнопка «Скопировать» у каждой; секрет по-прежнему виден один раз. Ниже ссылка «Показать скрипт» (открывает `install.sh`). Вкладки работают с клавиатуры (`role=tablist`), на узком экране команда переносится.

### 3.4 Проверки

Unit: генерация команд (без секрета в скрипте, маскирование), шаблон скрипта (`shellcheck`-подобные проверки: POSIX sh, `set -eu`), маршрут (публичный, без секретов). Интеграционные: ответ создания токена, скрипт запускается в `HSE_RUNNER_DRY_RUN=1` и в песочнице без Docker сообщает понятную ошибку. e2e: создать токен, переключить вкладки, скопировать команду, проверить содержимое буфера.

## 4. Срез 2: на этой же машине (п.1)

### 4.1 Возможности

`GET /api/admin/runner-install/local` отвечает:

```json
{"docker": {"available": true, "reason": null}, "kubernetes": {"available": false, "reason": "disabled"}}
```

- **docker**: доступен, если Студия видит docker socket (тот же клиент, что у страницы «Диск», `infra/docker/cli.py`) и Docker отвечает.
- **kubernetes**: доступен, если Студия работает в поде (есть ServiceAccount), в Helm включено `runner.installFromUi.enabled` и права ServiceAccount позволяют создавать Deployment (проверка `SelfSubjectAccessReview`). По умолчанию в чарте выключено: на проде общие раннеры сознательно не включены.
- Причины (`reason`): `no_socket`, `docker_unreachable`, `not_in_cluster`, `disabled`, `no_permission`. Интерфейс показывает кнопку только при `available`, иначе пояснение по причине.

### 4.2 Docker

`POST /api/admin/runner-install/local/docker`: создаёт одноразовый токен, запускает контейнер `hse-runner-<суффикс>` из образа текущей версии с метками `managed-by=hse-doc-studio`, рестарт `unless-stopped`, `docker.sock` раннера как у `registration_docker_command`. Ответ: имя контейнера и id задачи; ход виден опросом раннера в списке (появится онлайн). Повтор: удаляет контейнер с тем же именем и создаёт заново.

### 4.3 Kubernetes

`POST /api/admin/runner-install/local/kubernetes`: создаёт в namespace релиза ServiceAccount `hds-runner-ui-<суффикс>`, Role и RoleBinding на поды сборки (как в `runner-kubernetes.yaml`: `pods` create/get/list/delete, `pods/log` get, `pods/exec` create/get), Secret с токеном и Deployment с `executor=kubernetes`, `securityContext` под restricted. Права самой Студии в чарте: Role на `deployments`, `serviceaccounts`, `secrets`, `roles`, `rolebindings` в своём namespace, только при включённом `installFromUi`. **Развилка:** Студия получает право создавать Role, поэтому чарт даёт ей `escalate`-free набор: Role раннера не шире её собственной (иначе Kubernetes откажет), это заодно проверка «минимальных прав».

### 4.4 Проверки

Unit: определение возможностей по подмене (`FakeDockerClient`, `FakeKubeApi`), формирование манифестов. Интеграционные: маршруты с правами, скрытие кнопки. Helm: golden-рендер с `installFromUi` вкл и выкл (по умолчанию выкл).

## 5. Срез 3: по SSH (п.2)

### 5.1 Поток

1. **Цель.** Форма: адрес, порт (22), логин, способ входа (пароль или приватный ключ с необязательной passphrase), sudo. Ничего не сохраняется.
2. **Проверка адреса (SSRF).** До соединения адрес разрешается в IP, запрещены loopback, link-local (включая 169.254.169.254 метаданные облака), адреса кластера (CIDR pod/service из окружения, `kubernetes.default`), приватные сети по умолчанию разрешены только если админ включил `HSE_STUDIO__RUNNER_INSTALL__ALLOW_PRIVATE`. Пинг по IP, а не по имени после проверки (защита от DNS rebinding). Проверка повторяется при каждом соединении.
3. **Отпечаток.** Первое соединение только получает ключ хоста и возвращает SHA256-отпечаток и тип; сессия ждёт подтверждения админа, пока не подтверждено, учётные данные не используются. При известном ранее отпечатке (сохранённая цель) несовпадение блокирует установку.
4. **Разведка.** После подтверждения: `uname -sm`, `/etc/os-release`, `docker version`, `systemctl`. Возвращается план шагов (проверка, установка Docker при желании, запись юнита, запуск, ожидание регистрации).
5. **Установка.** Шаги выполняются по SSH; состояние каждого шага (ожидает, идёт, успех, ошибка с понятным текстом) отдаётся потоком SSE и опросом `GET …/{job}`. Повтор: «повторить с шага».
6. **Хост.** Службу ставит тот же скрипт из среза 1 (`sh -s -- install`), токен создаётся Студией и передаётся через stdin, не в аргументах команды (не виден в `ps`).

### 5.2 Учётные данные

По умолчанию одноразовые: живут в памяти процесса api на время задачи (TTL, затирание после), не пишутся в БД, логи, аудит. Явная галочка «сохранить зашифрованно» записывает их в таблицу `runner_ssh_targets` под ключом шифрования секретов Студии (`infra/secrets`, как токены git). Просмотр это факт наличия и подпись цели (значение не показывается), удаление, обновление и переустановка раннера «в один клик» с сохранёнными данными. В многозвенном api (несколько реплик) состояние задачи в памяти одной реплики: **Развилка**, задача привязана к реплике, маршруты читают её же (sticky не нужен, пока реплика одна; при нескольких вызов на чужую реплику отвечает 409 «повторите»).

### 5.3 Ограничения

- Частота: не больше N попыток подключения в минуту на админа и на целевой адрес (`core/rate_limit`), после превышения 429.
- Одновременно не больше нескольких задач установки на инстанс.
- Таймауты соединения и шагов, предел вывода.
- Аудит: `runner_install.ssh.probe|confirm|run|delete_credentials` с адресом, логином, отпечатком, исходом, без секретов.

### 5.4 Проверки

Unit: SSRF-политика (таблица адресов), шифрование записи цели, редактор вывода (секреты вырезаются из ошибок). Интеграционные: SSH подменён тестовым сервером (asyncssh-сервер в процессе) для сценариев пароль, ключ, неверный отпечаток, нет Docker, обрыв. e2e на подменённом API.

## 7. Открытые вопросы

- Нужен ли режим без Docker (нативный запуск раннера на хосте)? Сейчас нет: пакета раннера вне образа не существует.
- Разрешать ли по умолчанию приватные сети (LAN) для SSH? Предлагается запрет, включаемый настройкой.
- Хранить ли отпечатки хостов отдельно от учётных данных, чтобы они переживали удаление данных? Предлагается да.
