# Студия шаблонов: паки мышкой, выпуск через PR

Статус: предложено 13.11.2026, решения приняты по умолчанию (раздел 2), неочевидные помечены **Развилка**. Идея владельца продукта: «мини-образ для создания шаблонов нам как разработчикам и другим, мини-UI, где можно собирать и редактировать шаблоны; по сути он управляет шаблонами в git в виде PR».

Основа: справка `docs/ru/reference/pack.md`, раздел 15 `docs/design/signing-route.md` (пресеты маршрута, исключение для patch), `docs/design/collaboration.md` (один образ, git-синхронизация 11, админка 13, раннеры 14), `docs/design/mcp.md` (слой тулов), код `infra/template/*`, `core/template_versions.py`, `infra/project_init/template_renderer.py`, `features/signature-stamper`.

Документ не входит в сайт документации, это рабочий дизайн для разработки.

## 0. Коротко

Студия шаблонов это отдельное приложение внутри той же Студии (адрес `/pack-studio`, свой лейаут и чанк, как `/admin`). Автор пака открывает git-репозиторий паков или локальную папку, правит пак формами и визуально (поля анкеты, документы, точки сдачи, места подписей прямо на собранном PDF), смотрит сборку на тестовых данных в разных комбинациях, а мастер «Новая версия» сам считает класс изменения и пишет заметки. Кнопка «Предложить изменения» коммитит в ветку и открывает PR (GitHub) или MR (GitLab). Выпущенные версии тронуть нельзя. Произвольный LaTeX и шаблоны пака исполняются только в песочнице.

Первый шаг, полезный сразу и без всей Студии шаблонов: кнопка «Скопировать как пресет шаблона» в редакторе мест подписей проекта (раздел 13).

## 1. Что есть сейчас

### 1.1 Пак

```text
packs/<pack>/pack.yaml                         манифест пака: id, имена ru/en, maintainer, license, source
packs/<pack>/templates/<tpl>/template.yaml     шаблон вне версий: имена, иконка, default_version, author_group_placeholder
packs/<pack>/templates/<tpl>/releases.yaml     реестр выпусков: версия, digest каталога, kind
packs/<pack>/templates/<tpl>/versions/<v>/     полная копия версии
    version.yaml                               манифест: langs, documents, meta_fields, signatures, pack_submission, ...
    files/<doc>/doc.yaml, *.tex, *.ru.tex      документы (bundle-раскладка v2, языковые суффиксы)
    files/common/meta.tex.j2                   динамический инклуд: макросы \hse... из project.json
    checks/*.yaml                              правила проверок с шапкой label/ref/source
```

- Каждая версия это полная копия каталога. Выпущенная версия неизменна: `releases.yaml` хранит её дайджест, `test_releases.py` и `releases check` падают при любой правке, `releases freeze` вносит новую версию (только `stable` или `deprecated`).
- Номер `ГОД.MINOR.PATCH`, класс перехода считается по номерам (`classify_update`), `release.kind` может быть строже, не мягче. Исключение для patch (signing-route.md, 15.10): `placements`, `default_dates`, `signing_slots`, `signatures.route`, `signing_route`, `deadline_hint`. Сейчас это правило записано в docstring и справке, но **ничем не проверяется**: класс по содержимому никто не считает.
- `pack_lint` проверяет версию: Jinja, языковые суффиксы, `\input`, `source_file`, анкеты в пакете, шапки проверок, заметки `changes` ru/en, маршрут, места и метки, `signing_slots`, подсказки сроков. Тест `test_pack_lint.py` гоняет его по всем пакам репозитория в CI.
- Лоадер `YamlTemplateRepository` терпим к незнакомому: битый элемент выпадает, остальное работает; `manifest_format` новее известного прячет версию.
- Для автора пака уже есть CLI предпросмотра обновления на реальных проектах: `infra/template_update/cli.py plan|compare`.

### 1.2 Как Студия получает паки

- Паки вшиты в образ: `COPY packs /app/packs`, сборка пишет опись `/app/packs-manifest.json` (`infra/template/packs_source.py`).
- Подменить каталог можно монтированием поверх `/app/packs` или через `HSE_STUDIO__PACKS_DIR`. Студия это замечает (`PacksKind.external`) и честно говорит, что отстал каталог, а не Студия.
- Каталог читается один раз при старте (`get_template_repo`, `Scope.APP`); горячей перезагрузки нет.
- Раздела паков в админке нет, хотя `collaboration.md`, 13 относит «паки и шрифты» к уровню установки.
- Итог: пак попадает в прод только вместе с релизом Студии: PR в `packs/`, релиз, образ, выкатка.
- В проекте версия закреплена (`project.lock`, дайджест содержимого). Новая версия приходит через «Обновить шаблон»: patch карточкой на обзоре, minor и major в настройках; трёхстороннее слияние, отмена, пресеты подписей переносятся (R26).

### 1.3 Что переиспользуем

| Что | Где | Зачем Студии шаблонов |
|---|---|---|
| разбор пака, `pack_lint`, `releases`, `template_versions` | `infra/template`, `core` | один и тот же код проверяет пак в инструменте, в CI и в Студии, куда его выложат |
| создание проекта из версии и динамические инклуды | `template_renderer.build_context`, `instantiate_base`, `regenerate_dynamic_includes` | предпросмотр на тестовых данных |
| где печатается поле | `core/meta_usage.py` | подсказки «поле печатается в: ...», макросы `\hse...` |
| сборка задачами на раннерах | `JobKind.compile`, встроенный раннер локально, раннеры сервера | сборка предпросмотра в песочнице |
| просмотр PDF | `shared/ui/PdfViewer` | вкладка предпросмотра |
| редактор мест и меток даты | `features/signature-stamper` (`PdfStampEditor`, `SignatureOverlay`, `DateMarkOverlay`, `SlotDateMarks`) | места подписей пака на собранном PDF |
| порядок маршрута | `features/signing-route-editor` | шаги `signatures.route` и `signing_route` |
| редактор кода | `shared/ui/CodeEditor` (CodeMirror 6, автодополнение, внешние диагностики) | LaTeX, YAML, Jinja с ошибками линтера в строке |
| доступы git | `infra/git_sync`: секреты Fernet, каталог провайдеров `contracts/git-sync/providers.json`, проверка токена, TLS своих серверов, закалка стора | клон, ветка, push репозитория паков |
| генерация CI | `infra/git_sync/ci_renderer.py` | CI для внешнего репозитория паков |
| слой тулов | `core/agent`, `use_cases/mcp/tools` | MCP для агентов авторов паков |

### 1.4 Чего не хватает

| Пробел | Почему важно |
|---|---|
| правка YAML с сохранением комментариев и выравнивания | паки густо комментированы; переписанный целиком `version.yaml` даст нечитаемый PR |
| классификатор изменений по содержимому | исключение для patch сейчас держится на внимательности автора |
| песочница для шаблонов пака | `template_renderer` и `form_renderer` рендерят Jinja обычным `Environment` в процессе api: для чужого пака это исполнение кода на сервере |
| тестовые данные пака | собрать документы пака можно только создав проект руками |
| схема манифеста | формы строить не по чему, кроме кода лоадера |
| создание PR и статус CI | `git_sync` умеет fetch и push, но не API хостинга |
| перезагрузка каталога без рестарта | выкладка пака без релиза Студии невозможна |

## 2. Решения

|---|---|---|---|
| D1 | Форма поставки | Приложение `/pack-studio` в том же образе и том же процессе api, свой лейаут и lazy-чанк, API `/api/pack-studio/*` со своим гардом | Отдельный образ `hse-doc-studio-pack-studio`: дублирует парсер, линтер, сборку, просмотр PDF и редактор мест, а главное, версия парсера в инструменте разъедется с версией в Студии, куда выкладывают пак. Принцип `collaboration.md`, 4.1: один код и один образ. Раздел `/admin`: авторы паков не админы, в локальном режиме админки нет |

| D4 | Кто пользуется | Локально: включается в Настройках («Инструменты автора шаблонов») или в standalone. | D6 | Монорепа | Неглубокий частичный клон: `--filter=blob:none --sparse`, в выборке только каталог паков (`packs/` по умолчанию, путь задаётся) | Полный клон монорепы ради одного пака |
| D7 | Авторизация | MVP: личный токен пользователя из доступов git (11.5) с расширенными правами под PR. Плюс «служебный доступ» репозитория, который задаёт админ установки, для методистов без аккаунта на хостинге. GitHub App потом (S-later) | GitHub App сразу: каждой self-hosted установке пришлось бы регистрировать своё приложение с публичным callback |

Для внешних репозиториев инструмент генерирует CI на образе Студии | Только локально: CI это то, что видит ревьюер; только CI: долгая обратная связь |

## 3. Форма поставки и пользователи

### 3.1 Одно приложение того же образа

- Фронтенд: страница `pages/PackStudioPage`, фичи `features/pack-*`, общий лейаут как у `/admin` (свой сайдбар, хлебные крошки «Репозиторий, пак, шаблон, версия»). Чанк грузится только тем, у кого раздел включён.
- Бэкенд: роутер `/api/pack-studio/*`, сценарии `use_cases/pack_studio`, чистая логика `core/pack_studio` и `core/template_diff.py`, адаптеры `infra/pack_studio` (рабочие пространства, git, YAML-правки, синтетический проект).
- Режим: `HSE_STUDIO__PACK_STUDIO__ENABLED` (по умолчанию локально выключено, раздел включается в Настройках; на сервере выключено, включает админ), `HSE_STUDIO__PACK_STUDIO__STANDALONE`.

### 3.2 Где запускается

| Где | Как | Сборка | Каталог паков Студии |
|---|---|---|---|
| разработчик в монорепе | `make pack-studio`: api из исходников и vite, рабочее пространство над `packs/` рабочей копии, git и PR через `gh`-совместимый токен | встроенный раннер, локальный Docker | тот же `packs/`, как сейчас |
| локально, автор другой программы | `docker compose -f deploy/pack-studio/docker-compose.yml up`, том данных и папка с паками | встроенный раннер | вшитые паки плюс подключённые папки (10.3) |
| сервер | раздел `/pack-studio` у пользователей с правом | раннеры установки, организации или свои, в квоту пользователя | вшитые плюс каталоги из `/admin` (10.3) |

### 3.3 Кто и с какими правами

| Кто | Где работает | Что может |
|---|---|---|
| разработчик Студии | монорепа, локально | всё; PR в наш GitHub своим токеном |
| автор пака другой программы или вуза | своя локальная Студия или свой сервер | свой репозиторий паков; в наш репозиторий через форк |
| методист без аккаунта на хостинге | сервер, право «Автор шаблонов» | правка в ветке и «Предложить изменения» через служебный доступ репозитория; автор коммита он сам, push от служебного доступа |
| админ установки | `/admin` | включает раздел, выдаёт право, задаёт служебный доступ, подключает каталоги паков (потом) |
| студент | нет раздела | только кнопка «Скопировать как пресет шаблона» (раздел 13) |

Сервер: право `pack_studio` это флаг пользователя или группы организации (`collaboration.md`, 6); у PAT новая область `packs` для MCP и CLI. Решение о слиянии принимает хостинг git, а не Студия: право в Студии разрешает только готовить предложения.

## 4. Рабочее пространство: источник и цель

### 4.1 Источник

Рабочее пространство это пара «откуда и куда»:

| Поле | Значение |
|---|---|
| вид | `git` или `folder` |
| адрес | URL репозитория (провайдер определяется как в 11.5) или путь папки (только локально) |
| путь паков | каталог внутри репозитория, по умолчанию `packs` |
| базовая ветка | по умолчанию HEAD сервера |
| доступ | личный доступ git пользователя или служебный доступ репозитория |
| рабочая ветка | `pack-studio/<логин>/<пак>-<шаблон>-<версия>` или своя |
| PR | URL и номер, если открыт |

- Где лежит: `data_dir/pack-studio/workspaces/<id>/` (на сервере на томе, как папки проектов; свои у каждого пользователя). Клон с той же закалкой, что стор проекта: пустой `core.hooksPath`, `core.fsmonitor=false`, `credential.helper=`, `core.symlinks=false`, окружение git по списку разрешённого.
- Папка без git (`folder`): правки пишутся прямо на диск, история только локальная (снимки в изолированном сторе, как у проектов). PR нет. Так автор ведёт свой пак без хостинга.
- Состояние: локально `data_dir/pack-studio/workspaces.json`, на сервере таблица `pack_workspaces` (владелец, источник, ветка, ссылка на доступ, PR, последний статус CI).

### 4.2 Доступ и права токенов

Токен никогда не пишется в клон: как в 11.5, только `http.<url>.extraheader` в окружении процесса git. Проверка токена (`POST /git/credentials/{id}/check`) получает профиль «репозиторий паков» с расширенным набором прав:

| Провайдер | Нужно | Зачем |
|---|---|---|
| GitHub, точный токен | `Contents: Read and write`, `Pull requests: Read and write`, `Commit statuses: Read`, `Checks: Read`, `Metadata: Read` | ветка, PR, статус CI |
| GitHub, классический | `repo` (или `public_repo` для открытого) | то же; нужен для PR из форка в чужой открытый репозиторий |
| GitLab | `write_repository`, по желанию `read_api` | MR через push options; статус конвейера только с `read_api`, без него ссылка на конвейер |
| Gitea, Forgejo | `write:repository` | PR через AGit (`refs/for/<ветка>`), потом |

Ссылки на создание токена с заполненными полями переиспользуют каталог провайдеров; в него добавляется профиль прав `packs`.

**Служебный доступ** задаёт админ установки для конкретного репозитория паков: тот же вид доступа, но уровня установки. Им пользуются только рабочие пространства этого репозитория у людей с правом «Автор шаблонов». В коммите автор это пользователь Студии (профиль 11.1), в описании PR строка «Предложено в Студии шаблонов пользователем ...». **Развилка:** служебный доступ или только личные токены. Принято: оба, личный по умолчанию.

### 4.3 Ветка, коммиты, «Предложить изменения»

1. Первая правка в рабочем пространстве над git создаёт рабочую ветку от свежей базовой.
2. Сохранение пишет файлы; коммит делает «Сохранить версию» (как снимок в проекте) или «Предложить изменения». Сообщения по соглашению репозитория: в нашем conventional commits (`fix(packs): ...` для patch, `feat(packs): ...` для minor и major), в чужом свободный текст.
3. «Предложить изменения»: локальные проверки (4.4), коммит, push рабочей ветки, PR или MR в базовую ветку. Описание PR собирает инструмент: пак, шаблон, версия, вычисленный класс и его причины, заметки `changes` ru/en, сводка проверок, превью изменённых страниц (ссылки на артефакты не нужны, картинки не прикладываются).
4. Нет права push в репозиторий: инструмент предлагает форк. GitHub: пользователь указывает свой форк (или инструмент создаёт его, если токен позволяет), push туда, PR из форка. Если API отказал, ссылка «Открыть PR в браузере» на страницу compare с готовой веткой.
5. После слияния рабочее пространство предлагает «Начать заново от базовой ветки»; старая ветка удаляется на хостинге по желанию.

Конфликт с базовой веткой (кто-то выпустил ту же версию раньше): инструмент делает fetch и сравнивает `releases.yaml` базы. Если номер занят, мастер предлагает следующий номер и переносит каталог; содержимое других файлов сливается тем же движком, что синхронизация проектов (11.4).

### 4.4 Проверки

| Проверка | Локально | В CI |
|---|---|---|
| `pack_lint` всех изменённых версий | при каждом сохранении (быстро, без TeX), ошибки в строке редактора | да |
| `releases check` | при сохранении | да (`test_releases.py` в нашем репозитории) |
| классификатор (7.2): номер не мягче минимума | при сохранении | да, новое правило линтера |
| сборка изменённых документов в комбинации по умолчанию | перед «Предложить изменения» | да, `hse-doc-studio pack build --examples` в образе TeX |
| схема (`version.schema.json`) | при сохранении | да |

Статус CI: по sha головы ветки. GitHub: `check-runs` и `status` коммита; GitLab: конвейеры по sha (`read_api`). Опрос при открытии рабочего пространства и раз в 30 секунд, пока страница открыта и проверки идут. Показ: список проверок с состоянием и ссылкой; упавший шаг с последними строками журнала, если хостинг их отдаёт.

CI для внешнего репозитория паков: кнопка «Добавить CI» генерирует `.github/workflows/hse-packs.yml` или `.gitlab-ci.yml` (как `ci_renderer` для проектов): образ Студии той версии, что у автора, команда `hse-doc-studio pack check <путь паков>`, сборка примеров в образе TeX. Секреты CI не нужны.

Наш репозиторий: PR, который трогает только `packs/**`, сейчас запускает весь бэкенд. Отдельный быстрый джоб `packs` (lint, releases, классификатор, сборка примеров изменённых версий) и фильтр путей сокращают ожидание; это срез T18.

### 4.5 Выпущенные версии

- Список выпущенных берётся из `releases.yaml` базовой ветки после fetch. Их каталоги в дереве отмечены замком, формы и редактор только для чтения, запись отвечает `409 version_released`.
- Попытка правки выпущенной версии предлагает «Создать новую версию» (раздел 7) с этой правкой.
- Перед push инструмент запускает `releases check`: ручная правка мимо интерфейса тоже не уйдёт.

## 5. Что редактируется

### 5.0 Принцип

- Каждая сущность это форма поверх YAML, построенная по схеме (D12), и вкладка «Исходник» с тем же файлом в редакторе кода. Форма пишет точечные правки (D11): поменялось значение, заменяется его фрагмент; новый ключ вставляется в конец своего блока с отступом соседей; удаление убирает строки узла с его комментарием над ним.
- Все локализуемые строки идут парой ru и en; пустой перевод подсвечивается.
- Справа панель «Проблемы»: ошибки и предупреждения линтера по этой сущности, клик ведёт в поле или строку.
- Незнакомые схеме ключи (пак от более новой Студии) форма показывает только в «Исходнике» и не трогает.

### 5.1 Структура пака и версии

- Дерево: пак, шаблоны, версии (с бейджем `stable`, `beta`, `deprecated`, замком у выпущенных), внутри версии разделы: Документы, Поля, Анкеты, Подписи, Точки сдачи, Проверки, Файлы, Заметки.
- Пак: `pack.yaml` (имена, описание, maintainer, license, source). Шаблон: `template.yaml` (имена, иконка lucide с поиском, `accent_hue` с образцом цвета, `default_version`, подсказка группы).
- Версия: шапка (`summary`, `status`, `released_at`, `min_studio`, `supported_kinds`, `supported_staffing`, `langs`, `engine`, `latex_packages`).

### 5.2 Метаданные и поля анкеты

- `meta_groups`: список с перетаскиванием (порядок равен порядку в настройках проекта).
- `meta_fields`: таблица полей (ключ, тип, группа, `required_at`, `scope`), карточка поля: `type` (string, bool, person, select, font), `label`, `placeholder`, `help`, `default`, `auto` (`academic_year` с подсказкой, что даёт сегодня), `options` для select, `supported_kinds`.
- Справа живой образец поля так, как его увидит студент в мастере проекта (те же компоненты `features/project-create`).
- «Где печатается»: по `core/meta_usage.py` список документов и макросов `\hse...`, которые печатают поле. Поле, которое нигде не печатается и не нужно анкете, получает предупреждение.
- Переименование ключа меняет ключ во всех `.j2` и `.tex` версии (поиск по `project.meta.<ключ>`) и помечает изменение как удаление с добавлением (класс в 7.2).
- Анкеты (`forms`): секции и поля движка анкет, `required_for_pack`, `per_author`, `output`. Форма редактора та же, что для `meta_fields`, по своей схеме; образец справа рисует `features/form-fill`.

### 5.3 Документы

- Ростер `documents`: порядок перетаскиванием, добавление из библиотеки (документы существующих паков как заготовки: титул по ГОСТ 7.32, заявление о теме, лист утверждения ЕСПД) или пустой.
- `doc.yaml`: `name`, `code`, `output_name` ru/en, `source_file`, `output_file`, `gost_ref` (выбор из проверок версии), `required`, `supported_langs`, `scope` (personal или shared), `supported_kinds`, `group`, `variants`.
- Языки: таблица «файл, ru, en» по грамматике суффиксов; «Создать перевод» копирует редакцию языка по умолчанию в `<stem>.<код>.<ext>`; смешение bare и суффиксов линтер называет ошибкой и тут.
- Группы навигации (`group`): список групп с подписью, документ перетаскивается между ними.

### 5.4 LaTeX-исходники и `meta.tex.j2`

- Редактор кода Студии с режимами LaTeX, YAML, Jinja-в-LaTeX (разделители `((* *))`, `((# #))`, `{{ }}`).
- Автодополнение в `.j2`: переменные контекста `build_context` (`project.name`, `project.lang`, `project.kind`, `project.staffing`, `project.authors[]`, `project.meta.<ключ>` по `meta_fields`, `project.supervisor.name` и другие персоны, `author.*`, `team.is_team`, `team.is_shared_base`, `pack.id`, `template.id`, `template.version`) и фильтры (`texesc`, `xmlesc`). Наведение на `project.meta.x` показывает поле: подпись, тип, группу.
- Автодополнение в `.tex`: макросы `\hse...`, объявленные в динамических инклудах версии (разбор `_DEFINITION` из `meta_usage`), с подсказкой, какое поле печатает макрос.
- Ошибки Jinja и `\input` из `pack_lint` приходят в строку через внешние диагностики `CodeEditor`.
- Файлы ресурсов (картинки, шрифты, pptx): загрузка и замена в дереве «Файлы», предел размера как у pre-commit (2 МБ на файл).

### 5.5 Профили сдачи и точки

- Список профилей с перетаскиванием; карточка: `name`, `description` ru/en, `deadline_hint` ru/en (5.8).
- Пункты (`items`): документ из ростера, подписи (слоты, применимые к документу), `methods` по слоту (image, detached, pades галочками), `skip_if_nda`, `supported_kinds`.
- `extra_items`: анкеты и файлы, которые едут в пакет; правило линтера про `required_for_pack` показывается прямо у пункта.
- Маршрут точки: блок 5.6.

### 5.6 Подписи: слоты, места, метки, маршрут

- Каталог слотов: `id` (без `--`), `label`, `applies_to`, `per_author`, `required`, `default_placement`.
- **Места на PDF.** Вкладка «Подписи» показывает собранный предпросмотр документа (раздел 6) и рамки слотов, применимых к документу: место документа (`placements`), иначе `default_placement` (рамка пунктиром с подписью «по умолчанию»). Рамки двигаются и тянутся тем же `PdfStampEditor`, что у проекта; вместо картинки подписи заглушка с именем слота и типичным соотношением сторон 3:1 (высота рамки в проекте зависит от картинки, это написано под рамкой). Перетаскивание рамки «по умолчанию» создаёт запись `placements` для этого документа; «Сделать местом по умолчанию» переносит в `default_placement` (это не входит в исключение patch, 7.2).
- **Метки даты** (`default_dates`): тот же `SlotDateMarks` и `DateMarkOverlay`, формат и выравнивание из списка, не больше восьми на документ.
- Подсказки на месте: рамка за краем листа, место `per_author` на общем документе командного шаблона, узкое место под плашку открепленной ЭП, если точка её разрешает (правила `pack_lint` 15.8 работают на клиенте по той же схеме и на сервере при сохранении).
- **Порядок маршрута** (`signatures.route`, `signing_route` профиля): шаги перетаскиванием, внутри шага параллельно; компоненты `signing-route-editor` в режиме пака (без людей и статусов).
- **`signing_slots` точки**: таблица «документ, слот, условие `when`, `optional`». Условие выбирается из закрытого списка (15.3): всегда, человек указан, человек указан и из ВШЭ, человек указан и из компании; персоны `supervisor`, `co_supervisor`, `academic_supervisor`. `optional` недоступен у слота с `required: true`.
- Справа «Маршрут в этой комбинации»: по переключателям предпросмотра (6.2) видно, какие подписи попадут в черновик точки: «автор; научрук; академрук появится, если научрук из компании».

### 5.7 Проверки и правила

- Файлы `checks/*.yaml`: шапка (`label`, `ref` ru/en, `source`), правила списком.
- Правило: `id` (с префиксом файла), `title`, `description`, `category`, `applies_to`, `default_severity`, `engine`, `params`. Для известных структурных проверок (`page_geometry`, `line_spacing`, размер шрифта и другие из движка проверок) форма параметров; для прочих движков `params` в YAML-редакторе по схеме.
- `checks_version`: отключённые категории и правила, переопределение важности.
- «Проверить на предпросмотре»: прогон проверок на собранных документах комбинации, находки рядом с правилом (тот же движок, что `run_checks` проекта).

### 5.8 Подсказки сроков и заметки

- `deadline_hint` ru/en у профиля: счётчик до 200 знаков, запрет конкретных дат (правило линтера и `scripts/docs/lint_docs.py` по сути одно: даты меняются каждый год).
- `changes` и `breaking_changes` ru/en: пункты парами, длины списков равны (правило линтера); их пишет мастер версии (7.4).

## 6. Предпросмотр

### 6.1 Тестовые данные

`templates/<tpl>/examples/<имя>.yaml` описывает синтетический проект: имя, язык, вид, состав, авторы, люди проекта с ролями, `meta`, ответы анкет. Пример:

```yaml
name: { ru: "Контур согласования действий LLM-агента", en: "An Approval Gate for LLM Agents" }
authors:
  - { name: "Иванов Иван Иванович", group: "МСПИН261" }
supervisor: { name: "Петров Пётр Петрович", position: "доцент", role: university }
meta:
  proposal_stage: "Предварительная"
```

- Примеры лежат вне каталога версии: их правка не меняет дайджест и не требует выпуска (D13). Лоадер Студии каталог `examples/` не читает.
- Без примеров инструмент строит три набора сам: «Обычный» (из `placeholder` и `default`), «Длинные значения» (каждое строковое поле в три раза длиннее: ловит переполнение строк титула), «Пустой» (только обязательные при создании, остальное печатается плейсхолдерами `\hseFill`).
- «Сохранить как пример» записывает текущие значения в `examples/`.

### 6.2 Переключатели комбинаций

| Переключатель | Значения | Откуда |
|---|---|---|
| язык | коды `langs` | версия |
| вид работы | `supported_kinds` | версия |
| состав | solo, команда из 2 или 3 авторов | `supported_staffing` |
| научный руководитель | из ВШЭ, из компании, не указан | `PersonRole` |
| консультант | есть, нет | персона `co_supervisor` |
| академический руководитель | указан, не указан | персона `academic_supervisor` |
| NDA | да, нет | если у версии есть `nda` |
| поля select и bool | значения поля | `meta_fields` (до пяти полей, остальные в наборе данных) |

Переключатели поверх набора данных: набор задаёт имена и тексты, переключатели задают ветки. Комбинация кодируется в адресе страницы, ей можно поделиться.

### 6.3 Как собирается

1. Синтетический `Project` в памяти из набора и переключателей.
2. Песочный рендер (раздел 9): `instantiate_base` и `regenerate_dynamic_includes` во временную папку `data_dir/pack-studio/previews/<ключ>/` отдельным процессом с пределами.
3. Задача `compile` на раннере для выбранных документов, вход это обычный манифест `{путь, sha256}` (14.3), выход PDF и журнал.
4. Ключ кэша: дайджест каталога версии (рабочей, с несохранёнными правками) плюс комбинация плюс набор данных. Повтор той же комбинации не собирает ничего; правка одного документа пересобирает только его.
5. Сборка запускается кнопкой и после сохранения (с задержкой 2 секунды, отменяет предыдущую той же комбинации). На сервере минуты идут в квоту пользователя (`stage6-quotas-gateway.md`), одновременных сборок предпросмотра у пользователя не больше двух.

### 6.4 Что видно

- PDF документа с рамками мест и метками даты из пака (5.6); слот, которого в этой комбинации нет в маршруте точки, показан бледным.
- Журнал сборки и ошибки TeX со ссылкой в строку исходника (SyncTeX работает и здесь).
- «Сравнить»: та же страница в двух комбинациях рядом или две версии шаблона (`PdfDiffView`), например «2026.1.3 против черновика 2026.1.4».
- Потом: сетка «все комбинации» одной страницы миниатюрами (до 8 сборок).

## 7. Мастер «Новая версия»

### 7.1 Ход

1. «Новая версия» на шаблоне: база это последняя версия (выбор другой из списка), каталог копируется в `versions/<черновой номер>/`, `status: beta`, `release` пуст.
2. Автор правит черновик. В шапке живой бейдж класса: «patch: только места подписей и метки даты» или «minor: новое поле `name_en`». Клик раскрывает причины списком со ссылками на изменения.
3. Номер: предложение по классу (patch `2026.1.3` в `2026.1.4`, minor в `2026.2.0`, major спрашивает год набора: `2027.1`). Номер мягче минимума выбрать нельзя; строже можно.
4. Заметки к версии (7.4).
5. «Выпустить»: `status: stable`, `released_at` сегодня, `release.kind`, по галочке `default_version` в `template.yaml`, затем `releases freeze`. Всё это коммиты рабочей ветки, PR один.

Повторное редактирование после «Выпустить», пока PR не слит: версия ещё не в `releases.yaml` базы (D10), поэтому правка разрешена, а мастер пересчитывает дайджест сам (`freeze` с заменой своей же записи). После слияния версия становится неизменной.

### 7.2 Классификатор

`core/template_diff.py`: `classify_change(base_dir, new_dir)` возвращает `ChangeReport` с минимальным классом и списком причин. Сравнение по разобранной модели (лоадер) и по файлам.

| Изменение | Класс | Вид правила |
|---|---|---|
| `id`, `released_at`, `status`, `release`, `summary`, `changes`, `breaking_changes`, комментарии YAML | не влияет | |
| `placements`, `default_dates`, `signing_slots`, `signatures.route`, `signing_route`, `deadline_hint` | patch (исключение 15.10) | жёсткое |
| содержимое существующих файлов `files/**` | patch по умолчанию; автор может поднять до minor («новые разделы») | мягкое |
| `description`, `title`, важность, `params` существующих правил проверок | patch («ложные срабатывания») | мягкое |
| `methods` пункта, `default_placement` слота | minor по умолчанию; patch только с объяснением автора (уходит в PR) | мягкое |
| новые документы, файлы-документы, поля, группы полей, анкеты, профили, пункты точек, слоты, правила и файлы проверок, языки, `extra_items`, `required: true` у слота, `supported_kinds`, `supported_staffing` | minor | жёсткое |
| `engine`, `latex_packages`, `dynamic_includes`, `requirements`, `nda`, `manifest_format`, `min_studio` | minor | жёсткое |
| удаление или переименование документа, поля, профиля, слота, анкеты | minor с переносом данных; пока формата декларации миграции нет, мастер просит major или отказ от удаления | жёсткое |
| другой год в номере | major | по номеру |

- Жёсткое правило задаёт минимум, мягкое только предложение. Объяснение автора к мягкому правилу пишется в `release.note` (новый необязательный ключ, лоадер его не читает) и в описание PR.
- Новое правило линтера: для версии, которой нет в `releases.yaml`, номер (и `release.kind`) не мягче минимума по жёстким правилам относительно предыдущей выпущенной версии того же шаблона. Выпущенные версии не проверяются задним числом: 2026.1.3 сузила `methods` patch-версией, по таблице это мягкое правило с объяснением.
- CLI: `hse-doc-studio pack classify <каталог шаблона> <база> <новая>`.

### 7.3 Защита выпущенных версий

- В мастере выпущенные версии только база для копии.
- Если автор правил выпущенную версию мимо интерфейса (папка, редактор), инструмент показывает diff и предлагает «Перенести правки в новую версию»: копирует изменения в черновик и возвращает выпущенный каталог к базе.

### 7.4 Заметки к версии

- Черновик `changes` ru/en строится из отчёта классификатора по шаблонам фраз: «Места подписей научного руководителя на "Описании проекта" и "Заявлении" заданы шаблоном», «Новое поле "Название работы на английском"». Пункты парами, автор правит.
- Перевод ru в en по кнопке через ИИ-провайдера пользователя (если настроен); без провайдера автор пишет сам.
- `breaking_changes` предлагается, если классификатор нашёл сужение (`methods`, удалённое поле).

## 8. Пак с нуля

- «Новый пак»: id (латиница, цифры, дефис; уникален в репозитории и среди вшитых паков Студии), имена ru/en, maintainer из профиля, license (по умолчанию Apache-2.0), source.
- Заготовки:
  - «Минимальный»: один шаблон, одна версия `<год>.1` в `beta`, языки ru, один документ «Отчёт» по ГОСТ 7.32 с титулом и `meta.tex.j2`, поля «Учебный год» (`auto: academic_year`), «Программа», слот автора и одна точка сдачи;
  - «Копия пака» или «Копия шаблона»: выбранная версия существующего пака копируется с новыми id, `releases.yaml` пуст, версия `beta`, номер `<год>.1`, `source` и maintainer свои, атрибуция исходного пака сохраняется в комментарии `pack.yaml` (лицензия Apache-2.0 её требует).
- Сразу после создания: пример данных «Обычный», сборка предпросмотра, линтер.
- Новый шаблон в существующем паке: то же, на уровне шаблона.

## 9. Безопасность

| Угроза | Мера |
|---|---|
| исполнение кода через Jinja пака в api | `ImmutableSandboxedEnvironment` для всех шаблонов пака (`template_renderer`, `form_renderer`); черновой пак рендерится в отдельном процессе с пределом времени (10 с) и памяти; линтер использует тот же парсер. Срез T3 идёт до открытия раздела на сервере |
| произвольный LaTeX | только на раннере: контейнер без сети, rootfs только для чтения, `cap-drop ALL`, лимиты CPU, памяти и времени, в Kubernetes под restricted (gVisor на общих раннерах по `collaboration.md`, 14.2). `latexmk_argv` фиксирован, `engine.flags` пака при сборке не используются; линтер предупреждает о `-shell-escape` во `flags` |
| чтение файлов из TeX (`\input{/etc/...}`) | в контейнере задачи только вход задачи; токенов, ключей и переменных Студии там нет |
| пути и ссылки в паке | файлы пишутся только внутри рабочего пространства; `..`, абсолютные пути, симлинки и подмодули в паке отвергаются (`core.symlinks=false` в клоне, новое правило линтера) |
| секреты git в паке и журналах | токены только в окружении процесса git (11.5), в клон, журналы, ответы API и вход задач не попадают; журнал git проходит маскировку; новое правило линтера ищет похожие на секреты строки в файлах пака (`ghp_`, `github_pat_`, `glpat-`, закрытые ключи PEM) и не даёт предложить изменения |
| чужой репозиторий как источник | хуки, fsmonitor, помощники учётных данных и ssh-команды из конфигурации выключены, как у стора проекта; размер клона и файла ограничен |
| персональные данные в паке | тестовые данные синтетические; «Скопировать как пресет» не выносит имён и названий проектов (раздел 13) |
| предпросмотр как способ нагрузить раннеры | право «Автор шаблонов», квота пользователя, не больше двух сборок одновременно, кэш |
| ссылка PR от имени служебного доступа | только для людей с правом, в журнале аудита `pack_studio.proposed` с автором и URL |

## 10. Выкладка паков в Студию

### 10.1 Сейчас

PR в `packs/` нашего репозитория, слияние, релиз Студии (release-please), образ, выкатка (прод в кластере, процедура в `deploy/`). Пак и Студия выходят вместе. Локальная Студия видит пак после обновления образа или через монтирование папки.

### 10.2 Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Пересборка образа | ничего не строить; пак проверен вместе с той Студией, что его читает | другой вуз зависит от наших релизов; patch пака ждёт релиза Студии |
| B. Каталог паков из git | админ установки подписан на репозиторий и тег; выпуск пака без релиза Студии | горячая перезагрузка каталога, хранилище версий, проверки при подтягивании |
| C. Загрузка админом | закрытые контуры без доступа к хостингу | ручной процесс; тот же конвейер проверок, что у B |

### 10.3 Решение

- MVP: A для наших паков (они в монорепе и проверяются её CI). Студия шаблонов в MVP выкладку не меняет.
- Потом (T17): «Каталоги паков» в `/admin`, B и C одним конвейером.
  - Источник: вшитые паки образа плюс подключённые: git (URL, путь паков, тег, ветка или sha, доступ) или архив.
  - «Проверить» тянет выбранную ревизию, разбирает её лоадером этой Студии, гоняет `pack_lint` и `releases check`, показывает, какие версии появятся. Версии с `min_studio` новее или с неизвестным `manifest_format` помечаются «не для этой Студии».
  - «Применить» кладёт версии в хранилище `data_dir/packs-store/<пак>/<шаблон>/<версия>@<digest>/` и атомарно переключает каталог (`YamlTemplateRepository` получает несколько корней и метод перезагрузки, `PacksSource` новый вид `subscribed`). Без рестарта.
  - Отслеживание: по кнопке или по расписанию (раз в сутки), только выпущенные версии (есть в `releases.yaml` источника).
- Локально: «Подключить к каталогу этой Студии» в рабочем пространстве над папкой: выпущенные версии пака из папки появляются в мастере проекта. Пак с id вшитого пака подключается только с явной галочкой «Заменить встроенный» (так сейчас работает оверлей разработчика).

### 10.4 Неизменность в установке

- Версия, которой уже пользуются проекты, никогда не удаляется и не заменяется: хранилище только дополняется, ключ с дайджестом.
- Источник принёс ту же версию с другим дайджестом: отказ «версия изменена в источнике», ничего не применяется (проекты закрепили дайджест в `project.lock`).
- Один id пака из двух источников: отказ, админ выбирает источник явно.
- Отключение источника прячет пак из мастера проекта, но версии остаются для существующих проектов.
- Потом: «План обновления по установке» (на базе `template_update/cli.py plan`): сколько проектов на старой версии, сколько файлов обновится молча, сколько сольётся, где будут конфликты. Читает проекты без записи; на сервере только агрегаты для админа, без содержимого проектов.

## 11. MCP и CLI

CLI `hse-doc-studio pack` собирает уже существующие модули в одну команду (нужна для CI и агентов в репозитории паков):

| Команда | Что делает |
|---|---|
| `pack lint <каталог>` | `pack_lint` всех версий под каталогом |
| `pack check <каталог>` | lint, `releases check`, классификатор для невыпущенных, схема; код выхода 1 при ошибках |
| `pack classify <шаблон> <база> <новая>` | отчёт класса с причинами, `--json` |
| `pack new-version <шаблон> [--from V] [--to V]` | копия каталога, `beta` |
| `pack freeze <шаблон> <версия>` | как `releases freeze` |
| `pack build <шаблон> <версия> [--example NAME] [--combo k=v ...]` | сборка примера через встроенный раннер, PDF в `--out` |

MCP: набор тулов `pack_*` в том же слое (`core/agent`, `use_cases/mcp/tools`), виден, если у пользователя есть право «Автор шаблонов» (область PAT `packs`):

| Тул | Аннотация | Что |
|---|---|---|
| `pack_list_workspaces` | только чтение | рабочие пространства пользователя |
| `pack_read` | только чтение | дерево и разобранная модель версии (документы, поля, слоты, профили) |
| `pack_read_file`, `pack_write_file` | запись только в невыпущенные версии | файл версии; `version_released` для выпущенной |
| `pack_lint` | только чтение | отчёт линтера |
| `pack_classify` | только чтение | класс черновика и причины |
| `pack_preview_build` | запускает задачу | сборка комбинации; PDF читается существующим `read_pdf` |
| `pack_set_placement` | запись | место или метки даты слота на документе (то же, что визуальный редактор) |
| `pack_new_version` | запись | шаг 1 мастера |
| `pack_propose` | внешнее действие | коммит, push, PR; требует `confirm: true` и возвращает сводку перед действием при `confirm: false` |

Тулы ничего не знают о токенах: `pack_propose` пользуется доступом рабочего пространства на стороне Студии. Агенту, который работает в репозитории паков сам (Claude Code, Cursor), чаще хватает CLI; MCP даёт ему сборку на раннерах без TeX у себя.

## 13. Первый шаг: «Скопировать как пресет шаблона»

Зачем: пресеты `hse-cs-sse` 2026.1.4 (R27) и будущие `hse-cs-se` (девять документов ЕСПД, 15.16) снимаются ровно так: автор ставит рамки на собранном PDF живого проекта, а потом переписывает координаты в `version.yaml` руками. Кнопка убирает переписывание.

Где: меню вкладки «Подписи» документа (`widgets/DocumentTabs/panes/DocSignaturesPane.tsx`), пункт «Скопировать как пресет шаблона». Окно с выбором «Этот документ» или «Все документы проекта», галочкой «Включая выключенные места», предпросмотром YAML, кнопкой «Скопировать» (`CopyField`) и предупреждениями.

Что выдаёт:

```yaml
# Пресет мест подписей для пака hse-cs-sse, шаблон coursework, собран на версии 2026.1.3.
# Перенесите в signatures.slots новой версии шаблона (слоты с тем же id). Это patch-изменение.
signatures:
  slots:
    - id: supervisor
      placements:
        project_proposal: { page: 1, x_mm: 80, y_mm: 139, width_mm: 40 }
        topic_application: { page: 1, x_mm: 163, y_mm: 168, width_mm: 40 }
      default_dates:
        project_proposal:
          - { page: 1, x_mm: 81, y_mm: 156, width_mm: 7, height_mm: 5, format: day }
          - { page: 1, x_mm: 90, y_mm: 156, width_mm: 24, height_mm: 5, format: month_word }
    - id: author
      placements:
        topic_application: { page: 1, x_mm: 165, y_mm: 200, width_mm: 30 }
```

Правила:

- Источник: `SignaturesStateResponse.placements` (место и `dates` по документу и слоту), `runtime_slots`, документы проекта. Ничего нового на сервере.
- Документ проекта переводится в id определения (`def_id`: в команде личный документ `report--ivanov` становится `report`), слот рантайма в слот каталога (`author--ivanov` становится `author`). Если у двух авторов разные места одного слота на одном определении, берётся место первого автора, остальные перечислены в предупреждении.
- Только слоты каталога пака: свои подписи проекта пропускаются с предупреждением.
- Выключенные места пропускаются (это затравки), если не стоит галочка.
- Координаты округляются до 1 мм (как в 15.10), ширина места не меньше 10 мм. Метки даты без `id` и `text`; `align` пишется, только если не `center` (значение по умолчанию лоадера). Порядок ключей как в справке.
- Проверки на клиенте тем же набором, что `parse_slot_placement` и `frame_problem`: рамка внутри A4, страница с 1, слот применим к документу (`applies_to`), место `per_author` на общем документе пропускается (15.5), не больше восьми меток.
- Шапка называет пак, шаблон и версию проекта; имя проекта, люди и тексты в YAML не попадают.
- Место, которое уже как в шаблоне (`origin: pack`), выводится как есть, с комментарием `# как в шаблоне`.
- Видна всем, кто видит вкладку «Подписи»: действие только читает состояние.

Срез T0, размер S: чистая функция `buildPackPresetYaml(state, documents, slots, version)` в `features/signature-stamper/lib` с юнит-тестами (командный проект, свои слоты, выключенные места, метки, округление, рамка за краем), окно, пункт меню, тексты ru/en, статья справки «Для авторов паков» дополняется абзацем.

**Сразу и независимо:** T0, затем T1 и T3 (полезны и без инструмента: класс версии в CI, песочница для паков в любой установке).

**MVP** (T0 до T10 и T19): автор открывает репозиторий паков или папку, правит любой файл в редакторе с линтером, видит сборку на тестовых данных в комбинациях, ставит места подписей и метки даты мышкой на PDF, создаёт новую версию с вычисленным классом и заметками и открывает PR или MR со статусом CI. Этого хватает для пресетов `hse-cs-sse` и `hse-cs-se` и для patch-версий с исправлениями файлов. Порядок внутри MVP: T0, T1, T3, T4, T2, T5, T8, T6, T7, T9, T10, T19.

**Потом:** формы T11 до T14 (по частоте правок: профили и маршрут, поля, документы, проверки), пак с нуля T15, MCP T16, CI T18, выкладка из git T17, справка T20 вместе с первым публичным выпуском.

## 15. Тесты

- Классификатор: таблица 7.2 построчно на парах каталогов во временной папке; реальные пары репозитория (`hse-cs-sse` 2026.1.0..2026.1.3) дают ожидаемые причины; правило линтера не трогает выпущенные версии.
- YAML-правки: для каждого `version.yaml`, `doc.yaml`, `checks/*.yaml` репозитория нулевая правка даёт тот же байт-в-байт текст; замена, вставка и удаление ключа сохраняют соседние комментарии и выравнивание; результат проходит лоадер и линтер.
- Схемы: все паки репозитория проходят схему; ключ, который лоадер читает, есть в схеме (сверка по списку ключей лоадера).
- Песочница: шаблон с доступом к `__class__`, `range(10**9)`, бесконечным циклом отвергается или обрывается по пределу; обычные паки рендерятся так же, как раньше (снимки `meta.tex` по всем версиям).
- Git: фейковый хостинг (`httpx.MockTransport`) для PR GitHub, статуса проверок, отказа прав; push options GitLab проверяются по argv; токен не встречается в argv, журнале, клоне и ответах (как тесты 11.5).
- Предпросмотр: синтетический проект по всем переключателям даёт корректный `project.json`; ключ кэша меняется при правке файла и не меняется при правке примера другой комбинации.
- T0: чистая функция на фикстурах состояний подписей (solo, команда, свои слоты, метки, выключенные места, рамка за краем).
- e2e: сценарий «открыть папку, поставить место на PDF, новая версия patch, предложить изменения» на демо-стенде с фейковым хостингом.

## 16. Риски

| Риск | Что делаем |
|---|---|
| Рендер Jinja чужого пака в api исполняет код | T3 до открытия раздела на сервере; без T3 раздел на сервере не включается |
| Пак проверен одной версией Студии, а выложен в другую | один образ (D1); `min_studio`; при подписке (T17) проверка лоадером той Студии, что применяет |
| Точечные YAML-правки портят файл | тест байт-в-байт на всех паках, показ diff перед коммитом, «Исходник» всегда рядом, откат к сохранённой версии |
| Классификатор ошибается в мягкую сторону | жёсткие правила, правило линтера в CI, ревью PR человеком; мягкие правила только с объяснением в PR |
| Точный токен GitHub не открывает PR из форка | ссылка «Открыть PR в браузере»; подсказка про классический токен для открытых репозиториев |
| Объём: пять L-срезов | MVP ограничен путём пресетов и редактором; формы после MVP; T0, T1, T3 полезны сами по себе |
| Сборки предпросмотра нагружают общие раннеры | право, квота, кэш, предел одновременных |
| Монорепа тяжела для частичного клона и CI | `--filter=blob:none --sparse`; быстрый джоб `packs` (T18) |
| Авторы паков ждут полноты против текстовой правки | любая сущность доступна в «Исходнике»; форма не обязательна |
| Два автора выпускают одну версию | fetch перед «Выпустить», перенос номера (4.3), `releases check` в CI |
