# Серверы ИИ-моделей: установка Ollama, vLLM и SGLang из админки

Статус: срезы 1-5 реализованы (07.11.2026). Решения из раздела 10 ждут подтверждения владельца продукта. Основа: локальный `ai-runtime` (проба железа, управление Ollama в режиме «локальная Студия»), общие ИИ-провайдеры установки (`use_cases/admin/ops_ai_providers.py`), хранилище секретов (`infra/secrets`), соседние контейнеры (`infra/docker`).

## 1. Задача

Администратор инстанса должен из интерфейса поставить сервер ИИ-модели и сразу получить рабочего ИИ-провайдера в Студии:

- движки: Ollama, vLLM, SGLang;
- где: (а) локально, рядом со Студией (соседний Docker-контейнер, с GPU, если он виден); (б) на другой машине по SSH;
- выбор модели из каталога или по имени (Hugging Face, библиотека Ollama), размер и оценка требований до скачивания;
- запуск, остановка, статус, ход загрузки модели, логи, удаление;
- после установки сервер сам регистрируется как общий ИИ-провайдер (OpenAI-совместимый эндпоинт для vLLM и SGLang), проверка «модель отвечает»;
- секреты (токен Hugging Face, ключ API сервера) только зашифрованно и не в логах.

Только администратор. Локальный режим Студии (один пользователь) использует прежний `ai-runtime` и не меняется.

## 2. Что уже есть и что используем

## 3. Модель домена

`ModelServer`: `id`, `engine` (`ollama | vllm | sglang`), `target` (`local | ssh`), `name`, `model` (то, что запрошено), `status` (`installing | running | stopped | failed | removing`), `endpoint` (внутренний адрес для Студии), `provider_id` (созданный провайдер), `exposure` (`internal | localhost | public`), `created_at`. Для `ssh` дополнительно `machine_id` (запись общего SSH-слоя, раздел 6).

Источник истины для локальных серверов в срезах 1-3: сами контейнеры, помеченные `com.hse-studio.managed=true` и `com.hse-studio.model-server=<id>`, плюс метки `engine`, `model`, `provider`. Это переживает перезапуск Студии без своей таблицы. Таблица `model_servers` появилась в срезе SSH (раздел 6): в ней и локальные, и удалённые серверы; метки остаются для подхвата старых установок.

Ход установки (шаги, процент, ошибка) пишется в таблицу `model_servers` на каждом шаге; живой процент загрузки и журнал шагов дополнительно в памяти процесса. Для Ollama прогресс берётся из потока `/api/pull`, для vLLM и SGLang загрузка весов идёт при старте контейнера, и прогресс берётся из логов контейнера (грубо: «скачивание», «загрузка в память», «готов»), состояние «готов» определяется по `GET /v1/models`.

## 4. Движки

| Движок | Образ (настраивается) | Порт | GPU | Модель |
|---|---|---|---|---|
| Ollama | `ollama/ollama` | 11434 | по желанию | `ollama pull <имя>` после старта, библиотека ollama.com |
| vLLM | `vllm/vllm-openai` | 8000 | нужна NVIDIA | аргумент `--model <HF id>` при старте |
| SGLang | `lmsysorg/sglang` | 30000 | нужна NVIDIA | `python3 -m sglang.launch_server --model-path <HF id>` |

vLLM и SGLang без видимой NVIDIA-карты не предлагаются как подходящие: интерфейс показывает причину, а API отвечает `409 engine_requires_gpu` (админ может включить `force`, на свой риск, например для CPU-сборки образа). Тег образа задаёт админ или настройка по умолчанию; значения не зашиваются в код как «последние».

Токен Hugging Face передаётся контейнеру переменной `HF_TOKEN` через `--env-file` во временном файле с правами 0600, который удаляется сразу после `docker run`; в аргументах процесса, журналах и ответах API токена нет. Сохранённый токен лежит зашифрованным в хранилище секретов (ключ `model_servers.hf_token`), наружу отдаётся только признак `hf_token_set`.

Привязка и защита: контейнер публикуется на `127.0.0.1` хоста либо вообще не публикуется и доступен Студии по имени в сети `hse-studio-net` (по умолчанию для локальной установки). vLLM и SGLang запускаются с `--api-key`, ключ генерируется (32 байта) и хранится зашифрованным как ключ общего провайдера.

## 5. Оценка требований до скачивания

Чистая функция `estimate_requirements(model_ref, size_b, quant, context)` без сети:

- вес модели ≈ параметры × байт на параметр (fp16/bf16: 2, int8: 1, 4-bit: 0.5-0.6);
- KV-кэш и накладные расходы: +20 % к весу плюс оценка по длине контекста;
- сравнение с VRAM (GPU) или RAM (CPU), со свободным диском и архитектурой; вердикт `fits | tight | too_large | unknown`, причины как коды для i18n.

Размер берётся из каталога (встроенный короткий список популярных моделей с параметрами и квантованием), для Ollama из тега библиотеки, для Hugging Face из имени (`7b`, `70b`, ...) либо из `GET https://huggingface.co/api/models/<id>` (метаданные безопасных весов), запрос только к фиксированному хосту. Если размер определить нельзя, вердикт `unknown`, установка не блокируется. Оценка приблизительная, и интерфейс так и пишет.

## 6. SSH: общий слой с установкой раннеров

Слой SSH-установки один: он влит вместе с установкой раннеров (`SshInstallService`, сеансы, `AsyncSshConnector`, SSRF-политика, одноразовые и зашифрованно сохранённые доступы в `runner_ssh_credentials`, HTTP `/api/admin/runner-install/ssh/*`). Серверы моделей его не дублируют, а подключаются к нему через подключаемый шаг «что запускать».

- `SshInstallService.install(..., payload=None)`: без `payload` ставится раннер (поведение и публичные имена прежние, раннерный код вынесен в `RunnerSshPayload`). С `payload` после входа, определения системы и сохранения доступа выполняется `payload.run(ctx)`.
- `SshPayload` (Protocol): `steps`, `run(ctx)`, `on_failure(ctx)`, `secrets(ctx)` (что вырезать из текста ошибки). `SshStepContext` отдаёт сеанс, задание, sudo и общий шаг `ensure_docker()`.
- Новые общие методы слоя: `ensure_docker(ctx)`, `open_saved(actor, credential_id)` (SSRF и закреплённый ключ хоста), `saved_sudo(credential_id)`.
- Установка сервера: тот же `POST /runner-install/ssh/{session}/install` с необязательным полем `model_server` (`engine`, `model`, `name`, `exposure`, `acknowledge_public`, `force`); probe, confirm, отмена, сохранённые доступы и опрос задания общие. Мастер SSH в интерфейсе получает пропсу `modelServer`.
- Шаги: connect, docker, gpu, container, model, provider, verify. Шаги идут через те же `InstallJobStore` и состояния.
- Секреты едут по stdin во временный файл 0600 на хосте (`docker run --env-file`), в аргументах и записи их нет.

Доступ к эндпоинту: по умолчанию `-p 127.0.0.1:порт:порт`, провайдер не регистрируется (Студия не достанет до loopback чужой машины). `public`: `0.0.0.0`, ключ API (только vLLM и SGLang, у Ollama ключа нет), явное подтверждение, провайдер создаётся, предупреждение в интерфейсе и документации.

Состояние в базе: таблица `model_servers` (миграция `ms_01`) хранит все серверы, локальные и по SSH, с шагами, ходом, ошибкой и ссылкой на сохранённый доступ. Запись идёт на каждом шаге; оборванная перезапуском установка показывается как ошибка. Метки Docker остаются: контейнеры, поставленные до появления таблицы, подхватываются списком. Управление сервером по SSH (запуск, остановка, журнал, удаление) возможно только с сохранённым доступом.

## 7. API (только `/api/admin`)

- `GET /model-servers/capabilities`: Docker виден, GPU, VRAM, RAM, CPU, диск, архитектура, включена ли локальная установка, сохранён ли токен HF.
- `GET /model-servers/catalog?engine=`: каталог и поиск по имени.
- `POST /model-servers/estimate`: оценка требований.
- `POST /model-servers`: создать (engine, target=`local`, model, name, exposure); `202` и задача установки.
- `GET /model-servers`, `GET /model-servers/{id}`: статус, ход, провайдер.
- `GET /model-servers/{id}/logs?tail=`; `POST .../start`, `.../stop`; `DELETE /model-servers/{id}` (с удалением провайдера, том с весами по параметру).
- `PUT /model-servers/settings`: сохранить или стереть токен HF.

Аудит: `model_server.install|start|stop|remove`, в деталях engine, model, target, без секретов. Ограничение частоты на запись: общий `rate_limit_guard` админки плюс предел одновременных установок (по умолчанию 1).

Локальная установка выключена в Kubernetes по умолчанию: Helm `modelServers.local.enabled: false` превращается в `HSE_STUDIO__MODEL_SERVERS__LOCAL_ENABLED=false`; в compose-стендах по умолчанию `true`, если виден Docker. При выключении API отвечает `409 local_install_disabled`, интерфейс скрывает вариант «на этой машине».

## 8. Интерфейс

Страница «Серверы моделей» в админке (по образцу страниц админки): шаги «движок (с подсказками под железо) → модель (каталог, поиск, оценка) → размещение (эта машина или SSH) → установка (прогресс, журнал)» и список установленных серверов с запуском, остановкой, журналом, удалением. Строки на ru и en, мобильная раскладка в один столбец, крупный шрифт (rem, как соседние страницы).

## 10. Решения (подтверждены владельцем продукта 06.11.2026)

1. Локальные серверы без своей таблицы, состояние по меткам Docker. Состояние установки (шаги, журнал) переезжает в БД вместе со срезом SSH.
2. vLLM и SGLang без NVIDIA не ставятся без `force`.
3. Каталог моделей встроенный и короткий, остальное по имени.
4. Образы движков закреплены конкретными тегами (Ollama 0.40.15, vLLM v0.32.0, SGLang v0.5.23; наличие тегов проверено на Docker Hub 06.11.2026), переопределяются настройкой `*_IMAGE`. `latest` по умолчанию не используется.
5. Токен Hugging Face: отдельным срезом, только зашифрованно под ключом секретов (`instance_settings.secret_enc`), в интерфейсе и API только признак наличия, замена и удаление; значение не возвращается и не логируется.
6. Kubernetes: docker.sock в под api не монтируется, локальная установка выключена и без ручной правки чарта не поддерживается (явно описано в документации администратора).
7. e2e: Playwright на подменённом API на стенде server-lite (`make e2e-model-servers`).
8. SSH-срез не начинается, пока не влит общий SSH-слой установки раннеров (проект установки раннеров из UI (PR #165), PR #165). Интерфейс сеанса из раздела 6 согласуется с владельцем слоя в этом PR.
