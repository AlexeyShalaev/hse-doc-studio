Self-diagnostics lets an installation run without a dedicated DevOps engineer: the server checks
itself regularly, shows what is wrong and calls an administrator only when a problem persists.
Checks are grouped: **Data**, **Builds and background jobs**, **Certificates**, **Operations**.

<Steps />

## What common problems mean

- **Database**, “The database is unreachable”: check that the Postgres container is running and
  that HSE_STUDIO__DB__* is correct.
- **Database migrations**, “The database lags behind the code”: restart api, it applies migrations
  by itself. “The database was migrated by a newer version” means an image older than the schema is
  running: run a version no older than the one that migrated the database.
- **Object storage**, “The storage is unreachable”: check the address, keys and bucket in
  HSE_STUDIO__S3__* and that MinIO or S3 is reachable from the api container.
- **Disk and data retention**, “critically low”: free space in “Data retention” or grow the volume;
  large uploads are rejected meanwhile.
- **Runners**, “No runner is online”: start the runners and check their token and the network to
  api. See [Connect build runners](/help/en/admin/runners/).
- **Public address certificate**, “The certificate of … expires in … days”: renew the certificate
  or check auto-renewal in the proxy.
- **Backups**, “There has been no successful backup yet” or “The last backup attempt failed”: open
  [Backups](/help/en/admin/backups/) and look at the run history.
- **Background jobs**, “No background-job leader found”: restart api; if that does not help, check
  the database connection.
- **Email delivery**, “… of … emails did not go out in the last hour” or “The last email did not go
  out”: the check looks at the mail log, not only at the sign-in to SMTP. Open the row: it leads to
  [Mail](/help/en/admin/mail/) with the Failed filter. Fix the **Mail (SMTP)** block by the reason in
  the email card, send a test email and click **Send unsent**. The share is counted for the last
  hour and day when the window has at least five emails; the **Unsent emails** thresholds (20% and
  50% by default) are edited in **Thresholds and notifications**. A single refusal for one address
  (code 550) does not trip the check by itself.

## Accept a warning on purpose

If you knowingly do not back up or do not connect public runners, you can accept the warning: click
**I accept: this is on purpose** in the check row (or in the banner on the “Backups” page), write a
reason of up to 200 characters and pick a term, indefinitely or until a date. The row turns grey
(“Accepted”), and the menu dot, the overview line and admin notifications go away. All accepted
warnings are listed at the bottom of the page under **Accepted warnings**; **Bring the warning back**
removes the acceptance. Failures and checks that protect data and uptime (database, migrations, disk,
queue, certificate expiry) cannot be accepted. When “no backups” is accepted, a manual update on
Kubernetes no longer asks you to confirm the risk each time and shows the reason in one line.

## If something goes wrong

- **“No checks have run yet”**: the server runs the first scheduled pass on its own within
  minutes. Click **Check now** to skip the wait.
- **“Scheduled checks are off (HSE_STUDIO__DIAGNOSTICS__ENABLED)”**: the environment turned
  scheduled checks off. Manual checks still work; set the variable and restart api.
- **“The check did not finish in … s”**: the service answers too slowly. Check the network to it
  and the host load, then run the check again.
- **“Could not check the certificate of …”**: the address did not open from the api container. If
  your proxy is not reachable from inside, this is not an error; otherwise check DNS and the port.
