A runner is a machine that builds PDFs and runs checks. The server does not build documents
itself: without at least one runner online, people’s builds wait in the queue. A runner connects
with a one-time registration token and then works with its own token.

## Update a runner installed from the admin area

A runner installed with **Install a runner** on this same machine (Docker next to the Studio or a
Deployment in the cluster) is updated in place, without removing and installing it again.

- When the runner is older than the Studio, the **Version** column has an **Update to vX** button. The
  same button is in the **Deployment details** window next to the "Older than the Studio" mark. A
  runner on the Studio version can be updated from the row actions menu: **Update** applies the
  settings again and restarts it.
- The confirmation shows what is kept: the runner name, its token and record, the data volume and
  the limits it was installed with. No new token is issued.
- The runner restarts for a short while. It finishes running builds for up to 30 seconds, the rest
  stop and have to be built again. Queued jobs wait for another runner or for this one.
- Progress is shown step by step; the last step waits until the runner is online again with the new
  version.
- If the new pod or container does not come up or the runner does not come online, the Studio
  brings the previous version back by itself: a **Rollback to the previous version** step appears.
  The Studio waits for the runner to come online with the previous version, and the result says
  which version it is back on, whether it came online, or why the rollback failed.

The same menu has **Remove install**: the Studio revokes the runner like **Revoke runner** does (the
jobs it was running go to another runner, its token stops working) and deletes the Deployment or the
container. There is no need to revoke the runner separately. If the install could not be removed
completely, the runner is already revoked and the install stays in the **Installs without a runner**
block below the table: remove it again. That block also lists installs whose runner is not in the
table, for example one that has not connected yet.

## Runner disk

Images of earlier Studio versions, old TeX Live and service tags and the Docker build cache pile up
on a runner machine. Choose **Disk** in the runner row actions menu: the window shows how much space
is used and what can be freed. Shared and personal runners both have it. Under a shared runner's
name a link “N can be freed” appears when the last measurement can free 1 GB or more.

- **What you see.** A bar by category (LaTeX, LanguageTool, the app itself, build cache, the runner
  file cache and working copies), free space on the runner data volume and the measurement time. The
  runner sends a measurement by itself every 6 hours and after every cleanup; **Refresh** measures
  right away.
- **What can be cleaned.** **Remove old versions**, **Remove unused**, **Clear build cache**,
  **Remove dangling images**, **Clear runner cache**, or everything at once with **Clean up
  everything**. Every button asks for confirmation with a list and sizes.
- **What is never touched.** The current version and the previous one kept for rollback; volumes
  (the TeX Live cache and downloaded models); images and containers that are not the Studio's, such
  as Postgres and MinIO on the same host. The runner cache keeps files touched in the last 10 minutes
  and working copies used by running builds.
- **The previous version.** It is removed only with the **Also remove the previous version** box in
  the **Remove old versions** confirmation. After that the runner cannot go back to the previous
  version without downloading it again.
- **Kubernetes.** For a runner in a cluster the window shows only the runner cache and the data
  volume. Kubernetes removes images on the nodes itself when a node runs low on space.
- **Local Studio.** When the runner is a desktop Studio, the window shows only the runner cache.
  Images on that computer are cleaned in the Studio itself: **Settings**, **Disk**.
- **Personal runners.** You can view and clean someone else's personal runner, but only the owner can
  remove its previous version. The owner gets an **Inbox** notice about a cleanup you started.
- **“Update the runner to see its disk”.** A runner below 0.22.0 does not report its disk. A runner
  installed from the admin area has an **Update runner** button in the window; update the others with
  a new image.

The cleanup runs on the runner itself: until it picks up the command you see “Waiting for the
runner”, then the steps and the result **N freed**. It can be stopped after the current step. Every
cleanup goes to the audit log. Cleaning everything past its retention period on the server itself:
[Storage and space](/help/en/admin/storage/).

## If something goes wrong

- **“No runner is online”**: builds and checks wait in the queue. Check that the runner machines
  are up and can reach the server address, then restart the runner.
- **A token shows “Expired” or “Used up”**: it no longer connects runners. Create a new token;
  runners already connected keep working.
- **A job failed with “The runner disappeared mid-job”**: the runner lost its connection during a
  build. Studio retries the job on another runner; if it keeps happening, check the network and the
  resources of the runner machine.
- **“No suitable runner”**: no online runner can take the job, for example all suitable ones are
  paused. **Resume** a runner or connect another one.
